1.4 目标控制

入口鉴别

  • 应用层校验 Authorization: Bearer <ONEBOT_TOKEN 的值>，使用常量时间比较；Token 为空时拒绝启动或拒绝全部事件，不能默认放行。
  • NapCat 的 HTTP 客户端配置里填入同一个 secret；部署文档把这一步写成必做项。
  • Nginx 对 /onebot/event 单独建 location，只允许 172.16.0.0/12 与 127.0.0.1，client_max_body_size 1m，其余 deny all。
  • 事件体做最小校验：post_type、message_type、self_id、time 必需；时间偏离超过 5 分钟拒绝，防重放。
  • 入口限流单独一个 zone，例如 300r/m，不和公开页面的 120r/m 混用。
location = /onebot/event {
    allow 172.16.0.0/12;
    allow 127.0.0.1;
    deny all;
    client_max_body_size 1m;
    proxy_pass http://qqbot;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

后台会话与授权

  • 角色判定必须使用归一化后的路径。先拒绝原始 URI 中的 ;、..、%2f，再用 UrlPathHelper.getPathWithinApplication 取路径。
  • 更稳的做法：把权限写在 Controller 方法或路由元数据上，过滤器只做会话校验，避免“路由表”和“字符串前缀表”两套真相。
  • 写操作增加 CSRF 防护。单管理员场景用 Origin 白名单加双提交 Token 即可，不引入 Spring Security 也能做。
  • Cookie 加 Secure；SameSite 用 Strict，若登录跳转受影响则用 Lax 并校验 Origin。
  • 改密、删号、降权后立即失效该账号全部会话；会话设置绝对上限与空闲上限。
  • 登录失败按真实客户端 IP 加账号计数；再加一个账号级全局阈值，超过后拉长锁定并告警，避免单点锁死管理员。
  • 多人后台默认公开，靠账号密码、真实 IP 锁定与 Origin 校验；单管理员可保留 IP 白名单或 VPN。密码只能是最后一道防线。
  • 后台未启用时返回通用文案，路径诊断只写日志，不回给匿名访问者。

命令与数据授权

  • 不要信任事件里的 sender.role。入口鉴权只能证明事件来自 NapCat，不能证明角色没被篡改；管理员命令应再调用 get_group_member_info 核对一次，或只允许通过后台配置。
  • 板块删除校验群号与作者：本群记录允许作者或管理员删除；跨群记录只允许管理员，且必须有明确提示。
  • /prompt 的群级提示改为管理员或群主才能写、删、清空；个人提示可以继续对所有人开放。
  • 所有按编号操作的命令都当作越权入口审查一遍，编号必须和群、作者一起查。

数据保护

  • 聊天采集默认关闭，数据库默认 capture_all_groups=0；开启时必须显式填写群号，管理页显示“当前采集 N 个群”。
  • 实现保留期清理：按 message-retention-days 删除 chat_message，按 image-retention-days 删除 chat_image 行与磁盘文件；清理任务要有日志、计数、失败告警。
  • 能存哈希就不存原文：sender_id 目前是明文 QQ 号，除蒸馏需要外，统计侧只保留 sender_hash。
  • 数据库、日志、备份文件权限设为 600，目录 700；备份加密后异地保存，至少做一次恢复演练。
  • 日志在写入端脱敏，或在 Logback 里挂一个 Converter 调用现有 LogMasker；不要记录完整事件对象。
  • 管理审计表也要有保留期，避免成为另一份长期行为记录。

出站与网络

  • 图片下载禁止跟随重定向，或对每一跳重新做公网校验；补齐 IPv6 ULA fc00::/7、IPv4-mapped IPv6、0.0.0.0。
  • NapCat 镜像固定 digest，不用 latest；容器用非 root UID/GID，配置与登录态目录按最小权限挂载。
  • 服务器出站只放行 QQ、模型、向量、wiki 所需域名；至少对 80/443 做日志与告警。
  • 云安全组不开放 8080、3000、3001、6099；主机防火墙只放行 22、80、443，8080 只允许 Docker 网桥与回环。

成本与可用性

  • 上线前设置全局每日回复数与 token 上限，以及每群、每用户上限；0 只作为明确的“关闭预算”开关，不作为默认值。
  • 预算用到 80% 时告警，100% 时熔断并保留 ERROR 日志；不要只静默丢弃。
  • 发送队列满、采集队列满、检索降级、模型全失败都要有计数与告警，不能只在日志里留一行。
  • 入口、公开 API、后台登录三层限流分别配置，避免一个 zone 被所有路径共享。

运维

  • 证书到期前 30 天告警。域名版使用固定路径证书，没有自动续期，必须加 systemd timer 或日历提醒。
  • 每周跑依赖漏洞扫描与镜像扫描；每月打一次系统补丁；每季度做一次恢复演练。
  • 发布前跑密钥扫描，确认 .env、overrides.yml、备份没有进版本库。
  • 保留一份“断网也能看”的运行手册：如何停机器人、如何轮换 Token、如何回滚、如何从备份恢复。

1.7 残余风险

  • QQ 协议依赖 NapCat 与专用账号，协议变更、风控、封号都不在应用控制范围内。需要备用号与明确的停机预案。
  • 单实例 SQLite 与内存缓存不支持水平扩展。用户量增长后先拆读路径或换 PostgreSQL，不要直接加副本。
  • 提示词注入无法靠系统提示完全消除。知识库与群聊内容始终是“资料”，但模型仍可能被诱导。高风险群建议关闭 /prompt 群级写入。
  • DNS 重绑定在 Java HttpClient 上没有便宜的彻底解法。禁用重定向并接受残余风险，或在容器网络层限制出站。
  • 自签证书方案会有浏览器警告，也会训练用户忽略警告。正式运营应使用受信任证书。
  • 没有 WAF 与 DDoS 清洗。公开站被打时，先保机器人，必要时在云侧封禁或切维护页。

02 / CODE AUDIT代码审查

这个仓库做什么：一个自托管的 QQ 群知识库问答机器人。它通过 NapCat 接 OneBot 11，先检索本地 SQLite 知识库，再让大模型依据资料回答；同一个进程还跑命令、定时板块、交互地图、语音、聊天蒸馏、公开站和管理后台。

假设的负载：2 核 2 GB 单机，两个活跃群，日提问量数百到数千，公开站偶发访问；单个管理员，少量编辑账号。判断按这个量级做，不按大规模多租户。

以下 1 至 5 已在本次修复中关闭，正文保留审查时的证据；6 至 19 仍未处理。

Must fix

1

事件入口没有鉴权，公网可以伪造 QQ 消息

Must fix

incoming/OneBotEventController.java:40-52 · command/CommandRole.java:43-52 · deploy/nginx/qqbot-domain.conf:126 · docs/architecture.md:46

这是什么

/onebot/event 接收 NapCat 上报的 JSON，去重后立刻返回 204，再异步处理。

问题

控制器和过滤器都没有校验任何 Token；Nginx 的 location / 把它一起代理到公网；下游又直接信任请求体里的 sender.role。攻击者可以伪造任意群、任意用户、任意角色的事件。

修法

在入口校验 Authorization: Bearer <ONEBOT_TOKEN 的值>，常量时间比较，失败返回 401；NapCat 的 HTTP 客户端填同一个 secret；Nginx 对公网 /onebot/ 返回 404，NapCat 只直连 8080。再加 1 MB body 上限。

不修的后果

任何人都能让机器人发消息、执行群主命令、写数据库、烧模型额度。身份、审计、成本三件事同时失真。

2

后台角色校验可被分号路径绕过，编辑能提权到管理员

Must fix

admin/AdminAuthFilter.java:80,102,131-141 · admin/AdminUsersController.java:50-103

这是什么

过滤器用 request.getRequestURI() 的字符串前缀决定角色：/admin/api/users 要 ADMIN，其余写操作要 EDITOR。

问题

Spring 匹配路径时会去掉矩阵参数，/admin/api;x/users 仍然命中 /admin/api/users 的控制器；但过滤器看到的前缀不是 /admin/api/users，于是只要求 EDITOR。我用 spring-web 6.2.19 的 PathPatternParser 验证过，这个 URI 匹配成功。编辑可以创建管理员、重置管理员密码，审计还会因为路径前缀不匹配而漏记。

修法

先拒绝原始 URI 里的 ;、..、%2f，再用 UrlPathHelper.defaultInstance.getPathWithinApplication(request) 取归一化路径做角色判定和审计。更彻底的做法是把权限声明放到 Controller 方法上，过滤器只负责会话。补一个使用 /admin/api;x/users 的回归测试。

不修的后果

任何一个编辑账号都等价于管理员。只要有一个帮忙维护知识库的人，后台就已经被接管了。

3

群聊采集默认开启并默认采集所有群，保留期配置是死代码

Must fix

resources/application.yml:121-124,137-140 · persistence/DistillSettingRepository.java:59,85 · distill/DistillPolicy.java:37-40

这是什么

聊天蒸馏会把群消息与图片落库，供后面生成知识笔记。

问题

capture-enabled 默认 true，数据库表 capture_all_groups 默认 1，于是首次启动就采集机器人所在的所有群，不只是 yml 里那两个群。配置里的 90 天、30 天保留期没有任何代码读取，消息与图片永远不会被清理，QQ 号还是明文存储。

修法

两个默认值都改成关闭；开启时必须显式填群号。实现定时清理：按 message-retention-days 删消息，按 image-retention-days 删图片行与文件；清理要有计数和失败告警。补迁移，让已有库也回到关闭状态，由管理员主动开启。

不修的后果

你在没有告知群友的情况下长期保存他们的发言和图片，磁盘也会随图片增长。这是隐私承诺与运维成本的双重问题。

4

板块删除不校验群和作者，任何人可按编号删别群记录

Must fix

command/BoardRunner.java:232-245 · command/BoardRecordStore.java:178-180

这是什么

/板块 /delete 编号 用来撤销一条板块记录，删除是软删，数据还在。

问题

代码只按全局编号取记录，然后只比对板块名，不比对群号，也不比对作者。编号是自增的，很容易枚举。A 群的人可以删 B 群的公告，普通成员也可以删别人的记录。

修法
