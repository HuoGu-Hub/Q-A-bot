### ⑥ 的模板：业务侧声明只读接口，config 侧实现它

以 `CommandProperties` 为例（`command/CommandPolicy` + `config/CommandProperties implements CommandPolicy`）：

```java
// command 包自己声明 —— 这是业务概念，不是配置形状
public interface CommandPolicy {
    boolean isEnabled();
    boolean isRequireMention();
    ...
}

// config 包实现它。★ 方法名和已有 getter 一模一样，所以一行都不用改
@ConfigurationProperties(prefix = "app.commands")
public class CommandProperties implements CommandPolicy { ... }
```

业务类改成注入 `CommandPolicy`，于是 **业务包对 config 的 import 就没了**，
而依赖方向变成 `config → command`（装配层去满足业务声明）—— 正是该有的方向。

**⚠️ 三个必须守住的点：**

1. **不能写成 record 快照。** 配置是热生效的：`SettingsService` 改值时**就地改字段**，
   各个 Bean 长期持有引用、实时读。写成 `record CommandPolicy(boolean enabled, ...)`
   就是在装配时**拷了一份值** —— 后台改配置再也看不到效果，而且不报错。
   （`CommandMatcherTest` 里有三处「构造完 matcher 之后再改 props」的用例，换快照会当场挂。）
2. **方法名保留 `isXxx`/`getXxx`。** 这样配置类不用改一行就能实现接口，
   也就不存在"适配器写漏一项"的可能 —— 那是个会静默吃掉配置项的错误。
3. **反向转回可变对象必须 import config** —— 那会被这条护栏当场抓住。所以接口不只是好看。

**粒度：一个配置类一个接口**，不做更细的拆分（拆细会让后台控制器拿好几个参数）；
等某个消费者只用一两项、而字段继续膨胀时再拆 —— 那时是加一个接口 + 改一个构造器。

### 判据：什么时候「挪类」，什么时候「声明接口」

⑥ 走到现在有两种做法，**别混用** —— 判据是「这个东西是不是完整的领域词汇」：

| 情形 | 做法 | 例子 |
|---|---|---|
| 配置类是**扁的**（没有嵌套类），字段是零散开关 | **声明只读接口**（业务侧声明、config 侧 implements） | `CommandPolicy` `LogPolicy` `AdminPolicy` `PlazaPolicy` `OneBotPolicy` |
| 配置类**有嵌套类**，而那些嵌套类是完整的领域词汇 | **把嵌套类整体挪进领域包**，根字段用一个小接口 | `GuardProperties` → `guard.*` + `GuardSwitch`（已做）；`KbProperties` → `kb.*` + `KbPolicy`（已做）；`LlmProperties` → `llm.*`（待做） |
| 字段的 **yml 键在根上**，挪不动 | **只给那几个字段声明一个只读接口** | `GuardProperties.enabled/killSwitch` → `guard.GuardSwitch` |

一句话：**能整体搬走就搬走（零新抽象），搬不动就声明只读视图。**

**为什么嵌套类优先"搬"而不是"包一层接口"**：`GuardProperties` 那 7 个分组一共
**37 个 getter**，各写一个接口等于把同样 37 个签名写两遍；而收益（挡住误写）在这里
**实测等于零** —— 13 个消费者一个 setter 都没调过。搬迁则是**纯搬运**：
零语义变化、零新抽象、yml 键一个不动。

**顺带撤销了两个例外**（`noGodConfigObjectInBusinessCode` 那条规则）：
`GuardPipeline` 原先注入整个 `GuardProperties` 只为读根上两个布尔 + 三个嵌套组，
而那三个组本来就是独立 bean —— 现在它只拿 `GuardSwitch + Access + RateLimit + ContentGate`；
`settings` 拿到的是 `SettingsRoots`（一张 Object 表），压根不认识 `GuardProperties`。

而那句修改正是**本项目既有的热生效惯用法**（`SettingsService` 也是就地改字段）。
改成副本反而会让"配置对象 = 当前生效值"这个不变式在两个地方各说各话。

<p>（查清但没用上的事实，留档）：`SettingsWhitelist` 只白名单了 `app.llm.reply-style.*`，
**没有** `app.llm.providers.*` —— 运行期唯一改 provider 的入口是 `ModelController`，
它先 `router.swapModelName(...)` 再写 `overrides.yml`，**重启时才由 Spring 绑定**。

**顺带说明 `GuardProperties` 那一轮（`GuardConfig` 把嵌套组暴露成 bean）只做了一半**：
fan-in 从 17 降到 3，但业务类 import 的仍然是 `config.GuardProperties.RateLimit`，
**这条护栏照样会失败**。要让 ⑥ 转正，`guard` 那几个类也得按上面的模板再走一遍。

### `settings` 包：**已解决** —— 它本来就不依赖 config 的类型

这一项曾被记成"待决策：要么给 `settings` 开例外，要么把它并进 `config`"。**两个都是错的**，
因为问题的前提就不成立：`SettingsService` 改配置用的是**纯反射**
（`getDeclaredField(h.field)` + `Field.set`），它**从不静态引用任何一个配置字段**。
原来构造器收 8 个配置类，只是构造器注入的仪式 —— 它要的是**若干个可变对象**，`Object` 就够。

**做法：让装配层把「前缀 → 对象」那张表建好递进来。**

```
settings/SettingsRoots        —— record(Map<String,Object> byPrefix)，业务侧声明它要什么
config/SettingsConfig         —— @Bean 建表，唯一认识那 8 个配置类的地方
SettingsService(whitelist, overrides, roots)   —— 一个 config 类型都不认识
```

于是护栏那句「配置只应在装配层注入」**字面上成立**，不需要开例外。
（要用 record 包一层，不能直接注入 `Map<String,Object>` —— Spring 会把它解析成"全部 bean"。）

**为什么不并进 `config`**：唯一的外部使用者 `llm/ModelController` 用
`settings.OverridesFile` 写覆盖层；`settings` 一旦变成 `config.settings`，
这一处立刻变成 `llm → config` 的**新违反** —— 得再发明一个接口去补救自己刚造成的破坏。

**顺带一个测试上的讲究**：`SettingsPrefixTest` 现在**调用真实的 `SettingsConfig.settingsRoots(...)`**
取那张表，而不是测试自己拼一个 map —— 否则「加了白名单却忘了注册」这件事就测不出来了。

### ⑤ 的进度与地基

地基 `persistence/Jdbc` 已就位，能力：全局可重入锁、`query`/`queryOne`/`count`/`update`/
`insert`/`batch`/`inLock`/`transaction`。

**顺带修掉一个真实并发缺陷**：全项目共用一个非线程安全的 SQLite 连接，而 14 个手写 SQL
的类里 **8 个完全不加锁**（`KbMapStore` / `KbWikiPageStore` / `AnswerAggregator` /
`QaAnalytics` / `QaStore` / `SiteTextService` / `KbProposalService` / `PlazaAdminController`）。
统一走 `Jdbc` 之后，迁移一个就修好一个。

**还修掉一个事务缺陷**：`Jdbc.batch` 原先自己开关自动提交，被调在已开启的事务里会
**提前提交外层事务**并报 `database in auto-commit mode`。即"事务里调用 batch 会静默破坏原子性"。
已加事务嵌套深度，只有最外层才提交/回滚。

| 已迁 | 待迁 |
|---|---|
| `SiteTextService` · `KbWikiPageStore` · `AnswerAggregator` · `PlazaAdminController` · `CategoryStore` · `CarouselStore` · `KbTermStore` · `KbProposalService` · `CommandStore` · `PlazaStore` · `KbMapStore` · `KbBlockStore` · `QaAnalytics` · `QaStore` | **（无）** |

**迁移时每次都要保住的三类东西**（它们最容易在搬迁中被当成冗余删掉）：
1. **业务规则**：如 `KeywordFilter.isTooGeneric` 的泛词过滤、`CarouselStore.move` 的"交换后整表重写 0..n-1"
2. **正确性条件**：如 `s.guard_action = pass`（不过滤则热词榜被闲聊灌满，实测「装备」16 次 vs 真实 6 次）、`v.vote = up`
3. **容易误删的 SQL 变体**：如 `KbCategoryRepository` 的两条 upsert —— 第二条刻意**不覆盖 `label_zh`**，
   合并就会把几十条人工填的中文标签一次性清空，而且看不出来

**迁 `KbTermStore` 时多带出三件事**（都写进了代码注释）：

- **`status` 的取值域下沉到了 Repository**。`draft/verified/rejected` 与「认不出来归 draft」
  本来在业务类里；但批量改状态要**在同一个事务里**拿旧值跟目标值比较，归一化留在业务侧
  会让持久层反向依赖它。业务侧保留 `KbTermStore.STATUSES` / `normalizeStatus` 作转发，
  公开 API 一个都没变。
- **两个死参数**：它的构造器收 `KbProperties` 与 `ObjectMapper`，**全文件零引用**，顺手删掉。
- **一个误导性的错误返回**：`setStatusBatch` 失败时旧实现把回滚前攒到的 `missing` 报了出去
  （"这几条没找到"，可实际上一条都没改）。事务已整体回滚，部分统计没有意义，现在返回全 0。

**迁 `QaAnalytics` 时**：它的构造器收 `QaProperties` 与 `SqliteDatabase`，其中
`QaProperties` **全文件零引用**（又一个死参数），`SqliteDatabase` 只用来判断"库在不在" ——
两个都删掉，改成只收 Repository。另外持久层为此多了一处对 `config.AppTime` 的依赖：
`AppTime.SQL_DAY` 是**唯一**的日期口径定义，复制一份到持久层是更糟的选择，
已写进 `QaAnalyticsRepository` 的注释并挂到债务⑥。

**迁 `KbBlockStore` 时又发现两处没有事务的多语句写入**：`delete`（块 + 正文向量 +
标题向量）与 `clearAll`（三张表）都是三条独立语句 —— 中间失败就留下"块没了但向量还在"
这类**对不上号**的状态。现在都在一个事务里。同时 `upsert` 的"是新增还是覆盖"
原来在事务外算，两个并发导入可能都判成"新增"。

**迁 `PlazaStore` 时发现一个静默的数据缺陷**：`saveGeneratedAnswer` 要写三张表
（`qa_stat` + `qa_raw` + `qa_keyword`），原来**没有事务** —— 第二步失败就留下一条
**没有原文的统计行**：它在统计里算一次问答，在广场上却没有内容。现在整段在一个事务里。
（这个方法的另一个坑 `has_quote`/`text_len` 是上一轮就发现并写进注释的。）

**迁 `KbProposalService` 时**顺手改了一处**会削弱运维可见性**的地方：让 `PersistenceException`
把 cause 的 message 拼进自己的 message。持久层的 message 说的是「做了什么」
（`更新失败：UPDATE kb_proposal ...`），真正有用的原因（`database is locked`）在 cause 里，
而这个服务有 3 处把 `e.getMessage()` **直接回给前端** —— 不拼的话那些提示会退化成一句 SQL 文本。
