# 知识库标题向量召回方案

> 2026-10-01 · 起因：用物品名提问时 A 路（向量）经常排不到本体 —— 实测「什么是酸蚀之咬」本体第 **7** 名。
> 本文给出根因、四套候选方案的**实测对比**，以及推荐方案（标题单独一条向量 + 高阈值闸门 + 置顶）的落地细节。
> 全部数字来自探针 `tests/probe-kb-title-embedding.py`，可在你本机重跑（见文末）。

## 一、问题：名字根本不在文档向量里

语料的形状（实测，2649 个未下架块）：

| 项 | 值 |
|---|---|
| 块数 | 2649（全部有向量） |
| 标题总字数 | 6.1 万字（平均 23 字） |
| 正文总字数 | 24.2 万字（平均 91.5 字，最长 604 字） |
| 「中文名（English）」型标题 | **2486 / 2649 = 94%** |
| 词条表 `kb_term` | 2649 行（每块一条，服务启动时自动按语料补齐） |
| 词条展开后的可匹配名字 | 5121 个，**100% 覆盖块名**（状态全是 draft，只有 rejected 会被跳过） |

问题出在这一行：

```java
// KbDocImporter.java:95 —— 建索引时
float[] v = embedding.embedOne(b.body());
// KbBlockAdminService.java:129,160 —— 管理端改正文 / 新增块时
store.upsert(updated, embed(text, id));
```

**块的向量只对正文算。** 而正文是"简介"，几乎不会重复标题里的名字 ——
「酸蚀之咬（Acid Bite）」这一块的正文是：

> 魔法弹药，向施法者正前方喷出一道锥形酸液，使所有被命中的敌人中毒。类型：法术｜稀有度：稀有｜等级：17 …

正文里一次都没出现"酸蚀之咬"。于是**用户打的那个名字，在文档向量里根本不存在**，
A 路只能靠"语义擦边"去猜，实测本体余弦 0.4915（阈值 0.45，压线过），
前面全是同族词：

| 名次 | 余弦 | 块 |
|---|---|---|
| 1 | 0.582 | 永恒酸蚀咬击（Eternal Acid Bite） |
| 2 | 0.540 | 酸蚀砍刀（Acid Cleaver） |
| 3 | 0.529 | 腐化野猪獠牙（Corrupted Boar Tusk） |
| … | | |
| **7** | **0.4915** | **酸蚀之咬（Acid Bite）** ← 本体 |

现在能救回来的是 **B 路（术语表字面匹配）**：名字原样出现在提问里时，B 路一击命中并吃标题加成。
但 B 路的词典是"字面"的 —— 问法里没写出完整名字（"那个咬人的酸液法术是哪个"）、
名字写错一个字、或者用英文却没人把英文名填进词条，B 路就完全帮不上忙，只剩 A 路这个盲区。

## 二、实测：四种改法在 200 条"名字查询"上的表现

**测试集**：从 2486 个名字型块里随机抽 200 个（按中文名去重），查询 = 标题里的**纯中文名**，
正确答案 = 该块；检索库 = 全部 2649 块。指标 R@k 是"正确块是否在前 k 名"，分母是 200（保守口径）。

| # | 方案 | R@1 | R@5 | R@20 | MRR |
|---|---|---|---|---|---|
| ① | **现状**：只用正文向量 | 27.0% | 50.0% | 64.5% | 0.376 |
| ② | 方案 1：标题拼进正文后**全量重建**向量 | 96.5% | 100% | 100% | 0.980 |
| ③ | 方案 2：标题**单独一条**向量 | **99.5%** | 100% | 100% | **0.998** |
| ④ | 方案 2：`max(正文余弦, 标题余弦)` | **99.5%** | 100% | 100% | 0.998 |
| ⑤ | 方案 2：`正文余弦 + w × 标题余弦`，w=1.0 / 1.5 | 94.0% / 98.0% | 99.5% / 100% | 100% / 100% | 0.966 / 0.990 |
| ⑥ | 方案 3：标题**字面命中**（零成本，不调模型） | 88.5% | 99.0% | 100% | 0.933 |
| ⑦ | 方案 2 变体：标题向量当**独立一路**与正文路做 RRF（w=1.0） | 49.5% | 94.5% | 100% | 0.677 |

一句话：**把标题放进向量，R@1 从 27% 拉到 99.5%。** 你的判断是对的。

### 但"多一路"不等于"融合它"—— ⑦ 是个陷阱

把标题向量当成和正文路平等的一路做 RRF，结果反而只有 49.5%。
原因：RRF 是"按名次投票"，它假设两路都可能对；而 A 路在名字查询上是**系统性错**的
（正文里没有这个名字，它必然把同族词排前面）。让它平等投票，等于用一半的票数把错误答案抬上来。

真正的口语场景更能说明问题 —— 从生产库 `qa_raw` 的 6289 条真实提问里抽 120 条：

| 指标 | 值 |
|---|---|
| 现状 A 路 top1 的平均余弦 | 0.548（其实挺自信） |
| 标题路 top1 与正文路 top1 **相同**的比例 | **9.2%**（两路分歧极大） |
| 加标题路（RRF w=1.0）后，融合 top1 仍是正文 top1 的比例 | **50.8%（一半被带偏）** |
| 正文 top1 仍留在融合 top5 的比例 | 93.3% |

标题路是个**精确度很高、但只在"用户在问名字"时才成立**的信号。
对口语提问它是噪音源。所以它必须带**闸门**。

## 三、推荐方案：标题向量 + 高阈值闸门 + 置顶

### 3.1 闸门阈值怎么定（实测扫描）

"闸门"= 先算一遍"查询 × 所有块的标题向量"的余弦，取最高值；超过阈值 θ 才让标题路说话。

| θ | 名字查询：本体命中率 | 真实口语提问：触发率 |
|---|---|---|
| 0.50 | 100% | 82.5% |
| 0.55 | 100% | 52.5% |
| 0.60 | 100% | 21.7% |
| 0.65 | 100% | 10.0% |
| **0.70** | **100%** | **2.5%** |
| 0.75 | 100% | 0.0% |
| 0.80 | 95.5% | 0.0% |

**θ = 0.70** 是明显的拐点：名字查询 100% 能触发，真实口语提问只有 3/120 误触发。
再往上（0.75）口语零误触，但安全余量在变薄；再往下（0.65↓）误触发成倍上涨。
建议默认 **0.70**，做成配置项，上线后按日志微调。

触发后的动作**不是加权重融**，而是**置顶**：把那个块排到融合结果第 1 位，其余顺序不动。

| 规则 | R@1 | R@5 | MRR | 口语侧影响 |
|---|---|---|---|---|
| 闸门 + 置顶 θ=0.70 | **99.5%** | 100% | 0.998 | 2.5% 的提问会被置顶（多半本来就是名字提问） |
| RRF 平等融合（⑦） | 49.5% | 94.5% | 0.677 | 一半 top1 被换掉 |

### 3.2 为什么不用其它三个方案

| | 方案 1（标题拼进正文，全量重建） | 方案 2（标题单独一条向量） |
|---|---|---|
| R@1 | 96.5% | **99.5%** |
| 一次性成本 | 全量重算 **24.2 万字**正文向量（≈¥0.15，3-5 分钟） | 只补 **6.1 万字**标题向量（≈¥0.02，2 分钟） |
| 正文向量 | 全部作废、需要重建 | **一个字节都不动** |
| 标题信号 | 被正文**稀释**：同一对「酸蚀之咬」，标题单独算 0.8143，拼进正文后掉到 0.6913 | 不稀释，标题与正文各算各的 |
| 过期风险 | `ChunkImportPlan:82` **只把"正文变了"当更新**（`!sameText(old.body(), b.body())`）→ 改标题不会重算向量，会静默过期 | 标题向量表里存一份"生成时用的标题"，比对不一致就重算，天然幂等 |
| 附带收益 | 无 | 标题里的英文名（`Acid Bite`）也进了向量 → 英文提问不再依赖"词条 zh 里是否写了英文名" |
| 在线检索耗时 | 1 次全量扫描 | 2 次全量扫描（**实测 2.64 ms → 5.29 ms**，见 §3.2.1） |
| 内存 / 存储 | 10.8 MB | 21.6 MB |

#### 3.2.1 性能差异到底有多少（实测，不是估算）

在容器里用 JDK 17 复刻了 `KbRetriever.byVector()` 的算法（2649 条 × 1024 维，含每条现算模长），预热后跑 3000 轮：

| | 耗时 |
|---|---|
| 1 次全量扫描（现状：只有正文路） | **2.64 ms** |
| 2 次全量扫描（加标题路） | **5.29 ms** |
| 线上一次完整检索（日志 `[PUBLIC] 检索「…」→ 5 条 … 耗时 343ms`） | 343 ms |

也就是说，**多一路标题向量 = 多扫一遍 2.6 ms，占整轮的 0.8%**；
整轮 99% 的时间花在"把问题发给 embedding 模型"这一次 HTTP 请求上。加这一路的在线开销可以当零。

### 3.3 为什么要单列"一路"，而不是并进 A 路

A 路和 C 路**技术上是同一类东西**（都是 bge-m3 的向量余弦），但在这个系统里，"路"指的是
**一条召回通道（一个 ranker）**，不是一种技术栈。两者的角色完全不同：

| | A 路（正文向量） | C 路（标题向量） |
|---|---|---|
| 拿什么比 | 正文向量 | 标题向量 |
| 候选集 | 所有过阈值的块，取前 pool 条（几十条） | **只取最高的那一条** |
| 阈值说的是什么 | `min-score 0.45`：这段正文够不够相关 | `title-gate 0.70`：这次提问是不是在问某个名字 |
| 怎么进结果 | 进 RRF，和 B 路**平等投票**（权重 1.0） | **不进 RRF**，命中即置顶 |
| 问答统计桶 | `vector` | `title` |
| 关掉它 | `app.kb.enabled=false`（整个知识库） | `app.kb.title-gate=0`（只关标题那一路） |

这不只是叫法问题 —— **名字是设计意图的载体**。实测已经说明：一旦把标题向量当成"又一条向量候选"
塞进 RRF 平等投票，R@1 就从 99.5% 掉到 49.5%（§2 的 ⑦）；真正让它起作用的是"高阈值闸门 + 置顶"。
把它并进 A 路，下一步最自然的动作就是"那它也是向量路，一起融合吧"，而那正是效果最差的写法。

**能合并的东西其实已经合并了** —— 多出来的只是召回策略，不是第二套向量系统：

- 问题只 embedding **一次**，A/C 两路共用同一个查询向量（`KbRetriever.safeVector()`）；
- 语料只取**一份**快照（`corpus.entries()`）；
- 余弦计算、向量存储格式（BIG_ENDIAN float32）、维度校验都是同一套；
- 两路都走同一个 `safe(...)` 兜底：拿不到向量就一起跳过，绝不抛异常。

所以准确的叫法可以是三层：**向量召回（A 正文 + C 标题闸门）、词法召回（B 术语表）**；
代码与日志里继续用 A/B/C 这套既有简称，是因为它比"向量召回通道之二"省字，
也正好和问答统计、日志里的桶名一一对应。

稳态下的 embedding 花费两者几乎一样（都是"标题嵌一次 + 正文嵌一次"，平均 114 字/块），
真正的差别在**一次性迁移**（30.3 万字 vs 6.1 万字 = 5 倍）、**改标题时的重算量**（114 字 vs 23 字 = 5 倍）
和**工程可维护性**（能不能分别卡阈值、能不能诊断、能不能发现标题过期）——后者才是选方案 2 的理由。

- **⑤ 加权求和（`body + w×title`）**：R@1 94-98%，比置顶略低，而且把两条量纲相同的余弦相加后，`min-score 0.45` 这个阈值就不再是"正文相似度"了，调阈值时会失去参照。不推荐。
- **③ 只用标题向量**：名字查询 99.5%，但口语提问会崩（标题里没有口语语义）。它只能作为 A 路的**补充**，不能替代。
- **方案 3（标题字面命中，88.5%，零成本）**：和现有 B 路的口径基本重合（B 路就是术语表 + 标题命中），**不值得单独做**；它的价值是在 B 路的词典没收录时兜底，而实测词典覆盖率已经是 100%。

## 四、落地设计

### 4.1 数据（不动现有的表）

```sql
-- 新增一张小表：2649 行 × 4KB ≈ 10.8MB（和现有向量表同量级）
CREATE TABLE IF NOT EXISTS kb_block_title_vec (
  id    TEXT PRIMARY KEY,   -- 块 id
  title TEXT NOT NULL,      -- ★ 生成这份向量时用的标题（比对不一致 = 过期，需要重算）
  dim   INTEGER NOT NULL,
  vec   BLOB NOT NULL       -- 与 KbBlockStore 一致：BIG_ENDIAN float32
);
```

`kb_block_vec`（正文向量）**完全不改**，迁移零风险；回滚也只是这张表不再被读。

### 4.2 写入（三处）

1. `KbDocImporter`：导入时把 added + updated 的**标题**和正文一起批量 embed（一次 batch 调用，标题短，成本≈0），写进 `kb_block_title_vec`。
2. `KbBlockAdminService.add() / updateText()`：新增块、改正文时同步维护标题向量。
3. **补建入口**（幂等、可反复跑）：扫 `kb_block` 与 `kb_block_title_vec`，
   对"缺失"或"title 与库里不一致"的块补算。启动参数 `--app.kb.title-index.enabled=true`
   或管理端「补标题向量」按钮（推荐后者，看得见进度）。
   —— 这一条同时解决了"标题改了没人重算"的历史问题。

### 4.3 检索

```
A 路：正文向量（现状不变）        ┐
B 路：术语表字面（现状不变）      ├─→ 现有 RRF 融合 → 结果列表
C 路：标题向量（新增，只做闸门）  ┘        │
                                          ▼
                          若 C 路最高余弦 ≥ app.kb.title-gate(0.70)
                          → 把那个块【提到第 1 位】，其余顺序不动
```

- `KbCorpus.Entry` 加一个 `float[] titleVector`（可为 null，缺向量时 C 路自动跳过）。
- **C 路不参与 RRF 投票**（这是实测结论，见 §2/§3）。
- 闸门的余弦阈值与正文路的 `min-score` 相互独立：前者是"这是不是一次找名字的提问"，后者是"这段正文够不够相关"，混在一起会两头都调不准。
- ⚠️ C 路也要像 A 路一样**绝不抛异常**（读不到标题向量就当作没有）—— 知识库只该是锦上添花。

### 4.4 上下文里放什么（与命中哪一路无关）

一个容易担心但**其实已经做好了**的点：标题路命中时，进 prompt 的会不会只有标题？

不会。命中后统一由 `ChatService.appendHits()` 渲染（ChatService.java:234）：

```java
sb.append('[').append(n++).append("] ").append(hit.entry().title()).append('\n')
        .append(hit.entry().url()).append('\n')
        .append(hit.entry().text()).append("\n\n");   // 正文是整块，不截断
```

**不管这个块是被 A 路（正文向量）、B 路（术语表）还是 C 路（标题向量）召回，
进模型的都是「[n] 标题 / url / 正文全文」。** 标题路只是"多一种找到它的方式"，
不改变找到之后给模型看什么。

顺带两个边界，值得心里有数：

- 进 prompt 的正文**不截断**（本语料最长 604 字），top-k=5 → 资料块总量最多约 3000 字，不构成上下文压力；
- 唯一会"只有标题"的情况是块正文为空 —— 导入器会当场警告（`ChunkMarkup:304`），实测 2649 块都有正文；
- 公开站**列表页的摘要**确实只截 170 字（`KbTextDisplay.excerpt`），那是给人看的排版，和机器人回答无关。

### 4.5 可观测

日志与 `KbTrace` 增加：

```
[KB-TITLE] 闸门命中 id=acid-bite 余弦 0.814 ≥ 0.700（已置顶）
[KB-TITLE] 闸门未命中（最高 0.532 < 0.700，块=水与储水方式）
```

配合 "闸门命中 / 未命中之后用户有没有追问" 就能反过来校 θ。

## 五、验收

1. **离线**：`python3 tests/probe-kb-title-embedding.py` —— 名字查询 R@1 应从 **27.0% → ≥95%**；
   口语侧不应出现成片退化（本方案在 θ=0.70 时只有 2.5% 的提问被置顶）。
2. **线上**：`什么是酸蚀之咬` 的融合结果里，本体应稳定第 1（现在是第 2，前面挂着「酸蚀砍刀」）。
3. **回归**：公开站搜索 + 群内问答各抽 10 条真实提问人工看一遍；重点看口语提问（"怎么给水箱加水"这类）有没有被标题路带偏。
4. **回滚**：`app.kb.title-gate=0`（或 `off`）即回到现状，数据不用删。

## 六、顺手要修的两个小坑（与本方案独立，可以一起做）

1. **标题精确加成不该发给"片段猜出来的词"**。
   `TITLE_EXACT_BONUS`（+0.5）本意是"用户打的就是这个名字"，但 `byChineseFragment` 猜出来的词
   （问「酸蚀之咬」时补进来的「酸蚀砍刀」）同样吃满这份加成，于是正主被压在后面。
   解法：`fuse()` 里区分词的来源，精确加成只发给 `matchChinese` 真命中的词。
2. **`kb_term.en` 存的是 slug，B 路拿它当"英文名"是无效的**。
   `en = acid-bite` 在标题/正文里根本不存在（语料里写的是 `Acid Bite`），
   英文能不能命中完全取决于人工有没有把英文名写进 `zh`。
   本方案落地后这项影响变小（英文名进了标题向量），但 B 路这一处仍值得改成"优先用 zh 里的英文别名"。
