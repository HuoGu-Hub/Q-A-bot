# 知识库运营手册

> **这份文档给谁看**：**自己人** —— 负责扩充和维护知识库的运维/管理员。
> 「怎么把网页变成合规文档」的交付标准在另一份：`docs/md/知识库文档格式规范.md`（那份是给**外部 AI** 看的）。
> 本文回答的是：**现在有什么、往哪扩、扩完怎么验、平时怎么维护。**

## 0. 先建立测量纪律（最重要的一条）

**扩充知识库的唯一风险是"改坏了没人知道"。** 所以先记住这条：

```bash
mvn test -Dqqbot.golden.rerank=on -Dtest=RetrievalGoldenTest
```

| 类别 | 门槛 |
|---|---|
| entity R@1 | ≥ 83% |
| entity R@5 | ≥ 95% |
| colloquial R@1 | ≥ 75% |
| chitchat clean | ≥ 80% |

**任何语料改动前后都跑一次，对比这几个数字。** 门槛是实测定的，不是拍的。

> 不跑黄金集就扩充 = 闭着眼睛改检索质量。这是本手册里唯一不可省略的一步。

### 📌 **当前基线已记录在 `docs/md/检索基线.md`** —— 动手前先看它

那份文档里有：完整的两张表（重排开/关）、重排的实际贡献、
最高余弦分布，以及**这条基线的盲区**。

> ⚠️ **动手扩充语料之前必须先知道的一件事**：黄金集总共 42 条，
> 而 `colloquial`（口语提问，**正是我们要改善的那一类**）**只有 2 条**。
> `colloquial R@1 = 100%` 是 n=2 测出来的，**没有统计意义** ——
> 加 500 页语料之后，**没有任何办法证明口语问答变好了**。
>
> **所以"扩充语料"之前，先补黄金集的口语部分。**

## 2. 扩充：两条路

两条路**互补**，不是二选一：

| | 路 A：从 wiki 自动抓 | 路 B：手写文档 |
|---|---|---|
| 覆盖 | 大（一个分类几百页） | 小（一份文档几十块） |
| 质量 | 取决于 wiki 本身 | **我们自己把关** |
| 适合 | 物品、技能、世界观这类**结构化**内容 | 攻略、版本更新、易错点这类**要判断**的内容 |
| 成本 | embedding 计费（几毛钱量级） | 一次 embedding（忽略不计） |

---

### 路 A：从 wiki 自动抓

三个入口，**顺序有依赖**：

```bash
# ① 地图同步（地点/NPC 的来源）—— 增量，只拉 revid 变过的页
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.map-sync.sync-on-start=true --spring.main.web-application-type=none"

# ② 地点语料派生（由 marker 生成地点/NPC 块）
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.location-corpus.build-on-start=true --spring.main.web-application-type=none"

# ③ wiki 文章导入（任务 / 机制 / 世界观…）
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.wiki-import.import-on-start=true --spring.main.web-application-type=none"
```

**每一步都能先空跑**（加 `--app.kb.xxx.dry-run=true`），也都能单独回滚。

#### 抓什么：往 `app.kb.wiki-import.categories` 里加分类名

实测过的候选（**页数与字节数都是查 API 得到的**，不是估计）：

| 分类 | 页数 | 建议 |
|---|---|---|
| `Lore` 世界观 | 264 | ✅ **高价值**，口语提问常见 |
| `Ranger/Mage/Warrior Skills` | 148 | ✅ 技能问答是刚需，且都是小页、风险低 |
| `Wildlife` 生物 | 38 | ✅ 便宜 |
| `Armor Set` 套装 | 59 | ⚠️ 与现有单件护甲块部分重叠 |
| `Quests/` 前缀 | 155 | ✅ **配置里早就有了，但从未导入过** |
| `Item catalogs` 索引页 | 70 | ❌ **别开**：占新增文本量 34%，但内容是链接与表格，会和现有物品块在向量空间里几乎重合 |
| `Music` | **0** | ❌ **开了等于没开**：正文命名空间 0 页（95 是含子分类/文件的计数） |

#### 三个必须知道的坑

1. **`max-pages-per-source: 300` 是"每个来源"独立算的**，超了会**静默截断**。
   `Lore` 264 刚好压线 —— 它再涨就会丢页。
2. **`max-body-chars: 1500` 现在是「单块上限」**，超长页面会**按段落切块**（不再是截断）。
   调它只影响块的粒度，不影响"有没有丢内容"。
3. **每个分类是一个独立来源**，所以 `bySource` 的输出就是"哪个分类贡献了多少页"。

### 路 B：手写文档（我们自己维护的那部分）

**格式规范见 `docs/md/知识库文档格式规范.md`** —— 那里有完整定义、反面教材，
以及一段**可以直接粘给外部 AI 的指令**。这里只说运营上的要点：

#### 三步

```bash
# ① 校验格式（不启动 Spring、不碰数据库、不联网）
./scripts/validate-kb-doc.sh 你的文档.md

# ② 带上基线，看"这次导入会改动多少条"
./scripts/validate-kb-doc.sh --against docs/gamedata/现有文档.md 你的新文档.md
```

实测输出（三种用法都验证过）：

```
[可导入] kb-doc-ok.md
  文档头 : name=Absorb  url=…  ⚠缺 tags
  分块   : 6 块，正文共 5782 字（平均 963 字/块）
  导入计划：新增 0 条，覆盖 1 条，无变化 1 条；库里未被触及 4 条
结论：格式全部通过，可以导入。        ← 退出码 0
```

> ⚠️ **脚本依赖两件事**：`$JAVA_HOME`（没设时回退到 `.toolchain/jdk-17.0.2`，
> 而那个目录**在本仓库里并不存在** —— 请确保 `JAVA_HOME` 指向一个 JDK 17+），
> 以及 `server/target/classes`（即**先编译过**）。缺任何一个它会明确报出来。

③ **导入走管理后台**：知识库 → 「文档」面板 → 拖进去。
（对应的接口是 `POST /admin/api/kb/blocks/preview` 先预览、`POST /admin/api/kb/blocks/import` 真导入。
**先 preview 再 import** —— 预览会告诉你"新增几条、覆盖几条"。）

#### ⚠️ `source` 字段决定模型怎么引用它 —— 现在**全部填错了**

代码里的判据是 `source == "manual"`：

| `source` | 模型看到的分段 | 措辞 |
|---|---|---|
| `manual` | **【我们维护的内容】** | "我们资料库里写的是…" |
| 其他（`wiki`/`doc`/…） | **【导入的资料】** | "资料上写的是…**可能已经过期**" |

**实测：`docs/gamedata` 下 34 份文档全部写的是 `source: wiki`** ——
所以现在**100% 的知识库都被标注成「可能已经过期」，「我们维护的内容」永远是空的**。

**怎么改**（按文档性质分，不要一刀切）：

| 文档 | 建议 | 理由 |
|---|---|---|
| 物品图鉴（27 份） | 保持 `wiki` | 它是 wiki 数据的翻译整理，wiki 本身会过期 |
| 更新/攻略（铸路更新、水体系统、雾水盆地攻略、补丁14、热修） | 改成 `manual` | **是我们自己写的摘要与判断**，模型该说"我们资料库里写的是" |

改完之后**重新导入那几份文档**即可（覆盖，不会重复）。

> ⚠️ **2026-10-04 修了一个 bug，这个改动以前是空转的。**
> 导入计划（`ChunkImportPlan`）只比对**正文**，而 `source` 是**文档级**字段、不在块里 ——
> 所以"只改了文档头 `source`"会被判成**无变化**，导入什么都不写。
> 也就是说 `source` 在首次导入之后**永远改不掉**。
>
> 现在 `KbDocImporter` 会额外比对文档级字段：正文相同、但库里那一块的 `source`
> 与本次文档头不一致时，把它从「无变化」挪进「覆盖」。
> **预览与真导入共用同一份计算**，所以不会出现"预览说 0 条、实际改了 N 条"。
>
> 因此导入这 6 份时，预览应当显示 **覆盖 72 条、无变化 0 条**（6 份文档的块数：
> 21 + 15 + 15 + 9 + 8 + 4）。**如果预览说"无变化"，说明改动没生效，别继续。**

## 3. 维护：日常循环

### 3.1 增量是自动的

- **wiki 文章**：按 `revid` 比对，没变的页不重新清洗、**不重新向量化**（embedding 按量计费）
- **手写文档**：导入计划会告诉你"新增 / 覆盖 / 无变化"各几条

所以**定期重跑导入是安全的、便宜的**。

### 3.2 词条表会自动长（一块一条）

导入时**每个块**都会在词条表占一行：块 id = 词条 key，块标题 = 中文名。

- 标题结尾的 `（English）` 会自动拆成别名（`深渊之翼斧（Abyssal Wing Axe）` → `深渊之翼斧、Abyssal Wing Axe`）
- **已存在的词条不会被覆盖** —— 人工核对过的名字不会被导入冲掉

所以「知识库 → 词条」面板就是**分块的目录**：导一份 147 块的图鉴，就多 147 条词条。

### 3.3 三个需要手动做的动作

| 动作 | 什么时候做 | 接口 / 位置 |
|---|---|---|
| **补标题向量** | 导入后，或 `/stats` 里 `titleVectors` 少于 `blocks` 时 | 块面板「补标题向量」/ `POST /blocks/title-vectors/backfill` |
| **清理孤儿词条** | **每次 purge/下架之后** | 词条面板 / `POST /terms/clear-orphans` |
| **补中文名** | 导入之后（英文页没有译名） | **见 §3.5** —— 当前最高价值的一件 |
| **看检索统计** | 定期 | 提案面板 / `GET /proposals/stats` |

> **为什么孤儿词条要手动清**：手工加的、还没导正文的名字也长那样（"先起个名字、正文以后再导"），
> 自动清会把它一起删掉。所以这个决定权留给人。

### 3.4 回滚

```bash
# 清掉全部 wiki 文章块（含切出来的续块）+ 导入状态
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.wiki-import.import-on-start=true --app.kb.wiki-import.purge=true \
--spring.main.web-application-type=none"

# 清掉全部派生地点块
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.location-corpus.build-on-start=true --app.kb.location-corpus.purge=true \
--spring.main.web-application-type=none"
```

回滚是**双向**的（会连状态一起清），回滚后可以重新导入。**回滚完记得清孤儿词条。**

### 3.5 ★ 补译名：缺口词的正解（按板块分批）

**这是当前最高价值的一件维护工作** —— 比再抓 300 页都管用。

#### 为什么

实测：**651 / 3,416 条词条（18%）没有中文名。**

| 属性 | 块 id | 词条表的 `zh` |
|---|---|---|
| 力量 | `wiki-strength` | `Strength` ← 纯英文 |
| 智力 | `wiki-intelligence` | `Intelligence` |
| 体质 | `wiki-constitution` | `Constitution` |
| 战斗机制 | `wiki-combat-mechanics` | `Combat Mechanics` |

B 路（关键词）判定「命中」靠的是**词条名出现在问句里** ——
中文问句里永远不会出现 `Intelligence`，所以这些内容**中文提问永远够不到**。

> 这解释了缺口词表（法师 71 / 技能 44 / 属性 13 / 力量 13 / 智力 10 …）：
> **不是「库里没有内容」，是「库里有内容但没有中文名」。**

这个缺口是代码里**早就写明**的（`NameZhIndex` 类注释）：

> 实测 `Combat Mechanics` / `Crafting` / `Survival` 这类机制词条语料里没有译名，
> 就只能留英文（**那部分要靠别名表人工补**）。

**别名表就是词条表的 `zh` 列。**

#### 怎么补

**在后台逐条改**（适合少量）：

```
管理后台 → 知识库 → 词条 → 点「无中文名 · N」→ 选一个板块 → 逐条填中文名
```

改完**立即生效，不用重启机器人**。

**走 Excel**（651 条推荐这条路）：

```
① 选「无中文名」+ 一个板块 → 点导出
   得到 kb-terms-unnamed-quest.tsv
② Excel 里**只填第 2 列**（中文名，多个别名用「、」分隔）
③ 导回（POST /admin/api/kb/terms/import）
```

导出/导入的 TSV 格式（导出文件头部就写着）：

```
# 列：英文名 <TAB> 中文名 <TAB> wiki页面 <TAB> 类别 <TAB> 状态
# ⚠️ 导入时只读第 1、2、5 列；中间两列是导出时算出来的派生信息，改了没用
```

> **导出会带上当前筛选**（视图 + 板块 + 搜索词）—— 「看到什么就导出什么」。
> 所以先在后台选好板块再点导出，得到的就只是那一批。

#### 建议的批次顺序（按数量从小到大）

| 批次 | 板块 | 待补译名 | 说明 |
|---|---|---|---|
| 1 | `combat` 战斗装备 | 4 | 先熟悉流程 |
| 2 | `build` 建造装饰 | 33 | |
| 3 | `creature` 敌人生物 | 50 | |
| 4 | **`system` 系统机制** | **145** | ← 技能/属性，缺口最痛 |
| 5 | **`quest` 任务剧情** | **416** | |

> 数字是 2026-10-04 的实测，补完会变。

#### ⚠️ 三条硬规矩

1. **宁可少一个中文名，也不要编一个错的。** 这是 `NameZhIndex` 里定下的原则 ——
   编错的名字会**污染整个检索**。查不到就留着，别硬翻。
   - 标准属性/机制（`Strength`→力量、`Intelligence`→智力、`Crafting`→制作）可以放心补；
   - **技能名**（`Absorb` / `Arcane Concentration` / `Battle Heal` …）
     需要**游戏官方中文**，不要自己编。
2. **导入不会覆盖已有的中文名**（只在为空时补齐）—— 所以重复导入是安全的。
3. 「无中文名」的判定是 **`zh` 里一个汉字都没有**（不是空字符串）——
   所以 `Bamboo Ladder、Bamboo Ladder` 这种「中文名和别名都是英文」的**也算没名字**。

#### 怎么确认生效

补完一批，直接问一个之前够不到的问题（例如「智力有什么用」），
看机器人是不是开始引用资料了。**不用重启。**

### 3.6 提案：从真实提问里找缺口

问答记录（`qa_stat`）会积累**真实提问**。提案面板能从里面找出"我们答不好"的问题，
比对现有文本后产出"新增/覆盖"提案 —— **一律人工确认后才写进知识库**，不自动落库。

这是**最有价值的一条维护线索**：它告诉你群友实际在问什么，而不是我们猜他们问什么。

## 4. 三条最容易踩的坑（都实测过）

1. **`.toolchain/` 是 PathGuard 的禁止片段**
   —— 在隔离构建目录里跑带媒体目录的命令会被拒（`路径命中禁止片段 .toolchain/`）。
   正常在 `server/` 下跑没这个问题。

2. **启动/导入命令必须带 `--spring.main.web-application-type=none`**
   —— 否则会和正在跑的服务抢 8080 端口。

3. **导入会写生产库**（`server/data/qa/qqbot.sqlite`）。
   **先备份**：`cp server/data/qa/qqbot.sqlite* /tmp/`

## 5. 建议的下一步（按性价比排序）

> 下面这份清单是 2026-10-04 更新过的。**早先那五条（改 `source` / 记基线 /
> 导 Quests / 加技能 / 加 Lore）都已经做完了** —— 进度见 `docs/md/检索基线.md`。

### ① ★ 补译名（651 条，按板块分批）—— 见 §3.5

**直击缺口频次最高的那一簇**（力量 13 / 属性 13 / 智力 10 / 技能点 28）。
成本极低、可立即验证：补完 `system` 那 145 条之后，「智力有什么用」这类问题就该开始有资料了。

### ② 补完译名之后再决定要不要推批次 3（Armor Set 59 页）

已有的实测结论：

| 批次 | 效果 |
|---|---|
| 批次 1（Quests/ + 技能 + Wildlife，+403 块） | **有效** —— 2 条 gap 变成可回答，gap 干净率改善 |
| 批次 2（Lore，+364 块） | **无退化也无改善** —— 因为它没触及任何缺口 |

批次 3 大概率同理（Lore 的前车之鉴）。**先做 ①，再回来判断。**

### ③ 两个实测到的检索问题（尚未解决）

- **近名污染**：具体物品块赢过通用页 ——
  `空洞独眼巨人战利品` > `空洞独眼巨人`、`腐蚀之血` > `腐血`、`城堡屋顶方块` > `城堡方块`
- **短提问返回空**：`游侠跑得快算有用吗` / `可以挤牛奶吗` —— 东西在库里却 **0 命中**。
  **这和 `gap` 恰好相反**：gap 是"不该答却硬答"，这里是"该答却说没查到"。两类要分开盯。

### ④ 自动导入正文的整理（Boss / 机制页）

自动导入的块**正文是英文**，且清洗后有模板残渣：

```
[wiki-abyss] "is a skill in Enshrouded."        ← 开头没主语（模板剥掉留下的）
[wiki-quests-nursery-supplies] "…started by reading ."
```

需要人工整理成中文 —— 用**路 B（手写文档）**重写那几页，见《知识库文档格式规范》。
