# 知识库导入设计（定稿）

> **⚠️ 文档状态（2026-10-04 更新）**：这是**当时的导入设计**，已实现并继续演进。
> 其中**已经变了**的部分：词条表载体从 CSV 改成 **xlsx**（CSV 在中文 Windows 上有
> 静默乱码的陷阱，见《知识库运维命令速查》第六节）；术语表已迁进 SQLite `kb_term` 表。


> 本文取代之前关于"语料重建 / 合并式写入 / 三路合并"的讨论 —— **那些设计已被废弃**，
> 原因见第三节。现状诊断与回答策略部分见 `回答策略与知识库设施设计.md`。

---

## 一、边界（用户 2026-09-28 明确）

```
系统外（另一个 AI / 人）                系统内（本仓库）
──────────────────────────            ──────────────────────────
联网搜索、抓取网页
清洗成"人话"
翻译成中文
按格式生成文档          ───────────▶   解析 → 块 → 索引 → 检索回答
```

- 系统**不做**：抓取、清洗、翻译、生成文档
- 系统**只做**：符合格式的文档 → 知识库
- 格式契约见 `知识库文档格式规范.html`

## 二、文档头（推荐版，待用户最终确认）

放在文件**最前面**：

```
<!-- doc
name: 灵火祭坛
url: https://enshrouded.wiki.gg/wiki/Flame_Altar
tags: 基础, 据点
source: wiki
-->

=== 灵火祭坛 === <!-- id: flame-altar-0 -->
祭坛是复活点…
```

| 字段 | 必填 | 作用 | 缺了的后果 |
|---|---|---|---|
| `url` | **强烈建议** | 回答时给出处；人工核对原文的唯一线索 | 机器人说不出资料从哪来 |
| `tags` | 建议 | 板块归类 + 公开站筛选 | 分类体系塌掉 |
| `name` | 建议 | 管理端显示资料名 | 只剩裸块 |
| `source` | 可选 | 来源标记 | 无法区分来路 |
| 其他 | 可选 | 原样保留 | — |

**解析规则**：首行**恰好**是 `<!-- doc`（大小写不敏感）；必须有闭合 `-->`；
正文是 `key: value`；未知键保留。忘了闭合会导致它把后面正文一起吃进去 ——
校验器会专门报这个。

**它是可选的**：不写也能导入，只是丢掉 url / tags 两样能力（校验器提示 `⚠缺 url`）。

## 三、⚠️ 已废弃的设计（不要照旧做）

用户明确"**外部 AI 只给改动过的块**"，于是下面这些**全部不需要**：

| 废弃 | 原因 |
|---|---|
| **base 快照**（记住上次导入的原文） | 没有"整份替换"，就没有三路合并的第三个输入 |
| **三路合并 / 冲突提案** | 文件里出现的 id → 覆盖；没出现的 → 不动。**没有"冲突"这个概念** |
| **`mergeChunkLines`（按行号合并语料）** | 它是为"系统内重建语料"服务的；系统不再重建语料 |
| **`.premerge.bak` 备份** | 同上 |
| **`KbEditThenRebuildTest`（3 个端到端测试）** | 测的正是上面那套 |
| wiki 增量判断（revision timestamp） | 系统不再抓 wiki |

> 用户两轮前的判断是对的：合并式写入在"系统内不再重建语料"之后失去了意义。

## 四、块身份：id 即身份（用户已确认）

**退休"行号 = 块号"**这条铁律。要改的地方：

| 改什么 | 内容 |
|---|---|
| `index.bin` | 除了向量，还要存**块 id 列表**（否则不知道第 k 行是谁） |
| `KbIndex` | 提供 `id → 向量` 的检索路径 |
| `KbRetriever` | `Hit` 带 id |
| `qa_stat.retrieved` | 历史存的是行号 `{"i":770}` → 要能映射到 id（老数据兼容） |
| 管理端 | 按 id 引用块（现在按 `i`） |
| **墓碑机制可退休** | 不再需要"不删行" —— 这是最大的简化收益 |

### id 命名约定（建议，待确认）

**用「英文页面名-序号」**，例如 `flame-altar-0`、`flame-altar-1`。

理由：它与**术语表里原有的「英文页面名」列天然对齐** ——
术语表说"炉子 → Flame Altar"，块的 id 就是 `flame-altar-*`，两边能对上。

（之前的示例里我用了 `p5233-0` 这种"pageid-序号"，与术语表对不上，**建议改掉**。）

## 五、导入流程

```
文档(.md)
  │
  ├─ 1. 解析（ChunkMarkup）：文档头 + 块（id / 标题 / 正文）
  │
  ├─ 2. 校验：有致命错误就停，并把每条错误报给人
  │
  ├─ 3. ★ 预览（dry-run）：告诉人"这次会新增 N 条、修改 M 条、无变化 K 条"
  │      不改任何数据，纯比对
  │
  ├─ 4. 写入（按 id upsert）
  │      文件里出现的 id → 覆盖；没出现的 id → **一个都不动**
  │
  └─ 5. 只为"新增/修改的那些块"重算向量，追加/更新索引，热重载
```

### 增量语义（用户原话）

> 现有知识库一共有 1-100 个分块，我有一个文件里只有 4、6、30 这三个分块的内容，
> 那么导入之后，就只更改这三个分块的内容，其他的不变；导入前告诉我会改动多少条。

### 幂等（用户要求）

同一份文件导两次，结果必须完全一致（第二次报告"新增 0、修改 0、无变化 3"）。

## 六、两个连带后果（需要用户确认）

### ① 手工订正会被覆盖

"只给变更 + 以最新为主"意味着：**你手工改过的块，如果外部 AI 也给了它，会被直接覆盖**。
系统没有"上一版原文"，无法判断"这是 AI 改的还是你改的"。

- 若接受 → 什么都不用加
- 想保住 → 需要一条：**手工改过的块默认不覆盖，只在预览里列出来等你决定**

### ② 删除表达不出来

"只给变更"的另一面：AI **删掉**一块时，它只是不出现 —— 系统会当成"不用改"，
旧块**永远留着**（还会被检索到）。

可选解法：
- (a) 约定一个删除标记（如 `=== 标题 === <!-- id: xxx retired -->`）
- (b) 管理端的「下架」功能人工处理（量小时够用）

## 七、术语表

用户决定：**用 Excel 维护、走 CSV 导入、要做幂等、冲突以最新为主**。

**它不是分块文件，两者别混**：

| | 知识库文档 | 术语表 |
|---|---|---|
| 装什么 | 知识正文（喂给模型当资料） | 词汇映射（检索时做查询扩展） |
| 形态 | 自由长文本 + 分块 + id | 表格：一行一组对照 |
| 载体 | `.md`（含文档头） | **`.xlsx`**（Excel/WPS 编辑；CSV 因中文编码陷阱已不推荐） |
| 落到哪 | 块表（待建） | `kb_term`（**已存在**） |

**但两者必须共用同一套 id** —— 这是关键连接点：
术语表里写 `flame-altar, 灵火祭坛, 祭坛, 火焰祭坛` 的那个 `flame-altar`，
就是分块文件里 `<!-- id: flame-altar-0 -->` 的同一个标识。

**建议的 CSV 列**（正文翻译成中文后，"英文名"这列要重新理解成 id）：

| 列 | 说明 |
|---|---|
| `id` | 英文标识，与块 id 对齐（原来是 wiki 页面名） |
| `中文名` | 标准中文名，与块的标题对齐 |
| `别名` | 逗号分隔。群友的口语说法 → 检索时映射到标准名 |
| `状态` | 可选：待核对 / 已核对 / 弃用 |

**当时的资产**：`kb_term` 表里已有 3,903 条（3,359 条填过中文名），
~~以及 `data/kb/glossary/zh-en.tsv`（236 KB，由 `GlossaryBuilder` 从 wiki 生成）~~
—— **已废弃**：2026-09-27 迁进 `kb_term` 表，文件与生成器都已删。
导入入口 `POST /kb/terms/import` **已存在**，且已支持 **xlsx / csv / tsv** 三种输入。

## 八、新老语料切换（用户已确认）

**首次导入中文文档之前，清空现有语料。**

现有 4,131 块是**英文**的；新的都是中文。中英混装会互相抢检索结果，
所以用户选择：**导入前清空**。

要清空的：
- `data/kb/chunks.jsonl`（4,131 块）
- `data/kb/index.bin`（17 MB 向量）
- `data/kb/raw/`（3,908 个 wikitext）
- `data/kb/pages.jsonl`、`build.json`
- **不动的**：`kb_term`（3,903 条人工成果）、`kb_category`、`kb_contribution`、`kb_proposal`
