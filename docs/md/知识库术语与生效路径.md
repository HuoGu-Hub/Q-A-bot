# 知识库：生效路径与四个词的含义

> 面向想搞清楚"这东西到底怎么起作用的"的人。
> 现在这套东西处于**迁移中途**（新旧两套存储并存），所以有些词的含义刚变过 —— 这份文档按**代码里的实际含义**写。

---

## 零、先定一个标准：什么叫"生效"

知识库只有一个目的：**让机器人在回答时手里有资料**。
所以"生效"的唯一标准是：**它有没有出现在那一次回答的提示词里**。

按这个标准看那四个词，**只有两个能生效**（文档、词条），
另外两个各有别的职责（分类管浏览、提案是"待办"）。
这是最容易搞混的地方 —— 它们并列在一排 tab 里，看着像同一层的东西，其实不是。

---

## 一、生效路径（一条主线）

```
外部 AI：搜索 → 清洗 → 翻译成中文 → 产出【文档】
                    │
                    ▼
       管理端「文档」导入（预览 → 确认）
                    │
                    ▼
    kb_block 表（块 + 正文）+ kb_block_vec 表（向量）
                    │
                    ▼
   KbBlockIndex（常驻内存的快照：块 + 向量成对）
                    │
                    │   ← 【词条】在这里起作用：把群友的中文说法对齐到资料里的写法
                    ▼
   KbRetriever 两条路一起跑：
     A 路 向量：问题 → embedding → 和每块算余弦 → 过阈值取前几
     B 路 关键词：词表把问题里的名词展开 → 在标题/正文里找
     → RRF 按排名融合 + 标题精确命中加成
                    │
                    ▼
   拼进提示词 <<<KNOWLEDGE>>>（分两段：【我们维护的内容】【导入的资料】）
                    │
                    ▼
              模型据此回答
```

### 现在只有一套存储

2026-09-29 起，旧的 wiki 抓取 + 语料文件那一套**已经整块删掉**，`app.kb.store` 开关也没了。**管理端导入文档 → 立刻就是回答用的资料**，不需要切换、不需要重启（索引在写入后自动重载）。

## 二、四个词，一个一个说

### 1. 文档（新）

| | |
|---|---|
| **存在哪** | `kb_block`（正文）+ `kb_block_vec`（向量），SQLite |
| **是什么** | 一份符合格式规范的资料文件，**正文中文**。最小单位是**块**，块的身份是 **id**（如 `flame-altar-0`） |
| **生效吗** | **能** —— 切换之后它就是这个系统**唯一**的资料来源 |

**关键规则（就一条）**：
> 文件里出现的块：**id 存在就覆盖，不存在就新增**。文件里没出现的块：**一个都不动**。

所以"只给改动过的几块"是完全支持的，也正是推荐的用法。
块 id 用英文（`flame-altar-0`）、正文和标题用中文 —— 因为 id 是数据库主键，
跟着中文标题改的话，块的身份会跟着标题一起断。

### 2. 词条

| | |
|---|---|
| **存在哪** | `kb_term` 表（`en` / `zh` / `status`），现有人工成果 3,903 条，其中 3,359 条填过中文名 |
| **是什么** | 一张**名字对照表**：「英文名 → 中文名 + 别名」。别名不是单独的列，就是 `zh` 里用 `、` 分隔的若干写法（如 `熔炉、炉子、窑`） |
| **生效吗** | **能，但是间接的** —— 它不提供内容，它**让检索能命中** |

它解决的是一类具体问题：
> 群友问「**炉子**怎么用」，而资料里写的是「**熔炉**」。
> 字面上一个字都对不上，纯靠向量也可能排到很后面。
> 词条表里有一条「熔炉、炉子」，检索时就知道这两个词指的是同一件东西。

**状态（`status`）到底管什么**：只排除 `rejected`。
`draft`（没核对）和 `verified`（已核对）**都参与检索** ——
状态是给**人**看的进度，不是准入的门槛。别以为没标 verified 就不生效。

**关键词路认两种东西（2026-10-01 起）**：

1. **整条名字出现在问句里** —— 精确匹配。靠人写别名（`zh` 里用 `、` 分隔）。
2. **问句里的一小段是某个名字的一部分** —— 子串匹配，**不需要人工写别名**。
   例：「抱枕怎么得」能命中「大型农场动物抱枕」。
   做法是把问句切成长度 2~3 字的连续中文片段，看哪个名字含有它；
   命中名字太多的片段整段丢掉（便宜的停用词表，会跟着语料自己变）——
   所以「这个怎么合成」「今天天气怎么样」这类问句**一个词都不会多出来**。

有了第 2 层，导入文档自动生成的 2,000 多条词条**不用人补别名也能被检索到**。
实测（真实 2,649 个物品名）：稳态开销 0~2ms。

**切换之后它的作用会变**：资料变成中文了，所以它从"中文 → 英文"变成"**别名归一**"
（炉子 → 熔炉）。机制没变，方向变了。

### 3. 分类

| | |
|---|---|
| **存在哪** | `kb_category` 表 |
| **是什么** | 把 Wiki 六百多个原始分类**映射**成 9 个玩家能懂的大类 |
| **生效吗** | **不参与检索**。它只影响**浏览** |

9 个大类：战斗装备 · 建造装饰 · 材料消耗 · 敌人生物 · 地点探索 · 任务剧情 · 系统机制 · 大佬攻略 · 其他

具体影响两个地方：
- **公开站的「浏览资料库」**（玩家按大类翻资料）
- **管理端词条列表里的「板块规模」**（每个大类底下有多少条）

> **一句话：分类是货架，不是货。** 它摆得再整齐也不影响机器人怎么答。

顺带说清一个容易混的点：块的 `tags`（标签，如 `基础, 据点`）**就是**"原始分类"，
`kb_category` 存的是它的中文名和归属大类。两者指向同一批数据。

### 4. 提案

| | |
|---|---|
| **存在哪** | `kb_proposal` 表 |
| **是什么** | 由**被认可的问答**反推出来的知识库改进建议 |
| **生效吗** | **它本身不生效** —— 它是**待办**，人工确认之后才落地 |

它怎么来的：
```
群友给某次回答点「有帮助」 → 攒够阈值（默认 10 条）
        → 让 agent 对比「当时检索到的资料」和「这次被认可的回答」
        → 产出一条提案：覆盖某页正文 / 新增一条
```

人工确认（approve）之后分两种落地方式：

| 提案类型 | 落地方式 | 生效时机 |
|---|---|---|
| **覆盖** | 直接改那一块的正文 + **重算那一块的向量** | **立刻生效** |
| **新增** | 直接落成一个新块（docId 用 `proposal-<提案号>`） | **立刻生效** |

> **一句话：提案是待办，不是资料。**
> 它存在的意义是"群友觉得这个回答好，那就把它沉淀进知识库" —— 但沉淀必须过人这一关。

## 三、一张表看完

| 词 | 存在哪 | 干什么 | 参与回答吗 |
|---|---|---|---|
| **文档** | `kb_block` | 资料本体（中文、按块 id 增量覆盖） | ✅ **切换后唯一的来源** |
| **词条** | `kb_term` | 名字对齐（别名归一） | ✅ **间接** —— 帮关键词路命中 |
| **分类** | `kb_category` | 浏览用的货架 | ❌ 只影响浏览 |
| **提案** | `kb_proposal` | 人工确认后才落地的改进建议 | ❌ 确认后才落地 |

---

## 四、"什么时候才生效"四条规则

1. **文档**：**导入即生效**（写进块表 + 索引自动重载，不用重启）
2. **词条**：保存即生效（词表按版本号自动感知，**不用重启**）
3. **提案**：**人工确认**之后才生效（新增的提案直接落成块，不再绕投递）
4. **分类**：改了就生效，但只影响浏览

---

## 五、最容易混的两组

**词条 vs 文档**
: 文档是**内容**，词条是**名字**。同一份文档在两边各有一条记录，靠英文名 / id 对齐。
改内容去「文档」，改名字去「词条」。

**分类 vs 标签**
: 标签是块自己带的原始分类（`基础`、`据点`），分类是这些标签的**中文名 + 归属大类**。
两者指向同一批数据，只是一个是原料、一个是成品。

## 六、已经不存在的（免得你去找）

| 已经删掉的 | 替代做法 |
|---|---|
| wiki 抓取 / 清洗 / 建索引（kb/build 全套） | 外部 AI 产出符合格式的**文档**，从「文档」面板导入 |
| chunks.jsonl / index.bin / pages.jsonl / raw/ | SQLite 的 kb_block / kb_block_vec 表 |
| 「资料」tab：投递 + 邀请码 | 下线了 —— 资料一律以文档形式导入 |
| 「词条」里按行号改文本块 | 改正文在「文档」面板按**块 id** 做（会自动重算向量） |
| app.kb.store 切换开关 | 没了，只有一套存储 |

旧语料已归档到 server/data/.legacy-archive/。

## 七、如果要记一句话

> **文档**是货，**词条**是标签机，**分类**是货架，**提案**是待办清单。
>
> 只有货（和帮忙认货的标签机）会进到机器人嘴里。
