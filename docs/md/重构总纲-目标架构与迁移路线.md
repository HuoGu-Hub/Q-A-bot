## 一、现状体检结论（摘要）

| # | 症状 | 实证 | 后果 |
|---|---|---|---|
| 1 | **配置是最大耦合源** | fan-in 前十里 6 个是 Properties：`GuardProperties` 被 **17** 个类注入、`KbProperties` 11、`QaProperties` 10；`GuardProperties` 单类 661 行；`config` 包 18 类 / 2,800 行 | 改配置结构 = 改一片类；功能无法独立实例化测试 |
| 2 | **持久化单点** | `QaStore` 被 **12 个类** import，横跨 8 个业务包 | SQLite 连接这个纯技术细节，成了 8 个业务包的公共依赖 |
| 3 | **编排层是上帝类** | [`MessageRouter.java`](../server/src/main/java/com/example/qqbot/router/MessageRouter.java) 452 行、跨包依赖 24 个，横跨 7 个子系统 | 加任何功能都必须动它 |
| 4 | **知识库包切碎 + 半迁移** | `kb` 包 8 子包 / 6,935 行；新老两套身份并存；**`KbIndex.java` 已删除但 4 个文件仍 `{@link KbIndex}`**（Javadoc 坏链） | 认知成本高，新人（和新 AI）容易读错 |
| 5 | **术语表是标题的镜像** | `kb_term` 2,649 行 = `kb_block` 2,649 行，1:1 派生；`en` 列存的是**块 id**；`status` **100% 是 draft** | B 路只在用户打出词条名时生效，不提供任何口语桥 |
| 6 | **统计口径混乱** | `qa_stat` 6,558 条里 6,444 条 `hit_count=0`、6,410 条 `guard_action='drop'` | "数据大屏"建立在这张表上，已知 7 处口径错误 |
| 7 | **前端上帝组件 + 类型手抄** | `TermPanel.vue` 1,720 行 / 17 个 API 调用点；`types.ts` 679 行手写 DTO 镜像 | 必然漂移，改后端字段要人肉找前端 |
| 8 | **探针不可移植** | 多个脚本硬编码 `/app/workspace/qqbot/...` | 在宿主 Windows 上直接跑不了 |

## 二、目标架构

### 2.1 一句话

把"按技术分包的贫血单体"改成 **"按业务能力分模块 + 模块内端口-适配器"**：模块之间只认接口，技术细节（SQLite、HTTP、模型 SDK）全部退到适配器层。

### 2.2 模块划分

现状 21 个包收敛为 **9 个业务模块 + 3 个基础模块**。括号内是现状对应包。

| 模块 | 职责 | 拥有的数据 | 对外暴露的端口 |
|---|---|---|---|
| `protocol` | OneBot 协议细节（现状 `onebot/`） | — | `OutboundPort`（唯一发消息出口）、`EventSource` |
| `guard` | 唯一有权说"不"（现状 `guard/`） | `rate limit` 内存态 | `GuardPort`（`GuardResult decide(GuardRequest)`） |
| `command` | 指令匹配与渲染（现状 `command/`） | `bot_command` | `CommandPort` |
| `conversation` | 回答编排（现状 `agent/` + `router/` 的问答部分） | — | `ReplyUseCase` |
| `knowledge` | 知识库：检索 + 语料 + 术语 + 地图（现状 `kb/` + 新 map） | `kb_block*`, `kb_term`, `kb_map_*` | `RetrieverPort`、`CorpusPort`、`MapPort` |
| `qa` | 问答记录与统计（现状 `qa/`） | `qa_stat`, `qa_raw`, `qa_keyword` | `QaRecordPort`、`QaAnalyticsPort` |
| `plaza` | 问答广场（现状 `plaza/`） | `answer_vote`, `help_request` | `PlazaPort` |
| `site` | 公开站文案与轮播（现状 `site/`） | `site_text`, `site_carousel` | `SitePort` |
| `llm` | 唯一知道"用哪个模型"（现状 `llm/`） | — | `ChatModelPort`、`EmbeddingPort`、`RerankPort` |
| `platform` *(基础)* | 配置、日志、线程池、脱敏（现状 `config/` + `logs/`） | — | 由装配层使用 |
| `persistence` *(基础)* | **唯一持有 SQLite 连接**、事务、迁移 | 全部表 | 各模块自己的 Repository 接口 |
| `adminapi` *(基础)* | 后台鉴权与 HTTP 装配（现状 `admin/` + `settings/`） | `admin_visit` | — |

> ⚠️ **`publicapi` 不是模块**：现状 `publicapi/`（6 类 / 1,023 行）与 `admin/`（4 类 / 944 行）都只是**传输适配器**，它们应当分别调用 `knowledge`/`qa`/`plaza`/`site` 的端口，而不该自己承载业务逻辑。现状 `PublicController` 449 行直接 import `Glossary`/`category`/`KbRetriever`/`QaAnalytics`，就是"适配器里长出了业务"。

### 2.3 把"四条铁律"升级为**可自动校验**的规则

现状的四条铁律写在 [`server/README.md`](../server/README.md) 里，方向完全正确——**但它们只是文档，没有任何机制强制**。重构的第一件事是让违反铁律的代码**编译不过或测试挂掉**。

用 [ArchUnit](https://www.archunit.org/)（`com.tngtech.archunit:archunit-junit5`，开源、纯 Java、无运行时开销）写成普通单测：

| # | 规则 | 现状是否满足 | ArchUnit 断言（示意） |
|---|---|---|---|
| R1 | 只有 `protocol` 能 import OneBot 协议类型 | ✅ 满足 | `noClasses().that().resideOutsideOfPackage("..protocol..").should().dependOnClassesThat().resideInAPackage("..protocol.model..")` |
| R2 | 只有 `protocol` 能发消息（唯一出站） | ✅ 满足 | 禁止 `protocol.client` 被 `protocol` 之外引用 |
| R3 | 只有 `llm` 知道模型厂商 | ✅ 满足 | 禁止 `dev.langchain4j` 被 `llm` 之外引用 |
| R4 | 只有 `guard` 能否决 | ✅ 满足 | 禁止 `GuardResult` 被 `guard` 之外构造 |
| **R5** | **任何模块不得直接持有 SQLite 连接** | ❌ **违反 12 处** | 禁止 `java.sql` / `javax.sql` 出现在 `persistence` 之外 |
| **R6** | **模块之间只认端口，不 import 实现类** | ❌ 待建 | `slices().matching("com.example.qqbot.(*)..").should().beFreeOfCycles()` |
| **R7** | **`config` 的 Properties 不得被业务模块注入** | ❌ **违反多处** | 业务包不得依赖 `..config..`（仅 `platform` 装配层可依赖） |

> R1–R4 现在**本来就满足**，加上测试是"防退化"；R5–R7 是**现状就在违反**的，先写成 `@Disabled` 的"目标测试"，随各阶段逐个打开——这比"写进文档"有约束力得多。

## 三、五台手术

每台手术都给出：问题 → 方案 → 影响面 → 回滚 → 验收。

### S1 持久化去单点 ★收益最高

**问题**：`QaStore` 同时是"问答记录仓储"和"全项目 SQLite 连接提供者"，被 12 个类直接依赖。这个耦合是**技术约束逼出来的**（代码注释写明：两个连接开同一个 SQLite 文件会因 WAL 共享内存冲突报 `SQLITE_IOERR_SHMOPEN`），所以不能简单"每个 Store 开自己的连接"——那正是当年的坑。

**方案**：
1. 新建 `persistence/SqliteDatabase`：**全项目唯一**持有 `Connection` 的地方，暴露 `inTransaction(...)` 与 `query/update`。
2. 各模块定义自己的 Repository **接口**（如 `knowledge` 的 `BlockRepository`），实现放在各模块的 `internal/` 下，构造时注入 `SqliteDatabase`。
3. `QaStore` 退回"只做问答记录"，删掉它作为连接提供者的身份。
4. 迁移脚本集中到 `persistence/SchemaMigrator`（保留现有幂等 `PRAGMA table_info` 补列的做法——这个做法是对的）。

**影响面**：12 个类的构造签名；无表结构变化、无数据迁移。

**回滚**：保留旧的 `QaStore.connection()` 委托到 `SqliteDatabase`，一个提交即可回退。

**验收**：ArchUnit R5 打开并通过；12 处 `import QaStore` 降为 0（或仅 `qa` 模块内）。

#### ✅ S1 第一步已落地（2026-10-02）：连接提供者接口

先只换**依赖类型**，不动 SQL —— 这一步行为零变化，却能把一条架构规则从目标变成已生效。

- 新增 [`persistence/SqliteConnectionProvider`](../server/src/main/java/com/example/qqbot/persistence/SqliteConnectionProvider.java)：
  `connection()` + `isAvailable()`。**技术细节留在技术包里**。
- `QaStore implements SqliteConnectionProvider, AutoCloseable`。
- **10 个类**的依赖从 `qa.QaStore` 换成 `SqliteConnectionProvider`，字段名 `qaStore` → `db`
  （名字也是耦合：叫 `qaStore` 会让人以为它们在读写问答记录）。

**实测效果**：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| `QaStore` 的依赖方 | **12** | **2**（`AdminAuthFilter.recordVisit`、`AdminController.annotate`） |
| `kb → qa` 编译依赖 | 4 个 Store | **0** |
| ArchUnit「kb 不得依赖 qa」 | `@Disabled`（目标） | **已生效** |
| 测试改动 | — | **0 个测试文件需要改**（测试传 `QaStore`，它实现了接口） |

> **诚实说明**：依赖**数量**几乎没有下降（新的 `SqliteConnectionProvider` 有 11 个依赖方），
> 变的是**依赖什么** —— 从"依赖 qa 这个业务模块的具体类"变成"依赖一个技术接口"。
> 真正的收益是：`kb` 不再知道"问答记录"存在，且 kb↔qa 的编译期环被**单向打破**。
> 依赖总数要降下来得靠后面的 Repository 化，那是 S1 的第二步。

**剩余（S1 第二步）**：
1. 把 10 个 Store 的手写 SQL 收进各自模块的 Repository，业务模块连 `Connection` 都不再直接拿；
   然后 ArchUnit R5（`java.sql` 只许出现在 `persistence`）才能真正打开。
2. **反向依赖 `qa → kb` 仍在**（3 处：`QaCollector` 用 `kb.Glossary` / `KbRetriever` / `KbTrace`）。
   要解它得把 `KbTrace` 挪成中性 DTO（它是"这次检索命中了什么"的记录，本就不该属于 kb 的实现细节）。
3. `@DependsOn("qaStore")` 这个**字符串**耦合还在 8 处 —— 它是运行期初始化顺序，不是编译依赖；
   等 `SqliteDatabase` 独立成 bean 后一并去掉。

### S2 配置去中心化

**问题**：`GuardProperties` 661 行被 17 个类注入；`SettingsService` 注入 7 个 Properties；`CommandController` 注入 7 个。

**方案**：
1. 按**使用方**而不是按**技术名词**拆：把 `GuardProperties` 拆成 `RateLimitConfig`、`AccessConfig`、`ContentGateConfig`、`BudgetConfig`、`OutboundConfig`、`FileAccessConfig`，各自只被真正需要它的类注入。
2. 业务类**不再注入 Properties**，改为在装配层（`@Configuration`）把需要的值作为**小而明确的参数对象**传入构造器。可选进一步：用 records 做只读配置快照。
3. 保留 `config/overrides.yml` 覆盖层与 `SettingsWhitelist` 白名单机制——**这套设计是对的**（安全默认 + 白名单，值得原样保留）。

**影响面**：`config` 包与所有注入方；`application.yml` 键名不变（避免运维破坏）。

**回滚**：新旧 Properties 并存一个迭代，逐个切换。

**验收**：ArchUnit R7 打开并通过；单个配置类不超过 ~150 行。

### S3 编排解体

**问题**：`MessageRouter` 452 行、24 个跨包依赖，是所有功能的必经之路。

**方案**：改成**显式注册的用例链**——
1. 定义 `InboundHandler` 接口（`boolean supports(InboundContext)` / `Outcome handle(InboundContext)`）。
2. 实现拆成：`CommandHandler`、`PlazaHelpHandler`、`ChatHandler`。
3. 顺序由 `List<InboundHandler>` 的 `@Order` 决定，**在装配层显式列出**，而不是埋在 452 行的 if-else 里。
4. `GuardPipeline` 本身已经是好设计（`GuardStage` + 有序 5 层），**照搬**这个模式即可。

**影响面**：`router` 包整体重写，但**行为必须逐条对齐**——这会引入最高的行为回归风险。

**回滚**：保留 `MessageRouter` 作为 `InboundHandler` 链的第一版实现，逐段搬。

**验收**：`MessageRouterCommandTest`（现有）全绿 + 新增"顺序与短路行为"测试；每个 handler 跨包依赖 ≤ 4。

### S4 知识库内核化

**问题**：`KbRetriever` 597 行，三路算法、RRF、加成、闸门全部硬编码在一个 `@Component` 里；加一条召回路径就要动这个类。

**方案**：抽成**可组合流水线**（详见[知识库方案](知识库口语问答重构方案.md)）：
```
QueryUnderstanding → [RecallStage...] → FusionStage → RerankStage → AssembleStage
```
- 现有的 A/B/C 三路变成三个 `RecallStage` 实现，参数外置到配置。
- `RerankStage` 是新插入的一层（现状没有）。
- **必须保留**：RRF 按排名融合、关键词权 2.0 / 标题权 3.0 / 标题精确 +0.5、C 路"闸门+置顶"而非进 RRF——这些是实测调出来的，换实现但不许改数值。

**影响面**：`kb` 包内部；对 `conversation` 只暴露 `RetrieverPort`。

**回滚**：新旧 `Retriever` 并存，由配置开关切换。

**验收**：第 5 节的检索 golden set 指标**不低于**改造前基线。

### S5 前端收敛

**问题**：`TermPanel.vue` 1,720 行；`types.ts` 679 行手抄 DTO。

**方案**：
1. `TermPanel` 拆成"列表 + 筛选 + 批量操作 + 抽屉"四个子组件（现状文档 [`知识库维护成本收敛方案.md`](知识库维护成本收敛方案.md) 早有此意图）。
2. **DTO 由后端生成**：加一个 Maven 目标，把 `@RestController` 的返回类型导出为 TS 类型，替换手抄的 `types.ts`。
3. 保留：`publicApi`/`adminApi` 客户端分离、18 个自研组件、设计令牌——**这三样都是对的**。

**影响面**：`web/`；无后端行为变化。

**验收**：`vue-tsc` 零错误；`TermPanel.vue` < 400 行。

## 四、迁移路线

> 原则：**先建安全网，再动刀**；每个阶段结束时代码都是可发布状态。

### Phase 0 — 安全网与基线【必须先做，不改行为】

| 项 | 内容 | 产出 |
|---|---|---|
| 0.1 | 建立**隔离构建**（本机复刻 `scripts/build-server.sh` 的 `.toolchain/server-ci/` 做法） | 宿主上可跑 `clean test`，且不污染 `server/target` |
| 0.2 | 跑通并记录现有 34 个测试 | 基线：通过/失败清单 |
| 0.3 | 修掉坏掉的 Javadoc 引用（`KbIndex` 已删除，4 个文件仍 `{@link KbIndex}`） | 编译告警清零 |
| 0.4 | 探针去硬编码：把 `/app/workspace/qqbot` 改成"从仓库根推导" | 探针可在宿主与容器同时跑 |
| 0.5 | **建检索 golden set**（见第五节） | 评测脚本 + 基线指标 |
| 0.6 | 引入 ArchUnit，R1–R4 立即生效、R5–R7 以 `@Disabled` 形式登记 | 架构护栏 |

**回滚**：本阶段不改业务代码，无需回滚。
**验收**：`clean test` 全绿 + golden set 输出基线数字。

### Phase 1 — 最小解耦缝
S1（持久化去单点）+ S2（配置去中心化）+ S4 的**接口部分**（先只抽 `RetrieverPort`，不改算法）。
理由：这三件是后续所有工作的**地基**，而且**不改变任何对外行为**，风险最低。

**验收**：ArchUnit R5/R7 打开并通过；golden set 指标与基线**完全一致**（证明纯重构）。

### Phase 2 — 知识库内核 + 口语方案
S4 完整实现 + 第六节的地图数据接入。**这是唯一会改变问答效果的阶段**，所以必须在 Phase 0 的 golden set 上量化。

**验收**：口语子集 R@1 提升（目标值在知识库方案里给）。

### Phase 3 — 语料扩维
地点/NPC/任务/机制语料入库 + 地图 marker 全量同步 + 区域推断。

### Phase 4 — 编排解体 + 前端收敛
S3 + S5。放最后，因为 S3 的行为回归风险最高、S5 的用户可见收益最低。

## 五、回归基线怎么建（Phase 0 的核心交付）

现状**没有**任何"回答质量"的自动化度量——`KbRetrieverTest` 测的是"三路各自是否工作"，不是"口语提问答得对不对"。没有度量，Phase 2 的收益只能靠感觉。

**做法**：
1. **黄金集**：人工整理 150–200 条真实口语提问，分四类：
   - `entity`：报名字（"酸蚀之咬怎么获得"）— 现状尚可，防退化
   - `descriptive`：描述需求（"有没有加移速的鞋"）— 现状差
   - `location`：问位置（"永霜堡在哪"）— 现状**完全失败**（语料没有）

2. 每条标注**期望命中的块 id 集合**（允许 1–3 个正确答案）。
3. 指标：`R@1` / `R@5` / `MRR`，**并按四类分别统计**——混在一起算平均值会掩盖问题（现状 entity 类 99.5%、location 类 0%，平均看着还行）。
4. 数据来源：`qa_raw` 有 6,543 条真实提问可直接挖（注意先做去重，实测存在同题重复入库）。
