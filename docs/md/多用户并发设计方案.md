# 多用户并发 @ 方案设计

> 场景：2 个 2000 人群 ｜ 每日活跃约 1/20 ｜ 极端情况：**50 人在 1 分钟内同时 @**
> 结论写在最后，前面是实测数据和问题定位。

---

## 0. 先说结论

**当前有个隐藏的严重瓶颈，不换模型、不调线程池的话，50 人同时 @ 时中位回复延迟是 23 秒。**

按优先级排：

| 优先级 | 动作 | 效果 |
|---|---|---|
| **P0** | 线程池 core 从 2 调到 16（并把 core 设成等于 max） | 延迟从 32s 降到约 5s |
| **P1** | 换 flash 模型（`glm-5.3-flash` 实测 2.3s，比现在的 mimo-v2.5 快 4 倍） | 再降一半 |
| **P2** | 队列等待超时丢弃 | 防止「30 秒后才回你」，宁可不说 |
| **P3** | 每群并发上限 | 防止一个群占满整个池子 |
| **P4** | 合并回复（进阶） | 调用次数再降 5~10 倍 |

---

## 1. 实测数据（不是估算）

我用一个假大模型（每次固定延迟 3 秒，模拟 flash 模型的速度）压了一次：

```
50 个人分散在 2 个群，同时 @ 机器人

50 条事件注入完成耗时   97 ms
上报响应码             全部 204（响应没被阻塞 ✅）
模型调用次数           20 次（2 群 × 群限流 10 条）
模型并发峰值           2  ❗
实际回复               26 条（20 真实 + 6 条限流提示）

回复延迟分布：
  最快 3.2s   中位 23.2s   P90 32.3s   最慢 32.3s
```

**限流工作得很好**（每群 10 真实回复 + 3 条提示，完全符合配置），
**但延迟完全不能接受**。

---

## 2. 问题定位：三个

### 问题 1：`maxPoolSize` 形同虚设（根因）

`AsyncConfig` 现在是：

```java
executor.setCorePoolSize(2);
executor.setMaxPoolSize(4);
executor.setQueueCapacity(200);
```

**Java 线程池的扩容规则是**：核心线程满了 → **先入队** → 队列满了 → 才创建新线程直到 max。

队列容量是 200，意味着**永远填不满**，所以线程数**永远停在 2**，`maxPoolSize=4` 从来没生效过。

压测数据完美印证：20 个任务 ÷ 2 并发 × 3 秒 = 30 秒，实测最慢 32.3 秒。

> 这是 Java 线程池最经典的坑之一。**要么把 core 设成等于 max，要么把队列设得很小。**

### 问题 2：模型本身慢

`mimo-v2.5` 实测生成速度约 18 tokens/s，比 flash 类模型慢 4 倍：

| 模型 | 实测平均 |
|---|---|
| mimo-v2.5（当前） | 9.7 s |
| kimi-k2.6 | 9.2 s |
| deepseek-v4-flash | 2.5 s |
| **glm-5.3-flash** | **2.3 s** |

模型慢的直接后果：线程被占用时间 ×4，吞吐 ÷4。

### 问题 3：`CallerRunsPolicy` 是个定时炸弹（还没爆）

```java
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
```

队列满时，任务会**在调用它的线程上执行** —— 而调用者是 **Tomcat 的 HTTP 线程**。
后果：`@RestController` 里的 `handleAsync()` 变成同步执行，
**204 响应会被拖到模型调用结束才返回** → NapCat 上报堆积 → 雪崩。

现在队列 200、实际负载 26 条/分钟，触发不了。但**被人恶意刷爆时会触发**。

正确做法：**丢弃 + 记录日志**（宁可少回一条，也不能阻塞接收通道）。

## 3. 五个方案

### 方案 A：调大线程池（P0，改 3 行）

```java
executor.setCorePoolSize(16);
executor.setMaxPoolSize(16);      // 和 core 相同，避免扩容陷阱
executor.setQueueCapacity(100);
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());  // 换成拒绝
```

| 项目 | 评估 |
|---|---|
| 效果 | 20 个任务 ÷ 16 并发 × 3s ≈ **3.75s**（P90 约 7s） |
| 用慢模型的场景 | 20 ÷ 16 × 9.7 ≈ 12s，勉强可接受 |
| 优点 | 改动最小，立刻见效 |
| 缺点 | 线程多了内存开销增加（每线程约 1MB 栈）；模型侧可能有并发限流 |

**这是必须做的一步**，无论选哪个方案。

### 方案 B：每群一个串行队列（per-group worker）

每个群一个独立队列 + 一个 worker 线程，群内串行、群间并行。

| 项目 | 评估 |
|---|---|
| 效果 | 单群吞吐 = 1 ÷ 单次延迟。flash 模型 3s → 20 次/分钟 > 群限流 10 ✅ |
| 优点 | **群之间完全隔离**（一个群卡住不影响另一个）；回复顺序绝对正确（不会插队）；限流天然精确 |
| 缺点 | **强依赖快模型**：用 mimo-v2.5（9.7s）时单群只有 6.2 次/分钟 < 群限流 10，队列会一直堆积 |
| 适用 | 群数量少（2 个），但要保证群内体验 |

> 这个方案和你的场景**非常契合**：只有 2 个群，群内串行反而让回复读起来更自然。

### 方案 C：队列等待超时丢弃（P2）

任务入队时记下时间戳，worker 取出执行前检查：**如果已经等了超过 N 秒，直接丢弃**。

```
收到 @（t=0）→ 入队 → 前面排了 10 个人
              ↓
        t=25s 终于轮到 → 已超过 20s 上限 → 丢弃，回一句「刚才太挤了，你再说一遍？」
```

| 项目 | 评估 |
|---|---|
| 效果 | 杜绝「30 秒后才回你」这种毫无意义的回复 |
| 优点 | 实现简单（一个时间戳 + 一个判断） |
| 缺点 | 用户需要重新提问 |

### 方案 D：合并回复（batching）

开一个 2~3 秒的窗口，把同一个群里这段时间的多条 @ **合并成一次模型调用**。

```
t=0.0s  张三 @：今天天气怎么样？
t=0.5s  李四 @：帮我写个正则
t=1.0s  王五 @：1+1=？
        ↓ 等待 3 秒窗口
t=3.0s  一次性问模型：「群里三个人分别问了这些问题，请你分别回答」
        ↓
t=6.0s  一条回复里回答三个人
```

| 项目 | 评估 |
|---|---|
| 效果 | **调用次数降低 5~10 倍**（50 人 → 可能只要 5~10 次调用） |
| 优点 | 从根本上解决负载问题；也是「群聊感」最自然的方式 |
| 缺点 | **实现复杂**；答案质量有风险（模型可能答串）；回复会合并成一条，有人可能觉得被忽略 |
| 适用 | 高活跃群，M6 之后再考虑 |

### 方案 E：两段式回复（ACK + 结果）

```
t=0.2s  立刻回：「收到，我想想～」
t=8.0s  模型好了再发：「@你 答案是……」
```

| 项目 | 评估 |
|---|---|
| 效果 | 用户感知延迟从 8s → 0.2s |
| 优点 | 体验上「机器人立刻理我了」 |
| 缺点 | **消息条数翻倍**（群里更吵，和防炸群的初衷冲突）；如果模型失败还得解释 |

## 4. 方案对比

|---|---|---|---|---|---|
| 改动量 | 极小 | 中 | 小 | 大 | 中 |

| 解决「乱」 | 否 | **是** | 否 | **是** | 否 |
| 群间隔离 | 否 | **是** | — | — | — |

| 消息变多 | 否 | 否 | 否 | **变少** | 变多 |

## 5. 我的推荐：A + C（现在做），B 视情况（可选），D 以后再说

### 第一阶段（建议立刻做，约 30 行改动）

1. **线程池**：`core=16, max=16, queue=100`，拒绝策略改成丢弃 + 记录
2. **换模型**：`OPENCODE_GO_MODEL=glm-5.3-flash`
3. **队列等待超时**：等待超过 20 秒就丢弃

预期效果（估算）：

```
50 人同时 @：
  真实回复    20 条（限流决定，不变）
  延迟中位    ~2.5s
  P90        ~5s
  最慢       ~8s（超过 20s 的直接丢弃）
  被丢弃     0 条
```

### 第二阶段（观察一段时间后再定）

- 如果发现「一个群占用太多线程」→ 加**每群并发上限**（方案 B 的简化版，不重写队列，只加信号量）
- 如果发现调用量还是偏高 → 上**合并回复**（方案 D）

### 为什么不直接上方案 B

方案 B（每群串行）很优雅，但它**强依赖快模型**：一旦哪天换回慢模型，
单群吞吐会掉到 6 次/分钟，队列会无限堆积。
先用 A+C 把「并发能力」和「丢弃保护」做好，B 属于锦上添花。

## 7. 实施结果（方案 A + C 已落地）

改完之后重跑同一份压测（50 人、模型延迟 3 秒）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 线程池 | core=2, max=4（从未生效）, queue=200 | core=8, max=8, queue=100 |
| 拒绝策略 | CallerRunsPolicy（会阻塞 Tomcat 线程） | 丢弃 + 记录 |
| 空闲回收 | 无 | allowCoreThreadTimeOut=true |
| 队列等待上限 | 无 | 20 秒 |
| **模型并发峰值** | **2** | **8** |
| **延迟中位** | **23.2s** | **6.5s** |
| **延迟 P90** | **32.3s** | **11.6s** |
| 上报响应 | 全 204 | 全 204 |
| 被丢弃 | — | 0 条 |

启动日志会打印生效的配置，方便确认：

@B@@B@@B@
[ASYNC] 事件线程池：core=8 max=8 queue=100 空闲回收=true 队列等待上限=20s
@B@@B@@B@

全部参数都在 @B@app.async.*@B@ 里可调，不用重新编译。

### 顺带修掉的一个隐患：空回复

测试推理模型（@B@deepseek-v4.1-flash@B@）时发现：它的 token 预算如果被「思考」吃光，
@B@content@B@ 会返回**空字符串**（@B@finish_reason: length@B@）。
如果不处理，机器人就会往群里发一条**空白消息**。

现在 @B@LlmRouter@B@ 把空回复当成失败，自动走降级链；全部失败则回兜底话术。

## 8. 顺带回答：为什么现在 204 不被阻塞

压测里 50 条事件全部返回 204、耗时 97ms —— 因为队列容量 200 没满，
任务只是排队，Tomcat 线程没有被占用。

**但这恰恰说明问题 3 的危险**：一旦超过 204 条并发（被恶意刷），
`CallerRunsPolicy` 会让 Tomcat 线程去跑模型调用，204 就会被拖到几十秒后返回。
所以**拒绝策略必须改**，这是安全底线，不是性能优化。
