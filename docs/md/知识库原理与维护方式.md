# 知识库原理与维护方式

> 2026-09-25 ｜ 在做分类改造之前，先把「它到底怎么工作」讲清楚

---

## 一、一句话概括

**一个「问题 → 相关资料」的查找器。**

它**不训练模型**，只是在提问时找出最相关的几段文字，塞进 prompt 让模型参考。

```text
用户问：废料杯怎么合成？
        ↓
知识库从 4238 段里挑出 3~5 段相关文字
        ↓
拼进 prompt：「以下是检索到的资料：… 用户的问题：…」
        ↓
模型读完资料再回答
```

**模型本身没有被改过** —— 它只是「带着参考资料回答问题」。

---

## 二、离线构建（一次性，跑脚本）

```text
enshrouded.wiki.gg
        ↓ 爬取 3908 个页面
pages.jsonl（页面清单）
        ↓ 清洗 wikitext → 纯文本（清洗规则见第十一节）
chunks.jsonl（4131 段，每段 ≤1600 字）
        ↓ 每段送去 embedding API 算向量（约 4 分钟）
index.bin（4131 × 1024 维 float32 ≈ 16.1 MB）
```

| 产物 | 内容 | 大小 |
|---|---|---|
| `pages.jsonl` | 页面清单 | 170 KB |
| `chunks.jsonl` | **切好的文本段**（检索原料） | 3.4 MB |
| `index.bin` | **每段的向量**（检索索引） | 16.1 MB |
| `glossary/zh-en.tsv` | 中英术语对照 | 237 KB |

## 三、在线检索（每次提问都跑）

**两条路同时跑，然后融合**：

```text
                     用户问题
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   【A 路：向量】                  【B 路：关键词】
   问题算成向量                    用术语表把中文换成英文
        ↓                               ↓
   和 4238 个向量算余弦            在文本里找英文名
        ↓                               ↓
   取最像的 N 个                    取命中的段落
        │                               │
        └───────────┬───────────────────┘
                    ▼
              RRF 融合排序
                    ▼
             取前 5 段进 prompt
```

### 为什么要两条路

**各有盲区**（实测数据）：

| 问题 | A 路（向量） | B 路（关键词） |
|---|---|---|
| 「废料杯怎么合成」 | ❌ 把 Scrap Cup 排到第 **69** 名 | ✅ 一击命中 |
| 「这游戏怎么建造」 | ✅ 能理解大意 | ❌ 没具体英文名可匹配 |

**只跑一条都会漏，所以两条都跑。**

---

## 四、术语表为什么是关键（B 路的命脉）

B 路的逻辑：**把中文词换成英文词，再去文本里找**。

```text
用户说「废料杯」
        ↓ 查术语表
得到英文「Scrap Cup」
        ↓ 在 chunks 里找含 "Scrap Cup" 的段落
命中「Scrap Cup」那一页
```

**术语表没有这个词 → B 路就找不到 → 只剩 A 路（而 A 路可能排到第 69 名）。**

所以 **补术语表 ≈ 直接提升检索命中率**。

---

## 五、分类是干什么用的

**结论：分类不参与检索，只用于「给人看」。**

| 数据 | 参与检索吗 |
|---|---|
| 向量（index.bin） | ✅ 检索核心 |
| chunks 的文本 | ✅ 命中的就是它 |
| 术语表 | ✅ B 路命脉 |
| **cats 分类字段** | ❌ **完全不参与检索** |

分类只在**公开站资料库浏览**时用到 —— 帮人「按类别找资料」。

**所以改分类不会影响问答质量，可以放心大改。**

---

## 六、你的核心问题：能不能「增量训练」

### 6.1 先纠正一个说法

**这不叫「训练」** —— 没有模型被训练。准确说是「**增量重建索引**」。

### 6.2 三种改动，代价完全不同

| 改动 | 需要重建什么 | 耗时 | 花钱 |
|---|---|---|---|
| **改术语表** | 什么都不用重建 ✅ | **0** | **0** |
| **改分类标签** | 只改 chunks.jsonl 的字段 | 秒级 | 0 |
| **新增资料文本** | 给新增的段算向量，追加进 index.bin | 与新增量成正比 | 按量 |

### 6.3 关键结论

**① 改术语表是「纯赚」的 —— 零成本、立即生效。**

术语表是运行时加载的 TSV 文件。改完重启（或热重载），B 路立刻变强。
**不需要碰向量，不需要花钱。**

**② 改分类完全不涉及检索 —— 随便改。**

**③ 真正的「增量」是指：只给新增的段落算向量。**

```text
现在：4238 段 × 1024 维，全量算一次 21 秒

增量：新增 50 段 → 只算这 50 段的向量
      追加到 index.bin 末尾
      总量变成 4288 段
```

**技术上完全可行**，因为：

- 每段的向量**独立计算**，互不影响
- index.bin 是扁平数组，**追加**即可
- 只要还用同一个 embedding 模型（`BAAI/bge-m3`），新旧向量就在同一空间

---

## 七、什么情况下必须全量重建

| 情况 | 原因 |
|---|---|
| **换了 embedding 模型** | 向量空间变了，新旧不可比 |
| **切块规则改了** | 段落边界变了，旧向量对应旧文本 |
| **清洗逻辑改了** | 文本内容变了，向量失效 |

**只要不动这三样，就都能增量。**

---

## 八、这决定了「怎么完善知识库」

按**性价比**排序：

| 优先级 | 做法 | 成本 | 效果 |
|---|---|---|---|
| **1** | 补术语表 | 零成本、零等待 | ★★★ 直接提升 B 路 |
| **2** | 改分类标签 | 零成本 | 只影响浏览体验 |
| **3** | 新增资料段落 | 要算向量（花钱） | 补充 Wiki 没覆盖的 |
| 4 | 全量重建 | 21 秒 + 全部 embedding 费用 | 只在换模型/改切块时做 |

**「完善知识库」的重心应该放在 1 和 2**，而不是动不动全量重建。

---

## 九、对接下来改造的指导

| 你要做的 | 影响检索吗 | 需要重建吗 |
|---|---|---|
| 分类标签规划（英文→中文大类） | ❌ 不影响 | 只改字段，秒级 |
| 资料库页面重构 | ❌ 不影响 | 不用 |
| 问答广场并入资料库 | ❌ 不影响 | 不用 |
| About 加群说明 | ❌ 不影响 | 不用 |
| **补术语表** | ✅ 影响（变强） | 不用，改文件即可 |

**结论：你想做的这些改造，全都不需要重建索引，可以放心动。**

## 十、公开站检索（和群内**不一样**）

群内检索和公开站检索共用 `KbRetriever`，但**参数和刹车完全不同**。

| | 群内问答 | 公开站搜索 |
|---|---|---|
| 谁在用 | 群友（可信） | 任何人（公网） |
| 目标 | 给模型当依据，宁缺毋滥 | 排给人看，宁可多给 |
| 向量路 | 每次都走 | 走，但有缓存 + 每日配额 |
| 相似度下限 | 0.45 | 0.32 |
| 取几条 | 5 | 20（同页去重后） |

### 为什么公开站也必须走向量路

语料是**英文**的，本地关键词路靠术语表把中文换成英文 ——
术语表只有 3,300 个**标准名词**，遇到口语提问直接一条都搜不到：

| 用户输入 | 只走关键词路（旧行为） | 走向量路（现在） |
|---|---|---|
| 木头 | **0 条** | Hardwood / Wood Logs / Farm Soil |
| 等级上限 | **0 条** | Attributes / Skills / Skill Points |
| 怎么种地 | **0 条** | Farm Soil / Reed Seedling / Corn Seedling |
| 废料杯 | 1 条（Scrap Cup） | Scrap Cup / Tableware / Glass |

bge-m3 是**多语言**模型，中文问句和英文段落落在同一个语义空间里，
所以「木头」和 "Wood Logs" 的余弦能到 0.55。

### 三层刹车（都在 `PublicSearchService`）

| 刹车 | 作用 |
|---|---|
| **LRU 结果缓存**（512 条） | 同一句话重复搜不再调 API —— 有人刷同一个词不花钱 |
| **每日配额**（默认 800 次） | 超了**静默降级**成纯关键词，搜索照常可用，不报错 |
| **同页去重** | 一个 Wiki 页切成好几块，不去重会出现 4 条一模一样的 Flame Altar |

配额用完那一瞬间会在日志里 WARN 一次；用量在
`/admin/api/kb/overview` 的 `publicSearch` 字段里，管理后台知识库页有卡片展示。

**开关**：管理后台 → 设置 → 知识库 → 「公开站语义搜索」/「语义搜索每日上限」，
改完立即生效（写进 `config/overrides.yml`，优先级高于 application.yml）。

### 标题加成：让「物品本体页」压过「提到它的页」

RRF 只看排名，会出现「搜 `废料杯` → Tableware 页面第一」这种颠倒 ——
因为 Tableware 正文里提到过 Scrap Cup，两路都排得靠前。

所以融合时加一条**标题加成**：

```text
chunk 标题 == 查询里的游戏名词   → +0.5（几乎必然第一）
chunk 标题 含有这个名词         → +0.15
```

实测修正效果：

| 查询 | 加之前 | 加之后 |
|---|---|---|
| 废料杯 | Decorations/Tableware | **Scrap Cup** |
| 火把 | Crypt Skull Torch | **Torch** |
| 卷毛山羊 | Baby Frizzy Goat | **Frizzy Goat** |
| 黑曜石 | Obsidian ✅ | Obsidian |

这一条对**群内问答同样是改善**（模型拿到的第一条资料更准了）。

## 十一、构建期文本清洗（2026-09-26）

清洗发生在**建语料的时候**（`WikiTextCleaner`），不是显示的时候：`chunks.jsonl` 里的文本本身
就是干净的，向量、关键词命中、投稿比对全都基于干净文本。

> 之前用 `KbTextDisplay` 在 API 返回时洗 —— 那只是把垃圾**藏起来**，语料本身还是脏的。
> 现在改成构建期清洗 + 全量重建（显示层那层保留，当兜底）。

### 修掉的 6 类机器文本

| # | 长什么样 | 根因 | 处理 |
|---|---|---|---|
| 1 | `{\| class="wikitable" style="width:90%;"`、`! style="width:9%;" \| Objective #` | 两个任务页的表格**忘了写 `\|}` 收尾**，`renderTables` 直接放弃整张表 | 找不到 `\|}` 就退到第一个分类行之前，照常转换 |
| 2 | `rowspan="5" class="armor-mobile" style="text-align:center;" !` | `{{!}}` 是 MediaWiki 的"竖线模板"，没还原成 `\|`，单元格被切错位置，属性前缀漏进正文 | `{{!}}` → `\|`，属性前缀按原有规则整段丢掉 |
| 3 | `Blackmire Stone.png` | 图片说明的最后一段又是文件名 | 说明文字遇到 `xxx.png` 当排版选项跳过 |
| 4 | `title: Snap Trap.png` | 模板参数拿文件名当标题（`\| title= {{PAGENAME}}.png`） | 参数值抹掉扩展名；抹完为空就整条丢掉 |
| 5 | 裸 `[[` / `]]` | 说明文字里嵌链接（`[[File:A.png\|...\|You need 4 [[B]], ...]]`），`[[` 配对错位 | 收尾统一去掉，里面的人话保留 |
| 6 | `[[fr:Armure]]`（400+ 条） | 右上角语言切换用的元数据 | 按语言代码白名单整条丢 |

### 效果（同一套正则扫全语料）

| 噪声 | 改造前 4238 块 | 现在 4131 块 |
|---|---|---|
| `DataQuery`（Lua 查询模板） | 1763 | **0** |
| `.png` | 465 | **0** |
| `link=` | 256 | **0** |
| `\|-\|`（tabber 分节符） | 522 | **0** |
| `## \|`（表头残标记） | 159 | **0** |
| `rowspan` / `style=` / `class=` | 0 / 10 / 2 | **0 / 0 / 0** |
| `[[` 或 `]]` 残留 | 230 | **0** |
| `{{!}}` / `<gallery>` / `<tabber>` / `&nbsp;` / 三个单引号 | 0 | **0** |

正文 2,848,868 字 → **2,686,790 字**（-5.7%），少掉的全是标记与导航垃圾。

### 改清洗规则后怎么办

**必须两步走，缺一不可**（都在 `server/` 下跑，因为 `app.kb.dir: ./data/kb` 是相对路径）：

```bash
# ① 重建语料：复用 raw/，不联网，18 秒
java -cp "target/classes:$(cat /tmp/cp.txt)" com.example.qqbot.QqbotServerApplication \
  --app.kb.build.enabled=true --app.kb.build.from-raw=true --spring.main.web-application-type=none

# ② 重建向量：要 .env 里的 SILICONFLOW_API_KEY，4131 块约 4 分钟，按量计费
java -cp "target/classes:$(cat /tmp/cp.txt)" com.example.qqbot.QqbotServerApplication \
  --app.kb.index.enabled=true --spring.main.web-application-type=none
```

> 只做 ① 不做 ②：`chunks.jsonl` 换了、`index.bin` 还是旧的，**检索出来的向量和文本对不上**。
> 两步做完要**重启后端服务**，否则内存里还是旧索引。

对照第六节的结论：清洗规则属于"改了就要全量重建"的三件事之一（另外两件是换模型、改切块）。
