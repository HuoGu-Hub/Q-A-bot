# 问答记录、统计分析与管理系统 —— 规划

> 状态：**待评审** ｜ 2026-09-22
> 目标读者：项目作者（本文档同时作为面试项目经历的技术设计材料）

---

## 一、结论先行

**把机器人的每一次问答完整记下来，用它同时解决三件事：**

| # | 用途 | 产出 |
|---|---|---|
| 1 | **知识库质量评估**（P4 的直接输入） | 未命中问题排行 → 该补哪些术语、阈值该定多少 |
| 2 | **使用统计** | 关键词提问排行、命中率、响应延迟、Guard 拦截分布 |
| 3 | **管理系统** | 只读后台 + 人工标注 + 访问统计 |

**推荐技术选型**：SQLite（单文件，零运维）+ Spring Boot 现成的 Web + 静态页面。
**不引入**：独立数据库服务、前端构建链、ELK。

**关键设计约束**：**采集绝不能拖慢回答**。它是"顺带记一笔"，不是回答流程的一部分。

## 四、数据模型

### 4.1 核心设计：两层结构 —— 原文会删，统计永久留

```text
            qa_stat                    ← 派生层（永久保留）
              │ 1:1                      时间 / 群 / 用户 / 检索指标 / 耗时 / 标注
              │
              ├── qa_raw                ← 原始层（有保留期，到期删除）
              │     问题原文 / 引用原文 / 回答原文
              │
              └── qa_keyword            ← 派生层（永久保留）
                    从问题里抽出来的游戏名词
```

**保留线画在「自然语言原文」上：**

| 层 | 存什么 | 生命周期 |
|---|---|---|
| **qa_raw** | 用户说的话、机器人说的话 | **定期删除**（默认 180 天，可配置） |
| **qa_stat** | 谁在什么时候问的、命中几块、分数多少、耗时、标注结论 | **永久保留** |
| **qa_keyword** | 从问题里抽出来的游戏名词 | **永久保留** |

> 这个划分的关键好处：**所有统计能力都永久可用**（关键词排行、命中率、延迟分布、准确率），
> 而真正属于"个人信息"的自然语言原文按期消失。
>
> 而且**删除原文不需要先做聚合** —— 因为统计所需的字段本来就在另一张表里。
> 很多系统要做到"删明细留统计"得先跑一遍归档任务，这里靠表结构就解决了。

### 4.2 表结构

```sql
-- 派生层：永久保留。所有统计都查它
CREATE TABLE qa_stat (
  id           INTEGER PRIMARY KEY,
  ts           TEXT NOT NULL,        -- ISO8601
  group_id     INTEGER,
  user_id      INTEGER,              -- 不哈希（群内本来就能看到 QQ 号）
  message_id   INTEGER,

  image_count  INTEGER DEFAULT 0,

  -- 检索到了什么（★ 分析答错原因全靠这几列）
  kb_enabled   INTEGER,
  hit_count    INTEGER,              -- 最终带进 prompt 几块
  top_score    REAL,                 -- 最高相似度
  sources      TEXT,                 -- vector / keyword / both / none
  retrieved    TEXT,                 -- JSON: [{"i":12,"title":"Scrap Cup","score":0.53}]

  -- 回答形态（不含原文）
  answer_len   INTEGER,
  answer_empty INTEGER,
  guard_action TEXT,                 -- pass / drop / rate_limited / fixed_reply

  -- 性能
  retrieve_ms  INTEGER,
  llm_ms       INTEGER,
  total_ms     INTEGER,
  model        TEXT,

  -- 标注
  verdict      TEXT,                 -- unknown / good / bad / no_source / hallucination
  verdict_note TEXT,
  verdict_by   TEXT,                 -- auto / me / human
  verdict_at   TEXT
);
CREATE INDEX idx_st_ts      ON qa_stat(ts);
CREATE INDEX idx_st_group   ON qa_stat(group_id, ts);
CREATE INDEX idx_st_verdict ON qa_stat(verdict);
CREATE INDEX idx_st_hit     ON qa_stat(hit_count);

-- 原始层：到期整行删除。只放自然语言原文
CREATE TABLE qa_raw (
  id         INTEGER PRIMARY KEY REFERENCES qa_stat(id),
  question   TEXT NOT NULL,
  quote_text TEXT,
  answer     TEXT
);

-- 派生层：永久保留
CREATE TABLE qa_keyword (
  id         INTEGER PRIMARY KEY,
  stat_id    INTEGER NOT NULL REFERENCES qa_stat(id),
  keyword    TEXT NOT NULL,     -- 问题里出现的中文名（如「废料杯」）
  term_en    TEXT,              -- 术语表里对应的英文（如 Scrap Cup）
  in_kb      INTEGER            -- 这个英文词是否在检索结果里出现过
);
CREATE INDEX idx_kw_keyword ON qa_keyword(keyword);
CREATE INDEX idx_kw_stat    ON qa_keyword(stat_id);

-- 管理后台自己的访问统计（和机器人统计分开）
CREATE TABLE admin_visit (
  id       INTEGER PRIMARY KEY,
  ts       TEXT NOT NULL,
  path     TEXT,
  ip_hash  TEXT,     -- 存哈希不存原始 IP
  ua       TEXT,
  action   TEXT      -- view / export / annotate / login
);
```

**两个容易忽略的点：**

- **`retrieved` 放在永久层**：它记的是"检索到了哪些块、分数多少"，是**系统自己算出来的结构化数据**，
  不是用户输入。体积也小（5 个标题+分数约 200 字节）。
  而正文不存 —— 正文在 `chunks.jsonl` 里，按标题回查即可（块序号在重建语料后会变，只作参考）。
- **`answer` 只在原始层**：永久层只留 `answer_len / answer_empty`。
  想知道"这条回答多长"的统计照样能做，但回答原文按期消失。

### 4.3 关键词怎么抽：直接复用现成的术语表（3,359 条）

遍历术语表的中文名，看问题里包含哪些 —— 零额外成本、零额外依赖，
而且**和检索用的是同一份数据**，统计口径天然一致。

> 这是整个设计里最省事的一环：不用分词器、不用 NLP 库、不用维护第二份词表。

### 4.4 到期清理

```text
每天凌晨 ──▶ 删 qa_raw 里 ts 早于 (now - retention-days) 的行
              │
              └─▶ qa_stat / qa_keyword 一行不动
```

| 项 | 设计 |
|---|---|
| 触发 | 复用现有 `@Scheduled`（和临时图片清理同一套机制） |
| 配置 | `app.qa.retention-days: 180`（0 = 永不删除） |
| 安全 | 支持 `--dry-run` 先看会删多少条；删除前记日志（删了几条、时间范围） |
| 幂等 | 重复执行无副作用 |

**数据量估算**：群里一天 50~200 个问题 → `qa_stat` 一年 2~7 万行，
**十年也就 70 万行、几十 MB**，SQLite 完全无压力，所以永久保留是可行的。

## 五、关键设计决策

### D1 存储用 SQLite，不用 JSONL

| 方案 | 统计查询 | 索引 | 并发写 | 结论 |
|---|---|---|---|---|
| JSONL 追加 | ❌ 每次统计要全表扫 + 自己写聚合 | ❌ | 简单 | 采集够用，**统计很痛苦** |
| **SQLite** | ✅ SQL 直接聚合 | ✅ | 单写者足够 | ✅ **推荐** |
| 独立数据库服务 | ✅ | ✅ | ✅ | ❌ 2G 机器上多一个常驻服务，不划算 |

数据量估算：群里一天 50~200 个问题 → 一年 2~7 万行，**SQLite 毫无压力**（几十 MB）。
Java 侧只需一个 sqlite-jdbc 依赖，常驻内存可忽略。

### D2 采集绝不阻塞回答（最重要的一条）

```text
回答完 ──▶ 投递到单线程队列 ──▶ 立即返回
                    │
                    └─▶ 后台慢慢写库
```

三条硬性要求：

1. **异步**：绝不在回答线程里写库
2. **有界队列**：队列满了就丢弃并计数（宁可丢记录，不可积压内存）
3. **吞异常**：写库失败只记日志 —— 记录系统挂了，机器人必须照常回答

### D3 必须记「检索内部状态」

只记「问题 + 答案」是不够的 —— 那样只知道答错了，不知道**为什么**错。

记下 hit_count / top_score / sources / retrieved 之后，才能区分：

| 症状 | 看哪个字段 | 说明 |
|---|---|---|
| 根本没检索到 | hit_count = 0 | 术语表缺词 / 阈值太高 |
| 检索到了但答错 | retrieved 里没有正确的块 | 排序问题，要调融合权重 |
| 检索对了但模型答错 | retrieved 正确、answer 不对 | 提示词问题 |
| 无关问题被误召回 | 问题本身无关但 hit_count > 0 | 阈值太松 |

**没有这几列，P4 就只能靠猜。**

### D4 准确率怎么判：三层信号

**① 自动（零成本，每条都有）**

- 检索是否命中（hit_count > 0）
- top_score 落在哪个区间
- 答案里是否出现「没查到 / 没有找到 / 资料里没有」这类话术
- 是否走了降级路径

**② 半自动（我离线判读）**

我可以直接读记录，逐条判断"答案是否被检索到的资料支持"，
重点抓两类错误：**有资料但答非所问**、**资料里没有但模型硬编**。

**③ 人工（你，在后台点一下）**

后台提供标注按钮：good / bad / no_source / hallucination。

> 三层的关系：① 负责**筛选**（把可疑的挑出来），② 负责**判断**（给出结论和改进建议），
> ③ 负责**确认**（你最终拍板）。这样你不用逐条看几万条记录。

**额外的免费信号 —— 追问检测**：
同一个人 60 秒内又 @ 机器人问一次，多半是上一条没答好。
这条规则零成本，而且往往比任何自动指标都准。

### D5 保留策略：原文定期删，加工结果永久留

**已定（2026-09-22）：**

| 项 | 决定 |
|---|---|
| QQ 号是否哈希 | ❌ **不哈希** —— 群内本来就能看到 QQ 号，哈希收益为零、还牺牲可排查性 |
| 提问原文 / 回答原文 | ✅ **定期删除**，期限可配置（默认 180 天） |
| 系统加工出的结构化数据 | ✅ **永久保留** —— 统计、关键词、检索指标、标注结论 |
| 后台访问 | 需登录；IP 只存哈希 |

**"加工结果"具体指什么**（永久层的内容）：

- 时间、群号、用户号
- 检索命中数、最高相似度、来源（vector/keyword）、检索到哪些块
- 耗时、模型、Guard 动作
- **从问题里抽出来的关键词** ← 这是关键词排行的唯一来源，必须永久留
- 人工/自动标注结论

**"原文"具体指什么**（到期层的内容）：问题正文、引用正文、回答正文。

> ⚠️ 机器人的系统提示词禁止它**对外泄露**个人信息；这里是**内部留存用于运营统计**，
> 是两件事。但正因为是两件事，更要主动把边界写清楚。

**为什么不哈希 QQ 号**（记录下来避免以后反复讨论）：

1. 这是**私人游戏群**，群成员互相都能看到 QQ 号，哈希没有实际隐私收益
2. 哈希后的 ID **防不住有意反查**（QQ 号空间只有 10¹¹，加盐也挡不住能访问系统的人）
3. 保留原始 ID 换来的是**可排查性** —— P4 阶段很可能需要"找那个问法特别典型的群友确认一下"
4. 真正的隐私风险在**问题正文**（自由文本，可能粘进任何东西），而它本来就要按期删除

**删除是不可逆的**，所以清理任务必须：

- 支持 `--dry-run`（先看会删多少条、什么时间范围）
- 每次执行都记日志
- 默认期限给足（180 天）

### D6 后台技术选型：先静态页面，不上前端框架

| 阶段 | 方案 | 理由 |
|---|---|---|
| S3 起步 | 服务端返回 JSON + 一个**单文件 HTML**（原生 fetch） | 零构建链、零依赖、够用 |
| 将来 | 真需要复杂交互再上框架 | 别为"可能"提前买单 |

后台挂在现有 Spring Boot 的 /admin 路径下，不新开端口、不新开进程。

### D7 采集与知识库的边界

- 记录系统**只读**知识库（术语表用来抽关键词），**不修改**它
- 知识库重建（换模型、改清洗规则）**不影响**历史记录 —— 记录里存的是标题，不是块序号

## 六、统计维度清单

### 机器人问答（你要的"关键词提问次数"在这里）

| 指标 | 说明 | 直接用途 |
|---|---|---|
| **关键词提问排行** | 哪些游戏名词被问得最多 | 决定术语表优先核对哪些词 |
| **未命中问题排行** | hit_count = 0 的问题 + 其中的关键词 | ★ **直接告诉我们要补哪些词** |
| 命中率 | hit_count > 0 的比例 | 知识库整体覆盖度 |
| 相似度分布 | top_score 直方图 | ★ **定 min-score 阈值的依据** |
| 降级统计 | A/B 各自失败次数 | 依赖稳定性监控 |
| 响应延迟 | 检索 / LLM / 总耗时 P50/P95 | 性能 |
| Guard 拦截分布 | 限流、敏感词、纯表情各多少 | 运营观察 |
| 群活跃度 | 每天/每群提问数 | 运营观察 |

### 管理后台

| 指标 | 说明 |
|---|---|
| 访问次数 / 独立访客 | admin_visit 聚合 |
| 页面访问排行 | 哪些统计页最常看 |
| 导出与标注次数 | 谁在什么时候导了数据、标了多少条 |

| R5 | 统计口径漂移 | 关键词抽取与检索**共用同一份术语表**，口径天然一致 |
| R6 | 面试项目"像玩具" | 有明确的问题→方案→量化闭环：**未命中排行 → 补词/调阈值 → 命中率提升**，可量化可复现 |

## 九点五、S1 实施记录（2026-09-22）

**已交付的类**（都在 `com.example.qqbot.qa`）：

| 类 | 职责 |
|---|---|
| `QaStore` | SQLite 存储：建表 + **幂等迁移** + 批量写 + 只删原文的清理 |
| `QaRecorder` | 异步单线程队列：有界、丢弃计数、吞异常 |
| `QaCollector` | 组装：抽关键词、序列化检索结果、取模型名 |
| `QaCleaner` | `@Scheduled` 到期清理（只动 qa_raw） |
| `QaProperties` | `app.qa.*` 配置 |

**改动**：`ChatService.reply()` 改为返回 `ReplyResult`（带 `KbTrace`）；
`MessageRouter` 加了一行调用；`KbRetriever.retrieve()` 改为返回 `Retrieval`（多带 `bestCosine`）。

### 真跑一遍才暴露的 4 个问题

| # | 问题 | 根因 | 处理 |
|---|---|---|---|
| 1 | **`top_score` 量纲错了** | 存的是 RRF 融合分（0.18），而调 `min-score` 需要**余弦**（0~1） | `Retrieval` 单独带出 `bestCosine`，新增 `best_cosine` 列 |
| 2 | **关键词抽多了** | 子串匹配没做最长优先，「爆炸箭 III」同时命中「爆炸箭 I」「爆炸箭 II」 | 按中文名长度降序匹配 + 已覆盖区间去重 |
| 3 | **改表结构会丢数据** | `CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做，加列不生效 | 加**幂等迁移**：查 `PRAGMA table_info`，缺列才 `ALTER TABLE` |
| 4 | **术语表缺词** | 表里没有 `Explosive Arrow III`（只有 I/II），但语料里有这一页 | **这是数据问题不是代码问题** —— 正好由这套记录系统暴露出来，交给人工核对补上 |

> 第 4 条特别值得说：**记录系统的价值不是"存下来"，而是"让缺失变得可见"**。
> 它自动告诉我们「术语表缺 Explosive Arrow III」，
> 而不是靠人翻 3,359 条记录去猜哪里漏了。

### 实测记录样例

```text
id  时间      命中  融合分  余弦    来源     guard   问题
#6  05:13:33  5    0.205   0.551   both    pass    废料杯怎么合成？
#7  05:13:37  5    0.232   0.517   keyword pass    卷毛山羊怎么驯服？
#8  05:13:40  5    0.182   0.567   both    pass    爆炸箭 III 是什么？
#9  05:13:45  0    0.000   0.000   none    pass    灵火祭坛是干什么的？
#10 05:13:47  5    0.091   0.553   vector  pass    今天天气怎么样？
```

**这张表已经把 P4 要的两个答案摆出来了**：

- **#9 灵火祭坛**：`hit_count=0`、余弦 0 → **术语表缺词**（表里是「火焰祭坛」）
- **#10 今天天气**：余弦 **0.553** 却召回了 5 块 → **阈值 0.45 太松**，
  无关问题的余弦甚至比 #7 的正常问题（0.517）还高

## 九点六、S2 实施记录（2026-09-22）

**核心设计：统计与展示分离**

```text
QaAnalytics        出结构化数据（Overview / KeywordStat / MissStat / Bucket …）
   ├─ QaReportRunner   CLI 打印（S2）
   └─ AdminController  返回 JSON（S3，待做）
```

> 为什么这么分：否则 CLI 和后台的"关键词排行"很可能算得不一样。
> 现在两边共用同一套 SQL 和同一套分位数算法。

**未命中排行分成两类** —— 这是 S2 最有价值的产出：

| 类别 | 查法 | 含义 |
|---|---|---|
| 认出了词、但知识库没资料 | `qa_keyword JOIN qa_stat WHERE hit_count=0` | 术语表有词，语料里检索不到 |
| **连词都没认出来** | `NOT EXISTS (SELECT 1 FROM qa_keyword …)` | **术语表根本没这个词** |

> 第二类**必须单独查**：它在关键词表里没有行，用 join 会被静默丢掉。
> 实测就抓到了「灵火祭坛」—— 术语表里只有「火焰祭坛」。

**实测报表给出的两个结论**：

| 观察 | 含义 |
|---|---|
| 未命中问题里出现「灵火祭坛」 | 术语表缺词，补上即可（已支持多别名） |
| 正常问题余弦 0.51~0.57，无关问题「今天天气」**0.553** | **两者完全重叠** —— 单靠余弦阈值分不开，需要引入别的信号 |

> 第二条推翻了"调高 `min-score` 就能解决误召回"的假设。
> 这正是**先做数据采集、再谈调优**的价值：不跑真实数据，
> 很可能会把阈值一路调到 0.6，结果把正常问题也一起滤掉了。

## 九点八、S4 实施记录（2026-09-22）

**闭环成立**（实测走通）：

```text
① 看板显示「未命中：连词都没认出来 → 灵火祭坛」
② /admin/glossary.html 搜 Flame Altar
③ 中文名改成「灵火祭坛、火焰祭坛」→ 保存
④ 【不重启】立即生效，日志：术语表已更新 → 术语表已重新加载
```

**新增**：

| 组件 | 职责 |
|---|---|
| `GlossaryStore` | 术语表读写（5 列 TSV，写前 sanitize 防注入） |
| `Glossary.reload()` | 热重载（把 loaded 置回 false，下次查询自然重读） |
| `AdminController` 写接口 | annotate / glossary CRUD |
| `glossary.html` | 术语表管理页 |
| 追问检测 | `QaCollector` 记时间窗口，`QaRecorder` worker 落库 |

**三个设计细节**：

1. **追问标记只覆盖未标注记录** —— `UPDATE ... WHERE verdict IS NULL OR verdict='unknown'`，
   绝不覆盖人工结论
2. **写术语表前 sanitize** —— 制表符/换行会把 TSV 结构弄坏（一条变多条），必须清掉
3. **热重载不加锁** —— 只是把 `loaded` 置回 false，下次查询自然重读；
   用 `volatile` + 双检锁，不需要停机、不需要文件监听

**实测**：非法 verdict → 400；不存在的 id → 404；`bad=1` / `unknown=9` 正确落库。

## 十、面试视角：这个项目的可讲点

> 这一节是给你准备讲稿用的，不是技术设计。

1. **有真实问题驱动**：不是"我想做个 RAG"，而是"群友问废料杯，机器人答不出来"
2. **有量化取舍**：4,238 块的索引为什么不用 pgvector（17MB / 亚毫秒，引入 200MB 服务不划算）
3. **有踩坑与修复**：explaintext 丢数据 → 模板渲染；Data:*.json 霸榜；
   **术语表 key/value 写反导致 B 路静默失效**（单元测试全绿、真跑才暴露）
4. **有闭环**：记录 → 未命中排行 → 补术语/调阈值 → 命中率提升，可量化
5. **有工程约束意识**：2G 内存、流量有限、采集不阻塞回答、隐私边界
6. **有演进规划**：从 CLI 报表到管理后台，按需演进而不是一次做全
7. **有数据生命周期设计**：原文按期删、加工结果永久留 —— 靠**表结构分层**实现，
   不需要"删除前先跑一遍归档聚合"这种容易出错的流程
8. **有"让问题可见"的工程意识**：记录系统上线后立刻暴露了
   「术语表缺 Explosive Arrow III」「无关问题余弦 0.553 高于正常问题」——
   这些都不是靠人翻记录发现的，是系统主动摆出来的
9. **踩过 schema 演进的坑**：`CREATE TABLE IF NOT EXISTS` 不会给老表加列，
   而这张库要永久保留数据 —— 所以加了幂等迁移，而不是"改结构就删库"
10. **用数据推翻了自己的假设**：本来以为"调高余弦阈值就能解决误召回"，
    实测发现无关问题（0.553）和正常问题（0.51~0.57）**完全重叠** ——
    说明这个方向根本走不通，得换思路。**先采集、再决策**的价值就在这里
11. **安全默认（fail-closed）**：后台没配密码时**整个返回 503**，
    而不是"无密码可访问"。这个默认值的选择比功能本身更重要 ——
    配错密码最多是打不开，配错默认值就是数据泄露
12. **又一个真跑才暴露的 bug**：过滤器把"后台未启用"和"未登录"用了同一个分支，
    导致 302 → 302 重定向死循环。单测覆盖不到（`isConfigured()` 返回值是对的），
    只能靠端到端走一遍
13. **闭环思维**：不是"做了个 RAG"，而是
    「**发现缺失（报表）→ 定位（未命中分类）→ 修复（后台改术语）→ 验证（再问一次）**」
    四步都在一个界面里完成，而且第③步**不用重启**
14. **自动化信号的成本意识**：追问检测（同一人 60 秒内再问 = 上一条没答好）
    是**零成本**的准确率信号 —— 不需要额外调模型、不需要人工标注，
    比任何自动评测指标都便宜
