# 知识库维护成本收敛方案

> 2026-09-27 ｜ 内测阶段，数据可重建，优先「好用、健壮、维护成本低」
> 目标：消灭「关键词 / 术语核对」这对高重复功能，把维护面砍掉一半

---

## 一、先给结论

**问题不是「两个功能重复」，而是「一个概念被实现了两遍——因为底层没有它的位置」。**

系统里**没有「词条」这个实体**。于是：

- 「关键词」面板每次打开，都在内存里把 `chunks.jsonl` 按 title 分组、再 **JOIN 一遍** `zh-en.tsv`，现算出来（`KbKeywordService.buildAll()`）
- 「术语核对」面板直接 CRUD 那个 TSV 文件（`GlossaryStore`，255 行里大半是"用文件当数据库"的代价）
- 检索时 `Glossary` **又独立解析了一遍**同一个 TSV

同一份数据，**3 个解析点、2 条写入路径、2 个前端面板**，key 空间还不一致（一边按 chunk 标题 3,630，一边按 Wiki 页面 3,359），互相漏掉对方 19 条和 290 条。

**方案：把「词条」变成真的实体——SQLite 单表 `kb_term`，成为唯一真源。**
「关键词」和「术语核对」都降级成这张表上的**一个筛选器**，而不是两套功能。

预计工作量 **约 3.5 人天**，一次性收益：**净删代码、净删面板、删掉一整类并发 bug**。

## 二、现状盘点（全部为实测数字）

| 层 | 现在是什么 | 存在哪 |
|---|---|---|
| 分类 | Wiki 原始分类 → 9 个板块的映射 | `CategoryStore` 的 overrides |
| **关键词** | **不是表**，是 `chunks.jsonl` 按 title 分组后 LEFT JOIN 术语表**现算的投影** | 内存 |
| **术语表** | 5 列 TSV | `data/kb/glossary/zh-en.tsv` |
| 文本块 | 4,131 段 | `chunks.jsonl` |
| 向量 | 每段 1024 维 | `index.bin` |

### 2.1 两个 key 空间不一致

| | 数量 | key 空间 |
|---|---|---|
| 关键词 | 3,630 | `chunks.jsonl` 的 distinct `title`（**有正文的页面**） |

| 位置 | 行数 | 干什么 | 读了 TSV 的哪几列 |
|---|---|---|---|
| `Glossary` | 208 | 运行时 B 路：中文 → 英文 | en, zh, status（**丢掉 page / category**） |
| `GlossaryStore` | 255 | 后台 CRUD：整表读改写 + 读写锁 + 临时文件 + 原子替换 | 全 5 列 |

| 列 | 验证结果 | 结论 |
|---|---|---|
| `page` | 对全部 3,359 行，`page == en.replace(' ', '_')`，**0 处不符** | **纯派生，可删** |

## 三、目标模型：一张表搞定

### 3.1 表结构

建在现有 SQLite（`qa.db`）里，直接挂到 `QaStore.migrate()` 那套**幂等补列**机制上（`addColumnIfMissing`，已经在用）：

```sql
CREATE TABLE IF NOT EXISTS kb_term (
  en         TEXT PRIMARY KEY,                    -- Wiki 页面标题 = 唯一 key 空间
  zh         TEXT,                                -- 中文名，别名用「、」分隔
  status     TEXT NOT NULL DEFAULT 'draft',       -- draft / verified / rejected
  board      TEXT,                                -- 板块；NULL = 跟随分类规则自动判
  updated_at TEXT,
  updated_by TEXT
);
CREATE INDEX IF NOT EXISTS idx_term_status ON kb_term(status);
CREATE INDEX IF NOT EXISTS idx_term_board  ON kb_term(board);
```

**只留 3 个真字段**：`en` / `zh` / `status`。其余全部派生：

| 原来的 | 现在怎么来 |
|---|---|
| `page` | `en.replace(' ', '_')` |
| `category` | 从该词条的 chunk `cats` 现算（`CategoryService` 已有） |
| 「有没有正文」 | `KbIndex` 内存里本来就有 title 集合，现算 `hasChunks` |
| 「几个块 / 多少字」 | 同上，现算 |

### 3.2 key 空间统一为 **Wiki 页面标题**

不再用 chunk 标题。这样三个数字第一次收敛到同一个列表里：

```text
pages.jsonl 3,908 个页面  ← 全部都有位置
   ├─ 3,340  有正文 + 有中文名
   ├─   290  有正文、没中文名     → 列表里显示「待补中文名」
   └─   278  没正文（重定向/汇总/消歧/版本页）
             └─ 其中 19 条有中文名 → 列表里显示「无正文」
```

那 19 条里包括 `Equipment`（命中 44 块正文）和 `Lore`（命中 404 块正文）——**B 路不要求英文词是某个块的标题**，所以它们对检索真有用，但今天在「关键词」面板里根本看不见。

### 3.3 「关键词」和「术语核对」变成同一列表的 4 个筛选预设

```
视图预设（都是同一个列表的 filter，不是四个页面）：
  [全部 3,908] [待核对 3,357] [待补中文名 290] [无正文 278]
```

1. 「Equipment」（无正文）和「Bamboo Bench」（无中文名）出现在**同一个列表**里。

4. 删掉 `GlossaryPanel.vue` 后 `KbView` 仍有 4 个可用 tab。

## 八、边界：明确不做什么

| 不动 | 为什么 |
|---|---|
| `chunks.jsonl` + `index.bin` 的写路径 | 那条「行数恒等」铁律和向量重算是**内容**的事，不是**名字**的事。改名永远不该碰语料——这是现有设计里正确的部分，保留。 |
| `提案` / `资料` 两个面板 | 它们是两条**独立闭环**，不是重复功能。合并只会制造耦合，增加维护成本。 |
| `KbGroups` / `CategoryStore` | 分类是「raw → group 的批量规则」，和逐条编辑不是一回事。 |
| 群内检索 / 公开站检索的参数与刹车 | 与本次重构无关。 |

---

## 九、备选方案 B（更保守，仍能砍一半）

不想动存储的话，可以只在**代码层**收敛：

- 把 `Glossary` + `GlossaryStore` 合成一个类（内存 Map + 原子落盘）
- 删掉 `KbKeywordService.buildAll()` 里的 glossary join，改从内存 Map 取
- TSV 补齐到全部 3,908 个页面（解决 key 空间不一致）
- 前端仍然合并成一个面板

**收益**：少 1 个解析点、前端合并、key 空间一致。
**没解决**：`ReadWriteLock` + 整表重写 + 临时文件那套「文件当数据库」的代码全部保留。

**不推荐**——它砍掉的是重复的界面，没砍掉重复的机制。方案 A 才能真正把「同一份数据的第 2、第 3 个解析点」从系统里删掉。

```text

```

**⑧ ★ 最关键的一条：管理员改词 → B 路检索立刻用上，全程只有 `kb_term` 一个来源**

```text

② 后台把 Scrap Cup 的中文名改成「喵喵测试杯」 → {ok:true}
③ 改名后立刻搜「喵喵测试杯」               → keyword 模式，命中 Scrap Cup ✅
④ 原名字搜「废料杯」                      → 0 条（已被改掉，符合预期）
⑤ 还原                                    → 「喵喵测试杯」又变 0 条 ✅
```
**没有重启、没有改文件、没有调 embedding** —— 这就是「补术语表零成本」的技术依据。

### 11.5 浏览器点测：25 项 + 65 项检查全绿，而且**揪出两个真 bug**

宿主 Vite dev 服务的正是本工作区源码，所以浏览器那一层是真点的（宿主真机 Chrome + 真 Vue + 真 DOM，
只有 `/admin/api/**` 是 mock）。两个脚本都更新到了新接口与新面板：

| 脚本 | 结果 |
|---|---|
| `tests/verify-redesign-t11.js` | **25 / 25 通过，0 console error，exit 0**（893 → 1066 行，整篇重写） |
| `tests/verify-redesign-t9.js` | **检查项 65，失败 0，exit 0** |

断言里锁死了两条这次改造的「契约本身」：
- `POST /kb/terms` 的 body **恰好只有** `en / zh / status` 三个键 —— 旧面板必须回填 `page`/`category`
  的那个坑，从此在测试上锁死。
- 列表里**同时**渲染出三种行：有中文名 / 没有中文名（`status === ''`）/ 没有正文（`chunkCount === 0`）。

**它抓到两个我自己写错的契约**（都已修好并复测）：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 抽屉永远显示「这个词条没有文本块」；提案的「先改再采纳」会在 `list[0].i` 上炸 | `GET /kb/terms/chunks` 返回的是**裸数组**，而契约（与前端）要 `{title, chunks}` | 加 `ChunksView(title, chunks)` 包一层。带 `title` 才能让前端对账"这批块属于抽屉里现在这一条"，否则快速连点两条会串台 |
| 2 | 批量核对之后进度条数字不刷新 | `POST /kb/terms/batch` 少回一个 `counts` | 补上重算的 `counts`（增量算数字容易错，直接重算） |

修复后真机复测：`chunks` 顶层键 `['chunks','title']`、含斜杠的 `Sets/Clothes` 也正常；
`batch` 顶层键含 `counts` 且幂等（`updated:0, unchanged:1`）；B 路闭环回归通过。

### 11.6 还没做 / 需要你知道的两件事

1. **宿主 Vite dev 的依赖预构建缓存目前是坏的**，公开站与后台的**所有前端路由都会渲染成空白**，
   而且 **0 console error**（极难自己发现）。实测证据：`vue.js` 引 `chunk-X.js?v=7e6f0953`、
   `vue-router.js` 引同一个 chunk 的 `?v=0f1fd56d` —— ESM 按完整 URL 认模块，于是浏览器里装了两份
   Vue 响应式系统，`RouterView` 的 computed 永不再求值。

   我没动。为了不让验收脚本被它卡死，`tests/lib/dep-shim.cjs`（新增 91 行）临时把 chunk 的 query 串
   统一掉、并补一个惰性 `__VUE_HMR_RUNTIME__` stub；缓存修好后它是恒等变换，可以留着也可以删。
2. **没有提交 git**：工作区里同时有你并行改动的文件（`AdminAuth`、`AdminProperties`、`application.yml`、
