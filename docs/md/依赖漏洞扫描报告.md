## 二、三条 Tomcat 漏洞的逐条判定

**结论：全部不影响本项目。** 依据是**触发条件我们一个都没用到**。

| # | 漏洞 | CVSS | 触发条件 | 我们用了吗 |
|---|---|---|---|---|
| 1 | DIGEST 认证重放 | 9.8 | 使用 Tomcat 的 **DIGEST authenticator** | ❌ 没用 |
| 2 | 安全约束绕过 | 9.1 | 用 **web.xml** 的 `<security-constraint>` | ❌ 没有 web.xml |
| 3 | FORM 认证绕过 | 9.1 | 使用 Tomcat 的 **FORM authenticator** | ❌ 没用 |

**验证方式**（可复现）：

```bash
# 没有 web.xml —— 说明没用容器级认证
find server/src -name "web.xml"          # 无输出

# 没用 Spring Security —— 认证是自己实现的
grep spring-boot-starter-security server/pom.xml   # 无输出

# 实际使用的认证
#   admin/AdminAuthFilter.java   ← OncePerRequestFilter + 自定义 token
#   admin/AdminAuth.java         ← 常量时间密码比较
#   publicapi/PublicRateLimiter  ← 按 IP 限流
```

**三者的共同点**：都是**容器级认证机制**（DIGEST / FORM / web.xml 安全约束）的缺陷。
而本项目**完全绕开了容器认证** —— 认证逻辑全在自己的 Filter 里，
Tomcat 只当纯 HTTP 服务器用。所以这三条对我们**没有攻击面**。

> `was not found in ... during a previous attempt` 时，先探一下镜像上到底有哪个版本。

## 四、升级的理由（虽然是低风险）

虽然不适用，但还是把 Tomcat 升到 **10.1.58**（修复版本）。原因：

1. **成本极低** —— Spring Boot 里覆盖一个属性就行
2. **消除噪音** —— 下次扫描干净，真有新漏洞时不会被旧告警淹没
3. **防御性** —— 万一将来引入 Spring Security 或 web.xml，就是实打实的风险

```xml
<!-- pom.xml -->
<properties>
  <!-- 覆盖 Spring Boot 管理的 Tomcat 版本（修复 3 条 CVE） -->
  <tomcat.version>10.1.58</tomcat.version>
</properties>
```
