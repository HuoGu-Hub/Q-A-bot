# 回答策略 与 知识库设施设计（v2）

> 本文是 `知识库时效性与回答策略方案.md`（下称 v1）的**设计升级**。v1 的**现状诊断全部有效**（回答链路、语料冻结、build.json 误导、Game Updates 结构缺失）；本文**取代 v1 的方案与路线图部分**，因为你的三条补充改变了设计的形状。
>
> **一句话结论**：你的第 1 点（时效）我 v1 已量化；第 2 点（温度）**需要纠正**——温度不控制"依赖哪份资料"，它控制采样的发散度；第 3 点（忠于**自有**知识库）**是最重要的一击**，它把诊断从"知识库权重过大"改成了更准确的**"知识库缺少区分度"**——系统现在无法区分「wiki 原文（未核对、可能过期）」和「你人工订正过的权威内容」，把两者一起升格成了"以资料为准"。**所以真正的第一优先级，是给知识库补上元数据骨架。**

## 一、关于温度：它不是"知识库依赖度"的旋钮

### 1.1 温度实际控制什么

温度是 **softmax 采样的温度**：

| 温度 | 行为 |
|------|------|
| → 0 | 近乎贪心解码：每步都选概率最高的续写。**同一份上下文，输出高度稳定** |
| 0.7（你现在两个 provider 的默认值） | 正常发散 |
| 1.0+ | 分布被压平，低概率词也有机会被选中 |

它改变的是**"在给定上下文下，怎么挑下一个词"**，不改变**"上下文里有什么"**，也不改变**"模型知道什么"**（知识截止时间不会因为调温度而移动）。

### 1.2 你的直觉不是空穴来风，但它指向的结论是错的

确实存在一个**间接**关联：温度调低时，模型更容易**复述**上下文里的原话（包括过期的那句）；温度调高时，它更愿意**偏离**上下文。

但关键在于——**偏离的方向不是"更新的事实"，而是"更流畅、更可能的文本"**。对事实性问题来说，这就是**编造率上升**。也就是说：

- 调高温度：过时答案**少了一点**，但编造答案**多了很多**；
- 你**没有**因此拿到"网上最新的知识"，只是把"照抄旧资料"换成了"自由发挥"。

**结论：温度不能用来选择知识来源。** 想控制"用哪份资料"，真正的旋钮是这四个：

1. **上下文里放了什么**（检索策略、资料块组装）——决定 90%
2. **系统提示词怎么要求**（`AGENTS.md` 第九章的"以资料为准"）
3. **允许不允许模型说"我不确定/我的资料可能过期"**
4. （可选）要求它标注每条事实的来源

### 1.3 但"严谨度档"作为功能是成立的

你要的"配置大模型的严谨度"**值得做**，只是它属于**风格层**，不是**知识来源层**：

| 档位 | 温度 | 用途 |
|------|------|------|
| 严谨 | 0.1 | 事实问答：稳、少编、可复现 |
| 默认 | 0.7 | 现在的行为 |
| 发散 | 1.0 | 闲聊、起名、玩梗 |

**实现要点（这是关键约束）**：温度现在是**构建模型客户端时**写死的参数，不是每次请求能传的：

```java
// llm/LlmRouter.java:70-91
private static ChatModel buildClient(LlmProperties.Provider cfg) {
    OpenAiChatModel.builder()
        .temperature(cfg.getTemperature())      // ← 第 75 行，构建期设定
        ...
}
// config/LlmProperties.java:194     private Double temperature = 0.7;
// resources/application.yml:526/546 两个 provider 都是 0.7
```

所以"每请求切换温度"要**为每个 provider 建多套客户端实例**（严谨/默认/发散），按模式选实例。工作量不大，但不是改个数字。

**而且这个功能有现成的家**：`LlmProperties.ReplyStyle`（`config/LlmProperties.java:116`）就是为了这类需求建的——它的注释写得很明白：

> 表现层约束，和 AGENTS.md 那份「安全底座」刻意分开。
> ① AGENTS.md 改它风险大、且每次都进系统提示词越长越贵；② 这里要能**热生效**（后台改完下一句就变）。

**严谨度档应该挂在 `ReplyStyle` 这套机制上**（后台可配、热生效、与安全底座隔离），而不是去动 `AGENTS.md`。

## 二、关于"忠于自有知识库"：这改变了诊断

你这句话把问题定位得更准了。我 v1 说"别降低知识库权重"，但理由还不够锋利。现在重新表述：

### 2.1 真正的机制不是"权重过大"，是"没有区分度"

知识库里其实躺着**两类性质完全不同的东西**：

| | 来源 | 可信度 | 会过期吗 |
|---|------|--------|----------|
| **A 类** | 你人工订正过的（提案采纳、直接改块、词条核对） | **高** —— 这是自有资产，应该权威 | 低（人负责） |
| **B 类** | wiki 原文，原样抓下来、没人看过 | **中** —— 只是原料 | **高**（游戏一更新就废） |

而现在系统**把 A 和 B 一视同仁**：

- `ChatService.java:221-224` 把它们混成**一个** `<<<KNOWLEDGE>>>` 块；
- `AGENTS.md` 第九章说"**以资料为准（它更新、更具体）**"——把 B 类和 A 类一起升格成权威；
- `KbChunk` 的字段是 `(i, title, cats, text, url)`（`kb/KbChunk.java:14`）——**没有任何字段能区分 A 和 B，也没有日期**。

**所以你感受到的"过度忠于 wiki"，准确说法是：系统没有能力区分"我们核对过的知识"和"wiki 的原料"，于是把原料也当成了结论。**

### 2.2 由此推出的正确方向

不是"降低知识库权重"（那会把 A 类一起削弱），而是：

> **给知识库补上"可信度"这一维** —— 每条资料带着它的**来源、是否人工订正、内容时间**进入上下文，让模型（和检索）能够区别对待：
> - A 类（已订正）→ **权威**，就是"以资料为准"
> - B 类（wiki 原文，截至 X）→ **参考**，允许模型说"我的资料可能过期"

这一步做完，v1 的 A/B/C/D、你的命令模式、严谨度档，**全都能挂上来**——因为它们都需要同一个东西：**chunk 级的元数据**。这正是你说的"先建好知识库设施"。

## 三、关于"新增 bot 命令强制走联网"：方向对，但现在的指令系统接不住

你的设计①是对的方向（**用户显式声明意图**来切换知识来源），而且比我 v1 的"方案 C1 自动触发"更好——**没有分类器误判风险，也不影响正常问答的延迟**。这点我采纳。

### 3.1 但是：现有指令系统有三个硬约束

我读了代码，`/命令 问题文本` 这个语法**现在跑不起来**：

| # | 约束 | 证据 |
|---|------|------|
| 1 | **指令不支持任何参数**。匹配正则是 `^/(\S+)\s*$`，且触发词要**完全相等**——"`/联网 今天什么版本`"里有个空格，**连"看起来像指令"都不会被记录** | `command/CommandMatcher.java` 的 `SLASH_COMMAND` + 完全相等匹配 |
| 2 | **指令是纯模板话术，永远不调模型**。`BotCommand` 的字段是 `trigger/reply/description/scope/minRole/...`，处理流程是"渲染模板 → 发出去" | `command/BotCommand.java`、`router/MessageRouter.java:180-229` |
| 3 | **指令跑在 Guard 之前**，故意绕过限流/敏感词/**成本预算**（为了 `/help` 秒回） | `MessageRouter.java:305`（指令）vs `317`（Guard）vs `336`（预算） |

第 3 条特别重要：**一条能调模型的"指令"，如果沿用现在的路径，等于开了一个不限量、不过预算的模型调用入口**——成本会被打穿。

### 3.2 两个集成点，我推荐第二个

| | 方案 A：扩展指令系统 | 方案 B：前缀约定（推荐） |
|---|---|---|
| 做法 | 改 `CommandMatcher` 支持参数；给 `BotCommand` 加 `kind=template\|agent`；把 agent 类指令**重新导回** Guard/预算链路 | 在问答链路里捕获一个**模式前缀**，像现有的 `求助：` 一样 |
| 语法 | `/联网 今天什么版本` | `/联网 今天什么版本`（UX 完全一样） |
| 后台管理 | ✅ 能进"指令"页列表里配置 | ❌ 不进列表（但可以进"设置"页） |
| 代价 | 要动匹配器 + 指令模型 + 路由顺序，还要小心**别让 agent 指令绕过预算** | 改动集中在 `MessageRouter` 一处 |
| 现成先例 | 无 | ✅ **已有**：`MessageRouter.tryHelpRequest()`（`MessageRouter.java:242`）就是"捕获 `求助：` 前缀 → 转给另一个服务" |

**方案 B 的落地形态**：

```
MessageRouter.handle()
  ①  黑名单
  ②  指令匹配（不变）
  ②.5 求助：前缀（已有）
  ②.6 回答模式前缀（新增）              ← 在这里插入
        /联网  xxx   → mode = web      （只用实时来源）
        /知识库 xxx   → mode = kb       （强制只用知识库，即使默认不是）
        /对照  xxx    → mode = hybrid  （两边都要，冲突时标注分歧）
        （无前缀）     → mode = default
  ③  Guard 五层
  ③.5 成本预算                            ← 模式在这里**必须**参与计费
  ④  ChatService.reply(event, text, quote, images, mode)   ← 多一个参数
```

**三个模式的行为差异**（注意：三个都是"检索 → 注入 → 调模型"，只是检索源和提示词不同，**不需要 tool calling**）：

| 模式 | 检索什么 | 资料块 | 提示词口径 |
|------|----------|--------|-----------|
| `kb`（默认） | 只知识库 | `<<<KNOWLEDGE as-of=... reviewed=true\|false>>>` | 现有规则，但按 A/B 类分档 |
| `web` | 只实时（wiki API 渲染结果 / 网页） | `<<<LIVE fetched-at=...>>>` | **明确告知"这是刚取的实时资料"**，不受知识库规则约束 |
| `hybrid` | 两边都取 | 两个块都给 | **要求它指出分歧**，而不是二选一 |

三条设计要点：
1. **预算必须按模式计费**（`web` 模式更贵：多一次外网往返），否则就是 3.1 第 3 条的坑；
2. **落库要带模式标记**（`qa_stat` 落库已有 `guard_action`/`sources` 的概念），这样你才能量化"哪种模式答得准"——**没有这个，所有方案都是凭感觉**；
3. `web` 模式**必须有降级**：外网挂了/超时 → 退回 `kb` 模式并说明，绝不能让群友等到超时还没回答。

## 四、地基：知识库要补的那一维

这是你说的"先建好知识库设施"。具体到代码，就是给每一块资料补上**元数据**。

### 4.1 现有资产盘点（别重复造）

| 已有 | 位置 | 说明 |
|------|------|------|
| 页面级人工成果表 | `kb_term(en, zh, status, updated_at)` | `status` = `draft/verified/rejected`（待核对/已核对/弃用） |
| **"人工成果不被冲掉"的保护** | `KbTermStore.reconcile` 用 `INSERT OR IGNORE` | 注释原话："中文名和核对状态是人工成果，**绝不能被语料重建冲掉**" |
| 订正链路 | `KbProposalService`（提案：新增/覆盖，人工确认后才落库）、`KbTermService.chunk`（直接改块）、`KbContributionStore`（投递） | 完整的"人改知识库"通道 |
| 增量索引 | `KbIndexIncrementalService` | 改完只重算这一块的向量，已实现 |
| 可配项机制 | `SettingsWhitelist.Item(key,label,group,type,default)` | 后台设置页的现成框架 |

**所以缺的不是"订正流程"，而是"订正状态的粒度"和"它进入检索/提示词的通道"。**

### 4.2 要补的东西：chunk 级三维元数据

```java
// kb/KbChunk.java —— 现在只有 (i, title, cats, text, url)
public record KbChunk(
    int i, String title, List<String> cats, String text, String url,
    Source source,        // WIKI（原样抓的）| CURATED（人工订正过）| BUILTIN（内置）
    boolean reviewed,     // 是否经过人工核对（来自 kb_term.status=verified 或 block 级标记）
    String contentAt,     // 内容时间：wiki revision 时间戳，或人工订正的日期
    String gameVersion    // 可选：该内容对应的游戏版本（从 wiki 页里解析）
) {}
```

三处使用：

| 用在哪 | 怎么用 |
|--------|--------|
| **检索融合** | `KbRetriever.fuse()` 现在只有"向量权重 1.0 / 关键词 2.0 / 标题加成"——加第 4 维：`CURATED` 加分、`WIKI` 且 `contentAt` 很旧则减分 |
| **资料块组装** | `ChatService` 把资料**分两段**注入：`<<<CURATED>>>`（已核对，权威）与 `<<<WIKI_SNAPSHOT as-of=...>>>`（原文，可能过期） |
| **提示词口径** | `AGENTS.md` 第九章改成：**已核对资料以它为准；wiki 原文与你的知识冲突时，说明分歧并在必要时指出"我的资料截至 X"** |

### 4.3 顺带把 v1 的 B1 修掉（这是 bug，不是功能）

`kb/build/KbCorpusBuilder.java:144` 那条"已有缓存就永远复用"的逻辑必须改：向 wiki 要 `rvprop=timestamp`（或用 `list=recentchanges`），**只重抓时间戳变过的页**。这一步同时给 4.2 的 `contentAt` 提供了数据来源——**所以 B1 和元数据设施是同一件事的两面，应该一起做。**

### ✅ 已完成：第 0 步 —— 知识库元数据地基（2026-09-28）

**动手前先挖到一个比"过期"更严重的问题**：

> `kb/build/KbCorpusBuilder.java` 的 `writeChunks` 用的是
> `Files.newBufferedWriter(file)`（默认 **TRUNCATE_EXISTING**）——**整体重写**。
> 而 `chunks.jsonl` 里不只装 Wiki 内容，还装着三类**人工成果**：
> ① 人工订正/追加的块（投递审核、直接改块、新建词条）
> ② 下架墓碑（{@code RETIRED_PREFIX}）
> ③ 行号本身（`qa_stat.retrieved` 的历史引用按行号指块）
>
> 也就是说：**"把 Wiki 更新进来"和"别弄丢自己的知识"在原来那套代码里是互斥的** ——
> 每次刷新语料，人工成果全部归零。`KbTermStore` 的 INSERT OR IGNORE 只保住了词条表
> （中文名/核对状态），**正文订正没有这个保护**。

这一步把上面这条一并修了。落点：

| 项 | 落点 |
|----|------|
| 块级元数据 `src`（wiki/curated）+ `at`（内容时间） | `kb/KbChunk.java` + `kb/KbIndex.java`（缺列时按 wiki + 时间未知，**不冒充权威**） |
| **只重抓真的变过的页** | `kb/build/WikiClient.java`（取 `rvprop=timestamp`）+ `KbCorpusBuilder`（比对 `pages.jsonl.revAt`） |
| **合并式写入，人工成果原地保留** | `KbCorpusBuilder.writeChunks` + `mergeChunkLines` |
| `builtAt` 与 `contentAsOf` 分开记 | `KbCorpusBuilder.writeBuildInfo`（原来混在一起，会让人误判语料新旧） |
| 人工写入打 `curated` 标记 | `KbTermService`（追加/编辑）+ `KbIndexIncrementalService`（投递审核） |
| **资料分两段注入**（已核对 / Wiki 快照带日期） | `agent/ChatService.java` |
| 提示词口径 | `AGENTS.md` 第九章（已改，见下） |

**合并规则**（`mergeChunkLines`，抽成 static 专为可单测）：

```
人工块 / 下架墓碑 → 原样留在原行号
其余槽位          → 依次填入本次新抓的 Wiki 块
新块多于槽位      → 追加到尾部
新块少于槽位      → 多出的旧行打成墓碑（不删行，保住「行号 == 块号」）
写之前统一重排 i  → 保证 chunks.jsonl 第 k 行的 i == k
```

想要"彻底从零重建"用 `--app.kb.build.reset=true`（**会丢弃全部人工成果**，默认关）。

**⚠️ 一处被用户纠正的设计过度推断（2026-09-28 晚）**

第一版把 `src=curated` 写成了**权威等级**：`AGENTS.md` 里写"已人工核对…**最可信，以它为准**"。
用户澄清：

> 不是有了人工订正就一定认定这个数据对的，只要保证**能够对知识库进行修改，

### ⚠️ 两件需要你知道的事

   已在构建日志末尾打了醒目 WARN 提醒。
