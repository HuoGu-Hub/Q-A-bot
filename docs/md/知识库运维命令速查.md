## 二、wiki 导入：三个入口，顺序有依赖

```bash
# ① 地图同步（地点 / NPC 的来源）—— 增量，只拉 revid 变过的页
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.map-sync.sync-on-start=true --spring.main.web-application-type=none"

# ② 地点语料派生（由 marker 生成地点 / NPC 块）
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.location-corpus.build-on-start=true --spring.main.web-application-type=none"

# ③ wiki 文章导入（任务 / 机制 / 世界观…）
mvn spring-boot:run -Dspring-boot.run.arguments="\
--app.kb.wiki-import.import-on-start=true --spring.main.web-application-type=none"
```

**每一步都能先空跑**（加 `--app.kb.xxx.dry-run=true`），也都能单独回滚。

> ⚠️ **导入之后必须重启服务** —— 索引只在进程内重载，没有定时刷新。
> 不重启的话后台还是旧数据。

### 抓什么：往 `app.kb.wiki-import.categories` 里加分类名

| 分类 | 页数 | 状态 |
|---|---|---|
| `Quests/` 前缀 | 155 | ✅ 已导入 |
| `Ranger/Mage/Warrior Skills` | 148 | ✅ 已导入 |
| `Wildlife` 生物 | 38 | ✅ 已导入 |
| `Gameplay` / `Bosses` / `Craftspeople` | 32 | ✅ 已导入 |
| `Lore` 收集品笔记 | 264 | ✅ 已导入（**不是世界观，是收集品故事**） |
| `Armor Set` 套装 | 59 | ⬜ 未导入（与现有单件护甲块部分重叠） |
| `Item catalogs` 索引页 | 70 | ❌ **别开**：占新增文本量 34%，但内容是链接与表格，会和现有物品块在向量空间里几乎重合 |
| `Music` | **0** | ❌ **开了等于没开**：正文命名空间 0 页（95 是含子分类/文件的计数） |

### 三个必须知道的坑

1. **`max-pages-per-source: 300` 是"每个来源"独立算的**，超了会**静默截断**。
   `Lore` 264 刚好压线 —— 它再涨就会丢页。
2. **`max-body-chars: 1500` 现在是「单块上限」**，超长页面会**按段落切块**（不再是截断）。
   调它只影响块的粒度，不影响"有没有丢内容"。
3. **每个分类是一个独立来源**，所以 `bySource` 的输出就是"哪个分类贡献了多少页"。

## 四、手写文档：校验格式

```bash
# ① 校验格式（不启动 Spring、不碰数据库、不联网）
./scripts/validate-kb-doc.sh 你的文档.md

# ② 带上基线，看"这次导入会改动多少条"
./scripts/validate-kb-doc.sh --against docs/gamedata/现有文档.md 你的新文档.md
```

输出示例：

```
[可导入] kb-doc-ok.md
  文档头 : name=Absorb  url=…  ⚠缺 tags
  分块   : 6 块，正文共 5782 字（平均 963 字/块）
  导入计划：新增 0 条，覆盖 1 条，无变化 1 条；库里未被触及 4 条
结论：格式全部通过，可以导入。        ← 退出码 0
```

> ⚠️ **脚本依赖两件事**：`$JAVA_HOME`（没设时回退到 `.toolchain/jdk-17.0.2`，
> 而那个目录**在本仓库里并不存在** —— 请确保 `JAVA_HOME` 指向一个 JDK 17+），
> 以及 `server/target/classes`（即**先编译过**）。缺任何一个它会明确报出来。

## 五、`source` 字段决定模型怎么引用它

代码里的判据是 `source == "manual"`：

| `source` | 模型看到的分段 | 措辞 |
|---|---|---|
| `manual` | **【我们维护的内容】** | "我们资料库里写的是…" |
| 其他（`wiki`/`doc`/…） | **【导入的资料】** | "资料上写的是…**可能已经过期**" |

**怎么分**（按文档性质，不要一刀切）：

| 文档 | 应该是 | 理由 |
|---|---|---|
| 物品图鉴（27 份） | `wiki` | 它是 wiki 数据的翻译整理，wiki 本身会过期 |
| 更新 / 攻略（6 份） | **`manual`** | **我们自己写的摘要与判断** |

> ⚠️ **2026-10-04 修过一个 bug，这个改动以前是空转的。**
> 导入计划（`ChunkImportPlan`）只比对**正文**，而 `source` 是**文档级**字段、不在块里 ——
> 所以"只改了文档头 `source`"会被判成**无变化**，导入什么都不写。
> 现在 `KbDocImporter` 会额外比对文档级字段，**预览与真导入共用同一份计算**。
>
> 因此导入那 6 份时，预览应当显示 **覆盖 72 条、无变化 0 条**。
> **如果预览说"无变化"，说明改动没生效，别继续。**

## 六、格式与用途对照（tsv / csv / xlsx）

系统里一共有四处用到表格格式，**真正在跑的只有前两处**：

| # | 用途 | 格式 | 谁读谁写 | 状态 |
|---|---|---|---|---|
| **①** | **词条表导入导出** | **xlsx**（主）/ csv / tsv | 人 ↔ 管理后台 | ✅ **活的主线** |
| **②** | **黄金集**（测试夹具） | tsv | 人（编辑器）↔ 测试 | ✅ 活 |
| ③ | 物品总表（翻译原料） | tsv / jsonl | 外部 AI | 📦 一次性产物 |
| ④ | 术语表本体 | ~~tsv~~ → **SQLite `kb_term`** | — | 🔄 已迁移 |

### ① 词条表 —— 唯一的「人机往返」通道

```
GET  /admin/api/kb/terms/export?format=xlsx|csv|tsv&view=&board=&q=
POST /admin/api/kb/terms/import     {xlsxBase64} / {csv} / {tsv}
```

- **筛选与列表接口共用同一份逻辑** —— 「看到什么就导出什么」
- xlsx 是**二进制**，用 base64 塞进 JSON（前端 client 永远走 `res.json()`）
- 导入防护：剥 BOM、**乱码拦截**（`U+FFFD` → 报错，不静默写坏）
- 规则：key 唯一、状态合法、**已存在的词条不覆盖**（只在中文名为空时补齐）

**为什么弃用 CSV**：WPS/Excel 在中文 Windows 上「另存为 CSV」默认是 **GBK**，
而浏览器读文件固定按 **UTF-8** 解码 → 中文变乱码**而且不报错**，直接污染词条表。
xlsx 内部就是 UTF-8 的 XML，**没有编码这回事**。

### ② 黄金集

- `tests/golden/retrieval-golden.tsv`（7.2 KB，**进版本控制**）
- 格式：`类别 ⇥ 问题 ⇥ 期望块 id ⇥ 备注`
- **不走 WPS、没有"另存为"这一步** → 纯文本 UTF-8 两端一致，**没有编码风险**
- 这也是它**不需要**改成 xlsx 的原因：它是版本控制里的测试数据，纯文本能 diff

### ③ 物品总表（一次性产物）

- `docs/gamedata/index/物品总表.tsv`（549 KB，9 列）
- `docs/gamedata/index/物品图鉴目录.tsv`、`items-full.jsonl`（2.2 MB）
- **没有代码读它** → 喂给外部 AI 做翻译的中间数据，不在任何运行时流程里

### ④ 术语表（已迁进 SQLite）

- 原：`data/kb/glossary/zh-en.tsv`（5 列 TSV，236 KB）**就是术语表本体**
- **2026-09-27 搬进 SQLite `kb_term` 表** → TSV 降级为「导入导出中间格式」
- **文件已不存在**；`Glossary` 类注释写着「以前本类自己去读…」
