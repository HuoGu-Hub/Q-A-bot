## 〇、结论先行

"日常口语提问答得差"**不是调参问题**，是三个独立问题叠加，**其中最大的一条是语料缺口**：

| # | 问题 | 性质 | 修法 |
|---|---|---|---|
| 1 | 用绝对余弦当相关性阈值（`min-score: 0.45`） | 口径错 | 改相对判别（D5） |
| 2 | **语料里没有"世界"这一层**（0 地点 / 0 NPC / 0 机制） | **覆盖缺口** | 语料扩维 + 地图接入（D7、第四节） |
| 3 | 没有查询改写、没有稀疏路、没有重排 | 能力缺口 | 五段流水线（D1–D4） |

**不要指望只做第 1、3 条就能解决**：实测里"永霜堡/崇山城在哪"这类问题返回空，**不是排错，是库里根本没有这个东西**。

预期收益（以重构总纲第五节的 golden set 衡量）：`entity` 类保持、`descriptive` 类显著提升、`location` 类**从 0 到可用**、`chitchat` 类不再误触发。

## 一、失败实证

### 1.1 真实样本（取自 `qa_raw` / `qa_stat`）

| 提问 | 返回 Top-1 | 真实情况 |
|---|---|---|
| 珍珠母有什么用 | **Pearl（珍珠）** `0.667` | 要的是 `Mother-Of-Pearl`，**本体被压到第 2**（`0.415`） |
| 酸蚀之咬如何获得 | 腐蚀之血（Corrosive Blood） | 本体「酸蚀之咬」**不在 Top-3**，前三是腐蚀之血 / 永恒酸蚀咬击 / 酸蚀砍刀 |
| 阳刺胸甲在哪里掉 | Flame Pact Hat | 完全不相干 |
| 分别介绍下永霜堡和崇山城 | **（空）** `raw 0.435` | **语料里没有地点类内容** |
| （闲聊消息） | 世界设置 / 高山鹿角胸甲 | 闲聊也照样检索并注入 5 块垃圾，`best_cosine` 竟达 **0.60–0.62** |

### 1.2 根因（按贡献度）

**R1 阈值低于噪声地板（最致命）**
实测：闲聊消息余弦 **0.60+**，而一条真问题（永霜堡/崇山城）**0.435** 被 0.45 挡掉。`min-score=0.45` **同时做错两件事**：放垃圾进来、把真问题挡在外面。根因是拿"余弦绝对值"当相关性，而它强依赖文本长度、语言、模型。

**R2 语料覆盖结构性缺失**
2,649 块**全部**来自物品图鉴 + 5 篇更新攻略；`doc_id` 全表 34 个值。**0 个地点、0 个 NPC、0 个任务、0 个机制词条。**

**R3 术语表只是标题的镜像**
`kb_term` 2,649 行 = `kb_block` 2,649 行，**1:1 派生**；`en` 列存的其实是**块 id**；`status` **100% 是 `draft`**（无人工核对痕迹）。用户说"回血""怎么回蓝""加移速的鞋"——词表里没有这些别名，B 路直接哑火。

**R4 中文片段匹配造成近名污染**
[`Glossary.expand()`](../server/src/main/java/com/example/qqbot/kb/Glossary.java) 用 2–3 字片段撞名字，**一个名字只挂在第一个命中的片段上、不按 IDF 加权**。"珍珠母" → 片段"珍珠"同时命中「珍珠」和「珍珠母」，两条都进 B 路，标题权重同为 3.0，正文里"珍珠"出现更多的 Pearl 页胜出。**这就是"珍珠母"排第 2 的确切机制。**

**R5 没有意图分流 / 没有 query 改写**
所有非指令消息无条件走向量检索。缺：闲聊判别、指代消解、口语→检索式改写、同义词/上位词扩展。

**R6 只有两段式，没有重排**
实测误差几乎全是"**召回了但排错了**"（珍珠母被召回却排第 2；酸蚀之咬被召回却排第 4+）——这正是重排最擅长修的问题。

**R7 块粒度对口语不友好**
块平均 91 字、最大 604 字，全是"一物品一卡片"。对"报名字"极友好，对"描述需求"极不友好。

**R8 时效字段名存实亡**
`ChatService` 用 `curated()` 区分"我们维护 vs 导入"，但实测 **2,649 块 `source` 全是 `wiki`**，永远走"导入的资料·可能已过期"这一支。

## 二、目标流水线

现状是"A/B/C 三路 → RRF"，新形态在**两端各加一层、中间加一路**：

```
用户提问
  │
  ├─① QueryUnderstanding   意图分流 · 指代消解 · 口语改写 · 同义/上位词扩展
  │                        （闲聊 → 直接短路，不检索）
  ▼
  ├─② Recall（多路并行）
  │    A 正文向量（bge-m3 dense）      ← 现状保留
  │    B 稀疏检索（char-bigram BM25 或 bge-m3 sparse）  ← 新增
  │    C 术语/别名精确命中              ← 现状扩强（D6）
  │    D 标题向量闸门                  ← 现状保留（0.70 不动）
  ▼
  ├─③ Fusion   RRF 按排名融合          ← 现状参数原样保留
  ▼
  ├─④ Rerank   cross-encoder 重排      ← 新增
  ▼
  └─⑤ Assemble 出处 · 时效 · 坐标 · 地图链接 · 分段标注
```

> **必须原样保留**（这些是实测调出来的，换实现但不许改数值）：RRF 按排名融合、关键词权 2.0、标题权 3.0、标题精确 +0.5、C 路"高阈值闸门+置顶"而非进 RRF、闸门阈值 0.70、一次检索只调一次 embedding（A/C 共用向量）。

## 三、关键设计决策

### D1 意图分流：不该检索的不检索
现状：每条非指令消息都走向量检索。加一个前置判定，输出三态：`CHITCHAT`（短路，不检索不注入）/ `KB`（正常）/ `WEB`（已有 `/联网` 指令）。
- 判定手段：规则优先（是否含疑问词、是否含已知实体、"你/我/谁"等自指词），规则不确定时才用小模型分类。
- **必须 fail-open**：分类器挂掉时按 `KB` 处理（宁可多检索，不可不回答）。

### D2 口语改写：把"怎么回血"变成可检索的词
- 用便宜模型做 query → 检索词扩展，**结果缓存**（群聊问题重复率高，缓存收益大）。
- **失败必须回退到原始 query**：改写超时/报错都不影响回答（沿用现状"知识库只是锦上添花"的容错基调）。
- 改写产物同时喂给 B（稀疏）和 C（别名）。

### D3 稀疏检索：中文用 char-bigram，避免分词依赖
- 两条路可选：
  - **(a) 自建 char-bigram BM25**：中文按 2 字滑窗切词，无需任何分词器。对口语、错别字、专有名词更鲁棒（"酸蚀之咬"切 `酸蚀/蚀之/之咬`）。
  - **(b) `BAAI/bge-m3` 的 sparse 输出**：与现有 dense 同源，**一次 API 调用同时给 dense + sparse**，省一次调用、省一次延迟。**推荐 (b)，(a) 作为离线兜底**。
- 关键：稀疏路要**按 IDF 加权**，这正好修掉 R4 的"片段命中不加权"问题。

### D4 重排：cross-encoder
- 模型：`BAAI/bge-reranker-v2-m3`（与现有 bge-m3 同源，硅基流动可直调）。
- 只对 RRF 融合后的 Top-20 重排，输出 Top-5。
- **走 API 而不是本地**：本地 ONNX 首次加载约 2 GB 内存，而目标机只有 2 GB（见待确认项）。

### D5 阈值改"相对判别"替代绝对余弦
保留 `min-score` 作为**硬下限**（建议降到 0.30，只用来排除明显无关），再叠加相对条件：
1. **margin**：`top1 - top2` 足够大 → 该条明显更优；
2. **z-score**：`top1` 相对本次查询全部候选的均值/标准差显著；
3. 最终由**重排模型给出绝对分**做最后判据。
> 理由：绝对余弦同时被语言、长度、模型影响，跨查询不可比；而"这次提问里哪条最突出"是可比的。

### D6 别名表：把"标题镜像"改成真正的口语桥
- `kb_term` 增加 `alias` 语义（一个实体对多个口语说法），并**允许人工维护**（现状 `status` 有 draft/verified/rejected，机制已在，只是从没用过）。
- **自动挖掘**：`qa_raw` 有 6,543 条真实提问，可直接挖"用户这么问、机器人答对了另一条"的映射，产出候选别名给你确认。

### D7 语料扩维 ← **本文最重要的一节，见第四节**

### D8 块粒度分层
- 保留现有"实体卡"（91 字，报名字好用）；
- 新增"**章节块**"（200–800 字，来自攻略/机制/地点描述），服务 `descriptive` 类提问。
- 两类块在检索时同池竞争，但 `Assemble` 阶段按用途分配条数。

## 四、语料扩维与地图数据接入

### 4.1 地图数据源（已实测拉取）

wiki 使用 **Interactive Data Maps** 扩展，数据存在 MediaWiki **`Map` 命名空间（id 2900）**，共 **32 页**，全部可通过标准 API 读取。

| 页面 | revid | 更新时间 | markers |
|---|---|---|---|
| `Map:Embervale/Main` | 50356 | 2026-08-02 | **505**（20 个 POI 组） |
| `Map:Embervale/Lore` | 50312 | 2026-07-26 | **448**（13 个区域 Lore 组） |
| `Map:Embervale/Collectibles2` | 47107 | 2026-03-12 | 64 |
| `Map:Embervale/Collectibles` | 41120 | 2025-12-09 | 46 |
| `Map:Embervale/Quests` | 42207 | 2026-01-04 | 1 |
| 其他（Blackmire / EarlyAccess / FrozenFrontier / Update4 / Test） | — | — | ~300（旧快照） |

**Embervale 合计约 1,064 个 marker。字段覆盖实测：`x, y, id, name, description, article` 各 100%，`image` 461 个。关联到 295 个不同的 wiki 词条。**

Marker 示例：
```json
{"x":3508,"y":1982,"id":"AncientSpire-Springlands",
 "name":"Ancient Spire - Springlands",
 "description":"The Ancient Spire in the Springlands.",
 "article":"Ancient Spire"}
```

**三个可直接复用的红利：**
1. **区域分类法免费获得**：13 个 Lore 组就是游戏区域名（`Revelwood` / `NomadHighlands` / `Kindlewastes` / `Hollow` / `AlbaneveSummits` / `VeilwaterBasin` / `Drak` …）。
2. **区域名可直接从 `description` 抽取**：实测 "…in the Springlands."、"…in the Low Meadows."、"…in the Kindlewastes"。
3. **`article` 是通往知识库的天然外键**（"Ancient Spire" → 词条），且 `description` 里还带 wiki 内链（`[[Fell Thunderbrute]]`）——**NPC 和怪物名字就藏在这里**。

### 4.2 同步设计

| 项 | 设计 |
|---|---|
| **增量判据** | 每页比对 `revid` + `timestamp`（已实测每页都有），变了才重解析 |
| **抓取方式** | `action=query&prop=revisions&rvprop=content\|ids\|timestamp&rvslots=main&formatversion=2`，**每次 ≤8 个 titles** |
| ⚠️ **坑** | `Map:Embervale/Main` 单页 **100,630 字符**，**超过 web 抓取工具的 100 KB 截断点**（实测触发 "Unterminated string"）。必须走原始 HTTP 并按页分批，不能走通用网页抓取路径 |
| **数据量** | 32 页合计约 548 KB（一次性全量） |
| **表设计** | `kb_map`（地图元信息 + crs + tile 配置）／`kb_map_page`（page, revid, ts, 同步状态）／`kb_map_marker`（map, group, marker_id, name, description, article, x, y, image） |
| **坐标语义** | `crs` 把游戏坐标映射到 10240×10240 图像像素（`0_0.jpg`…`0_7.jpg`，1280×1280 × 8×8 tiles）。**注意不同页的 `crs` 不同**（Main 为 `0..10240`，Collectibles 为 `-3695,-9045 \u2192 6545,1195`），靠 `include` 机制组合——同步时要按页各自的 crs 换算，不要假设统一坐标系 |
| **组合机制** | 页面通过 `"include": ["Map:Embervale/Background", ...]` 组合。根页 `Map:Embervale` 只是 include 列表——**同步时以"有 `markers` 字段的页"为准**，别去解析 include 图 |

### 4.3 与知识库的 join

- `kb_map_marker.article` → `kb_block` 的词条。**注意现状 `kb_block` 没有"wiki 页面名"字段**（只有 `url`），需要新增一列 `wiki_title` 并回填——这是扩维的**前置改造**。
- 反向：`kb_block` → marker，可让词条详情页显示"在地图上的位置"。

### 4.4 问答形态（location 类从 0 到可用）

> **问**：永霜堡在哪？

### 4.6 已落地：地图同步（2026-10-02 实测）

**这是"未来地图查看器"与"语料扩维"共用的同一块地基** —— 同步一次，两件事一起有。

| 组件 | 职责 |
|---|---|
| [`KbMapParser`](../../server/src/main/java/com/example/qqbot/kb/map/KbMapParser.java) | 解析 DataMaps JSON（四种页面形态） |
| [`WikiMapClient`](../../server/src/main/java/com/example/qqbot/kb/map/WikiMapClient.java) | MediaWiki API：列页 / 取版本号 / 取正文 |
| [`KbMapStore`](../../server/src/main/java/com/example/qqbot/kb/map/KbMapStore.java) | 三张表：`kb_map_page`（同步状态）/ `kb_map_group` / `kb_map_marker` |
| [`KbMapSyncService`](../../server/src/main/java/com/example/qqbot/kb/map/KbMapSyncService.java) | 增量同步编排，按页隔离失败 |
| [`KbMapSyncRunner`](../../server/src/main/java/com/example/qqbot/kb/map/KbMapSyncRunner.java) | CLI 入口 |

**实测结果**（真拉一次 wiki，写临时库）：

```
命名空间 32 页 → 解析 32 页 → 写入 1703 个 marker → 失败 0 页 → 7.6 s
再同步一次：0 页需要处理（revid 未变，增量为空转）
```

各分组 marker 数（Top）：`Lore 259`、`Flame_Shrine 111`、`Cave_Passage 103`、`Enemy_Camp 99`、
`Village 85`、`Fossil 67`、`Shroud_Root 66`，另有 13 个**按游戏区域划分**的 Lore 组
（`LoreVeilwaterBasin 54`、`LoreAlbaneveSummits 50`、`LoreRevelwood 47`…）。

#### 实现过程中实测到的四个坑（都已处理）

1. **底图有两套 schema，并存**。
   新的（`Map:Embervale/Background`）是 `{at, tileSize, tiles[]}` —— 8×8 张 1280px 瓦片拼成 10240×10240；
   旧的（`Map:Blackmire/Main`）是 `background: "Map-Blackmire.jpg"` —— **一整张图**，
   此时没有 tileSize，坐标范围就是图片像素（1485×1267）。
   解析器两套都读，分别落到 `tileSize/tileCount` 与 `backgroundImage`。做地图展示时前者可直接铺瓦片，后者只能整图缩放。
2. **主键必须是 `(map, page, marker_id)`，不能是 `(map, marker_id)`**。
   实测同一张地图的不同页会重复定义同一批 marker（`Collectibles` 与 `Collectibles2` 是同一份数据的两个版本），
   用 (map, marker_id) 做主键会让后同步的那页**静默覆盖**前一页。
3. **同一个 `article` 会出现在多张地图里**（实测 `Ancient Spire` 在 Embervale 与 Blackmire 都有），
   所以按 article 查询必须带 `ORDER BY`，否则返回顺序不确定、调用方会飘。
4. **单页超 100 KB**。`Map:Embervale/Main` 实测 100,630 字符 ——
   通用网页抓取工具会在这里截断成非法 JSON（报 "Unterminated string"）。
   必须走 API 分批取，且**不能一次把所有页内容拉回来**。

#### 增量的判据与失败语义

- 判据是每页的 **`revid`**，状态存在 `kb_map_page`。常态下同步只发两次"轻请求"（列页 + 取版本号），正文请求为 **0**。
- **按页隔离**：一页 JSON 坏了只记 `parse_error`，其余页照常同步。
- **单页失败不推进它的 revid** —— 否则下次同步会误以为"这页已经同步过"，把它**永久跳过**。

```bash
  -Dspring-boot.run.arguments="--app.kb.map-sync.sync-on-start=true --app.kb.map-sync.dry-run=true --spring.main.web-application-type=none"

# 真同步（幂等、增量）
./scripts/build-server.sh -q spring-boot:run \
  -Dspring-boot.run.arguments="--app.kb.map-sync.sync-on-start=true --spring.main.web-application-type=none"
```

## 五、评测方案

**没有度量就不能声称"变好了"。** 现状 `KbRetrieverTest` 只测"三路各自工作"，不测"口语提问答得对不对"。

1. **黄金集** 150–200 条，分四类（`entity` / `descriptive` / `location` / `chitchat`），每条标注期望块 id（1–3 个）。
2. **指标**：`R@1` / `R@5` / `MRR`，**分类分别统计**（混算平均值会掩盖问题：现状 `entity` 类 ~99.5%、`location` 类 0%，平均看着还能看）。
3. **数据来源**：`qa_raw` 6,543 条真实提问可挖（先做去重——实测存在同题重复入库）。
4. **反例集**：把 1.1 表格里那几条失败样本**永久纳入回归**。
5. **端到端**：用 `tests/manual/fake-onebot-server.mjs` 造消息，验证"注入进 prompt 的 `<<<KNOWLEDGE>>>` 块内容"而不只是检索返回值——**因为真正决定回答质量的是注入内容，不是排序分数**。

### 5.1 基线（2026-10-02 实测，已落地为自动化跑手）

黄金集 42 条，语料 2,649 块，术语表 5,121 条，真实生产参数（top-k=5 / min-score=0.45 / title-gate=0.70）：

| 类别 | 条数 | R@1 | R@5 | MRR | 干净率 | 注入块均值 |
|---|---|---|---|---|---|---|
| `entity` | 12 | 66.7% | 100% | 0.819 | 0% | 5.0 |
| `colloquial` | 4 | 50.0% | 100% | 0.708 | 0% | 5.0 |
| `gap` | 5 | — | — | — | **0%** | 5.0 |
| `chitchat` | 15 | — | — | — | **6.7%** | 4.7 |
| `descriptive` | 6 | 待人工标注 | | | | |

**最重要的一行：`gap` + `chitchat` 共注入 95 块无关资料。** 这 20 条问题根本不需要知识库，
却每条都往 `<<<KNOWLEDGE>>>` 里塞了 5 块 —— 这就是 R1 的量化形态。

三条与文档预期不同的实测发现：

1. **`entity` R@1 只有 66.7%，不是文档里说的 99.5%。** 差异来自提问方式：
   文档测的是**裸名字**（"酸蚀之咬"），黄金集里是**自然口语**（"酸蚀之咬如何获得"、"咖啡豆的那个烘培器怎么弄"）。
   失分集中在两处：**同族变体压过本体**（藏红花幼苗 > 藏红花；永恒连锁闪电 > 连锁闪电）、
   **问的是周边物而非主体**（问"烘培器"→ 烘焙机才是正解）。这两类都不是阈值问题，是排序问题（D4 重排的目标）。
2. **标题向量闸门确实修好了"珍珠母"**：早期实测本体被 Pearl 压到第 2（0.415 vs 0.667），
   现在闸门命中、本体第 1。这说明 C 路的设计是对的，**不要动 0.70 这个阈值**。
3. **`colloquial` 类靠向量路救回，关键词路救不回**：
   "氨液腺"对"氨腺"关键词 0 命中（字面不重合），向量路第 3；
   "电法师头"对"大法师帽"向量路第 1。
   所以 D3（稀疏路）**不能替代稠密路**，两者是互补关系 —— 这一点会影响 D3 的选型。

跑手与用法见 [`tests/golden/README.md`](../../tests/golden/README.md)。

#### 5.1.1 ⚠️ 负结果：**"调高 min-score"这条路是死的**（2026-10-02 实测）

这是本次调研里最重要的一条**否定性结论**，它推翻了我自己方案里 D5 的原始设想。

黄金集逐条记录 `bestCosineRaw`（卡阈值**之前**的最高余弦）后，四类的分布是：

| 类别 | min | p50 | max |
|---|---|---|---|
| `entity`（该答） | **0.548** | 0.602 | 0.700 |
| `colloquial`（该答） | 0.537 | 0.544 | 0.544 |
| `gap`（没资料） | 0.541 | **0.554** | 0.559 |
| `chitchat`（无关） | 0.372 | 0.511 | **0.634** |

**"该答"的分布和"没资料"的分布完全重叠。** 具体说：

- `gap` 类最高 0.559 > `entity` 类最低 0.548 —— 有些"库里根本没有"的问题，
  余弦**比**"库里确实有"的问题还高；
- 一条闲聊消息（"你得用超高清的片源…"）高达 **0.634**，超过多半个 entity 类。

所以任何**单一绝对值阈值**都必然两头不讨好：调到 0.55 能挡掉 14/15 的闲聊，
但会把 `colloquial` 类**全灭**（0.503~0.556），而那正是群友最常问的一类。

原因：双塔（bi-encoder）在中文短句上**基线高、方差小** —— 它算的是"大意像不像"，
不是"这段话回不回答这个问题"。硬要拿它当相关性判据，就是在用一个没有区分度的信号做决策。

> 附带修正：`application.yml` 里原来写"无关问题最高只有 0.43"，那只是**一个顺手的反例**
> （"今天天气怎么样"）。真去测 15 条真实闲聊，最高 0.634。注释已按实测改写。

#### 5.1.2 ✅ 正解：cross-encoder 重排（D4）已落地，效果实测

换用 cross-encoder（`BAAI/bge-reranker-v2-m3`，把问题与文档**拼在一起**看）后，同一个黄金集：

| 类别 | 指标 | 重排前 | **重排后** |
|---|---|---|---|
| `entity` | R@1 | 66.7% | **91.7%** |
| `entity` | MRR | 0.819 | **0.938** |
| `colloquial` | R@1 | 50.0% | **100%** |
| `colloquial` | MRR | 0.708 | **1.000** |
| `chitchat` | 干净率 | 6.7% | **93.3%** |
| `chitchat` | 注入块均值 | 4.7 | **0.3** |
| `gap`+`chitchat` | **注入垃圾块总数** | **95** | **30** |

两件事一起被修掉了：

1. **废话不再被硬凑资料**：闲聊的重排顶分是 0.0004 / 0.0017 / 0.0022，
   全部低于 `rerank.min-score: 0.02`；而所有**已验证正确**的真实问题 ≥ 0.04。
2. **同族变体不再压过本体**（这是重排前 R@1 只有 66.7% 的主因）：
   藏红花幼苗 → 藏红花、永恒连锁闪电 → 连锁闪电、咖啡豆 → 咖啡滚筒烘焙机、
   珍珠母/珍珠 —— **4/4 全部纠正到第 1 名**。

保留的实测细节：
- **标题必须一起送进重排**。「氨液腺」对「氨腺」字面完全不重合，关键词路 0 命中，
  正是靠标题那半截才被重排认出来（0.596、第 1 名）。
- **C 路闸门命中时不允许"一条都不给"**。闸门命中意味着标题向量余弦 ≥0.70 = 用户就是在问这个实体名，
  这种情况下丢弃资料是明确的错。
- **fail-open**：重排失败保持原 RRF 顺序继续回答，绝不因为"锦上添花的一层"而不回答。
- **公开站明确关掉重排**（`allowRerank=false`）：它有自己的按天配额与 LRU 缓存，
  "要不要给资料"的判断在那里没有意义，多一次外部调用只是白花钱。已有单测锁住。

#### 5.1.3 ❌ 仍未解决：`gap` 类干净率 0%

重排**没有**修好 `gap`。问"阳刺胸甲在哪里掉"时，重排给出的最高分是 0.559，
选中的是 `assassin-chest`（刺客胸甲）—— 它**语义上确实像**一件胸甲，
重排没有任何依据知道"阳刺"这个东西在语料里**不存在**。

修它需要的是**另一个机制**，不是分数阈值：**实体落地检查** ——
识别出提问里的游戏实体名（阳刺胸甲、不朽指环、氨液腺…），
如果在词条表/语料里找不到它，就应当**明说"资料里没有这条"**，而不是给出语义相近的邻居。
这属于 D6（别名表）的延伸，也是下一步要做的。

## 八、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 重排延迟拖慢体验 | 2G 机器 + 群聊并发 | 只对 Top-20 重排；超时直接跳过重排用 RRF 结果（fail-open） |

| 改动影响现有 `entity` 类表现 | 现状该类已 99.5% | 黄金集分类统计，**`entity` 类指标不许下降**是硬门槛 |
