# 知识库摄入边界与激活协议

> **状态**：已采纳（2026-10-06）｜**执行进度**见文末「落地追踪」
> **这份文档定什么**：知识库里"资料怎么进来"与"资料怎么生效"的**边界**和**契约**。
> 它约束的是**结构**，不是某个功能的实现 —— 所以任何一条被打破，都应该能在
> `ArchitectureTest` 或代码评审里被指出来。

---

## 一、结论（三句话）

1. **知识库核心不认识任何摄入来源。** 检索、管理端、真源（SQLite）只认"块"，
   不知道块是抓来的、还是人写的。
2. **摄入来源是平级的生产者，不是核心的一部分。** 目前两个：
   `kb.wiki`（自动抓取，可缺省）与管理端「文档」面板（人工 / AI 交付的合规文档）。
3. **"写块"是唯一出口，写完不需要调用方做任何事。** 生效（激活）由核心自己负责。

设计意图（用户 2026-10 明确）：**无论 wiki 能否正常批量获取，知识库都必须照常运转**；
抓不到的最坏后果只是"这次没有新资料进来"，人工补资料这条路始终可用。

---

## 二、边界长什么样

```
   生产者 A：自动抓取（可缺省）              生产者 B：人工 / AI 交付
   kb.wiki                                    .md 合规文档（知识库文档格式规范）
   WikiApiClient / WikitextCleaner            ↗ 管理端「文档」面板
   WikiArticleImporter（CLI 批处理）           /kb/blocks/preview|import
        │                                          │
        └──────────────────┬───────────────────────┘
                           ▼
        ┌──────────────────────────────────────────────┐
        │  知识库核心（真源 = SQLite）                   │
        │  kb_block / kb_block_vec / kb_term           │
        │  KbBlockStore（写口）→ KbBlockIndex（内存视图）│
        │  检索 / 管理端 / 公开站只认它                  │
        └──────────────────────────────────────────────┘
```

两条摄入链**在"写块"这一层汇合**；核心不反向认识任何生产者。

## 三、四条约定

### 约定 1：依赖单向 —— 生产者 → 核心

- 允许：`kb.wiki` / `kb.map` 依赖 `kb.block` / `kb.term` / `EmbeddingClient`。
- **禁止**：核心（`kb` 根 / `kb.block` / `kb.term` / `kb.category` / `kb.proposal`）
  import `kb.wiki` / `kb.map`。
- 已经犯过一次并已修（2026-10-06）：`KbRetriever` 为了读一个 docId 常量
  import 了 `kb.map.LocationCorpusBuilder`。修法是**把常量挪进核心**
  （`PlaceIntent.PLACE_DOC_ID`）—— 契约由消费它的一方定义。
- 护栏：`ArchitectureTest.kbCoreDoesNotDependOnIngestSources`。

### 约定 2：写口唯一 + 激活自动

- 生产者只碰 `KbBlockStore`（`upsert` / `setRetired` / `delete` / `clearAll` /
  `upsertTitleVector`）。
- **不许**生产者持有 `KbBlockIndex`、更不许手工调 `reload()`。
- 内核机制：`KbBlockStore` 每次写成功把 `version` +1；`KbBlockIndex.ensureLoaded()`
  发现版本对不上就自己重载（读数据**之前**取版本，宁可多重载一次）。
- 护栏：`ArchitectureTest.kbCoreDoesNotDependOnIngestSources`（后半条）。

### 约定 3：可回滚 + 幂等

- 每个生产者的块挂在自己的 `docId` 前缀下（`wiki·<来源>` / `地图·地点` / `物品图鉴·…`），
  `purge()` 只清自己那一份。
- 重跑幂等（块 id 由页面名确定性推导）。
- ⚠️ purge 必须**连同步状态一起清** —— 否则增量判据会让"回滚"变成单向门。

### 约定 4：缺省即降级，失败要可见

- 抓取失败**不得**影响核心：按页隔离 + 错误进账本（`kb_wiki_page.error`）+ 不推进 revid（下次重试）。
- 导入是**离线批处理**（`ApplicationRunner` + `@ConditionalOnProperty`，默认关），
  不占运行期路径、不在管理端暴露写入口。

## 四、激活协议：为什么是"版本戳"而不是"事件"

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 调用方手工 `reload()` | ❌ 原方案。全项目 12 处手工调用，新增一个写入口就漏一个；漏了=**检索一直用旧语料且不报错** |
| Spring 事件（写成功发事件、索引订阅） | ❌ 批量导入会触发 N 次重载（一次导入上千块）；要做去抖又得再引入一层状态 |
| **版本戳 + 懒失效** | ✅ 本次采用。`KbBlockStore.version` 自增，`KbBlockIndex` 读前比对；写 1000 块只会在下一次检索时重载一次。同一套路 `KbTermStore` 已经在用（Glossary 靠它自动重载） |

**读前取版本**而不是读完再取：读的这段时间里若有写入，我们记下的是旧版本 →
下次访问会再重载一遍（宁可多重载一次）；反过来会把"旧数据 + 新版本号"钉死，那才是真错误。

## 五、护栏（会失败的测试）

`server/src/test/java/com/example/qqbot/ArchitectureTest.java`：

- `kbCoreDoesNotDependOnIngestSources`：
  ① 核心（除 `kb.wiki` / `kb.map` 自己）不得依赖 `kb.wiki` / `kb.map`；
  ② `kb.wiki` / `kb.map` 不得依赖 `KbBlockIndex`。
- 单测 `KbBlockIndexTest`：**故意不调 reload()**，断言写完立刻可见（覆盖 / 下架 / 恢复 /
  删除 / 清空 / 标题向量六种写操作）。谁把版本戳改回手动重载，这里立刻红。

## 六、遗留：`termStore.reconcile()` 还没有归属

现状：`KbTermStore.reconcile()`（按语料补齐词条表）仍然是**生产者显式调用** ——
`WikiArticleImporter`（导入 + purge）、`LocationCorpusBuilder`（派生 + purge）共 4 处。
文档导入路径不受影响（`KbDocImporter` 是按块登记词条的，本来就逐块 `upsert`）。

这与"约定 2"是同一个味道（忘了调 → 新块的名字进不了词表 → B 路关键词搜不到，且不报错），
只是危害面小一些。**下一步的归属方案**：给 `KbCorpus` 加 `version()`，
`KbTermStore` 在读到"语料版本比我上次补齐时新"时自己补一次（幂等）。
不放在这次一起改的原因：它要给读路径加一次"可能写库"的动作，值得单独一个提交 + 单独验证。
