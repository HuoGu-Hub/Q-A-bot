# 知识库摄入边界与激活协议

> **状态**：已采纳（2026-10-06）｜**执行进度**见文末「落地追踪」
> **这份文档定什么**：知识库里"资料怎么进来"与"资料怎么生效"的**边界**和**契约**。
> 它约束的是**结构**，不是某个功能的实现 —— 所以任何一条被打破，都应该能在
> `ArchitectureTest` 或代码评审里被指出来。

---

## 一、结论（三句话）

1. **知识库核心不认识任何摄入来源。** 检索、管理端、真源（SQLite）只认"块"，
   不知道块是抓来的、还是人写的。
2. **摄入来源是平级的生产者，不是核心的一部分。** 目前三条：
   `kb.wiki`（自动抓取，可缺省）、`kb.map`（地图同步 + 地点派生，可缺省）
   与管理端「文档」面板（人工 / AI 交付的合规文档）。
   另有一条**旁路**：管理端「词条」面板直接维护词条表，它不写块，只供 B 路关键词匹配。
3. **"写块"是唯一出口，写完不需要调用方做任何事。** 生效（激活）由核心自己负责。

设计意图（用户 2026-10 明确）：**无论 wiki 能否正常批量获取，知识库都必须照常运转**；
抓不到的最坏后果只是"这次没有新资料进来"，人工补资料这条路始终可用。

## 二、边界长什么样

```
   生产者 A：自动抓取（可缺省）      生产者 B：地图（可缺省）      生产者 C：人工 / AI 交付
   kb.wiki                          kb.map                       .md 合规文档
   WikiApiClient / WikitextCleaner  KbMapSyncService             ↗ 管理端「文档」面板
   WikiArticleImporter              LocationCorpusBuilder        /admin/api/kb/blocks/preview|import
   （CLI 批处理）                    （CLI 批处理）
        │                                │                              │
        └───────────────┬────────────────┴──────────────────────────────┘
                        ▼
        ┌──────────────────────────────────────────────┐
        │  知识库核心（真源 = SQLite）                   │
        │  kb_block / kb_block_vec / kb_term           │
        │  KbBlockStore（写口）→ KbBlockIndex（内存视图）│
        │  检索 / 管理端 / 公开站只认它                  │
        └──────────────────────────────────────────────┘

   旁路：管理端「词条」面板
   /admin/api/kb/terms/import|export（xlsx 为主，CSV 弃用）→ kb_term → B 路关键词匹配（不写块）
```

三条摄入链**在"写块"这一层汇合**；词条表那条旁路不进"写块"这一层。核心不反向认识任何生产者。

### 四条摄入来路（入口 / 默认开关 / 触发）

| 来路 | 入口 | 默认开关 | 触发方式 |
|---|---|---|---|
| 后台文档导入 | `kb.block.KbDocImporter` | 无独立开关：`app.kb.enabled: true` + `app.persistence.enabled: true` | 管理端「文档」面板 → `POST /admin/api/kb/blocks/preview` 与 `/import`（先预览、后确认） |
| wiki 抓取 | `kb.wiki.WikiArticleImporter`，CLI 入口 `kb.wiki.WikiImportRunner` | `app.kb.wiki-import.import-on-start: false` | `mvn spring-boot:run -Dspring-boot.run.arguments="--app.kb.wiki-import.import-on-start=true --spring.main.web-application-type=none"`；`--app.kb.wiki-import.dry-run=true` 只看数量，`--app.kb.wiki-import.purge=true` 回滚 |
| 地图同步 | `kb.map.KbMapSyncService`，CLI 入口 `kb.map.KbMapSyncRunner`；地点派生 `kb.map.LocationCorpusBuilder`，CLI 入口 `kb.map.LocationCorpusRunner` | `app.kb.map-sync.sync-on-start: false`、`app.kb.location-corpus.build-on-start: false` | `--app.kb.map-sync.sync-on-start=true` 灌 marker；再 `--app.kb.location-corpus.build-on-start=true` 派生地点块 |
| 词条表 | `kb.term.KbTermStore`，HTTP 入口 `kb.catalog.KbCatalogController` | 无独立开关：`app.persistence.enabled: true` | 管理端「词条」面板 → `POST /admin/api/kb/terms/import`（xlsx 为主，CSV 弃用）；`GET /admin/api/kb/terms/export` 默认 `format=xlsx` |

## 三、四条约定

### 约定 1：依赖单向 —— 生产者 → 核心

- 允许：`kb.wiki` / `kb.map` 依赖 `kb.block` / `kb.term` / `EmbeddingClient`。
- **禁止**：核心（`kb` 根 / `kb.block` / `kb.term` / `kb.category` / `kb.proposal`）
  import `kb.wiki` / `kb.map`。
- 已经犯过一次并已修（2026-10-06）：`KbRetriever` 为了读一个 docId 常量
  import 了 `kb.map.LocationCorpusBuilder`。修法是**把常量挪进核心**
  （`PlaceIntent.PLACE_DOC_ID`）—— 契约由消费它的一方定义。
- 护栏：`ArchitectureTest.kbCoreDoesNotDependOnIngestSources`。

### 约定 2：写口唯一 + 激活自动

- 生产者只碰 `KbBlockStore`（`upsert` / `setRetired` / `delete` / `clearAll` /
  `upsertTitleVector` / `deleteTitleVector`）。
- 唯一被允许的例外：`KbDocImporter` 在导文档时**逐块登记词条**，所以它持有 `KbTermStore`；
  `kb.wiki` / `kb.map` 连词条表都不许碰（护栏见第五节）。
- **不许**生产者持有 `KbBlockIndex`、更不许手工调 `reload()`。
- 内核机制：`KbBlockStore` 每次写成功把 `version` +1；`KbBlockIndex.ensureLoaded()`
  发现版本对不上就自己重载（读数据**之前**取版本，宁可多重载一次）。
- 护栏：`ArchitectureTest.kbCoreDoesNotDependOnIngestSources`（后半条）。

### 约定 3：可回滚 + 幂等

- 每个生产者的块挂在自己的 `docId` 前缀下（`wiki·<来源>` / `地图·地点` / `物品图鉴·…`），
  `purge()` 只清自己那一份。
- 重跑幂等（块 id 由页面名确定性推导）。
- ⚠️ purge 必须**连同步状态一起清** —— 否则增量判据会让"回滚"变成单向门。

### 约定 4：缺省即降级，失败要可见

- 抓取失败**不得**影响核心：按页隔离 + 错误进账本（`kb_wiki_page.error`）+ 不推进 revid（下次重试）。
- 抓取与导入是**离线批处理**：`WikiImportRunner` / `KbMapSyncRunner` / `LocationCorpusRunner`
  三个 `ApplicationRunner` 各自挂 `@ConditionalOnProperty`，默认关，不占运行期路径，
  也不在管理端暴露写入口。

## 四、激活协议：为什么是"版本戳"而不是"事件"

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 调用方手工 `reload()` | ❌ 原方案。全项目 12 处手工调用，新增一个写入口就漏一个；漏了=**检索一直用旧语料且不报错** |
| Spring 事件（写成功发事件、索引订阅） | ❌ 批量导入会触发 N 次重载（一次导入上千块）；要做去抖又得再引入一层状态 |
| **版本戳 + 懒失效** | ✅ 本次采用。`KbBlockStore.version` 自增，`KbBlockIndex` 读前比对；写 1000 块只会在下一次检索时重载一次。同一套路 `KbTermStore` 已经在用（Glossary 靠它自动重载） |

**读前取版本**而不是读完再取：读的这段时间里若有写入，我们记下的是旧版本 →
下次访问会再重载一遍（宁可多重载一次）；反过来会把"旧数据 + 新版本号"钉死，那才是真错误。

## 五、护栏（会失败的测试）

`server/src/test/java/com/example/qqbot/ArchitectureTest.java`：

- `kbCoreDoesNotDependOnIngestSources`：
  ① 核心（除 `kb.wiki` / `kb.map` 自己）不得依赖 `kb.wiki` / `kb.map`；
  ② `kb.wiki` / `kb.map` 不得依赖 `KbBlockIndex`。
- 单测 `KbBlockIndexTest`：**故意不调 reload()**，断言写完立刻可见（覆盖 / 下架 / 恢复 /
  删除 / 清空 / 标题向量六种写操作）。谁把版本戳改回手动重载，这里立刻红。

## 六、词条表补齐：同样不需要调用方操心（2026-10-08 完成）

**旧样子**：`KbTermStore.reconcile()`（按语料把缺的词条补进表里）是**生产者显式调用** ——
`WikiArticleImporter`（导入 + purge）、`LocationCorpusBuilder`（派生 + purge）共 4 处。
这与"约定 2"是同一个味道（忘了调 → 新页面的中文名位置不存在 → B 路关键词搜不到，且不报错）。

**现在的机制**（和块索引同构）：

```
KbCorpus.version()            ← 接口上新增的默认方法（不支持版本感知的实现返回 0）
KbBlockIndex.version()        ← 运行期注入的唯一实现，转发给 KbBlockStore.version()
KbTermStore.list()/map()/deleteOrphans()
                              ← 读的入口：先比版本，对不上就 reconcile() 一次
                                （get() / count() 不走这条路；
                                 快路径只比一个 long；补失败**不记版本** → 下次再试）
```

于是 `WikiArticleImporter` 与 `LocationCorpusBuilder` **连 `KbTermStore` 都不再持有**
（字段 / 构造参数一起删掉）。
取版本的规矩同为"**先取版本、再读数据**"（宁可多重一次，也不能把"旧数据 + 新版本号"钉死）。

**为什么放在读路径（懒）**：写路径可能是 CLI 里一次写上千块 —— 在那里补齐既慢又没人看；
而真正要读的人（B 路检索 / 管理端）顺手补一次就够了。

⚠️ **孤儿词条不在自动范围内**：purge 会留下没有对应块的词条行，
但它们**只能由管理端手动清**（`deleteOrphans`）—— "先起中文名、正文以后再导"的人工行
长得和孤儿一模一样，自动清会误伤。（2026-10-07 实测：重导后按稳定块 id 重新认领，孤儿为 0，无需手点。）
