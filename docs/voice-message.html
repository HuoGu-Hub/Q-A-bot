QQ 语音条发送探索

不是发文件，是让对方收到一条可以点开播放的语音气泡。基于本机 NapCat 4.18.28 + 本项目的 OneBot 11 出口实测。

已验证语音条 = 消息段 {"type":"record","data":{"file":"..."}}。file 接受 base64://、公网 URL、协议端可见的路径。

已验证我们把 MP3 字节 base64 塞进去就行：NapCat 自己调 ffmpeg 转成 SILK v3，再算好时长、上传、发出。项目里不用写任何 SILK 编码器。

必须避开不要直接发 SILK 文件：NapCat 探测不到 SILK 的时长，会发出一条 0 秒的语音，而且日志里不报错。

02它在 NapCat 里到底怎么走

阅读容器内 /app/napcat/napcat.mjs 得到的确切链路，不是猜测：

// napcat.mjs 精简后的真实逻辑
[ze.voice]: async (e, n) => this.obContext.apis.FileApi.createValidSendPttElement(
    n, (await this.handleOb11FileLikeMessage(e, n)).path
);

async function pye(src, tmpDir, log) {
  if (await isSilk(src)) {
    let duration = 0;
    try { duration = await getDuration(src); }        // ffmpeg 没有 SILK 解复用器
    catch { duration = Math.max(1, size/1024/3); }    // 只有抛异常才按大小估算
    return { converted: false, path: src, duration };
  }
  await convertToNTSilkTct(src, tmp);                 // ffmpeg addon：任意音频 → SILK
  return { converted: true, path: tmp, duration: await getDuration(src) };  // 时长仍取源文件
}

最终 ptt 元素里几个固定值：formatType:1、voiceType:1、voiceChangeType:0，以及一个写死的 15 个波形值 —— 客户端上那条小波形不是真实音频振幅。

03三条硬规则

1. 给协议端「普通音频」，不要给 SILK

这是本次最有价值的发现。SILK 走的是 isSilk 直通分支，而 ffmpeg 无法解析 SILK 容器，getDuration 返回 0 且不抛异常，于是估算兜底也不会触发 —— 结果就是 0 秒语音。转换分支反而会拿源文件（MP3）去测时长，准确。

2. 路径必须是协议端能看到的路径

NapCat 跑在容器里，宿主机的 E:\... 对它不存在。图片模块早就踩过这个坑，语音完全同理：用 base64://，或者公网 URL。本项目已有约定，见 OutboundImage 的注释。

3. 语音是「一条消息」，不要和文本/图片拼在同一个数组里

技术上能拼，但客户端呈现会变得不可预期。语音应当独立成条，且不参与现有的分片与合并转发：合并转发卡片里的语音要展开才看得到，等于把语音藏起来。

04接入本项目的设计

现有边界不用动：onebot/ 是唯一碰协议的地方，OutboundSender 是唯一出口。

位置改动理由
MessageCodec新增 voiceMessage(byte[] audio) → [{type:"record",data:{file:"base64://…"}}]。已有的 TYPE_VOICE 常量目前没人用，正好落地。段格式只允许出现在这里
OutboundSender新增 sendVoice(OneBotEvent, byte[]) / sendVoiceToGroup(long, byte[])：占发车位、单条发、记日志。不切片、不合并。所有发送必须过同一条路，语音不能开侧门
MediaPolicy加 outbound.voice.enabled 与 max-kb（建议 1024）。与图片同构，出站闸门集中在媒体层
media/VoiceLibrary预置语音包：key → 音频字节，接口照抄 ImageLibrary。先跑通「找音频 → 发语音」，TTS 以后接同一个出口
回复标记可选 [[voice:key]]，与 [[img:...]] 同构。让模型能主动指定一条语音
 
// MessageCodec 里新增（草案）
public JsonNode voiceMessage(byte[] audio) {
    ArrayNode array = mapper.createArrayNode();
    array.add(segment(TYPE_VOICE, Map.of(
        "file", "base64://" + Base64.getEncoder().encodeToString(audio))));
    return array;
}

// OutboundSender 里新增（草案）
public void sendVoiceToGroup(long groupId, byte[] audio) {
    sleepQuietly(pacer.reserve(true, groupId));
    long id = apiClient.sendGroupMsg(groupId, codec.voiceMessage(audio));
    log.info("[OUT] 已发送语音到群 {}，message_id={}（{} KB）", groupId, id, audio.length / 1024);
}

注意返回的 message_id 与文本一致；QQ 侧没有「时长」回执，想要时长只能自己用 ffprobe 算，或者接受 NapCat 日志里的数值。

06素材从哪来

本来打算从网上抓几段现成语音，但这台机器的出网被 DNS 劫持到 198.18.x.x（Clash fake-ip），TLS 握手直接失败，web_fetch 也判定为非公网地址。所以这次改用 Windows 自带 SAPI 离线合成，效果上完全够验证链路。

网络恢复后，可下载的公开音频来源：

  • Wikimedia Commons 的语音样本，CC 授权，直接给 upload.wikimedia.org 的直链；
  • LibriVox 公共领域有声书片段，做长语音测试很合适；
  • 各语言发音库（如 Forvo 的公开条目）—— 注意逐条核对授权。

商用语音包、影视片段、他人语音条不要进仓库，也不要发到群里：语音是可直接传播的内容，版权与隐私风险比文字高。

07还没验证的

  • 私聊语音：链路应当一致，但没有实测；
  • 群语音的额外风控：短时间内连发多条语音会不会被限流，目前只在开发群试了 4 条；
  • 超过 89 秒的行为、以及客户端播放长语音的体验；
  • 入站语音：收到的 record 段带 url/path/file_size，将来做转写时要走 url 下载，容器内路径不可用。

08建议的下一步

  1. 先落最小能力：MessageCodec.voiceMessage + OutboundSender.sendVoice + 一个管理端「试听/试发」按钮，验证真实链路。
  2. 再做素材层：VoiceLibrary 收一批预置语音，用 [[voice:key]] 触发，不接任何模型。
  3. 最后才接 TTS：TTS 只是「产出一段 MP3」，出口复用第 1 步，不需要再碰协议。

证据来源：NapCat 4.18.28 容器内 napcat.mjs（createValidSendPttElement / pye / handleOb11FileLikeMessage）；docker logs napcat；get_msg 返回的 record 段；本机实测消息 908573181、1594269379、8835045、1729339701。
