意图识别：让 bot 先弄清你要什么

基于 qqbot 现有代码与 30 天 553 条真实提问的分析，以及对四种常见方案的取舍判断。

数据来源：server/data/qa/qqbot.sqlite，2026-09-25 至 2026-10-28；代码：server/src/main/java/com/example/qqbot

结论

先给三句话，后面都是展开。

一、你们的问题不是"分类不准"，是"只允许一种答案"。所有非斜杠消息都走同一条链：检索 → 注入资料 → 按"以资料为准"作答。产物形态只有一种。于是"给我推荐一套毕业装"和"珍珠在哪"得到同一个形状的回答，前者注定落在"资料里没查到"。

二、该补的不是分类器，是三个缺口。一个"可以先问一句"的出口、一段三轮的会话记忆、一份把"建议类"当合法产物的契约。三样都比分类器便宜，而且直接对应日志里能看到的失败。

三、视频里那四种方案是阶梯，不是并列选项。按你们 17 问/天、0 条人工标注的量级，微调和 RAG 分类都还在山脚以下；结构化工具调用你们已经有了，缺的是提示词契约和规则层。

一条消息进来之后发生的事，决定了"意图"这件事在代码里有没有位置。

三条代码事实值得单独点出来，它们直接决定了后面方案怎么选。

意图判定散在四处，词表已经开始漂移

同一个"这句话是不是在问位置"的判断，现在有四份实现：

位置用途关键词表
kb/PlaceIntent「X 有什么」聚合提问有什么 / 里面有什么 / 都有什么…
KbLookupTool.wantsLocation决定要不要附带地图分布在哪 / 哪里 / 分布 / 获得 / 挖
ChatService.wantsResourceShot决定要不要补一张资源图在哪 / 哪里 / 位置 / 采 / 找 / 比较多
VoiceTriggerService关键词触发语音各自一套

两份"位置意图"词表已经不一致：「挖」只在 KbLookupTool，「采」「找」「比较多」只在 ChatService。所以"这玩意在哪挖"和"这玩意哪里比较多"会走不同的附带逻辑。这不是靠调提示词能修的，得先把判定收成一处。

没有会话状态，引用是唯一的上下文

ChatService.buildUserMessage 拼进信封的只有：场景、群号、发言者、引用内容、资料块、本轮正文。上一轮问了什么、你答了什么，模型看不到。群里 41% 的提问是三分钟内的追问，这类问题（"那你说的这个她""不是 185 吗"）在结构上就接不住。

工具里没有"问一句"这个动作

五个工具全是"查"和"说"。遇到指代不明，模型只有两条路：硬猜一个具体答案，或者答"资料里没查到"。它没有第三条路——先问一句"你说的是哪个"。这不是模型笨，是动作空间里没这个动作。

四个根因

根因表现为什么光调提示词不够
回答契约只有一种产物建议类、闲聊类、边界外请求都被塞进"查资料"这个模具模型只能在"资料里有什么"里组织语言，没有"给结论"的授权
没有会话状态追问、纠正、省略主语全部按新问题处理提示词里没有可用的历史，写多少遍"注意上下文"都没用
没有澄清动作歧义被硬压成一个具体答案，且答得很自信动作空间里没有这个动作，只能靠"请不要乱猜"这种软约束
本地实体没有身份群友昵称撞上现实同名物，模型用通用知识补知识库里没有"碧潭飘雪=本群群主"这条事实，模型只能猜

四个方案的适配

视频里那四种做法本身没错，错在把它们当成并列选项。它们其实是一条按"标注量 → 意图空间 → 时延预算"递增的阶梯，你们现在站在最低一级。

方案它真正解决的问题在你们项目里的成本判断
结构化 Function Call 让模型在动作空间明确时选动作、填参数 AiServices 工具链现成，加一个工具约一百行 现在做
要加的是"判"的工具，不是"查"的工具
提示词分类 让模型读一份清单再决定走哪条路 system.md 已 74 行，且承载安全底座 改造后使用
不列意图清单，只写三条决策准则
RAG 分类 意图空间很大时，用检索压缩上下文 你们真正的分类维度只有五六类；术语表和标题向量已经在做类似的事 不做
重复建设，且没有标注集可喂
微调小模型 高 QPS、分布稳定、迭代不频繁 17 问/天，0 条标注，游戏版本按月变 不做
现在做等于先给自己造一个维护负担

为什么"加分类器"在这个项目里不是第一步

分类器解决的是"在多个已有分支里选一个"。你们现在只有一个分支。就算分类准确率 95%，产出仍然是"一段基于资料的回答"或"资料里没查到"——因为下游没有第二种产物可路由。先把产物扩成三种，再谈选得准不准，顺序不能反。

另一个细节：ReplyMode 的注释里已经写下了正确的哲学——"由指令显式指定，不让模型自己猜"。这个判断用在"要不要用知识库"上是对的，只是它只用到了一个维度。把它扩成"这次要哪种产物"，是同一套思路走第二步，不是推翻重来。

建议方案

三层，按投入产出排序，每层都能独立上线、独立回滚。处理链示意图。

L0 规则层：零 token，先吃掉 40% 的确定性情况

新建 com.example.qqbot.intent，一个 IntentSignals 组件，把散在四处的关键词判定收进来，并在进 ChatService 之前给出一个信号。

信号判据动作
裸名词整句 ≤10 字、无疑问词、无动词实体卡：是什么 + 怎么获得 + 在哪，一次说完。不反问
纠错不是…吗 / 又说错 / 明明 / 我说的是 / 不对读上一轮答案，只改被指出的那一点，不重新全量检索
社交整活卖萌 / 叫我 / 唱 / 女装 / 亲亲 / 抱抱不检索，≤40 字
元问题你是谁 / 有什么能力 / 什么模型 / 你是机器人吗固定事实，不检索
边界外帮我上班 / 生成视频 / 发照片 / 下单一句拒绝 + 一条替代，不解释规则
命令误用/stats 啥时候1.0 这类命令带尾巴命令成功就执行，剩下半句当追问

裸名词为什么不反问：群里问"香菇"的人，想要的就是三句话。反问在群聊里成本极高，能用一个默认答案补齐就不要问。这条也解释了为什么"澄清"只能作为最后手段。

L1 契约层：改一段提示词，不增加调用

核心是把"资料里有什么"从唯一产物降级为三种产物之一。下面这段可以直接接在 system.md 的"资料怎么用"之后。

## 先判断这次要什么

回答之前在心里分一次类，不要把这个判断说出来。

**事实类**：某个东西是什么、在哪、怎么获得、多少级、掉什么。
只用资料里的事实。资料没有就说没查到。

**建议类**：推荐、搭配、评价、哪个强、怎么选、值不值得。
可以给结论和排序，这是你的判断，不是资料：
- 先把资料里能支撑的事实说清楚，比如等级、属性、获取难度
- 再给结论，一句话说清为什么这么选
- 资料不够支撑判断时，写"资料里能确定的是 X，剩下的这是我的看法"
- 不要用"资料里没查到"给建议类问题收尾

**社交类**：卖萌、吐槽、开玩笑、问你是谁、让你做做不到的事。
一句话，不超过 30 字，不查资料，不长篇解释。

## 什么时候可以先问一句

只有一种情况：不知道对方在说哪个东西，而且猜错的代价比多问一句大。
比如"那个怎么获得""它在哪里"，而上一轮没有对应的东西。

问的时候只问一句，给两三个候选，别问"你是什么意思"。
同一轮只问一次。对方没回话，就按最可能的那个直接答。

这两段加起来 24 行。它替代的是现在"没查到就说没查到"这条万能兜底——那条兜底对事实类是对的，对另外两类是全错。

L2 会话层：数据已经在了，只差一张表

chat_message 表已经在存群消息，缺的是"bot 上次答了什么"。加一张小表，只保留最近几轮，按群 + 人隔离。

CREATE TABLE qa_turn (
  id            INTEGER PRIMARY KEY,
  group_id      INTEGER NOT NULL,
  user_id       INTEGER NOT NULL,
  ts            TEXT    NOT NULL,
  question      TEXT    NOT NULL,
  answer_digest TEXT    NOT NULL,   -- 一句话要点，≤60 字
  subject       TEXT,               -- 本轮主体：香菇 / 渔夫 / 技能点
  corrected     INTEGER DEFAULT 0
);
CREATE INDEX qa_turn_scope ON qa_turn(group_id, user_id, ts DESC);

信封里加一段，最多三轮：

<<<RECENT
上一轮
  你问：现在技能点上限是多少
  我答：目前是 10 点，满级……
  备注：对方说「不是185吗」，这可能是纠正
RECENT>>>

关键约束：最近三轮只进信封，不进检索 query。ChatService 已经把"给模型的消息"和"用于检索的问题"分开了，这个边界刚好用来隔离——否则历史会稀释查询向量，还会污染术语匹配，而且不报错。

L3 预判：可选，只在两层都不确定时才出场

不做成前置路由，做成"低置信时的第二意见"。触发条件三选一：规则层未命中、检索最高余弦低于 0.45、术语表一个都没命中。

{"move": "fact|advise|social|meta|clarify|out_of_scope",
 "subject": "香菇",
 "subject_state": "explicit|context|missing|ambiguous",
 "why": "只打了物品名，没有动词和疑问词"}

温度 0，限 120 token，结果按"群 + 归一化问题"缓存 5 分钟。一次约 200 token，只覆盖低置信的那部分。这一层不实现也不影响前两层成立。

落地顺序

迭代工作量改哪里验收
0 埋点半天 qa_stat 加四列：判定来源、是否澄清、是否纠正、是否检索；跑一遍自动打标得到基线 历史 553 条能回放，基线指标落表
1 规则层1–2 天 新建 intent 包；合并四处关键词；裸名词走实体卡 裸名词类回答 ≤120 字，检索调用下降；wantsLocation 两份合并成一份
2 契约层1 天 system.md 加两段；问答记录里区分三类产物 建议类不再出现"没查到"；社交类平均长度 ≤40 字
3 会话层2–3 天 qa_turn 表；buildUserMessage 加 RECENT 段；纠错通道 三分钟追问率从 41% 降到 30% 以下
4 预判按需 IntentSignals 低置信分支接一次小调用 低置信样本上人工抽检准确率 >80%

迭代 0 和 1 加起来两天，能覆盖掉裸名词、社交、元问题、边界外这四类——按分桶占全部提问的 40% 左右，而且这四类今天都在消耗完整的检索 + 模型预算。

怎么量

QaAnalytics 已经有 overview、keywords、misses、余弦分布、verdicts 五个视角，唯独 verdicts() 一直在空转：59,639 行全是 unknown。标注这件事不必等人，先从日志里自动推。

信号规则落到哪
疑似答非所问3 分钟内同人再问，且含"不是 / 错 / 没答 / 我说的是"verdict=bad
疑似不满意3 分钟内同人再问，且换了主体verdict=retry
疑似满意3 分钟内出现"谢谢 / 懂了 / 好 / 牛"verdict=good
其余不做推断verdict=unknown，不进正样本

自动标噪声不小，估计两三成，但足够做相对比较：改了提示词之后 bad 的比例是升是降。绝对准确率靠每周人工抽检 30 条补。

四个主指标，改之前先记下来：

指标现在目标
三分钟内追问率40.7%< 30%
回答含"没查到"占比20.4%< 12%，建议类 < 5%
社交类平均回答长度108 字< 40 字
每千问的检索次数1000< 750

不要做的

  1. 不要做成"分类 → 路由到不同 sub-agent"。你们只有一个回答者。多一层路由就多一处出错点，而且每个 sub-agent 都得重新接一遍安全底座、工具白名单和预算。
  2. 不要把意图标签写给用户看。"我理解您想问……""为您匹配到意图：事实查询"，在群里非常掉分。判断留在内部。
  3. 不要用一次模型调用来决定"要不要检索"。术语命中 + 检索最高分已经能挡掉大部分，剩下的才交给模型。两次调用的时延和成本都比一次高，而 41% 的对话本来就是追问，时延敏感。
  4. 不要为了分类继续加长 system.md。它现在是安全底座 + 资料规则 + 说话方式，74 行已经到边。分类逻辑要么写在代码里，要么压缩成三条准则。

面试怎么讲

这段分析比背四个方案的对比表有用得多，因为它有数据、有取舍、有放弃。

  • 现象：30 天 553 条提问，20% 以"资料里没查到"收场，41% 的对话是三分钟内的追问。
  • 归因：不是分类器不准。是回答契约只允许一种产物，加上没有会话状态接不住追问，加上动作空间里没有"问一句"。
  • 方案：规则层吃掉名词裸问和纠错，契约层把产物分成事实 / 建议 / 社交，会话层补三轮窗口，分类模型只在低置信时作为第二意见。
  • 取舍：为什么不做微调——0 条标注、17 问/天、游戏版本月更，训出来的模型三个月就过时。为什么不做 RAG 分类——真正的分类维度只有五六类，术语表和标题向量已经在干类似的事。
