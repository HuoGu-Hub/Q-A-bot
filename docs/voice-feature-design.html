Design / Voice Reply

语音回复与素材库

关键词直发、上传自家音频、大模型可调用的语音工具，以及 TTS 在其中的位置。

一句话结论：语音回复走三条入口 —— 关键词命中直接发素材、大模型判断后调工具发素材、TTS 现场合成。三条都收敛到已有的 VoiceSender，发送只有一条出口。

TTS 的定位：edge-tts 只当「随时能用的免费兜底」，不当主引擎。要稳定就换 Azure 或国内云；要离线就在宿主侧跑小模型。

工具的关键设计：工具不直接发，只把「要发哪一段」放进本次请求的待发队列；文字与语音谁先谁后随机，避免每条都一样。

01TTS 选型：还有哪些路

先把结论摆在前面：你的服务器跑不动本地大模型。部署文档里那台是 2GB 内存的 Debian，而 2026 年的中文 TTS 基本都要 4GB 以上显存。所以只有两类现实选择：云 API，或者把 TTS 放在另一台机器上跑。

方案在哪跑中文质量联网成本适合
edge-tts任意机器，20MB 依赖自然，8 个 zh-CN 声线每次都要免费日常、兜底
Azure Speech云与 edge-tts 同一批声线每次都要按量付费要稳定的正式环境
阿里百炼 CosyVoice / MiniMax国内云好，低延迟每次都要按量付费国内网络、合规
Qwen3-TTS本地 GPU中文优先，支持克隆离线自有算力有显卡的机器
CosyVoice 3本地 GPU150ms 级流式，18+ 方言离线自有算力实时对话
Fish Audio S2 Pro本地 GPU高保真多语言离线建议 24GB 显存配音级内容
Kokoro-82MCPU 可跑够用，情感弱离线免费轻量兜底
PiperCPU一般离线免费纯离线、嵌入式
GPT-SoVITS本地 GPU音色克隆，几十秒样本离线自有算力要「某个人的声音」

本地模型这一年的进步主要在中文自然度、流式延迟和克隆，代价是显存。你的开发机是 RTX 3050 4GB，CosyVoice 0.5B、Kokoro 这类能跑；那台 2GB 的服务器只能当客户端。

建议的降级链

主：edge-tts         免费、够自然、现成
备：Azure / 国内云    要稳定、要合规时换
底：Kokoro / Piper    断网、或云端限流时兜底
终：纯文字            合成失败绝不静默，退回文字回答

四层都实现同一个接口，配置里换一个 provider 就能切，发送链路完全不动。

三条入口的优先级是固定的：

  1. 关键词只决定「这条回复必须是语音」，不决定说什么。命中后照样问模型，只是给它加一条硬约束。
  2. 大模型自己挑内容来源：从素材库里放一段现成的，还是让 TTS 现场说一句。
  3. TTS 是内容来源之一，也是模型不合作时的兜底。

03关键词：只决定「要不要语音」

这是和你确认过的语义：关键词不绑定内容。命中之后，回什么、用素材还是用 TTS，全部交给模型。一个关键词因此可以对应任意多种回答。

voice_trigger(
  id, keyword, match_type, priority,
  cooldown_seconds, group_scope, enabled, note, created_at
)
匹配全角转半角、去空白后做包含匹配；同一句命中多条时取关键词最长的那条
命中后给这次请求打一个 voice-required 标记，正常进模型，不做直发
冷却按「群 + 规则」计，默认 120 秒，防止刷「唱首歌」
作用域空 = 所有群；填群号 = 只在指定群生效
额度复用现有的每人每分钟限流，不另开一套

默认三条：唱首歌 / 唱歌 / 来一首、喵 / 叫一声、晚安。它们只负责「触发语音」，素材和台词由模型临场决定。

04素材库与上传

这是你说的「有个地方上传歌曲录音」。文件落盘，元数据进库，后台一页管理。

voice_asset(
  id, title, aliases, tags,
  sha256, file_name, mime, size_bytes, duration_ms,
  enabled, created_at, play_count, last_played_at
)
目录server/data/voices/，文件名用内容哈希，天然去重、永不覆盖
上传multipart，单文件 ≤ 8MB，用 ffprobe 量时长，超过 5 分钟直接拒
转码原文件保留，发送时才转 24kHz mp3 —— 歌曲留着原音质，试听才有意义
试听GET /admin/api/voice/{id}/audio，走会话鉴权，直接给浏览器 audio 标签
试发POST /admin/api/voice/{id}/send，指定群号，立刻收到一条语音

后台页面就三块：拖拽上传、列表（时长 / 大小 / 标签 / 启用）、每行的「试听 / 发到群 / 删除」。上传后立刻可用，不需要重启。

05给大模型的工具

给模型两个工具，让它自己选内容来源：

@Tool("从语音素材库挑一段现成的发到当前聊天。query 可以是曲名、标签或描述。")
String playVoice(@P("曲名或描述") String query);

@Tool("让机器人现场说一句话。适合没有现成素材时。文字不超过 80 字。")
String say(@P("要说的话") String text);

两者都不直接发送，只把「要发什么」记下来，原因见下面「顺序」。

模型不合作怎么办

命中关键词但模型没调任何语音工具时，兜底是：把这次回答的文字截到 80 字，用 TTS 说一遍。语音回复是用户明确要的，不能因为模型忘了就静默降级成纯文字。文字本身仍然正常发出。

目标从哪来

不解析 caller 字符串。调用助手时把三个参数放进 InvocationParameters：tool.group_id、tool.user_id、tool.message_type。工具从 InvocationContext 里读，取不到就拒绝发送。

为什么不在工具里直接发

工具在模型生成过程中执行，直接发会把顺序钉死。正确做法是把意图放进本次请求的待发队列，等回答文本生成完，再按一次随机结果决定谁先谁后：

ChatService 造一个 MediaOutbox，塞进 InvocationParameters
  → 工具查素材或合成，outbox.add(voiceIntent)，返回"已安排"
  → 模型正常生成文字
  → 路由掷一次硬币：文字先，或语音先
  → 按这个顺序把两样都发出去

随机顺序是为了别每条都像模板：有时先甩一句语音再接文字，有时反过来。代价很小，观感差别很大。

授权与预算

  • 加进 KbToolAssistant.ALLOWED_TOOLS，默认拒绝的规矩不变。
  • 复用 ToolBudget：一次请求最多 3 次工具调用，语音工具算一次。
  • 工具只能读库，永不接受文件路径或 URL，避免被提示词诱导读服务器任意文件。
  • 目标固定为当前会话，模型无法指定别的群。

以后扩展成通用媒体工具

把工具名从 play_voice 扩成 send_media(kind, query)：kind 取 voice / image / file，每种类型一个素材库、一条发送通道。今天的 MediaOutbox 已经按「有序意图列表」设计，加类型只是多一种 MediaIntent。

位置新增内容

ArchUnit 的 14 条规则继续成立：voice 不碰 OneBotApiClient、不 import config、不直接读写 SQL；发送仍然只有 OutboundSender 一个出口。

07分阶段落地

P1 · 素材库 表、上传接口、后台页面、试听与试发。做完你就能把歌曲传进去、手动发一条。约 1 天
P2 · 关键词标记 触发规则表、匹配与冷却、把 voice-required 标记交给模型。做完喊「唱首歌」模型就知道必须用语音回。约半天
P3 · TTS SpeechSynthesizer 接口 + edge-tts 实现 + 磁盘缓存 + 降级到文字。约 1 天
P4 · 工具 play_voice + MediaOutbox + 白名单 + 回答后发送。约 1 天
P5 · 泛化 图片与文件走同一套工具与队列。按需

08风险与约束

  • 版权：歌曲只在你有权使用的范围内传。工具只读库，但库里的东西是你放的。
  • 刷屏：关键词冷却 + 每人限流 + 一条回复最多一段语音，三道闸都要有。
  • TTS 依赖：edge-tts 是逆向接口，微软随时可能改；必须能一键切 Azure，且失败退回文字。
  • 服务器：2GB 机器不跑本地模型；如果 TTS 放宿主，注意机器人服务和它的可达性。
  • 工具滥用：只允许当前会话、只读素材库、不接受路径，三条缺一不可。

09已定与待定

已定TTS 用免费 edge-tts

已定内容来源交给模型：素材库或 TTS

剩下两个细节可以边做边定：关键词冷却默认 120 秒够不够；TTS 兜底是否要把回答截到 80 字。
