铜矿定位问题排查

结论：猜测 1 成立，猜测 2 不成立。 locate 查不到「铜矿」——1703 个地点里没有一条含「铜」或「矿」； 那张图是知识库里「铜矿石（Copper Ore）」词条的物品图标，不是地图截图失败后的兜底。 代码里也不存在「截图与图标冲突、只留图标」的分支。

一、现场实测

直接用线上那份数据调机器人同款接口（/api/public/map/locate，与 locate 工具同一份算法）：

查询词结果

数据侧复核：启用地图的 1703 个地点中，名称、别名、备注含「铜」或「矿」的都是 0 条；含英文 mine 的有 29 条。 中文「铁矿 / 银矿 / 金矿 / 煤炭」同样 0 条——这不是铜矿一个词的问题，是所有「某矿」中文问法都查不到。

二、wiki 点位是怎么走通搜索与截图的

wiki「Map:」命名空间 32 页
→ KbMapSyncService 解析成 kb_map_marker：每行一个具名地点，带 page / markerId / 分组 / 名称 / article / 描述 / 坐标
→ WikiPlaceDirectory 现场拼 PlacePoint：中文名、区域、分类、ref = page#markerId
→ locate 子串匹配 → PlaceAnswer 算最近地标与方位
→ 命中后追加 [[img:map:page#markerId]]
→ MapShotSource 用同一个 key 回查 marker，拿画布、坐标、分组图标 → 渲染瓦片 + 图标 + 红圈

另外还有一条并行的：LocationCorpusBuilder 把 marker 按 article 聚成 83 个「地点」块，块尾也带 [[img:map:...]]。 所以就算模型不调 locate，资料注入或 lookup 也能把地点和截图带出来。

这套链路成立的前提是 marker 行同时具备四样东西：身份（page#markerId）、词条（article → 中文名/分类）、分组（grp → 图标）、坐标。wiki 的 marker 四样全有。

三、mod 资源点为什么没有同样生效

它不是同一类数据。mod 的 points.json 经 MapResourceImporter 落成 kb_map_resource：

wiki 点位mod 资源点
表kb_map_markerkb_map_resource
数量170336126（112 层；铜 747、铁 1398）
身份page#markerIdsource_id，如 p:874，没有 page

图标grp → Mine.png没有图标，网页按颜色画圆点
消费方locate、截图、地点语料只有公开站/管理端地图接口

接线只存在于网页这一侧：MapResourceService 被 PublicMapController 和 AdminMapController 注入， MapView.vue 按层拉点、MapCanvas.vue 画点。机器人这一侧的 PlaceDirectory、MapShotSource、 LocationCorpusBuilder 没有任何一处读 kb_map_resource。

所以不是「搜不到」或「截图坏了」，而是这批数据从导入那天起就没进问答链路。提交 c7649cf 改的是 web / public API / 管理端，没有动 KbLookupTool 和 MapShotSource。

四、为什么不能直接把资源点塞进 marker 表

  • 答法不对：PlaceAnswer 是「几个同名地点，按距离列 5 条」。747 个「铜」会变成 5 条一模一样的坐标，回答不了「哪里密集」。
  • 身份对不上：截图协议是 [[img:map:page#markerId]]，资源点没有 page 和 markerId，MapShotSource 回查不到。
  • 画法不对：现有截图是「一个目标点套红圈 + 邻近地标名字」，资源层要的是「一层点云」；两种图的取景和画法不同。
  • 体量不对：36k 行是 1703 的 20 倍，目录每次调用都重建，语料派生也会被灌进上千条近似块。

坐标本身不是问题：网页上 wiki 图标与资源点是叠在同一张底图上的，说明两套坐标已经对齐。缺的是「按层聚合 + 聚类 + 资源层截图」这层适配。

五、图标是从哪来的

知识库块 wiki-copper-ore 的正文末尾带着：

[[img:wiki:copper-ore/copper-ore.png]]

  • 图片文件存在：server/data/wiki-images/copper-ore/copper-ore.png（44 KB，物品图标）；
  • 检索「铜矿」时，前五条里出现两次「铜矿石（Copper Ore）」，标题向量闸门以 0.770 把 copper-ore 置顶；
  • 资料注入与 lookup 都会把标记提到块尾单独一行（TwoSectionInjector.java:57、KbLookupTool.java:89）；
  • 提示词明确允许「看到标记就原样抄进回答」，于是模型抄了图标标记。

这条链路不需要模型调用任何工具，注入的资料里就已经有图标凭据。

六、为什么不是「截图与图标冲突」

  • 图片标记逐个独立解析（ImageLibrary.java:69），一条回复上限 2 张，互不替代；
  • 截图失败只有一种表现：MapShotSource 返回空、该 map: 标记被丢弃，日志记 [MAP-SHOT] … 本次不出图，不会改发图标；
  • 而这次 locate 没有命中，连 map: 标记都没生成，谈不到冲突。

七、日志上怎么确认

  1. 搜该次回答前后的 [TOOL] 放行工具 locate：参数就是模型传的地名；
  2. 搜 [MAP-SHOT]：一条都没有 = 截图没被触发（本次情况）；有「缺瓦片 / 超预算」= 尝试过但失败；
  3. 搜 [IMG] 丢弃图片标记 map:：出现才说明截图标记生成后被丢弃。

八、修复方向

A新增资源层适配器：中文名/别名 → layer（铜矿 → ore:copper），对点做网格或 DBSCAN 聚类，取最密的几簇给区域、最近地标、点数；再新增一种资源层截图，按簇的包围盒画点云。这是能真正回答「哪里密集」的做法。

B只补文字：同样聚类，先只回「铜矿最密的一片在××区域，坐标……」，不承诺截图。

C只补别名：给地点目录补「Mine → 矿坑」。只能让「矿井在哪」有结果，回答不了铜矿，且会截到随机一个矿点，不建议单独做。
