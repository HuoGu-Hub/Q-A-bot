Change Propagation (R2) — 视觉问答的图片根本到不了模型已实测复现

Symptom: KbToolAssistant.Assistant.chat(@UserMessage dev.langchain4j.data.message.UserMessage, InvocationParameters) 声明在 KbToolAssistant.java:77，由 chatWithImages 传入多内容消息，见 KbToolAssistant.java:200-203。但 langchain4j 只把带 @UserMessage 的参数当模板：DefaultAiServices.getUserMessageTemplate 走 InternalReflectionVariableResolver.asString(arg)，对非 Content 参数取的是 arg.toString()，见官方源码 DefaultAiServices.java:1628。用官方 1.20.0 的 jar 加与生产同构的 augmentor 实测，模型收到的是：contents=1，唯一一条 TextContent 的正文为 UserMessage { name = null, contents = [TextContent { text = "...", ImageContent { image = Image { base64Data = "QUJD", ...，图片被当成文本内联，ImageContent 一个都没到模型。而且这个过程不抛异常，所以 ChatService.java:138 的兜底也不会触发。官方文档列出的合法签名只有 @UserMessage String 配 @UserMessage List<Content> / List<ImageContent>，没有 @UserMessage UserMessage 这一种。
Source: Hunt & Thomas — The Pragmatic Programmer: Programming by Coincidence · McConnell — Code Complete, Ch.8 Defensive Programming · Winters et al. — Software Engineering at Google: Hyrum's Law
Consequence: 所有带图提问都会走进这条分支。后台单张图上限 12MB、实测截图 6.27MB，base64 会以文本形式塞进提示词正文，单条请求轻松上百万 token：要么被服务端按超长拒绝，要么答非所问；即便侥幸不超限，模型也完全看不到图。更麻烦的是这次调用在问答记录与检索统计里看起来是「正常回答了一次」，故障不体现在数据里。上一版的视觉路径直接构造请求，不存在这个问题，是接入官方管线的这次重构引入的。
Remedy: 改成官方支持的形状：String chat(@UserMessage String envelope, @UserMessage List<ImageContent> images, InvocationParameters params)，chatWithImages 分别传信封文本与图片列表。这样 augmentor 拿到的 originalUserMessage 是纯文本，singleText() 正常，KNOWLEDGE 注入后 addContentsToUserMessage 会把 List<ImageContent> 合并回去，见 DefaultAiServices.java:1663-1702，图片与资料同时到位。改完必须补上断言「模型收到的消息里含 ImageContent」的测试，见下一个 finding。

Dependency Disorder (R5) — kb 核心与 kb.term / kb.block 三处互相依赖

Symptom: kb/Glossary.java:3 import kb.term.KbTermStore，每次回答都要用的热路径依赖了管理端词条存储；反向，kb/term/KbTermService.java:66,79,290 直接持有 com.example.qqbot.kb.block.KbBlockStore，而且是全限定名、不写 import，另有 kb.category.CategoryService 依赖 kb.KbCorpus。于是形成三条环：kb → kb.term → kb、kb → kb.term → kb.block → kb、kb → kb.term → kb.category → kb。项目已有 12 条 ArchUnit 规则，其中 kbCoreDoesNotDependOnIngestSources 只管 kb.wiki / kb.map 的方向，没有任何一条管 kb ↔ kb.term ↔ kb.block。
Source: Martin — Clean Architecture: ADP Acyclic Dependencies · SDP Stable Dependencies · Ousterhout — A Philosophy of Software Design, Ch.5 Information Hiding
Consequence: 检索核心无法脱离词条层、管理端与持久化单独编译或测试。Glossary 是纯本地、零成本、每次回答都要用的组件，现在它的任何一个测试与重构都被拖上 SQLite 依赖。全限定名写法让按 import 扫描的工具看不到这条边，下一个人排查依赖时会先被误导。
Remedy: 在 kb 侧为 Glossary 声明一个只读的 TermSource，由 kb.term.KbTermStore 实现，依赖方向变成 kb.term → kb；把 KbTermService 里只读的块视图搬到 kb.block 侧的查询服务，消掉 term → block 这条边；把全限定名改回正常 import，并补一条「kb 核心不得依赖 kb.term」的 ArchUnit 规则防退化。
Severity note: 按 R5 的 severity guide，存在依赖环默认判 Critical；此处降为 Warning，理由是三条环都在同一个 bounded context 内部、不产生运行期风险，代价集中在维护性与「能不能单独测」，属于下一个功能周期内会显露而不是今天就在流血的类型。
