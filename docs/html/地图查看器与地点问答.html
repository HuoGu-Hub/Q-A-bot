地图查看器与地点问答

设计说明与运维手册 · 公开站 /map + 管理端 /admin/map + 大模型 locate 工具

项目：飘雪喵问答机器人　｜　底图与点位来源：enshrouded.wiki.gg（CC BY-NC-SA 3.0）

一、这一版做了什么

能力入口说明
全地图查看器公开站 /map与 wiki 同源的底图与 1703 个点位；canvas 打点、CSS transform 平移缩放、缩略图分级
找地方公开站 /map 左侧搜索输入「铁矿」，给出它相对最近地标的方位、距离、坐标，并在地图上画出方位线
地图管理端 /admin/map点地图空白处新增点位（名称/分类/备注/别名/是否地标/是否公开）；点 wiki 点位补中文名与说明
大模型工具locate问「哪里有铁矿」时由模型调用，拿到**算好的**方位描述而不是让它自己猜
运维入口管理端「同步与状态」触发 wiki 同步与地点语料派生；查看画布、页、缓存与任务状态

二、怎么用起来

# 1. 重启后端（新接口与新表要加载）
# 2. 管理端 → 地图 → 同步与状态 → 「同步 wiki 地图」
#    首次约 7 秒：32 页 / 1703 个点位 / 0 失败
# 3. 打开公开站 /map
# 4. 管理端 → 地图 → 在地图上点一下，起个名（例如「铁矿」），保存
# 5. 回公开站搜「铁矿」，或在群里问「哪里有铁矿」

同步是增量的：只拉 revid 变过的页，常态下几乎瞬间完成。 底图瓦片按需从 wiki 拉取并缓存在 server/data/map-tiles/，同一张只下一次。

三、数据模型

在原有的三张 wiki 镜像表之外，新增三张。全部是 ADDITIVE DDL（CREATE TABLE IF NOT EXISTS），不删列不重建 —— 生产库是活的。

3.1 kb_map_canvas　画布

回答「这张图怎么铺」。主键 (map, page)。

为什么画布按页面存，而不是一张地图一条。 实测同名地图内部存在多套坐标系：Map:Embervale/Main 的 crs 是 (0,10240)→(10240,0)， 而 Map:Embervale/Collectibles 是 (-3695,-9045)→(6545,1195)。 按地图只存一个，另一批点位会整体偏移上万像素。

同步实测落库 30 张画布，其中 Embervale 恰好分成两组坐标系。

3.2 kb_map_place　管理员自定义点位

字段：map / page / x / y / name / aliases / category / note / icon / color / landmark / priority / visible / created_at / updated_at。

为什么不复用 kb_map_marker：那张表是「wiki 某一页的镜像」，同步时按页先删后插。 管理员辛苦标的地点会被下一次同步静默清掉。写入方不同的数据必须分表。

3.3 kb_map_marker_note　wiki 点位备注

主键 (map, page, marker_id)，与 kb_map_marker 同形 —— 于是同步既不会丢备注，也不需要知道备注的存在。

用途：给 Ancient Spire 补「远古尖塔」、写「离出生点最近的那个」、把它提升为方位参照、或整条隐藏。

四、后端结构

摄入（kb/map）　wiki JSON → 解析 → 三张镜像表 + 画布表
　　　　　　　　　　　wiki 图片 → MapImageCache 磁盘缓存（按需、分级缩略）
领域（kb 核心）　PlaceDirectory 契约 · RelativeLocation 算法 · PlaceAnswer 组装
出口　/api/public/map/**　｜　/admin/api/map/**　｜　工具 locate

为什么核心要摆一个接口

ArchitectureTest 有一条转正规则：kb 核心不得依赖摄入来源（wiki / map）。 而调用地点数据的工具住在核心 —— 直接 import kb.map 会让构建变红。 所以照 TermSource / KbCorpus 的既有做法：契约由消费方定义，实现由生产者提供。 kb.PlaceDirectory 是契约，kb.map.WikiPlaceDirectory 是唯一实现，Spring 负责注入。

相对位置算法（RelativeLocation）

  1. 方向：atan2(dx, dy) 分八扇区。地图正北朝上，所以罗盘方位与屏幕方位天然对齐 （东北 = 地图右上角）。两个说法都给 —— 玩家盯着地图想的是「右上角」。
  2. 距离：除以地图对角线归一化后分档（就在旁边 / 很近 / 不远 / 有点远 / 很远）。 同样的 800 单位在黑沼是横跨半张图，在余烬谷只是隔壁。
  3. 锚点：先排掉自己、优先同画布、优先地标；打分是「距离比例 × 10 − 名望」， 名望上限 1.0 —— 距离是主因，名望只在同级里做偏好。

关于「米」：默认不输出。 wiki 的 x/y 是游戏坐标系，公开资料查不到 1 单位等于多少米。 凭空写「约 800 米」会被大模型当成事实转述给群友 —— 那比不给距离更糟。 所以默认只给坐标单位与相对量级；确证比例后改一个配置即可： app.kb.map.units-per-meter。

五、接口

公开只读（按 IP 限流）

方法路径用途
GET/api/public/map/catalog地图 + 画布 + 图层定义
GET/api/public/map/markers?map=该地图全部点位（wiki + 本地，已合并为同一形状）
GET/api/public/map/search?q=按名称 / 别名 / 备注搜
GET/api/public/map/locate?q=相对位置描述：方位、距离、参照物、成句文本
GET/api/public/map/tile?map=&page=&name=&w=图片字节（缓存 + 白名单）

图片接口不走限流：一次打开地图就是几十个请求，走限流会让页面直接打不开。 它靠资源白名单兜底 —— 只放行确实属于我们地图数据的文件名（画布瓦片、底图整图、分组图标）， 否则这台机器就成了 wiki 的免费图片代理。宽度同样有白名单，防止 ?w= 任意值把缓存目录灌满。

管理端

方法路径用途
GET/admin/api/map/status存储 / 画布 / 页 / 缓存 / 长任务
GET/admin/api/map/places全部本地点位（含隐藏）
POST / PUT / DELETE/admin/api/map/places[/{id}]新增 / 修改 / 删除
GET / POST / DELETE/admin/api/map/noteswiki 点位备注
POST/admin/api/map/sync触发同步（后台跑，立即返回）
POST/admin/api/map/corpus派生 / 清除地点语料

两个长任务不在请求线程里跑：首次同步几秒、语料派生要上百次向量调用， 在 HTTP 里跑会被某一层超时掐断，而任务其实还在跑 —— 管理员会再点一次。 现在立即返回，进度看 /status 的 jobs。

六、前端为什么比 wiki 那份流畅

wiki 卡顿的根因这里的做法
一千多个 marker 是 DOM 节点，每帧重算样式与重排marker 画在一张 canvas 上；DOM 里只有底图容器与 canvas 两个节点
每帧给几十个瓦片写 left/top，触发布局瓦片放进一个 transform 容器，平移缩放只影响合成层，交给 GPU
指针事件里直接改样式，一帧改上百次rAF 合帧：指针只写目标值，绘制与 transform 统一在下一帧提交
一次性把整张图的瓦片与全部图标塞进视野视口裁剪 + 缩小时画圆点不画图标（细节分级）
缩到最小时仍拉 10240×10240 的原图缩略图分级：按瓦片在屏幕上的实际尺寸选 ?w=160/320/640/1280，由 MediaWiki 自己缩

另外，公开端与管理端复用同一个画布组件（web/src/shared/map/MapCanvas.vue）， 差别只在 mode：浏览模式点击弹详情，编辑模式点击落点。 坐标换算抽成纯函数 mapMath.ts，两端不会算出两个位置。

七、刻意的取舍

决定理由
不输出米比例查不到；编一个会被当成事实转述
地点语料不追加相对位置行改语料正文会改向量，进而动到既有检索黄金集的门槛。方位由 locate 工具确定性提供，不经过向量
隐藏的点位也不参与问答否则「藏起来」只是看不见，仍然会被说出来
画布按页面存同地图多套坐标系是实测事实
截图与相对位置算法都是纯函数能被单元测试钉死，而不是「跑一次看着对」

八、已知边界

  • 坐标 → 米的比例未确证。需要一次游戏内实测（读两个已知点位的坐标与格子距离）， 拿到后填 app.kb.map.units-per-meter。
  • 资源点要靠人工标：wiki 上没有铁矿、树脂这类点位，正是「管理员在地图上点一下」要补的那部分。
  • 底图版权：瓦片来自 Enshrouded Wiki（CC BY-NC-SA 3.0），页脚已保留署名； 本站只做缓存，不重新分发为独立资源。
  • 点位的纠错通道：目前只有管理员能改。群友提案（复用 kb_proposal）尚未接。
