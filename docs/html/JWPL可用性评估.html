JWPL 可用性评估

对象：org.dkpro.jwpl:dkpro-jwpl-parser:2.0.0。全部结论来自在本机跑的四个实验，脚本与结果留在 .toolchain/jwpl-spike/。日期 2026-10-11。

结论：能用，但不该拿来当清洗器的替代品。它的解析器在我们真实页面上很稳 —— 5 页 0 异常、单页 0~13 ms，能给出我们现在没有的两样东西：表格网格与任意模板的具名参数。

但它的文本输出质量并不比我们现在的清洗器高，实测在三处明显更差：分类链接泄漏、HTML 标签留在正文、实体不解码。它也没有解决我们最大的两个缺口 —— gallery 噪声与 {{Get}} 数据层，实测零改善。

如果目标是"最终质量"，真正的杠杆是渲染文本：同一页 Goo 现在清出 99 字，走 action=parse 能拿到 2387 字且数据层已填。

2026-10-13 更新：本文当时建议的两件事都已落地 —— 清洗器改成"默认保留"（Item Infobox 的 description 自然进来），渲染兜底也已实现（action=parse + jsoup）。 本文保留为当时的评估记录，现状见 wiki 清洗器升级与 wikiclean 借鉴。

二、它到底给什么

2.1 结构层：比我们的正则强

Comfort     解析 13 ms   节 3 / 段 7 / 表 1 / 单元格 46 / 模板 3 / 内链 62
Survivors   解析  6 ms   节 4 / 段 8 / 表 3 / 单元格 121 / 模板 83 / 内链 126
Decorations 解析  2 ms   节 1 / 段 3 / 表 0 / 单元格 0 / 模板 0 / 内链 146
Fool's Demise 解析 0 ms  节 2 / 段 6 / 表 0 / 模板 9 / 内链 3
  • 表格是真网格：TableElement.getRow() / getCol()，能按行列取单元格。我们现在把表格压成一串文本行。
  • 模板参数按名可取：Template.getName() + getParameters()。实测 Fool's Demise 的 {{Item Infobox}} 里 description=… 被完整取到 —— 这一段正是我们现在整块丢掉的剧情正文。
  • 链接有显示名：Link.getText()，Decorations 的 146 个内链能拿到 Doors、Secret Doors 这类标签。
  • 源偏移：每个对象带 Span，可以定位到原文位置，排障时比"第几步丢的"更精确。

2.2 文本层：三处比我们差

页面我们的清洗器JWPL 默认文本JWPL + 我们的策略层
Comfort2119 字3224 字，含 TEMPLATE[...]2530 字，0 泄漏
Decorations2508 字，全是 File:… 噪声3089 字，形态是 link=X|Y972 字，标签清单
Fool's Demise51 字1243 字107 字 + description 可取到
Goo99 字822 字183 字
Survivors5102 字，118 处实体10418 字4944 字，0 泄漏

三处它做不到而我们做到了：

  • 分类链接：Goo 输出里留下 Category:Crafting Materials Category:Early Access Launch；Fool's Demise 留下 C:Two-handed Greatswords。我们的 stripLinks 会把这类整条丢掉。
  • HTML 标签：Fool's Demise 的正文里 <i>"King of fools…" 原样留在文本中。JWPL 只解析 wiki 语法，不认识 HTML。
  • HTML 实体：Survivors 进 JWPL 后仍有 121 处 &nbsp;，和我们现在的处境一样。

而它同样解决不了的两处：Decorations 的 gallery 在它的文本里是 100px / link=Decorations/Doors|Doors，照样是噪声；Goo 的 description 它取到的是字面量 (TEMPLATE) —— 因为值是 {{Get|description}}，离线谁都解不出来。

还有一个配置陷阱。用 FlushTemplates 把模板冲掉之后，getTemplates() 也就拿不到参数了 —— Spike2 里 Fool's Demise 的 description 因此又丢了。也就是说这两件事在 JWPL 里是互斥的：要么正文里留占位符、要么参数不可取。想两者都要，就得选默认配置再自己剥占位符，这正是 Spike3 做的事，也意味着策略层得我们自己写。

三、依赖账单

dkpro-jwpl-parser 只是看起来轻。实测在**我们的工程**上解析出的传递依赖：

org.dkpro.jwpl:dkpro-jwpl-parser:2.0.0
 +- org.dkpro.jwpl:dkpro-jwpl-api:2.0.0          → 拖进 ORM
 |   +- org.hibernate.orm:hibernate-core:6.6.53.Final   ← Spring Boot 管理的版本
 |   +- jakarta.persistence:jakarta.persistence-api:3.1.0
 |   +- org.jgrapht:jgrapht-core:1.5.2            图算法
 +- org.dkpro.jwpl:dkpro-jwpl-swc-engine-shade:2.0.0   ← Sweble 引擎被 shade 进来
 +- org.antlr:antlr4-runtime / jaxb / byte-buddy …
共 34 条传递依赖

实测结论：不会炸，但很重。把 JWPL 挂上去之后跑 SpringWiringTest 与 ApplicationStartsTest，5 项全绿，上下文照常启动，没有触发 JPA 自动配置。真正的代价是三点：

  1. 一个只做文本清洗的项目，classpath 上多出一整套 Hibernate ORM 与图算法库；
  2. jwpl-api 是按 Hibernate 6.1 编的，在我们这里被 Boot 的 BOM 拉成 6.6.53 —— 只要不碰它的 DB 路径就没事，属于潜在错配；
  3. 供应链与扫描面变大，而它带来的收益（表格网格、模板参数）只在"要结构化字段"时才用得上。

顺带一个有价值的发现：dkpro-jwpl-swc-engine-shade 说明 JWPL 2.0 已经把 Sweble 的引擎打了进来。也就是说它那套 AST 的主力其实是 Sweble。若真要结构化解析，直接上 Sweble 可以绕开 api 与 ORM 那一坨 —— 这条路我还没实测，可以照同样方法验证。

五、那"全部推倒重构"该往哪走

实测数据指向的不是 JWPL，而是渲染。

口径Goo
原始 wikitext704 字
我们现在的清洗器99 字
JWPL 默认文本822 字，但 description=(TEMPLATE)
action=parse 渲染后去标签2387 字，description 已填成 "A sticky paste used to bind chemical substances."

差的不只是字数，而是那一页的核心内容到底在不在：原文里 {{Get|description}}、{{Get|stackSize}} 这些是 wiki 的数据查询层，离线解析器永远只能告诉我们"这里有个模板"。渲染让服务器把数据填好，我们只做 HTML 提取。

如果决定重构，我建议的形状：

  1. 抓取层：默认仍取 wikitext，同时对"清洗后过短 / 含 {{Get| / 是图鉴类"的页面加取一份 action=parse 渲染 HTML。两路并存，互不阻塞。
  2. 解析层：渲染路用 jsoup 取内容区、按语义标签切块；wikitext 路继续用我们自己的配对扫描，或换成 Sweble 的 AST。
  3. 策略层：按页面类型声明抽取规则 —— 攻略页要正文与章节、图鉴页要 infobox 字段、目录页要 gallery 标签。每类一个策略类，输出结构化片段而不是一坨文本。
  4. 分块与入库：KbTextChunker 与导入链路不动。
  5. 验收：现有 5 篇夹具扩到覆盖每种页面类型；加一条"逐页保留率对账"；黄金集门禁不退化。

这个形状下 JWPL 的位置很清楚：如果第 3 步要做"从 wikitext 抽结构化字段"，它值得用；如果只要更好的正文，它帮不上忙。

六、不引依赖也能拿的三点

  • 可配置的白名单。JWPL 用 addDeleteTemplate / addParseTemplate 加 SelectiveAccessHandler 的 XML 配置来表达"哪些模板留、哪些丢"。我们的白名单是三个 Set.of(...) 常量 —— 上次收窄就静默丢了内容。把它变成一份可评审的配置，是这个思路能立刻拿来用的部分。
  • 空结构清理。它有 EmptyStructureRemover，专门删"模板删完之后剩下的空壳"。我们的空缺就是 <i> 这类删了一半的残留。
  • 源偏移做诊断。它的 Span 让"这段内容是哪一步丢的"可以直接指出来，比我们现在的逐级长度 bisect 更省事。

七、建议

  1. 不要为了清洗质量引入 JWPL。实测文本质量没有提升，反而在分类与标签两处退步，还多 34 条依赖。
  2. 先把上一份文档里的三步做掉：gallery 按行取标签、实体反转义、白名单补 item infobox。这三条覆盖了我们实测到的全部 128 块缺口，成本很小。
  3. 把"渲染兜底"单独立项，它才是质量上限所在。先离线跑 20 页做对比，再决定是否进导入链路。
  4. 若确实要做结构化抽取，我可以照本轮的同一套方法（真实页面 + 可复现脚本）实测 Sweble —— 它就是 JWPL 内部用的那个引擎，但不用拖 Hibernate。要不要我做这一步，取决于你是否打算把"任务奖励 / 地点 / 图鉴字段"做成结构化数据。
