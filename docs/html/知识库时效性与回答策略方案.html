知识库时效性 与 回答策略方案

⚠️ 本文的方案与路线图部分已被 回答策略与知识库设施设计.md（v2）取代 —— 因为用户补充了三点（时效、温度参数、忠于自有知识库），设计形状变了。本文的现状诊断（第一~四节）仍然全部有效，v2 的结论建立在它之上。

结论先行：你说的"知识库权重过大"只命中了三分之一。 提示词确实把资料当成权威，但更根本的两个问题在它下面——语料只会单向变旧、而且系统没有任何地方能告诉你它旧了；另外「版本/更新」这类最需要新鲜的信息，在知识库里是结构性缺失（不是没同步，是这条路本来就没接上）。

三个问题要分开解，用一种办法（比如"把知识库权重调低"）去解三个问题，会把知识库里真正可靠的那部分（配方、材料、位置）一起削弱。

（启动时，只有显式开开关才跑）

⚠️ 第一个坑：已经抓过的页面，永远不会再抓

kb/build/KbCorpusBuilder.java:144：

if (!cfg.isRefreshWikitext() && Files.isRegularFile(f)) {
    texts.put(p.pageId(), Files.readString(f, ...));   // 有缓存就直接用
    reused++;
} else {
    missing.add(p);                                    // 只有"没有缓存"的才下载
}

注释写得很清楚："已经有 raw/ 的页面直接复用，只下载缺的"——这个设计是为了改清洗规则时重跑得快（16 分钟 → 1 分钟），本身没错。但它的副作用是：

情况 会不会进知识库
wiki 新建了一个页面 ✅ 会（它没有缓存）
wiki 修改了已有页面（改数值、改配方、改版本说明） ❌ 永远不会

要让已有页面的改动进来，只有两条路：refresh-wikitext=true（全量重抓 3908 页，约 16 分钟），或者手动删掉那个 raw/<pageid>.wiki。

⚠️ 第二个坑：没有任何自动刷新

全项目只有两个定时任务：QaCleaner.java:30（问答记录清理）和 TempImageCleaner.java:77（临时图片清理）。没有知识库同步任务。 管理端也没有"重建语料"的入口（我搜过前端，没有）。

所以更新语料 = 改配置 + 带参数重启进程。没人做，它就不会变新。

⚠️ 第三个坑：build.json 会骗人

当前 server/data/kb/build.json 的真实内容（节选）：

{
  "builtAt" : "2026-09-26T09:54:05Z",
  "mode" : "from-raw",
  "wikitextDownloaded" : 0,
  "wikiApi" : "https://enshrouded.wiki.gg/api.php",
  "pagesTotal" : 3908,
  "chunkCount" : 4131,
  "indexedAt" : "2026-09-26T10:00:03Z"
}

mode = from-raw + wikitextDownloaded = 0 意味着：那次"构建"根本没联网，只是把 raw/ 里的缓存重新清洗了一遍。而 raw/ 里 3908 个文件的时间戳全部是 2026-09-21。

也就是说：

你以为 实际
语料是 9/26 的（builtAt） 内容还是 9/21 抓的（raw/ 时间戳）
距今 2 天 距今 7 天（今天 9/28）

"看起来是新的、其实是旧的"——这正是最难发现的那种过期。任何只看 build.json 的人（包括未来的你）都会被误导。

⚠️ 第四个坑：版本/更新类信息是结构性缺失

wiki 的 Game Updates 页已经在 2026-03-04 改成了这样：

Wiki migrated to direct steam rss feed, for updates newer than [[patch 11]] see the steam feed
{{#cargo_query:table=GameUpdates
 |fields=..., versionNumber=Update Number, versionCode=Game Version
 |order by=releaseDate DESC ... }}

数据在 Cargo 数据库表里，渲染时才填进去。而 kb/build/WikiTextCleaner.java:245-248 明确把 # 开头的解析函数整段丢掉：

// 解析函数 / Lua 模块调用（#invoke、#if、#expr、#switch…）：
// 「#invoke:Perks/Data: getDesc; BluntDamage」这种垃圾。整段丢掉更干净。
if (name.startsWith("#")) { ... }

结果：这一页在语料里只剩 340 字的空壳，我直接查了 chunks.jsonl：

Game Updates（Game/Updates）：=List of game updates=
Wiki migrated to direct steam rss feed, for updates newer than patch 11 see the steam feed

## 2026
Updates on the same day may appear in the wrong order

## 2025
Updates on the same day may appear in the wrong order
...

一张版本表都没有。 这不是"没同步"，是再同步也没用——除非换抓取方式（见方案 D）。

（范围可控：raw/ 里只有 3 个页面直接依赖 #cargo_query，所以这不是全站性的灾难，但恰好砸在"版本/更新"这条最需要新鲜的线上。）

顺带核对：知识库现在是健康的

  • chunks.jsonl 4131 行；index.bin = 16,920,588 字节，正好等于 12 + 4131 × 1024 × 4（魔数+数量+维度+向量），行数与索引严格对齐——所以 KbIndex 没有静默关闭，检索是活的。
  • 语料里能查到 0.7.0.1 ... 0.7.4.1 五个版本页；我直接调 wiki API 核对了 apprefix=0.7，返回的正是这 5 个——语料和 wiki 在这条线上是一致的（wiki 自己也没有 0.9/1.0 的独立页面，它改用 Cargo + Steam RSS 了）。
  • 所以不要误判成"语料落后于 wiki"，真实情况是"这条信息在 wiki 上换了形态，我们没跟着换"。

三、三层"权重"分别在哪

你感觉到的"知识库权重过大"，具体是这三处叠加：

第 1 层：系统提示词（最强，且断言是错的）

AGENTS.md 第九章（这是模型每轮都会看到的系统提示词）：

  1. 回答游戏问题时优先依据资料。资料里没有明确写的，就说"资料里没查到"……
  2. 如果资料和你的既有认知冲突，以资料为准（它更新、更具体）。

第 5 条是问题的核心：它替模型做了一个关于事实的断言——"资料更新、更具体"。当语料是 7 天前（甚至 7 个月前）的快照时，这个断言就是假的，但模型被明确要求服从它。模型自己更新的知识被这条规则按住了。

第 2 层：注入话术（中）

ChatService.java:222 拼的是：

以下是从《雾锁王国》官方 Wiki 检索到的资料，供你参考：

"供你参考"本身是软措辞，但它是上下文里唯一的资料，没有任何竞争来源，也没有一个字的日期/版本标注。模型无从判断它是新是旧。

第 3 层：检索与数据（连"年龄"这个字段都不存在）

  • KbChunk 的字段是 (i, title, cats, text, url)（kb/KbChunk.java:14）——没有时间戳。
  • RRF 融合里只有三个维度（KbRetriever.java:206-236）：向量排名（权重 1.0）、关键词排名（权重 2.0）、标题命中加成（0.5 / 0.15）。没有任何新鲜度维度。
  • WikiClient.fetchWikitext() 只请求 rvprop=content，不请求 timestamp——所以构建时就算想记页面更新时间也拿不到。

结论：想给"新资料更高权重"，现在的数据基础是零。 得先有字段，才谈得上权重。

四、根因拆解：三个独立的问题

# 问题 本质 影响 归谁解
① 内容冻结 已有页面永不重抓 + 无定时同步 + build.json 误导 wiki 的所有编辑都进不来；且旧得看不出来 方案 B
② 形态断裂 动态页面（Cargo/RSS）被清洗掉 版本/更新类信息天然为空，再新也没用 方案 D
③ 权威错位 提示词断言"资料更新"，且资料块无日期 模型被要求放弃更新的自有知识 方案 A

关键判断：只做 ③（调提示词/降权重）会削弱知识库里真正可靠的那部分——配方、材料、位置、敌人属性这些静态事实，知识库比模型的记忆准确得多，也正是这套 RAG 的价值所在。正确方向是"给系统补上它缺的那一维（新旧）"，而不是"把知识库整体调轻"。

五、设计方案

方案 A：让"新旧"变成可见信息（止血，半天）

不改检索架构，只补信息。

编号 做什么 落点
A1 资料块头带上内容截止日，例如 <<<KNOWLEDGE as-of=2026-09-21>>> ChatService.java:221-224
A2 改 AGENTS.md 第九章的口径：按问题类型分档 仓库根 AGENTS.md
A3 「语料新鲜度」写进 build.json：区分 builtAt（何时构建）与 contentAsOf（内容截止），并让管理端显示 KbCorpusBuilder.writeBuildInfo + 看板

A2 是这次唯一动"人格规则"的地方，所以我列三个档位给你选：

档位 措辞方向 效果 风险
A2-a（保守） 静态事实（配方/材料/位置/属性）以资料为准；涉及版本、数值、当前赛季、最新改动时，资料可能过期，你可以用自己的知识，并说明"我的资料截至 X" 精准，保留 RAG 优势 需要模型自己判断"这是不是动态事实"，偶有误判
A2-b（激进） 资料与你的知识冲突时，把分歧说出来（"我资料里是 A，但我记得现在是 B"），不再无条件服从资料 最不容易给出过时答案 回答变长、偶尔自我打架；群里显得啰嗦
A2-c（最小） 只加 A1 的日期，提示词不动 零规则风险 模型仍然被要求服从资料，大概率仍会给出过时答案

我的建议：A2-a。 它保留了"游戏资料问知识库"的核心价值，只在真正会过期的维度上松开。

方案 B：让语料真的会更新（治本，1-2 天）

编号 做什么 说明
B1（核心，其实是修 bug） 让"改过的页"也能重抓：构建时向 wiki 要每个页面的 revision timestamp（prop=revisions&rvprop=timestamp，或用 list=recentchanges 拿增量），只重下时间戳晚于本地缓存的页 改 WikiClient + KbCorpusBuilder:144。成本从"全量 16 分钟"变成"只拉变过的几页，秒级"
B2 加定时增量同步（沿用现有 cron 风格，建议每天凌晨），复用已有的 KbIndexIncrementalService 做增量索引 目前只有 QaCleaner / TempImageCleaner 两个定时任务
B3 管理端「语料新鲜度」卡片：内容截止日、距今天数、上次同步结果、待更新页数；超阈值标红 落在看板。"过期"从静默变可见

B1 做完，B2 才有意义（否则定时任务每天跑一遍也只是"确认一遍没变"）。

方案 C：给模型一条"查最新"的路（可选，1-2 天）

这是唯一能拿到真正实时信息的路，也是唯一会改变群聊延迟的选项。WikiClient 已经写好了（MediaWiki API 客户端），现在只接在离线构建上，复用它即可。

编号 做法 成本 风险
C1（推荐形态） 规则触发 + 单轮注入：问题命中"最新 / 当前版本 / 改了什么 / 现在还……"这类模式时，先 WikiClient 拉对应页面（用 prop=extracts 或 action=parse 拿渲染后的结果，绕开 Cargo 问题），作为"实时资料"注入并标注抓取时间，优先级高于语料 中 多一次外网往返（0.5-2s）；wiki 限流；外网挂了必须静默降级为只用语料
C2 完整 tool calling：给模型 fetch_wiki(title)，它自己决定查不查 高 需要给 LlmRouter 加 function calling 支持（当前完全没有），改动面大、多轮调用延迟不可控

我的建议：先不做 C。 理由：群聊的核心体验是"快"；A+B 做完后，"过期"这件事已经从"静默发生"变成"可见 + 能自愈"，收益最大、风险最低。等 A+B 上线后仍然觉得不够（比如 wiki 更新当天就有人问新内容），再上 C1。

方案 D：补上动态页面的内容（顺手做，范围小）

  • 对含 #cargo_query 的页面（raw/ 里 3 个，含 Game Updates）改用 action=parse 拿渲染后 HTML 再清洗；
  • 或者直接消费 wiki 自己指向的 Steam RSS（store.steampowered.com/news/app/1203620），把版本更新做成一个专门的资料块。

这条解的是"内容缺失"，不是"内容过期"，但没有它，"当前版本"这类问题无论怎么同步都是空的。

六、建议的落地顺序

第 1 步（半天）   A1 + A3 + A2-a        ← 立刻止血：过期变可见 + 模型不再被要求盲从
第 2 步（1 天）   B1                     ← 真正的 bug 修复：改过的页能重抓
第 3 步（半天）   B2 + B3                ← 每天自动同步 + 看板显示新鲜度
第 4 步（半天）   D                      ← 补 Game Updates / 版本表
─── 以上做完，"过期知识库给出过时答案"基本消失 ───
第 5 步（可选）   C1                     ← 只有确实需要"当天的最新"才做

七、待你决断的四件事

  1. A2 选哪一档？ 我建议 A2-a（静态事实以资料为准，动态事实允许模型用自己的知识并说明"资料截至 X"）。这是唯一改你机器人人格规则的地方，所以我没动。
  2. B2 的同步频率和时间窗？ 建议每天凌晨一次（沿用现有 cron 风格，如 0 0 5 * * *，避开 4:30 的问答清理）。
  3. 要不要做 C（运行时真联网）？ 我建议先不做，等 A+B 跑一段时间再评估。这一项会改变群聊延迟，是唯一有"体验代价"的选择。
  4. B1 改完后 raw/ 缓存的性质会变：从"只增不改的快照"变成"带时间戳的本地镜像"。要不要保留全量缓存（磁盘约 3.4MB wikitext + 16MB 索引）？我建议保留。
