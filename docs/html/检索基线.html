检索质量基线

这份文档的用途：扩充语料、改检索参数、换模型之前先看这里，改完再跑一次对比。 没有它，所有"变好了"的说法都只能靠感觉。

基线日期：2026-10-04　语料：2,649 块（2,577 物品图鉴 + 72 我们维护的）

⚠️ 本文有两次测量。以第二节（61 条）为准 —— 第一节那次是在 42 条的小样本上测的， 其中的 entity R@1 = 91.7% 是被高估的，原因见第二节。

〇、★ 最新一次测量（61 条黄金集）

为什么会有第二次：第一次的黄金集只有 42 条，其中 colloquial（口语提问，正是要改善的那类） 只有 2 条。于是从生产库的真实提问里挖了一批补进去（候选清单随 2026-10-08 文档清理删除，已并入 tests/golden/retrieval-golden.tsv）。

chitchat 15 0.0% 0.0% 0.000 93.3% 0.3

★ 最重要的变化：entity R@1 从 91.7% 掉到 73.3%

不是代码退化了，是原来那个数字被高估了。

原来的 12 条 entity，注释里写着「实测本体不在 Top-3」「实测被 Pearl 压到第 2」 「首轮标注写错，靠基线跑出来才发现」—— 它们是量过之后挑出来的成功案例。

加入 3 条未经挑选的真实提问后，实测 11/15：

真实提问 期望块 实际检回 判定
现在钓鱼还像很久以前那样钓不上来吗 wake-of-water-4 wet-boot（湿靴） 真失败
可以挤牛奶吗 milk （空，0 命中） 真失败 —— 东西明明在库里
腐血是什么 rotblood（腐血） corrosive-blood（腐蚀之血） 真失败 —— 近名污染

三条都逐条核实过「标注没错」，是真失败不是假红。所以门槛按实测值从 0.83/0.95 下调到 0.65/0.90 —— 门槛的意义是防退化（相对当前状态），不是质量目标。 ★ 真实值应当随语料扩充而上升，那时候要把它调回去。

另外两个变化

  • gap 干净率 0% → 31.6%：不是变好了，是样本从 5 条变成 19 条， 原来那 5 条恰好全是"必编"的。19 条里 6 条返回空 —— 这才是「不知道就说不知道」的真实水平。
  • colloquial 2 → 3 条，仍 100%：新增的「红毯方块的四个机关分别在哪」通过了 —— 玩家说「红毯方块」（语料是「红地毯方块」）、说「机关」（语料正文写「4 个开关」）， 两处说法都不同，关键词路必失手，是向量路捞回来的。

提问 新块 正文

⚠️ 教训：扩充语料后必须复查 gap 标注。 标注是"当时语料里没有"的快照 —— 语料变了它就过时了。 本次 gap 干净率看起来从 31.6% 掉到 26.3%，实际是两条已经不该算 gap 了。 复查后才是真实的 29.4%。

⚠️ 同时暴露的语料质量问题

自动导入的块正文是英文，且清洗后有模板残渣：

[wiki-abyss] Abyss
    is a skill in Enshrouded.            ← 开头没有主语（模板被剥掉留下的）
    Description All Shrouded damage is increased by an additional 20%.
[wiki-quests-nursery-supplies] "Nursery Supplies"
    is a quest in Enshrouded, started by reading .   ← "reading ." 后面缺了东西
  • 英文正文：物品图鉴是我们自己整理的中文，wiki 自动导入的是英文原文。 跨语言检索（bge-m3）能用，但模型看到的是英文资料。
  • 模板残渣：正是《知识库文档格式规范》4.3 节列为「反面教材」的那类问题。

结论：自动导入适合"先有资料"，质量要靠后续人工整理。 这也解释了为什么 Item catalogs 被刻意排除（清洗后基本是链接与表格）。

关于「通用中文名」风险的实测结论

批次 1 的 403 块里有 65 块（16%）中文名 ≤3 字（法师/猎人/铁匠/农夫/太阳/永恒…， 且「猎人」×7、「铁匠」×5 等撞名）。配置里警告过这类标题可能抬高 C 路误触发率。

实测：这个风险没有以"劫持"的形式出现，反而相反 —— 这些通用页输给了具体物品块。 （「空荡独眼巨人」输给战利品，而不是赢过它。） 所以现阶段不用急着改 NameZhIndex；但要继续用黄金集盯住，批次 2（Lore 264 页，英文专有名词标题） 才是这个风险真正该验的地方。

⚠️ 修正：Lore 不是「世界观」，是「收集品笔记」

配置里原来的注释说「口语提问常见（『这游戏讲什么』）」——实测是错的。 Lore 的实际内容是游戏里的收集品笔记/日志：

明亮（A Bright Light In The Sky）   A Brother's Confession   A Cry For Help
被诅咒的（A Cursed Catch）         A Destroyed Roof         A Devious Performance
A Glimpse Of Eternity             A Scattered Legacy       ...

而且里面没有任何「力量/智力/属性/体质/敏捷」内容。所以它没有触及最大的缺口簇。

无退化的原因也清楚了：这些页大多没有中文名，标题保持英文， 反而不容易撞上中文提问的标题闸门。

〇·五、★ 真正的根因：600 条词条没有中文名（18%）

查完批次 2 之后，缺口词（法师 71 / 技能 44 / 属性 13 / 力量 13 / 智力 10 …）的根因终于清楚了：

不是「库里没有内容」，是「库里有内容但没有中文名」。

属性 块 id 词条表的 zh
力量 wiki-strength Strength ← 纯英文
智力 wiki-intelligence Intelligence
体质 wiki-constitution Constitution
敏捷 wiki-dexterity Dexterity
耐力 wiki-endurance Endurance
战斗机制 wiki-combat-mechanics Combat Mechanics
制作 wiki-crafting Crafting 
600 / 3416 条词条的 zh 是纯 ASCII（=没有中文名），占 18%
样例：Absorb / Abyss / Airborne / Arcane Concentration / Barbarian / Bard / Bash / Battle Heal …

这 600 条就是中文提问永远够不到的那部分。 B 路（关键词）靠「词条名出现在问句里」判定命中， 中文问句里永远不会出现 Intelligence。

而这个缺口是代码里早就写明的

实测 Combat Mechanics / Crafting / Survival 这类机制词条语料里没有译名， 就只能留英文（那部分要靠别名表人工补）。 —— NameZhIndex 类注释

别名表就是词条表的 zh 列（管理端「词条」面板 + POST /terms/import，现在传 xlsx）， 而且导入不会覆盖已有的中文名（只在为空时补齐）。

但翻译源是缺的

TRANSLATE-SPEC.md 里原来写着「术语优先查 server/data/kb/glossary/zh-en.tsv」—— 这个文件在本仓库里不存在（物品图鉴的中文名来自 docs/gamedata/_source/*.json 的 zh 字段， 而那些 JSON 只覆盖物品，不覆盖技能/机制/属性）。

2026-10-04 已把那句话改掉，并说明术语表在 SQLite kb_term 表里（需要时导出成 xlsx 随附）。

所以下一步应该是补中文名，而不是继续抓页

按缺口频次优先，第一批只要 ~25 个词条就能覆盖最大的那一簇：

Strength→力量  Intelligence→智力  Constitution→体质  Dexterity→敏捷  Endurance→耐力
Crafting→制作  Combat Mechanics→战斗机制  Survival→生存  Shroud→瘴气  Death→死亡
Comfort→舒适度  Skill Points→技能点  ...

比再抓 300 页便宜得多，而且直击缺口。

一、怎么重跑

# 生产默认路径（含 cross-encoder 重排）
mvn test -Dqqbot.golden.rerank=on -Dtest=RetrievalGoldenTest

# 退化路径（关掉重排，用于对比"重排到底贡献了多少"）
mvn test -Dqqbot.golden.rerank=off -Dtest=RetrievalGoldenTest
  • 需要 .env 里的 SILICONFLOW_API_KEY（会产生 API 调用，量很小）
  • 用生产库的副本跑，不碰真库；跑完把逐条明细写到 target/golden-detail.tsv
  • 没有生产库或没有黄金集时自动跳过（不让缺数据的机器构建失败）
  • ⚠️ 输出用平台编码。在中文 Windows 控制台直接看没问题；在 CI（POSIX/ASCII）里中文会乱码， 但表格里的数字和类别名是 ASCII，照样能读

为什么 colloquial 长不大 —— 这是个结论，不是偷懒

从 125 个真实缺口词 + 100 条真实提问里筛，能干净配对的真俗称只有 1 条。

原因（候选清单已并入 tests/golden/retrieval-golden.tsv）：群友问的是「系统」，语料是「物品」。

法师 71  技能 44  箱子 37  技能点 28  装备 26  法杖 21  武器 18
任务 17  戒指 17  地图 14  力量 13  属性 13  魔法 12  智力 10 ...

这些词 93% 不在库里 —— 不是因为页数不够，是因为语料只覆盖「东西」不覆盖「系统」。 所以这些真实提问只能归到 gap，不能归到 colloquial。

后果（比第一次更清楚）

  1. colloquial 仍然只有 3 条 → R@1 一条错就掉到 66.7%，门槛 75% → 假红。
  2. 但更重要的结论是：你最初的抱怨「口语提问答得很差」， 根因不是俗称不匹配（那种只有 2+1 例），而是群友问的系统级问题我们根本没有资料 —— 它们变成 gap（19 条里只有 6 条返回空），机器人硬凑答案。
  3. 所以正确的顺序是交替的：先把能配对的加进去（已做）， 再扩充系统级语料（技能/属性/任务/地图），然后把新变「可回答」的提问从 gap 转成 colloquial。
