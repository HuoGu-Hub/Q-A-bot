问答广场与答案质量闭环 —— 设计方案

状态：待评审 ｜ 2026-09-25 目标：公开站按关键词聚合历史回答 + 点赞机制 + 三级降级求助

一、结论先行

决策 结论
公开站功能 关键词 → 历史回答（点赞最高的 3 条）
投票 赞 / 踩 / 已过时 —— 每人每答案一票
三级降级 3 条全被踩 → 「问问新答案」→ 再全踩 → 「求助大佬」
管理后台 同一套数据 + 更多信息（未脱敏原文、投票明细）
实现顺序 先设计（本篇），你确认后再动代码

二、三个必须先对齐的问题

2.1 「回答」的粒度 —— 决定了整个设计

「三个历史回答」的来源只能是同一个问题被问过多次、每次回答不同：

群友A 问「废料杯怎么合成」→ 回答 X   ← 记录 1
群友B 问「废料杯怎么合成」→ 回答 Y   ← 记录 2
群友C 问「废料杯怎么合成」→ 回答 Z   ← 记录 3
                                    ↓
                        公开站展示 X / Y / Z，按赞数排序

但有个问题：这三条可能内容几乎一样（检索资料相同、模型相同）。 群友看到三个相似答案，体验并不好。

建议：展示时去重（相似度 > 0.9 的合并，只留赞数最高的）， 不足 3 条就少展示。不要把「凑够 3 条」当硬要求。

2.2 公开站展示问答原文 = 隐私风险

这是最需要你确认的一点。现在 qa_raw 里存的是：

字段 是否敏感
question ⚠️ 群里问的原文，可能含个人信息
answer ✅ 机器人答的，无隐私
user_id / group_id 🔴 绝对不公开

而且有个你可能没想到的场景：

群友 A 在群里问：「我女朋友生日是 3 月 5 日，帮我记一下」
        ↓ 被记录
公开站展示这条问答（即使去掉 QQ 号）
        ↓
群友 A 自己看到 → 「这不是我说的吗？怎么公开了」

即使脱敏，原文本身也可能含隐私。

三个可选策略：

策略 说明 推荐度
A. 只展示「被点赞过」的问答 有人点赞才公开 —— 相当于社区审核 ⭐⭐⭐
B. 全部公开（脱敏） 简单，但有风险 ⭐
C. 只展示管理员标记过 good 的 最安全，但覆盖慢 ⭐⭐

我推荐 A：没人点赞过的问答不上公开站。这样既保护隐私， 又能让"真正有价值的"浮现出来。冷启动时公开站是空的，但不会出隐私事故。

2.3 「求助大佬」发到群里 —— 最敏感的一步

问题 我的建议
发到哪个群？ 提问者所在的群（不能发到别的群）
发什么？ 关键词 + 问题，「这个我答不好，有懂的吗」
谁来发？ 机器人（作为一条群消息）
频率限制？ ⚠️ 必须限 —— 否则被刷屏
提问者同意吗？ 点按钮 = 同意，但要明确告知会发到群里

具体的频率控制：

  • 同一个问题每天最多求助 1 次（避免反复刷）
  • 每个用户每天最多求助 3 次
  • 每个群每小时最多 1 条求助（防刷屏）

三、数据模型

3.1 新增：答案投票表

CREATE TABLE answer_vote (
  id         INTEGER PRIMARY KEY,
  stat_id    INTEGER NOT NULL,      -- 指向 qa_stat.id（那条回答）
  voter_hash TEXT NOT NULL,         -- 投票者标识（QQ号的哈希）
  vote       TEXT NOT NULL,         -- up / down / outdated
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(stat_id, voter_hash)       -- ★ 每人每答案只能一票（可改票）
);
CREATE INDEX idx_vote_stat  ON answer_vote(stat_id);
CREATE INDEX idx_vote_voter ON answer_vote(voter_hash);

为什么用 UNIQUE(stat_id, voter_hash)：一个人对同一条答案反复点赞会刷榜。 加唯一约束后，重复投票 = 改票（UPDATE），不是新增。

3.2 投票者标识：为什么要哈希

不能存明文 QQ 号：公开站可能被爬，投票记录不该关联到人
不能存 IP：会变，同一个人换网络就能重复投

做法：voter_hash = SHA256(QQ号 + 服务器盐)

  • 同一个人永远得到同一个 hash → 能防重复投票
  • 但无法从 hash 反推 QQ 号 → 保护隐私
  • 盐存在 .env，不进 Git

3.3 新增：求助记录表

CREATE TABLE help_request (
  id         INTEGER PRIMARY KEY,
  ts         TEXT NOT NULL,
  keyword    TEXT,                  -- 关联的关键词
  question   TEXT NOT NULL,         -- 群友的问题
  group_id   INTEGER NOT NULL,      -- 发到哪个群
  user_id    INTEGER NOT NULL,      -- 谁求助的
  status     TEXT DEFAULT 'sent',   -- sent / answered / expired
  answer_id  INTEGER                -- 大佬回答后关联
);

4.2 三级降级（你要的核心机制）

第 1 级：展示 3 条最赞的历史回答
            │
            ├─ 有人觉得有用 → 结束 ✅
            │
            └─ ★ 3 条【全部被踩】→ 出现「问问新答案」
                        │
第 2 级：调机器人重新生成一条新回答
        展示：1 条新的 + 2 条库里其他
                        │
                        ├─ 有用了 → 结束 ✅
                        │
                        └─ ★ 又全被踩 → 出现「求助大佬」
                                    │
第 3 级：把问题发到群里，喊人来答

关键判定细节：

场景 判定
「全被踩」的阈值 每条答案 踩数 > 赞数 且 踩数 ≥ 2（避免一个人踩就触发）
新答案从哪来 调现有 ChatService —— 复用检索 + 模型，不新写
新答案要不要入库 ✅ 入 qa_stat，标记 source=plaza（区分来源）
第 2 级也全被踩 才出现求助按钮 —— 不能一上来就喊人

4.3 「问问新答案」的成本 —— ⚠️ 必须防刷

这个按钮会调用大模型，是真金白银：

措施 说明
登录才能点 公开站要有个轻量身份（见 4.4）
每关键词每天 N 次 如 3 次，超了说「今天问得有点多」
全局日限额 如 100 次/天，防恶意刷爆
失败不计入 模型调用失败不算用了配额

4.4 公开站的身份问题

点赞需要知道「你是谁」 —— 否则一个人能刷 100 个赞。但公开站不该要求登录。

方案 体验 防刷强度
A. 设备指纹 + IP 限流 无感 ⭐⭐ 可清缓存绕过
B. QQ 号 + 群验证 要输一次 ⭐⭐⭐⭐ 强
C. 不做身份，只限流 最简单 ⭐ 弱

建议 A 起步（localStorage 存随机 ID + 服务端按 IP 限流）， 够用且无感。发现被刷再升级到 B。

五、关于「给 AI 用的写词条 tool」

你说要做「一个 tool 给 ai 用，识别关键词后创建词条记录问答原文」—— 这个其实已经部分存在了：

现有能力 位置
从问题里抽关键词 QaCollector.keywords()（复用术语表）
记录问答 qa_stat + qa_raw
关联关键词与问答 qa_keyword

你要新增的是「词条」这个概念：

现在：关键词 = 一个字符串（"废料杯"）
你要：词条 = 关键词 + 结构化信息
        ├─ 中文名 / 英文名
        ├─ wiki 页面 URL
        ├─ 被问次数
        ├─ 最佳答案（投票最高）
        └─ 相关问答列表

建议先不建新表，用「聚合视图」：词条页 = 按 keyword 聚合 qa_keyword + 关联 qa_raw + 投票统计。

为什么不建表：数据已经在库里了，再存一份会有两边不一致的问题。

六、管理后台侧

能力 说明
看未脱敏原文 含 QQ 号、群号（只有你能看）
看投票明细 谁投的（hash）、何时、改过几次
下架某条答案 发现不当内容能一键屏蔽
标记为「标准答案」 为将来 FAQ 秒回做准备
看求助记录 谁求助了、有没有人答

七、实施计划

阶段 内容 验收
P1 数据层 建 answer_vote help_request + 投票接口 能投票、能改票、重复投票不增计数
P2 答案聚合 按关键词取 top-3（含去重） 关键词页正确排序
P3 公开站页面 关键词页 + 投票按钮 匿名可浏览，投票过限流
P4 二级降级 「问问新答案」→ 调模型 有日限额、失败不计费
P5 三级降级 「求助大佬」→ 发群里 限流严格
P6 管理后台 投票明细 + 下架 能下架不当内容

P1~P3 是「能用」的最小闭环，P4/P5 是降级机制。

八、风险清单

# 风险 应对
R1 原文含隐私被公开 只展示被点赞过的（社区审核）+ 脱敏
R2 「问问新答案」被刷爆 身份 + 每关键词日限额 + 全局日限额
R3 「求助大佬」刷屏群 同问题每天 1 次、每群每小时 1 条
R4 刷票 每人每答案一票（DB 唯一约束）
R5 三条回答雷同 展示前去重
R6 冷启动没内容 显示「还没有被认可的答案，去群里问吧」
R7 不当内容被点赞公开 管理后台一键下架
R8 求助暴露提问者 发群里时不带 QQ 号

九、需要你拍板

# 问题 我的建议
1 公开站展示问答原文，接受吗？ 只展示被点赞过的 —— 相当于社区审核
2 公开站身份怎么做？ 设备指纹 + IP 限流起步（无感）
3 「问问新答案」日限额？ 每关键词 3 次/天，全局 100 次/天
4 「求助大佬」发什么？ 关键词 + 问题，不带提问者 QQ 号

6 词条要不要建新表？ 先不建 —— 用聚合视图
