概率回复方案

现在的回复只有两档：必须被 @，或者每条都回。概率回复补上中间那段：先判意图，再按概率决定要不要接话，最后用每日上限兜住总量。概率管愿不愿意，频率交给现有的频率限制。

已落地：2026-11-06。下面保留设计取舍与默认值，具体行为以代码为准。

2026-11-06 二次简化：「群里必须 @」已删除，p=0 就是只回呼叫；同群间隔与用户冷却已删除，频率统一由「频率限制」管；「概率回复」组并入「回复行为」。

先说结论

  • 新增 app.reply.probability，取值 0 到 1，默认 0，后台改完立即生效。
  • 它只在「群里必须 @」关闭后生效。@、正文含「飘雪喵」、引用机器人、私聊仍然直通，不受概率影响。
  • 概率不是逐条掷骰子：明确提问必答，闲聊按 p 的二次曲线解禁，噪音永不回复。
  • 另加每群每日上限；频率不再单独配，统一由「频率限制」管。
  • 意图判定用本地关键词规则，不调模型。只有判定通过的消息才调模型。
  • 对当前「必须 @」的部署，默认 p=0，升级后行为不变。已经关闭「必须 @」、走「每条都回」的部署要先读迁移一节。

一句话：把「回不回」从布尔开关变成四档判定，呼叫直通，0.3 起疑问、0.6 起闲聊，低档只认关键词或严格疑问。

目标与边界

目标

  • p=0 时群聊只回应三种呼叫：@、正文含「飘雪喵」、引用机器人，其余一律不回；私聊仍按私聊策略。
  • p 分成四档：低档只接关键词或严格疑问，中档接所有疑问，高档逐步参与闲聊。
  • 任何一条被忽略的消息都不产生提示、不消耗 token、不写模型请求。
  • 默认关闭，对「必须 @」的部署行为与现在完全一致。
  • 概率、节奏、白名单都能在后台热改，改完下一条消息就生效。

非目标

  • 不做语义分类器，也不为每条消息调一次小模型。判定必须是零成本的本地规则。
  • 不做按群独立概率。第一版一个全局 p，用群白名单圈定范围。
  • 不做群聊上下文窗口。第一版只接自洽的话，上下文窗口留到下一步。
  • 不改变私聊策略、指令语义与安全中间层的顺序。

四档通道

概率曲线

mode(p) =
  0            只回呼叫
  0 < p < 0.3    关键词、严格疑问
  0.3 ≤ p < 0.6  所有疑问
  0.6 ≤ p < 0.8  疑问 + 低频闲聊 10%~30%
  0.8 ≤ p ≤ 1    疑问 + 高频闲聊 50%~100%

chance(呼叫 / 关键词 / 疑问) = 1
chance(闲聊) = 低频 10%~30%，高频 50%~100%
chance(噪音) = 0
p走哪条通道闲聊概率读法
0呼叫0必须 @、正文昵称或引用机器人
0.2关键词 + 严格疑问0只接明确问句和配置词，不接宽松疑问
0.4所有疑问0疑问词埋在句中也会接
0.7疑问 + 低频闲聊10%~30%开始接话，偶尔插一句
0.9疑问 + 高频闲聊50%~100%大部分有内容的聊天都会接
1.0疑问 + 全部闲聊100%有内容就接，纯图/复读/链接仍不接

0.6 是闲聊的起点：0.6-0.8 只低频插话，0.8 起进入高频。0.3 是疑问的放宽点：低于 0.3 只认句首疑问或问号，0.3 起句中的疑问词也算。每一档都包含低档的全部条件。

免@阈值是另一道门：主动回复概率低于它时，所有非呼叫消息都要求 @，档位不生效；概率达到阈值后，上面的档位才会放行。默认 0，表示始终允许免 @。

记录页只对闲聊显示接话概率和掷点；呼叫、关键词、疑问直接显示命中依据，例如「被 @ 叫到」「关键词：煤矿」「疑问：命中哪里」。

p=0 不等于完全静默。它的语义是「只回应呼叫」：@、正文包含「飘雪喵」、引用机器人。私聊不走这套判定，仍按私聊策略。p=0 就是唯一的呼叫模式，不再依赖「必须 @」开关。

昵称为空时跳过包含判定，否则 contains("") 会把每条消息都当成呼叫。 昵称按纯包含判定，不要求是问句。所以「飘雪喵好笨」也会被当成呼叫并回复。这是按你的要求做的取舍；要收窄，可以加「且是问句」，但 p=0 就不再是纯关键词。昵称取 BotIdentity.getSelfName()，和文本 @ 用的是同一个来源；当前 QQ 昵称是「飘雪喵」。改昵称后需要重启，这一点和现有 @ 识别一致。

为什么不直接对每条消息掷 p

假设每条消息都按 p 掷一次，p=0.3、群里每分钟 60 条消息，就会产生每分钟 18 次判定通过。群限流每分钟 10 条，会拦下 8 条，但此时真正的策略变成了限流；被拦的主动回复还可能触发「别急呀」的提示，群友收到的是莫名其妙的限流话术。

先判意图再掷概率，噪音和图片在第一步就被清掉，进入抽样的基数小得多，p 才真的能表达「参与度」。

触发流程

打开交互图：概率回复的触发判定 入站 → 触发判定 → Guard 与预算 → 生成发送。绿线是通过，灰线是静默。

图中把引用解析并进了触发判定节点。实际顺序是先判 @ 与昵称，没命中再取引用，最后才做概率抽样。

  1. 准入：黑名单、私聊策略。不通过直接 drop，不进入后续判定。
  2. 指令：斜杠开头先走指令，不受概率影响。指令本来就该秒回。
  3. 呼叫判定：@、文本 @、正文含「飘雪喵」先在本地判掉，命中直接放行到 Guard。私聊在准入阶段按策略处理，不进入这套判定。
  4. 引用解析：还没命中呼叫、且消息带引用时，取一次被引用消息；引用的是机器人直接放行，结果留给后面的回复复用。
  5. 触发判定：意图分类 → 概率抽样 → 每日上限。任一步不通过就静默 drop。
  6. 影子模式：判定通过也只记日志，不发送。仍然走每日上限，统计的是真实会发出去的条数。
  7. Guard 五层 + 预算：顺序不变，仍然在调模型之前。
  8. 生成与发送：闲聊不检索，疑问照常检索，回复走同一个出站口。

主动回复的硬约束

  • 不带图：带图的闲聊按噪音处理，不为接一句话去下载和识别图片。带图的疑问仍然走视觉。
  • 不发语音：主动回复跳过语音关键词，模型安排的媒体也直接丢弃，只发文字。
  • 不写长文：闲聊用插话提示，一句话，30 字内；疑问才允许正常长度的回答。

判定在 MessageRouter 里算，执行在 Guard 的 trigger 阶段。这样被概率丢掉的消息仍然计入 Guard 的入站与拦截指标，不会出现「路由层悄悄丢消息、看板看不到」的缺口。判定结果随 GuardContext 往下传，后面的限流、预算、固定话术才知道这条消息「不是呼叫」。

疑问词表

第一版只用高置信词形，宁可漏判也不误判。误判成疑问的代价是「多回一条」，误判成闲聊的代价是「少回一条」，后者更轻。

多少 几点 几个 多大 多久

反向词先判：出现「怎么会」「怎么就」「怎么这么」「没什么」「没啥」「有什么好」「不是…吗」时，即使带问号也按闲聊处理。这类句子形式像问句，实际是吐槽或反问。

问别人

消息里有 @ 别人的段，疑问降级为闲聊。群里互相提问非常常见，低 p 时抢答别人问另一个人的问题，是最招人烦的一种插话。引用别人的消息不降级，因为引用正文会一起送给模型，消息通常自洽；引用机器人在呼叫阶段就已经直通，不会走到这里。这条规则只作用于疑问档；正文含「飘雪喵」同样在呼叫阶段直通，即使同时 @ 了别人。

引用

引用机器人是呼叫，引用别人不是。没被 @ 或正文昵称命中时，判定前要取一次被引用消息，因为 QQ 的引用段只有 ID，没有作者。取到 Quote.fromSelf() 为真就直通；取失败按非呼叫处理，消息继续走意图分类。

取到的结果直接传给回复阶段复用。否则同一条消息在判定阶段取一次、在生成阶段再取一次，白白多一次 OneBot 调用。实现上把 resolveQuote 从 reply() 提到 handle()，判定与回复共用同一个 QuotedContent。

代价是概率模式下，没被 @ 或昵称命中、且带引用的群消息会多一次 get_msg，即使最后被丢弃。引用在群里不算高频，这个成本可以接受；如果以后觉得贵，可以加一个按引用 ID 的短 TTL 缓存，或者记录自己发出去的消息 ID 做本地命中。

失败关闭

判定函数保证不抛异常。文本为空、正则异常、配置读不到，一律按噪音处理，不回复。宁可少说一句，也不能因为判定挂掉一条正常提问。

每日上限

配置默认作用0 的含义
app.reply.daily-max-per-group40每个群每天主动回复的上限不限

每日上限独立于限流：限流是安全网，触发时会回「别急呀」；对于一条不是呼叫的消息，收到限流提示本身就是骚扰。每日上限只做一件事：超了就静默丢弃，不让用户看到任何提示。

白名单管的是主动概率回复，不管呼叫。@、正文昵称、引用机器人在任何群都照常回应；没列进白名单的群，非呼叫消息一律静默。所以空列表的效果是「所有群都只回呼叫」，不是「所有群都不理人」。

判定器先看群是否在白名单里。不在就按「群未启用」静默丢弃，不做分类、不做抽样、不占每日额度。

呼叫不占用每日额度，也不更新计数。否则会出现「@ 了机器人，却因为它刚随机插过话而被挡」这种荒唐情况。只有主动回复会更新每日计数。

并发下用一次原子占位完成「检查 + 记录」。多个线程同时判定时，最多多回一条，不会超发。代价是判定通过但后续被 Guard 拦下的那条也占了一个名额，这个损耗可以接受，因为主动回复被 Guard 拦下的概率很低。

影子模式只跑意图与概率，不占节奏额度、不更新时间戳、不消耗每日上限。它回答的是「判定层面想回多少」，这个数可能超过 40；拿它和 40 对比，就能判断上限是否合适。关掉影子后额度是干净的。

预算怎么算

主动回复只消耗全局预算，不消耗用户预算和群预算。理由：用户和群的额度是给「提问」用的，机器人自己插话不该把群友的提问额度吃掉。全局次数与 token 上限仍然生效，防止参与量整体失控。每日上限再兜一层，让主动回复不可能挤占正常的 @ 问答。

    /** 主动参与度，0 到 1，默认关闭 */
    private double probability = 0.0;

    /** 只在哪些群做概率回复，空表示所有群都不做；呼叫不受它限制 */
    private List<Long> enabledGroups = new ArrayList<>();

    private int minGapSeconds = 0;
    private int userCooldownSeconds = 0;
    private int dailyMaxPerGroup = 40;

    /** 只记日志，不发送 */
    private boolean shadowMode = false;
}

后台「回复行为」分组里新增四个主动回复项。概率用 ratio 类型渲染成滑块，前端显示两位小数；服务端再做一次 0 到 1 的校验，越界直接拒绝并返回错误文案。频率不再单独配：主动回复与普通提问共用「频率限制」。

列表类型有个现成的坑：SettingsService.convert 把列表统一转成 List<String>，反射写进 List<Long> 字段不会报错，但之后 contains(Long) 永远为 false。私聊白名单已经是这个形状。群白名单要么声明成 List<String> 并在判定侧按字符串比较，要么把 convert 改成按字段泛型转换。这次必须选后者，否则填了 209127588 也不会命中，白名单看起来生效、实际一条都放不进来。

判定核心

TriggerDecision decide(TriggerInput in) {
    if (!policy.enabledForGroup(in.groupId())) {
        return no("群未启用");
    }
    ReplyIntent intent = ReplySignals.classify(in);
    if (intent == NOISE) {
        return no("噪音");
    }
    double chance = chance(policy.probability(), intent);
    if (chance <= 0) {
        return no("概率为 0");
    }
    if (!pacer.allows(groupId, userId)) {
        return no("节奏未到");
    }
    double roll = random.nextDouble();
    if (roll >= chance) {
        return no("未命中");
    }
    if (policy.isShadowMode()) {
        return would(intent, chance, roll);
    }
    if (!pacer.tryReserve(groupId, userId)) {
        return no("并发占位失败");
    }
    return yes(intent, chance, roll);
}

规则每轮现读，不做缓存。后台改完 p，下一条消息就按新值走。随机数通过构造器注入，测试里传固定序列，生产用 ThreadLocalRandom。

接线

// MessageRouter，指令之后、Guard 之前
String selfName = identity.getSelfName();
boolean nameCalled = text != null
        && !selfName.isEmpty()
        && text.contains(selfName);

QuotedContent quoted = null;
if (event.isGroupMessage()
        && !guardAccess.isRequireMentionInGroup()
        && !mentioned
        && !nameCalled
        && hasQuote) {
    quoted = resolveQuote(event);
}

TriggerDecision trigger = null;
if (event.isGroupMessage()
        && !guardAccess.isRequireMentionInGroup()) {
    if (nameCalled) {
        trigger = TriggerDecision.call("正文昵称");
    } else if (quoted != null && quoted.quote().fromSelf()) {
        trigger = TriggerDecision.call("引用机器人");
    } else if (!mentioned) {
        trigger = replyTrigger.decide(...);
    }
}

if (guardAndBudget(req, mentioned, trigger)) {
    return;
}
reply(req, question, replyMode, trigger, quoted);

概率模式下引用先取一次，判定与回复共用同一个 QuotedContent；reply() 收到空值时才按原路径自己取，私聊与「必须 @」模式的行为不变。

GuardContext 增加 TriggerDecision trigger 字段，并提供 unsolicited() 便捷方法。判定阶段只读它，不再自己读配置，保证同一条消息只有一个结论。GuardMetrics 的阶段名从 mention 变成 trigger，计数只在内存里，重启归零，不需要迁移。

固定话术降级

限流提示、纯表情兜底、敏感词拒绝都会产生固定话术。对于一条不是呼叫的消息，这些回复都是噪音。在 GuardPipeline 出口统一处理：unsolicited 为真时，任何 Reply 结果都降级成 Drop，日志保留原 stage 与原因。改一处，三条路径同时生效，不用逐个 stage 打补丁。

提示词

闲聊插话用 TurnPlan.chime()，retrieve=false，信封里加一段：

这条群消息没有 @ 你，也没有点名问你。
你只是在群里接一句话：只接一句，30 字内；
不列点、不科普、不复述资料；接不上就短一点。

疑问插话仍然检索，但也要说明「没有被点名」：

这条消息没有点名问你，但像是在问群里。
知道就简短回答；不确定就直接说不确定，不要展开。

这两段放在用户消息里，不改 system.md。人格与回答契约仍然只有一份，场景差异只在当轮信封里表达。

app.guard.enabled=false 时整条 Guard 管线跳过，概率判定也不生效，等于回复全部。概率寄居在管线里，这是它的边界；要概率生效，保持安全中间层开启。

迁移

升级后 p=0 就是只回呼叫。如果某个部署原来走「每条都回」，升级前把 p 设成 1，并把群填进 enabled-groups；每日上限设 0 才接近原来的行为。空列表等于所有群都不主动回复。

差异在噪音档：纯图片、纯表情、两个字以内不再触发兜底话术，而是直接静默。这是有意的，旧行为在 「每条都回」 下会给每张图回一句「看不了图」，本身就是噪音。

统计口径

qa_stat.guard_action 现在有四个值：pass、drop、fixed_reply、command。产品对「提问」的定义是「@ 了机器人且机器人有效回应」，只有 pass 同时满足。主动回复如果记成 pass，会把看板上的提问量、命中率、独立用户全部灌水，这正是那段注释警告过的事。

新增的两种呼叫形态仍然记 pass。口径从「@ 了机器人」扩展成「呼叫了机器人」：@、正文含昵称、引用机器人、私聊。这样提问量仍然代表「有人明确找机器人」，只是找法多了两种。QaAnalyticsRepository 的注释、QaAnalytics 的产品口径说明要一起改，SQL 不用动，因为所有提问查询仍然只看 pass。

纯昵称呼叫也会记 pass，包括「飘雪喵好笨」这种吐槽。它确实是一次「有人叫机器人」，计入提问量是合理的；如果只想统计真问题，需要再加一个动作，第一版不做。

新增第五个值 auto：主动回复记 auto，不计入任何提问指标，但在消息总量与动作分布里可见。

  • 提问类查询全部显式带 guard_action='pass'，不需要改 SQL。
  • 总览用 COUNT(*)，新增取值不会破坏总量。
  • 概览面板 增加一项「主动回复」，不要混进「被拦」。
  • 加一条口径测试：五个动作之和等于总量。

主动回复还要跳过追问检测。QaCollector 会把每条记录当成一次「提问」来推断下一条是不是追问；机器人自己插的话如果也走这条路，会把别人的上一轮误标成「被追问」。记录时加一个 countsAsAsk=false 的分支，只落行、不参与追问。

统计层改动已经确定，不走「只记日志」的退路。需要改三处：QaAnalyticsRepository 增加 auto 常量与概览字段，QaCollector 增加 countsAsAsk，概览面板增加「主动回复」卡片。这个功能的调参完全依赖数据，不能省。
