wikily.gg 适配评估：能不能爬，值不值得

评估日期 2026-10-26 · 对象：https://wikily.gg/zh-cn/enshrouded · 依据：站点 robots.txt、Terms of Service、页面结构与 sitemap 实测

结论：技术上能解析，授权上不行。这个站的 Terms of Service 明确把 spidering、scraping 列为禁止行为，没有“个人非商用可以例外”的条款；地图标注数据还正好落在 robots.txt 禁止抓取的 /api/ 下。以现在的用法去爬，等于同时违反两条约束。

唯一正路是书面授权或官方数据合作。如果只是想要更好的中文名与地图标注，有两条成本更低、风险为零的替代路线，见第四节。

一、条款证据

1.1 robots.txt：页面允许，API 禁止

User-Agent: *
Allow: /
Allow: /api/media/
Allow: /api/og/
Allow: /api/map-icon
Disallow: /api/
Disallow: /admin/
Disallow: /*/translations/
Disallow: /*/extensions/
Disallow: /*/build/
Disallow: /*/edit

这条只说明“爬虫可以取 HTML 页面”，不是授权。真正决定能不能用的是服务条款。地图标注接口的路径是 /api/ext/tiled-maps/maps/<id>/embed-points，正好在 Disallow: /api/ 范围内。

1.2 Terms of Service：明确禁止 spidering / scraping

Except as expressly set out in this Agreement or as permitted by any applicable law,
you undertake: not to disassemble, decompile, reverse-engineer or create derivative
works based on the whole or any part of the source code of our website nor attempt
to do any such thing, or to reproduce, display or otherwise provide access to the
Services, our website or any of the contents therein, including but not limited to
framing, mirroring, linking, spidering, scraping or any other technological means;
not to provide or otherwise make available our website in whole or in part ...
in any form to any person without prior written consent from us;

同一条款还要求“在所有完整或部分副本上保留版权声明”，并禁止“未经许可把网站内容用于未声明的商业用途”。条款最后更新于 2026-10-25，运营方是法国的 NX Software SAS。

没有“个人非商用例外”。条款用的是 “without prior written consent”，不是“商业用途才需要授权”。所以“我们只是个人群里的机器人、不赚钱”不能作为抓取依据。

这不是法律意见。真要走授权路线，以站点运营方的书面答复为准。

1.3 版权归属

站点页脚署名 © 2026 Wikily · NX Software。中文词条、中文描述、地图标注的整理成果都属于对方。对比现在用的 enshrouded.wiki.gg，那是 CC BY-SA 4.0，允许在署名与相同方式共享的前提下复用。两者的授权基础完全不同。

二、纯技术可行性：如果只看“能不能解析”

2.1 文本页

站点是 Next.js App Router，正文服务端渲染在 HTML 里，不需要调 API 就能拿到。以 /zh-cn/enshrouded/ammunition/acid-bite 为例：

项实测
页面大小约 487 KB
正文标题<h1 class="wiki-heading ext-gwe-dossier-name">酸噬</h1>
简介p.ext-gwe-dossier-flavour，中文句子完整
结构化数据2 段 application/ld+json：Article 与 BreadcrumbList，含中文 headline / description
表格页面内有 <table>，配方与数值在 DOM 里
图片53 个 <img>，走 img.wikily.gg 与 /api/media/，后者 robots 明确允许
多语言每页有 hreflang 互链，zh-cn 前缀可直接构造
页面总量sitemap 分 6 个 part，每 part 约 1,000 条，约 5,000~6,000 页

所以“解析文本”本身不难：h1、简介、表格、JSON-LD 都是稳定钩子。难的是页面重、没有版本化 API、DOM 类名属于对方内部实现，随时会变。

2.2 地图标注

项实测

换句话说：你想要的“更好的地图标注”，恰好是对方唯一明确不让爬的那部分。页面本身给的是渲染后的画布，标注点在运行时由那个被禁的接口补进来。

三、值不值得为它改架构

即使拿到授权，也不建议把它做成“第二个 wiki 源”直接混进现有语料。原因：

  • 块 id 会撞。同一件物品在 wiki.gg 与 wikily 各有一份，直接并库会让检索出现两份近似正文，互相稀释。
  • 中文名是它最大的价值，正文不是。你真正缺的是“中文名 → 英文实体”的对照，而不是又一份中文攻略。
  • 地图坐标系不同。现有 kb.map 的投影、画布、点位表都是按 wiki.gg 的形状建的，换源等于重做一层。

四、合法且更划算的三条路

4.1 官方游戏本地化 → 中文名词表

这是收益最大、风险最低的一条。中文物品名、地名、技能名本来就来自游戏官方本地化，不是 wikily 的原创翻译。把官方中文名做成“英文 → 中文”的对照表，再套到现有 wiki.gg 的块上：

  • 现有 NameZhIndex 与 kb_term 已经支持“中文名（English）”的写法与别名，不需要改检索链路；
  • 只补名字，不搬正文，语料体积几乎不变；
  • 中文提问的命中率提升，主要就来自这一步。

具体从哪里取官方本地化文本，取决于你手上的游戏版本与 EULA。能确认的是：它比爬一个明确禁止抓取的第三方站干净得多。

4.2 人工核对的高频词表

先做最常被问的 200~500 条：武器、护甲、材料、Boss、地点。用管理端「词条」面板逐条补别名，或导一份 xlsx。人工核对的成本一次性，之后长期受益；也不会因为对方改版而失效。

4.3 继续用 wiki.gg 做结构化与地图源

它已经接入、授权清晰、地图数据是 JSON。地图观感不够好，可以在现有渲染器与标注上改，而不是换一个不能碰的源。真要补几个 wikily 上更准的点位，人工核实后作为“本地补充”写进 kb_map_note，不要批量搬运。

4.4 如果确实想要 wikily 的数据：去谈

条款写的是“without prior written consent”，那就去要这份 consent。问清楚这五件事：

  1. 允许抓取的范围：文本、图片、地图标注，分别是否授权；
  2. 用途：个人 QQ 群机器人，非商业，是否需要额外限制；
  3. 署名方式：回答里附来源链接是否足够；
  4. 缓存与保留期限：本地存多久、是否要定期删除；
  5. 速率与频控：每日/每分钟请求上限，是否提供正式 API 或数据导出。

联系方式在站点页脚「Contact us」与官方 Discord。拿到书面答复再动手，比先爬后补票稳得多。

五、一句话建议

不要爬 wikily.gg。先用官方本地化 + 人工词表把“中文名”这块补上，这是当前回答质量最直接的杠杆；地图继续用 wiki.gg，必要时人工补点位。真想要 wikily 的中文正文与地图，先拿书面授权，再按“独立来源、独立 docId、独立投影”的方式接，不要和现有语料混在一起。
