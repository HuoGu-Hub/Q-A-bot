系统日志可视化监测 —— 设计方案

状态：待评审 ｜ 2026-09-24 目标：在系统还没完全宕机时，通过网页看到日志 —— 不用 SSH 上去

一、结论先行

决策 结论
日志落地 先加文件 appender（现在只有 stdout，这是前提）
采集方式 不引 ELK/Loki，应用内环形缓冲 + 文件尾部读取
展示 管理后台新增 /admin/logs 页，实时跟随
推送 SSE（Server-Sent Events）—— 比 WebSocket 简单，够用
崩溃场景 文件 appender 是关键：进程没了，网页也就没了，但文件还在

⚠️ 先说清楚一个残酷事实

你想要的「系统还没完全宕机时能看到日志」有两种情况，方案完全不同：

情况 网页还能用吗 靠什么
A. 功能异常但进程活着（连不上 NapCat、模型超时、检索失败） ✅ 能 应用内实时推送
B. 进程正在死 / 已死（OOM、崩溃、被 kill） ❌ 网页一起没了 只能靠落盘的文件 + 事后看
C. 卡死但有响应（线程池满、GC 停顿） ⚠️ 勉强 环形缓冲（内存里的历史还在）

B 是大多数人真正担心的场景，而它恰恰是网页解决不了的 —— 网页跑在同一个进程里。所以文件 appender 不是可选项，是前提： 进程死了，你至少还能 tail -f，或者重启后回看。

二、现有日志状态（实测）

项 现状
应用日志 只输出到 stdout，由 systemd 收进 journal
日志文件 ❌ 没有 —— application.yml 里无 logging.file
NapCat 日志 ✅ 有文件（deploy/data/napcat/logs/，568 KB）
查看方式 journalctl -u qqbot —— 必须 SSH

所以第一步是补上文件输出，否则什么都做不了。

三、架构

┌────────────────── 应用进程 ──────────────────┐
│                                              │
│  Logback ──┬──▶ 控制台（systemd 收）          │
│            ├──▶ **滚动文件** data/logs/      │ ← 崩溃后唯一留存
│            └──▶ **内存环形缓冲**（最近 N 条）│ ← 网页的数据源
│                       ▲                      │
│                       │                      │
│              LogStreamController             │
│                 ├─ GET  /admin/api/logs      │ 历史（从缓冲）
│                 └─ GET  /admin/api/logs/stream│ 实时（SSE）
└──────────────────────────────────────────────┘
                       │
                       ▼
              /admin/logs 页面（Vue）
              实时跟随 · 级别过滤 · 关键字搜索

为什么不引 ELK / Loki

方案 内存 运维 结论
ELK +1 GB 重 ❌ 2G 机器上不可能
Loki + Promtail +200 MB 中 ❌ 为看日志引入两个服务不值
应用内环形缓冲 + SSE +几 MB 零 ✅ 推荐

关键取舍：我们只要「最近 2000 条 + 实时跟随」，这对定位问题绰绰有余。 真要查历史，文件在那里，grep 比任何界面都快。

四、关键设计

D1 文件 appender（最重要）

logging:
  file:
    name: ./data/logs/qqbot.log
  logback:
    rollingpolicy:
      max-file-size: 20MB
      max-history: 7
      total-size-cap: 200MB    # ★ 总量上限，防止写爆磁盘

没有它，进程一崩就什么都看不到 —— 这是和"网页实时看"完全互补的两件事。

D2 内存环形缓冲

用 Logback 的自定义 appender 把日志同时塞进一个固定容量的双端队列：

  • 容量 2000 条（约 1~2 MB，可配）
  • 满了丢最旧的
  • 只存结构化字段：时间 / 级别 / logger / 消息 / 异常摘要

为什么不用 List + 手动裁剪：ArrayDeque 的 addLast + pollFirst 是 O(1)， 高并发写日志时不会成为瓶颈。

D3 实时推送用 SSE 而不是 WebSocket

SSE WebSocket
协议 纯 HTTP 需要升级握手
服务端 一个 SseEmitter 要管连接生命周期
断线重连 浏览器原生支持 自己写
单向（服务端→客户端） ✅ 正好够用 过剩

我们只需要"服务器推日志给浏览器"，SSE 是更小的工具。

D4 ⚠️ 日志里可能含敏感信息

这是本设计最需要注意的地方：

风险 实例
Token 日志里出现过 Token：已设置（16 位）—— 幸好只打了长度
QQ 号 / 群号 问答日志里到处都是
用户提问内容 [QA] 相关日志
完整 URL（含签名） 图片 URL 里有 rkey
配置值 出错时可能打印整个配置对象

措施：

  1. 日志接口和后台其他接口一样要登录（/admin/api/** 已在过滤器保护下）
  2. 提供 maskSensitive 开关（默认开）：对常见的 key/token/QQ 号做正则替换
  3. 日志页面加显著提示：「这里可能含隐私数据，不要截图外发」
  4. logback 层面不打完整 URL（现有代码里 ImageFetcher 已经做了 mask()）

D5 崩溃场景怎么兜

进程 OOM 被杀
    │
    ├─▶ 网页断开（正常，因为网页和进程一体）
    │
    └─▶ data/logs/qqbot.log 还在
              │
              ├─ SSH: tail -100 /opt/qqbot/server/data/logs/qqbot.log
              └─ 重启后：网页能看到「上次运行」的历史（从文件读尾部）

额外加一个能力：日志页提供「读取文件尾部」的接口（?source=file）， 这样即使当前进程是刚重启的、内存缓冲是空的，也能看到上一次崩溃前的日志。

这是本方案里唯一能覆盖"已宕机"场景的部分。

五、页面设计

位置：管理后台新增 /admin/logs，导航加一项「日志」。

┌────────────────────────────────────────────────────────┐
│ 日志                          ● 实时   [暂停] [清屏]   │
├────────────────────────────────────────────────────────┤
│ 级别: [全部 ▾]  搜索: [____________]  来源: [内存|文件]│
├────────────────────────────────────────────────────────┤
│ 12:04:10 INFO  [KB] 索引已加载：4238 块 × 1024 维      │
│ 12:04:12 INFO  QqbotServerApplication 协议层连通 ✓     │
│ 12:04:13 ERROR 连不上 NapCat 的 HTTP 接口…             │
│   └ at com.example...OneBotApiClient.getLoginInfo      │
│ 12:05:09 INFO  [KB] 术语表已重新加载：3282 条          │
│ …                                                      │
└────────────────────────────────────────────────────────┘

功能：

  • 实时跟随（默认开，新日志自动滚到底）
  • 级别过滤（ERROR / WARN / INFO / DEBUG）
  • 关键字搜索（前端过滤，不占服务端）
  • 错误高亮（ERROR 红色、WARN 琥珀色）
  • 异常堆栈可折叠（默认收起，点击展开）
  • 暂停（想细看时不被打断）
  • 切换到文件视图（看历史/崩溃前）

不做的：图表、统计、告警。那是监控系统的事，这里只要"看一眼日志"。

六、实施计划

阶段 内容 验收
L1 文件 appender logging.file + 滚动策略 + 总量上限 日志文件生成、按大小滚动、不超总量
L2 环形缓冲 自定义 logback appender + 脱敏 写 3000 条后，缓冲里只剩最近 2000 条；token 被替换
L3 接口 /admin/api/logs（历史）+ /logs/stream（SSE）+ ?source=file curl 能拿到 JSON；SSE 能持续推
L4 页面 /admin/logs 实时跟随 + 过滤 + 搜索 浏览器实时滚动；断线自动重连
L5 兜底 文件视图 + 页面提示 + 文档 杀掉进程后重启，网页能看到崩溃前的日志

L1 是最关键的 —— 没有它，后面都是空中楼阁。

七、风险

# 风险 应对
R1 日志含隐私（QQ 号、提问内容） 需登录 + 脱敏开关 + 页面提示
R2 缓冲吃内存 固定 2000 条上限；只存结构化字段，不存完整堆栈
R3 SSE 连接泄漏 超时自动断（如 30 分钟）；连接数上限
R4 日志写爆磁盘 total-size-cap + 现有磁盘监控
R5 高频日志拖慢应用 环形缓冲用 O(1) 操作；DEBUG 级别默认不进缓冲
R6 崩溃时网页也没了 这就是要文件 appender 的原因，见 D1/D5

八、关于 CI 的必要性（顺带回答）

我的判断：现在做 CI，收益中等，不是必做项。 理由：

支持做 反对现在做
101 项测试目前只能手动跑 你是一个人开发，改完顺手跑一下的成本很低
能防"忘了跑测试就部署" 还没上服务器，没有多人协作的冲突风险
面试时是加分项 真正的痛点是部署流程，不是 CI

更划算的做法（我已经做了）：把「测试 + 构建」固化成一个脚本， 你部署时跑一条命令就行：./scripts/build-web.sh 已经做了前端， 我再补一个 ./scripts/preflight.sh（跑全部测试 + 前端构建）更实用。

真要上 GitHub Actions，等有第二个人参与、或部署频率高到记不住跑测试时再说。

九、#invoke 的取舍（实测数据）

我之前说"少数页面受影响"，实测后发现比我说的还轻：

指标 实测值
原始页总数 3,908
含 #invoke 的页 3 页（0.1%）
其中"几乎只剩 #invoke"的 1 页（0.03%）
最终被丢弃的页 1 页 —— Crafted Items List

取舍的实质：

{{#invoke:Perks/Data|getDesc|BluntDamage}}
        │
        ├─ 方案 A：整段丢弃（当前做法）
        │    ✅ 干净、不会有垃圾文本
        │    ❌ 这一页的内容没了
        │
        └─ 方案 B：保留原始代码文本
             ✅ 至少能搜到"这个页面存在"
             ❌ 塞给模型一堆 #invoke:Perks/Data: getDesc 的噪音

结论：当前做法（丢弃）是对的，因为：

  1. 只影响 1 页，且是 Crafted Items List（一个总览列表页，不是具体物品）
  2. 那一页的内容是Lua 运行时算出来的，静态解析根本拿不到
  3. 保留垃圾文本会污染检索 —— 实测过，#invoke 文本曾经抢走过 Top-1

如果将来发现某个重要页面因此缺失，正确做法是去抓渲染后的 HTML （action=parse&prop=text），而不是改清洗规则硬解析 Lua。

换句话说：这不是"取舍"，而是"静态解析的边界" —— 越界了就该换工具，而不是把边界内的规则改坏。
