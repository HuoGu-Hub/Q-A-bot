知识库模块分层与组合层方案

面向 kb.block 与 kb.term 互指这一处结构问题。目标结构、迁移四步、验收口径与明确不做的事。

一句话结论：现在的问题不是"出现了依赖环"，而是没有任何一层同时拥有块与名字这两半数据。合成动作因此被塞进一个服务里，同时造出两条互指的边。

目标结构：两个真源 + 一个组合层，依赖方向只有自上而下一条规则。

一、现状：两半数据，一个身份，没有主人

块与名字各自是真源，这不是问题；问题是它们共享同一个身份，而没有任何一层同时认识这两半。

位置事实后果
kb/block/KbDocImporter.java:179导入文档时调用 termStore.upsert(key, name, status)，"已有名字不覆盖"这条策略实现在块包里块层依赖名字层；一条本该属于名字表的数据策略，跑到了数据生产方
kb/term/KbTermService.java buildAll()词条目录由块表与名字表现场合并得出，住在服务里真正该独立存在的读模型没有自己的位置，只能伸一只手进另一个包
kb/block/KbDocImporter.java:185注释写着"词条身份 = 块 id"，紧接着 upsert(key, ...)块 id 与词条 en 是同一条跨包隐性契约，改名约定要两边同时动

所以两条边都是真实需求，不是误写：块层要"把名字登记进去"，名字层要"读块来拼目录"。互指是结果，不是原因。

二、目标结构

四层，箭头只能从上往下。同层之间不允许有箭头。

层包职责认识谁
入口控制器 / CLIHTTP 与命令行的适配组合层、核心
L2 组合层kb.catalog目录读模型、导入编排、导出视图两个真源 + 核心
L1 真源kb.block / kb.term内容与向量；名字与核对状态核心的只读契约
L0 核心kb共享身份、只读契约、检索不依赖任何上层

两条边换成三条边之后，环就没有了：块与名字之间不再有箭头，双方都只向上依赖组合层与核心。

管理后台 ──▶ kb.catalog ──┬──▶ kb.block  内容 + 向量
                          └──▶ kb.term   名字 + 核对状态
群聊 / 公开站 ──▶ kb 核心 ──▶ 只读契约 · 检索

允许的方向：上层 ─▶ 下层
禁止的方向：kb.block ↔ kb.term、核心 ─▶ 任何上层

三、三个关键动作

3.1 组合层落地：kb.catalog

把 buildAll 这一族目录读模型从 KbTermService 搬到 kb.catalog.KbCatalog，它同时依赖块表与名字表，是唯一同时拥有两半的地方。

上一轮已经把筛选口径与导出格式拆成了 KbTermViews 与 KbTermExport 两个纯规则类，它们跟着搬过去几乎是零改动。这正是先把规则与存储分开的回报。

搬完之后：KbTermService 只剩名字写入；kb.term 不再读块，kb.term → kb.block 这条边消失。

3.2 反转登记：让名字层决定覆盖策略

导入器只产出候选名字，由组合层交给名字层落库：

// 块侧：只产出，不写名字表
record NameCandidate(String key, String name);
List<NameCandidate> candidates = importer.importDocument(text).nameCandidates();

// 组合层：编排"块落地 → 名字登记"
catalog.registerMissing(candidates);

// 名字侧：决定"已有名字不覆盖"，因为数据是它的
int registerMissing(List<NameCandidate> candidates);

于是 kb.block → kb.term 也消失，环彻底不存在。

顺带修好一件事："不覆盖人工核对过的名字"从块包搬回名字层。策略回到拥有数据的包里。

3.3 身份类型化：EntryId

已落地。落地时补了一条边界约定：类型只用在领域内，字符串只出现在三层边界上。这样转换点可以一眼数清，也不会为了类型化去改 SQL 与前端协议。

把"块 id 等于词条 en"从注释与约定升级成类型：KbBlock.id() 与名字表的 en 都用 EntryId。

共享身份由编译器看住之后，跨包契约不再靠 grep 发现。这一步面最广，放在最后做，并且允许逐步替换：新代码先用力，旧的 String 重载暂时保留。

四、为什么不是"合并成一个包"

合并也能消掉环，代价是把最重要的那条区分藏起来。

判据合并成一个包两个真源 + 组合层
变化原因沉进包里。改名字零成本、改内容必须成对更新向量，这条区分再也看不出来两个真源各自表述变化原因；组合层表述它们如何汇合
可测性KbBlockStore、KbTermStore、导入、导出、目录同处一包，测试仍然要拖半个子系统组合层是可单独测的模型；两个真源各自带存储测试
方向可判包内互指不再被规则拦住，"顺手再 import 一下"照样发生规则能写成"同层禁止依赖"，下一个环在评审里就会红
入口复用导入编排埋在导入器里，第二条入口要复制一遍顺序HTTP 与 CLI 两条入口都调同一个编排

五、迁移四步

每一步独立可交付、可回滚，跑完都应当全绿。

步动作验证回滚点
0 机制加一条 ArchUnit 规则：只有 KbDocImporter 可以依赖 kb.term。零逻辑改动mvn test删规则
1 抽组合层新建 kb.catalog，搬目录读模型与 KbTermViews / KbTermExport；控制器改调新门面；KbTermService 只留名字写入mvn test + 手工过词条页：目录条数、板块统计、导出条数与改前逐项一致恢复旧的 KbTermService 调用
2 反转登记导入器返回候选名字，组合层编排落库；删除块层对名字层的依赖KbDocImporterTermTest + 黄金集 gap / chitchat 类不退化 + 一次真实文档导入后核对登记条数恢复导入器内联登记
3 固化方向加规则：kb.block 与 kb.term 互不依赖，核心不依赖任何上层。可选做 EntryIdArchitectureTest 全绿删规则

六、明确不做的三件事

不为了消箭头加只读视图接口。在核心声明一个 BlockSource 让箭头好看，耦合一模一样，还多一层跳转。这是我上一轮报告里差点犯的错，这里明确否掉。

不用事件解耦。用 KnowledgeChangedEvent 那套把登记改成异步或最终一致，会把"导入完成"与"名字可检索"之间的时序变成不确定。表现是中文提问偶尔够不到那些页，而且不报错。这是把一个编译期的结构问题换成一个运行期的静默问题。

不把 KbTermXlsx、CsvTable 这类格式解析跟着一起搬。它们属于名字层的导入导出，搬去组合层只会让组合层变大。

七、验收口径

  • 结构：ArchitectureTest 新增规则全绿，且没有为了过规则而新增的适配器类。
  • 行为：词条页的目录条数、板块统计、导出条数与改前逐条一致；导入一次真实文档后登记条数一致。
  • 检索：KbRetriever 与 Glossary 的构造签名不变，热路径不新增依赖。黄金集门禁不退化。
  • 可读性：新人在不看工具的前提下，能从包名判断出"该往哪边加依赖"。

八、什么时候别做

如果 kb 不会拆成多模块或多服务、也不会多人并行改同一片，第 0 步就够了：5 行规则，把已经写在注释里的豁免变成机制。

第 1 到 3 步的回报是方向可判、目录可测、两个入口可复用，属于整洁度投资，不是收益投资。判断标准很简单：如果这块代码下一步会有人接、或者要拆服务，就做；如果它一年不动、只有一个人维护，放着不会出事。

九、附：现状与目标结构的差异

本节数据来自对全体主代码的实测，规模 224 个 Java 文件 / 33,228 行。包级依赖环只剩两条：kb.block ↔ kb.term 与 guard ↔ guard.stage。

9.1 系统真实形状：一副骨架 + 两条链 + 若干垂直块

它不是一座四层塔。横向看是一副共用骨架，纵向看是两条正交的业务链，每个业务块内部再自成一个微缩三层。

骨架件规模唯一职责被谁依赖
onebot 及其子包4 个包协议边界：唯一认识 OneBot，唯一出站出口12 个包依赖 onebot.model
guard + guard.stage1898 行唯一有权说不：准入、限流、内容、词表、出站节奏9 个包
persistence3061 行SQL 与 java.sql 只在这里11 个包
config1832 行装配层，业务包不得依赖只有组合根
llm1354 行唯一认识模型 SDK，管降级链5 个包
trace / time / files小中性数据、时间、工程根定位4 / 2 / 1
链路径
消息处理链incoming → router → guard → agent → llm + kb + media → onebot.outbound
知识链kb 核心检索 → kb.block 语料与向量 / kb.term 名字层 → persistence

垂直块：kb 含 7 个子包、qa、plaza、site、command、media、logs、settings、admin、publicapi。HTTP 入口共 17 个，散在 13 个包中。

9.2 四层与现状的映射

方案的四层现状由谁承担差距
L0 核心契约与检索kb 直属 35 个文件 + trace基本一致，但 kb 比"核心"胖：还装着 6 个配置绑定类与一组算法协作类。核心零上向依赖，只依赖 trace.KbTrace
L1 两个真源kb.block 7 个文件 / kb.term 7 个文件两个真源都在，但互相认识，是唯一剩下的业务环；两个包同时把 L3 也装进来了
L2 组合层不存在。目录读模型在 kb.term.KbTermService，导入编排在 kb.block.KbBlockAdminService唯一的真缺口
L3 入口不是一个层：每个领域包自带 controller入口散在 13 个包。建议不改：多数是各领域自己的 HTTP 面，搬到统一包只会制造跨包转发
持久化底座persistence方案里漏画了这一层，补进来是五层而非四层

9.3 五条差异，按重要性

  1. L2 缺位。这是唯一的真缺口，也是本方案要补的那一层。
  2. L3 不成层。每个业务块自带出口，包内聚换来 API 面散落。判断：不改，但把 admin 这类跨领域聚合后台当作组合层看待。
  3. kb 不是纯 L0。它同时是检索管线、共享契约、配置词汇、算法协作类。Embedding、Rerank、MapSync、WikiImport、TitleIndex、PublicSearch 六个配置绑定类住在核心包里，是"配置词汇搬进领域包"的副产品。搬迁收益小于改签成本，建议留。
  4. 骨架比方案完整。onebot、guard、persistence、llm、config 各自有明确边界与 ArchUnit 规则，方案里只字未提。
  5. 两条链正交。消息链与知识链互不依赖，只有 agent 是交叉点。整个系统更像"两条链 + 一副底座"，而不是一个塔。

9.4 结论

本方案是局部方案：只补 kb 子系统的 L1 与 L2 之间那一层，动的是一条边。与四层结构的差别，一半来自方案的覆盖面，骨架与消息链都不在它的范围内；另一半来自系统自身确实缺的两块，即组合层与入口层。
