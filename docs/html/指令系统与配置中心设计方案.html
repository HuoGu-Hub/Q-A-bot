指令系统与 Bot 配置中心 —— 设计方案

状态：待评审（第二版） ｜ 2026-09-25 目标：1) 「@机器人 + /命令」模拟官方 Bot 命令；2) 只开放 Bot 行为类配置的可视化界面

一、结论先行

决策 结论
触发格式 群里 必须 @ + / 开头 + 完全相等（配置项，默认 true）
优先级 最高 —— 在 Guard 之前拦截，命令秒回、不受限流
回复内容 文本 + 变量插值（{cmd.list} 等）
/help /list 必须支持，用 {cmd.list} 变量实现（不写死）
QQ 号 高级变量，默认关闭
配置中心范围 ⚠️ 只开放 Bot 行为类，基础设施类一律锁死

二、⚠️ 配置开放范围（本方案的核心约束）

你明确说了「不能开放这么大权限，改坏了怎么办」——这个判断完全正确。

系统里有 135 个配置项，但其中绝大部分根本不该给界面碰：

档 范围 处理
🔴 禁止开放 基础设施与安全类 界面不显示，只能改 yml
🟡 只读展示 需要知道但不该改 显示当前值，灰掉不可编辑
🟢 可编辑 Bot 业务行为类 可改、可校验、可保存

2.1 🔴 禁止开放（改坏系统 / 泄露密钥）

app.qa.db app.kb.dir media.temp-images.dir 改路径 → 数据分裂或丢失
app.admin.password 改密码要走专门流程（且要踢会话）

2.3 ⚠️ 保存后需重启

技术事实：Spring 的 @ConfigurationProperties 是启动时绑定的。

取舍：本方案选 A（保存后提示重启） —— 零架构改动。

方案 说明
A. 保存后提示重启（推荐） 页面负责校验与持久化，提示「需重启生效」
B. 引入热刷新 要给配置类改造，且端口/线程池/DB 连接物理上做不到

真正能热生效的只有四类：指令配置、术语表、词表、系统提示词。 它们本身就有热重载能力，不经配置中心。

三、指令系统

3.1 触发规则（严格定义）

群里：@机器人 + /命令        ← 必须 @（可配置，默认 true）
私聊：/命令                  ← 不用 @

@飘雪喵 /帮助          ✅ 触发
@飘雪喵   /help        ✅ 触发（@ 与 / 之间空白忽略）
@飘雪喵 /帮助 额外内容  ❌ 不触发 → 走正常问答
@飘雪喵 /帮助一下      ❌ 不触发 → 走正常问答
@飘雪喵 帮助           ❌ 无 / 前缀 → 走正常问答

3.2 处理优先级

消息 → 准入控制（黑名单）─拦─▶ 丢弃
         │通过
         ▼
     【指令匹配】─命中─▶ 渲染变量 ─▶ 直接回复  ★ 不走 Guard、不走模型、不受限流
         │未命中
         ▼
     Guard 其余层 → 检索 → 模型 → 回复

为什么在 Guard 之前：

  1. 限流会拦住命令（/help 只能用一次？不合理）
  2. 命令不该走大模型（/help 该秒回）
  3. 命令是你配置的固定内容，不含用户输入

但准入控制（黑名单）仍要过 —— 被拉黑的人不该能触发。

3.3 内置必须命令

命令 回复（默认） 说明
/help {cmd.list} 必须支持
/list {cmd.list} 必须支持（你指定）

两者都用 {cmd.list} 实现（按你的选择），不写死 —— 你可以自由调整文案，比如前面加「我是飘雪喵，可以这样用：」。

{cmd.list} 渲染结果：

可用指令：
/help — 查看所有指令
/list — 列出所有指令
/ping — 看看我在不在
/stats — 查看知识库统计

（格式取自每个命令的 description 字段）

四、变量系统

4.1 基础变量（默认可用）

变量 说明 示例
{user} 提问者昵称（群名片优先） 示例用户
{group} 群名称 示例玩家群
{bot} 机器人昵称 示例助手
{time} {date} {datetime} {weekday} 时间类 14:32 / 2026-09-25
{uptime} 已运行时长 3 小时 12 分
{kb.count} {kb.terms} 知识库 / 术语条目数 4,238
{qa.total} {qa.today} {qa.hitrate} 问答统计 128 / 87.3%
{cmd.total} {cmd.list} 指令相关 见上

4.2 ⚠️ 高级变量（默认关闭）

变量 说明 开关
{user.id} 提问者 QQ 号 app.commands.allow-user-id（默认 false）
{group.id} 群号 同上

默认关闭的理由（按你的要求）：回复会发到群里， 被动能看到（群成员列表）和主动打出来是两回事。

关闭时渲染成 （未启用），并在配置界面提示如何开启。

4.3 安全约束

  • 不提供 {config.*} {env.*} {server.*} 这类读系统信息的变量
  • 变量值原样输出，不二次解析（防模板注入）
  • 未知变量原样保留 {xxx}（方便发现拼错）
  • {{ → 字面 {

五、数据模型

CREATE TABLE bot_command (
  id          INTEGER PRIMARY KEY,
  trigger     TEXT NOT NULL UNIQUE,   -- 触发词（不含 /）
  reply       TEXT NOT NULL,          -- 回复模板，支持 {变量}
  description TEXT DEFAULT '',        -- 用途说明（{cmd.list} 用它）
  scope       TEXT DEFAULT 'all',     -- all / group / private
  group_ids   TEXT DEFAULT '[]',
  min_role    TEXT DEFAULT 'member',
  enabled     INTEGER DEFAULT 1,
  sort_order  INTEGER DEFAULT 0,
  builtin     INTEGER DEFAULT 0,      -- 内置命令不可删
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

-- 命令使用记录：能看出「群友发了 /xxx 但没配」
CREATE TABLE bot_command_log (
  id         INTEGER PRIMARY KEY,
  ts         TEXT NOT NULL,
  trigger    TEXT,
  group_id   INTEGER,
  user_id    INTEGER,
  matched    INTEGER                  -- 1=触发 0=发了但没这条命令
);

bot_command_log 的价值和术语表未命中排行一样：直接告诉你该加什么命令。

6.3 保存流程

前端校验 → POST /admin/api/settings
              │
              ├─ 后端二次校验（白名单 + 类型 + 范围）
              ├─ 写入 config/overrides.yml（不改原始 application.yml）
              └─ 返回「已保存，重启后生效」

不改 application.yml，另写 overrides.yml 覆盖层：

# config/overrides.yml —— 由管理后台写入，不要手改
app:
  guard:
    access:
      private-chat-policy: "whitelist"
    rate-limit:
      per-user-per-minute: 2

Spring 通过 spring.config.import 加载，优先级高于 application.yml。

好处：原始配置保持干净（带注释、进 Git），后台改的单独一份， 出问题直接删掉 overrides.yml 就回到默认值。

6.4 白名单机制（安全的核心）

后端维护「允许改的配置项白名单」，不在白名单里的：

  • 接口拒绝写入
  • 前端不显示

即使有人伪造请求改 app.qa.db，也会被后端挡掉。

七、实施计划

阶段 内容 验收
C1 指令数据层 建表 + CommandStore + 内置 /help /list 首次启动自动建表并写入内置命令
C2 匹配与渲染 CommandMatcher + VariableRenderer 单测覆盖各种边界
C3 接入流程 准入之后、Guard 之前插入命令分支 命令秒回、不受限流；未命中照常走问答
C4 指令界面 /admin/commands 增删改 + 变量插入 + 预览 浏览器配一条命令，群里触发成功
C5 配置中心 白名单 + overrides.yml + /admin/settings 改话术保存后重启生效；改 DB 路径被拒绝
C6 统计 bot_command_log + 「未配置的命令」排行 能看到群友发过但没配的命令

八、风险

# 风险 应对
R1 误触发 @ + / + 完全相等，三重条件
R2 配置改坏系统 白名单 + 后端二次校验；禁改项根本不显示
R3 密钥泄露 密钥类绝不进白名单，接口不返回
R4 命令被刷屏 命令级限流，独立于问答限流
R5 改了不生效（用户困惑） 界面明确标注「需重启」；保存后弹提示
R6 模板注入 变量值不二次解析
R7 overrides.yml 被手改坏 启动时校验，坏了忽略并告警

九、澄清：与「配置热生效」的关系

类别 改完立刻生效？ 走哪个界面
指令配置 ✅ 立刻 /admin/commands
术语表 ✅ 立刻（已有热重载） /admin/glossary
词表 / 系统提示词 ⚠️ 需重启 改文件
Bot 行为配置 ⚠️ 需重启 /admin/settings
基础设施配置 ❌ 不开放 改 yml

「需重启」不是偷懒，是 Spring 的机制 —— 而且像端口、线程池、 数据库连接这些，物理上就不可能热改。

想要热生效的唯一正路是引入 spring-boot-starter-actuator + @RefreshScope， 但那只对一部分配置有效，且要改造 8 个配置类。建议先不做。
