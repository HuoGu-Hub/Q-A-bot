从零理解：NapCat 到底怎么用，我该写什么代码

这篇不讲架构，只回答一个问题：下载了 NapCat 之后，我到底要动它哪里？

一、先破除一个误解：NapCat 不是「机器人框架」

NapCat 是一台翻译机。

QQ 客户端和腾讯服务器之间说话，用的是一套私有的、不公开的协议。你的程序根本听不懂。NapCat 做的事情是：

  • 它假装自己是一个 QQ 客户端，登录你的 QQ 号；
  • 把腾讯那边发来的消息，翻译成人人都看得懂的 JSON，转交给你的程序；
  • 把你的程序想发的话，翻译回 QQ 的私有格式，发出去。

一个更好懂的类比：电源转接头。

   腾讯服务器                NapCat                你的程序
  （美标插座）            （转接头）             （国标插头的电器）
        │                     │                       │
        │  QQ 私有协议         │                       │
        ├────────────────────▶│                       │
        │                     │   标准 JSON 格式       │
        │                     ├──────────────────────▶│
        │                     │                       │ 你的代码在这里
        │                     │◀──────────────────────┤ 想好了要回什么
        │                     │                       │
        │◀────────────────────┤                       │

那个「标准 JSON 格式」有个名字，叫 OneBot 11 协议。你不用背它，用到的时候查文档照抄就行。

二、谁负责什么

角色 负责 不负责
NapCat 登录 QQ、收发消息、把协议翻译成 JSON 完全不管你的业务逻辑，它不知道你在做 AI 还是做签到
你的程序 决定「这条消息要不要回」「回什么」 不用管 QQ 协议细节，不用管登录
大模型 生成回复的文字内容 不知道 QQ 的存在，它只是被你的程序调用
数据库 记历史对话、长期记忆 ——

关键认知：NapCat 和你的程序是两个独立的程序，跑在两个进程里，通过网络说话。 就像浏览器和网站服务器一样，互不干涉。

三、所以，我要改它的代码吗？

不用。一行都不用改。

你只需要做两件事：

  1. 改 NapCat 的配置文件（在网页界面里点几下就行）—— 告诉它两件事：
    • 「有新消息，往这个地址推送」
    • 「我的接口在这个端口，允许你调用它发消息」
  2. 自己写一个程序 —— 接收它推来的消息，调用它的接口把回复发出去。

三个「不需要」：

  • ❌ 不需要把 NapCat 的源码 clone 下来改
  • ❌ 不需要懂 TypeScript（NapCat 是用它写的，但你不用碰）
  • ❌ 不需要把代码写进 NapCat 的插件目录

例外：只有当你想给 NapCat 本身加新功能（比如支持一个它还不支持的 QQ 新特性）或者修它的 bug 时，才需要看源码。99% 的人一辈子不需要。

四、「通信协议层」是什么意思？用大白话说

就是两个程序约定的说话格式。

比如约定好：要和 NapCat 说话，必须把内容写成这样：

{
  "action": "send_group_msg",
  "params": { "group_id": 123456, "message": "你好呀" }
}

NapCat 收到这段 JSON，就知道「哦，他要我往 123456 这个群发一句你好呀」。

反过来，QQ 群里有人说话了，NapCat 会推给你这样一段：

{
  "post_type": "message",
  "message_type": "group",
  "group_id": 123456,
  "user_id": 456789,
  "self_id": 999999,
  "message": [
    { "type": "at",   "data": { "qq": "999999" } },
    { "type": "text", "data": { "text": " 你好呀" } }
  ]
}

这段的意思是：「群里 456789 这个人发了条消息，内容是 @999999 你好呀」。

「协议层」= 这套约定俗成的 JSON 格式。 它不是玄学，就是一份双方约定的「信件格式规范」。你查文档照着填就行。

五、一个真实的来回（我们实测跑通的）

这是真机跑出来的日志，一字不改：

你的程序收到的（NapCat 推来的）：

{"post_type":"message","message_type":"group","group_id":123456,"user_id":456789,
 "self_id":999999,"message":[{"type":"at","data":{"qq":"999999"}},
 {"type":"text","data":{"text":" 你好呀"}}]}

你的程序发出去的（调用 NapCat 的接口）：

POST http://127.0.0.1:3000/send_group_msg
{"group_id":123456,"message":[{"type":"at","data":{"qq":"456789"}},
 {"type":"text","data":{"text":" 你说的是：「你好呀」"}}]}

结果： QQ 群里出现了「@456789 你说的是：「你好呀」」。

整件事就这么简单。所谓「基于 NapCat 开发一个机器人」，就是不断重复这个来回。

六、上手三步

第 1 步：把 NapCat 跑起来并登录

docker run -d --name napcat --restart always \
  -p 3000:3000 -p 3001:3001 -p 6099:6099 \
  -v $(pwd)/data/napcat:/app/napcat/config \
  -v $(pwd)/data/qq:/app/.config/QQ \
  mlikiowa/napcat-docker:latest

浏览器打开 http://127.0.0.1:6099，扫码登录一个专门注册的小号（这个号不能同时在手机 QQ 上登录）。

第 2 步：在网页界面里配置「消息推给谁」

新建一个网络配置，填两样：

配置项 填什么
HTTP 服务端端口 3000 ← 你的程序通过这个调用它发消息
HTTP 上报地址 http://你的机器IP:8080/ ← 它把消息推给你
Token 随便一串随机字符，两边填一样

第 3 步：跑你自己的程序

cd demo
NAPCAT_TOKEN=你刚填的token node http-bot.mjs

然后去群里 @ 一下机器人。

七、没有 QQ 号也能先开发

我另外写了一个 fake-napcat.mjs，它假装自己是 NapCat，只提供那个 HTTP 接口。这样你可以完全不碰 QQ，先把程序逻辑调通：

# 终端 1：起假的 NapCat
node demo/fake-napcat.mjs

# 终端 2：起你的机器人，指向假的 NapCat
NAPCAT_API=http://127.0.0.1:3999 node demo/http-bot.mjs

# 终端 3：伪造一条「群里有人 @ 了机器人」的消息
curl -X POST http://127.0.0.1:8080/ -H 'content-type: application/json' -d '{
  "post_type":"message","message_type":"group","group_id":123456,"user_id":456789,
  "self_id":999999,
  "message":[{"type":"at","data":{"qq":"999999"}},{"type":"text","data":{"text":" 你好呀"}}]}'

终端 2 会打印收到的消息，终端 1 会打印「我要发这个回复」。

八、从「能回话」到「接上大模型」，只差一行

// 现在（demo 里的样子）
const reply = `你说的是：「${text}」`

// 以后（接大模型）
const reply = await callLLM(text)   // 内部就是往 OpenAI / DeepSeek 发个 HTTP 请求

「接 Agent」听起来很玄，落到实处就是：把生成回复的那一行，换成一个调用模型的 HTTP 请求。 剩下的（多轮记忆、工具调用、防注入）都是在这个基础上加东西。

九、那篇复杂的架构文档什么时候才用得上？

分水岭很清楚：

你现在的情况 该用什么
就自己玩 / 一两个群 本文这一版就够了，一个文件，零依赖
想记住多轮对话 加一个 SQLite 存历史
想让它会用工具（搜资料、查天气） 加「工具调用」循环
群多、消息量大、怕被刷爆 加触发规则 + 限流
有人试图套你的提示词 / 骗它干坏事 加防注入
每月 token 账单失控 加路由过滤 + 预算

复杂架构从来不是起点，而是被真实问题逼出来的结果。 先把这一个文件跑起来，比读十篇架构文都有用。

十、你可以怎么验证自己懂了

回答这三个问题就够了：

  1. NapCat 挂掉的时候，你的程序会怎样？（答：收不到消息、发不出去，但它自己不崩——因为它们是两个独立进程）
  2. 你想让机器人换个性格，改哪个文件？（答：改你自己的代码里的回复逻辑，不是改 NapCat）
  3. 如果腾讯改了 QQ 协议，谁需要升级？（答：NapCat，你不用动）
