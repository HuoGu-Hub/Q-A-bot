路线 B 影响评估：AiServices 接管之后

B 不是多写一行配置。它会把三处现在由我们掌控的边界交给框架：系统提示词的所有权、模型选择的时机、提示词与资料的拼装方式。收益是官方的护栏与工具链；代价是这三处都要重新证明一遍。

本文所有结论都来自本地 jar 的方法签名与常量池，以及仓库源码，不是推测。

一、B 接管了什么

官方文档定义的调用链，由 AiServices 在内部串起来：

systemMessage → userMessage → RetrievalAugmentor → ContentInjector
→ chatMemory → ChatModel → AiServiceListener → 返回文本
步骤现在由谁做B 之后由谁做影响
系统消息LlmRouter.java:368 读 system.md 并追加风格systemMessageProvider中
检索ChatService.java:183 直接调 KbRetrieverRetrievalAugmentor低
资料拼装ChatService 拼两段出处ContentInjector高
模型选择LlmRouter 按降级链与能力过滤chatModel 绑定单一实例高
多轮记忆没有，逐条无状态chatMemory 可配，默认无中
调用痕迹返回值 ReplyResult事件监听中

二、六处具体影响

1. 系统消息换了主人

现在的加载链条是：外部 system.md 优先，读不到退到 classpath 内置副本，两条都没有就打 ERROR 并给兜底话术；每轮再追加后台配置的回复风格；另外还有一次未替换占位符的检查。这些全在 LlmRouter.loadSystemPrompt 与 systemPromptWithStyle 里。

B 之后换成 systemMessageProvider，它是按请求调用的，所以热生效仍然能做到。但要注意：如果漏删 LlmRouter 里那份 SystemMessage，就会出现两条系统消息，模型行为会变，而且不会报错。

2. 默认的资料拼装会破坏我们的提示词契约

我反编译了 core 1.20.0 的 DefaultContentInjector 常量池，它写死了两件事：

默认模板：{{userMessage}}\n\nAnswer using the following information:\n{{contents}}
每条内容：content: %s\n%s
metadata：逐行以「键: 值」追加

我们的契约是整块 KNOWLEDGE 标记，内含【我们维护的内容】与【导入的资料·时间】两段，并且位置在用户正文之前。系统提示词第九章的规则就挂在这些标记上。

用默认注入器会同时改变格式和顺序。顺序从"资料在前"变成"资料在后"，这会实打实改变模型行为，不是纯格式问题。B 必须配一个自研 ContentInjector。

3. 模型选择从"每次挑"变成"构建时绑定"

LlmRouter 现在承担：多厂商配置、降级链、按 vision 能力过滤、把空回复当失败换下一个、后台热替换模型 ID、以及 test 与 rollback 两个接口。AiServices.chatModel(ChatModel) 只在构建时绑定一个实例。

两条出路：

  • 把 LlmRouter 包成一个 ChatModel 适配器，降级、vision、计费都留在里面。所有能力保住，但 LlmRouter 必须改成不再注入系统消息的纯模型客户端。推荐这条。
  • 每个 provider 一个 AiServices：检索与聚合器要重复装配，热替换要整批重建。不可取。

4. vision 的分支语义要保住

现在 ChatService 先判 hasVision，不支持就回一句"我看不了图"，支持才下载图片、限张数、走 chatWithImages。

B 之后图片作为 Content 参数进服务接口，模型能力判定移进适配器。但提前拒绝那一层必须保留，否则图片路径的失败会变成模型报错，用户体验从"礼貌拒绝"退化成"报错"。

5. 检索痕迹与耗时是问答记录的数据来源

ReplyResult 带着 text、llmMs、kb 三个字段返回，MessageRouter.java:413 把它们交给 qaCollector，管理端的「未命中·该补什么」靠的就是这些数字。

AiServices 只返回文本。检索痕迹要靠监听器或聚合器自己落到请求上下文，耗时要从事件时间戳推算。这块从"显式返回值"变成"回调写上下文"，是本路线里最容易漏数据的地方。

6. 每轮的模式开关要多绕一层

ReplyMode.NONE 现在是最省的路径：连 augmentor 都不调，一个 embedding 都不发。

官方 _06 Skip Retrieval 样例的做法是自定义 QueryRouter 返回空集合，意味着模式要通过 Query.metadata 传进管线。多一层元数据传递，而且"完全不发外部请求"这条约束要在路由层重新验证。

三、B 真正换来的东西

能力是否必须走 B依据
AiServiceListener 事件是AiServices.registerListener
ChatModelListener不需要在 core 的 model.chat.listener 包里，独立于 AiServices
EmbeddingModelListener、ContentRetrieverListener、EmbeddingStoreListener不需要全在 core
输入、输出护栏自动执行是core 有 guardrail 包，但执行由 AiServices 驱动
工具调用是AiServices.tools
chatRequestTransformer是AiServices 独有

observability 不能当作选 B 的理由。官方监听接口在 core 里，路线 A 现在就能用。B 的独占收益只有两样：护栏自动执行链与工具调用。

四、必须盯住的四件事

  1. 不能出现两条系统消息。迁移时要显式删掉 LlmRouter 里注入 SystemMessage 的那一步，并加一条测试盯住消息条数。
  2. 自研 ContentInjector 的顺序要在黄金集上验证。把"资料在前"改成官方的"资料在后"属于行为变更，不是重构，必须单独测一次。
  3. 显式不配 chatMemory。一旦配上，机器人从无状态变成有状态，成本和隐私边界都会变。建议加一条架构测试，禁止 chatMemory* 出现在装配代码里。
  4. 版本要一起对齐。现在 core 是 1.20.0、主包本地只有 1.19.0，混用两个版本有运行期风险。走 B 时应当把两者一起升到 1.21.0，并跑一次完整回归。

五、迁移与回滚

  • 开关粒度：在 ChatService 里保留两个实现，配置切换。AiServices 路径失败时可以立刻切回现在的路径。
  • 验收：黄金集门槛不退化；问答记录里的注入块数、来源分布与迁移前同量级；两条系统消息的检查通过。
  • 回滚成本低：B 不改数据库、不改语料、不改索引，回滚只是切换实现。

六、结论：工具需求确定之后选 B

最初把 B 判为可选，依据是"它的独占收益只有护栏与工具，而这两样当前都不需要"。这个前提现在不成立了，所以结论反过来：选 B。

B 在工具这件事上多给了什么

能力所在位置路线 A 要自己写吗
工具循环本身主包 AiServices是
轮次上限，防死循环maxToolCallingRoundTrips是
参数错误处理ToolArgumentsErrorHandler是
执行失败处理ToolExecutionErrorHandler是
模型编造工具名的兜底HallucinatedToolNameStrategy是
调用前钩子，可做授权BeforeToolExecution是
工具并发执行executeToolsConcurrently是
工具过多时的动态检索toolSearchStrategy是
工具来源的 SPIToolProvider是

以上九项都不在 core 里。core 只给工具的原语：ToolSpecification、ChatRequest.Builder.toolSpecifications、AiMessage.hasToolExecutionRequests。手写循环可行，但等于自己实现整张表，而且每一项都是安全敏感代码。

三处只有加了工具才会暴露的影响

一、现在的"空回复当失败"会把工具调用当成故障。LlmRouter 里 text == null || text.isBlank() 就换下一个厂商。而模型请求调用工具时，AiMessage 的文本本来就是空的，hasToolExecutionRequests 才是 true。不改这个判断，第一次工具调用就会被判为失败并切换厂商。这是两条路线都要先修的第一件事。

二、降级链要能按"支持工具"过滤。现在只有 vision 一个能力标签。链里某个厂商不支持工具调用时，循环会在中途断掉。需要补一个工具能力标签，并让它对工具路径生效。

三、群友能靠说话触发工具，需要工具级授权。机器人跑在 QQ 群里，任何成员都能用一句话触发工具。系统提示词里"不许踢人改配置"那些约束是写给模型的，不能当作授权机制。好在 B 给了钩子：BeforeToolExecution 同时带着 request() 与 invocationContext()，而 InvocationContext 能拿到调用方传进来的参数、用户消息与记忆标识。按调用方决定工具是否放行因此是可行的，前提是从第一版起就把调用方上下文传进去。

之前担心的痕迹问题比想象的小

第四节把"检索痕迹要靠回调"列为中等风险。核对 InvocationContext 之后可以放宽：它带 invocationId、methodName、methodArguments、invocationParameters、userMessage、chatMemoryId、timestamp，足够把问答记录需要的字段拼回来。

代价仍然是那四条

第四节列的四件事不会因为选 B 而消失：不能出现两条系统消息、必须自研 ContentInjector、显式不配 chatMemory、core 与主包一起升到 1.21.0。它们要从建议升级为"上 B 之前必须先有的测试"。
