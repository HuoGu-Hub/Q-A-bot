数据大屏数据准确性核查

2026-09-28 ｜ 起因：「提问用户 / 群」显示 8 个群，但 bot 明显没进那么多群

一、结论速览

# 发现 性质 影响 状态
F1 生产库里有 5 个假群号（700000~700004）的测试数据 数据污染 就是「群 = 8」的直接原因；关键词榜也混进假热词 清理 SQL 已备好，需你在宿主机执行（容器写不了这个库）
F2 每日图表按 UTC 日期分桶 代码 bug 本地时间早上 8 点前的提问被算到前一天（实测 09-25 差 11 条） 已修（AppTime，东八区）
F3 COUNT(DISTINCT group_id) 会把 0 当成一个群 代码疏漏 广场生成的答案（group_id = 0）一旦带上 pass 就凭空多一个群 已修（加 group_id > 0）
F4 「群消息总数」= qa_stat 全部行，含广场生成的答案 口径疏漏 总数会大于各 action 之和 已修（同一处过滤）
F5 PlazaStore 往不存在的列 has_quote / text_len 写数据 真 bug 广场「生成新答案」100% 抛 SQLException 已修（并在迁移里补上一直缺失的 source 列）
F6 大屏固定近 7 天、看板窗口可切换，但卡片上没写 表述疏漏 同一张卡片两处数字不同 → 第一反应是"数据不对" 已修（卡片加窗口提示）
F7 预算的「今日」用 LocalDate.now()（UTC） 代码疏漏 日额度在北京时间早 8 点重置，而不是零点 已修（与 F2 共用同一个时区常量）

二、F1：你看到的「8 个群」是怎么来的

在真实库上实测（server/data/qa/qqbot.sqlite）：

group_id 分布（全部 3949 行）
  866095282    2824 行   ← 真实群
  100000004    1114 行   ← 真实群
  700000          2 行   ← 假的
  700001          2 行   ← 假的
  700002          2 行   ← 假的
  700003          2 行   ← 假的
  700004          2 行   ← 假的
  100000002      1 行   ← 真实（你自己那个群，见 server/README.md 的日志示例）

那 5 个假群的来源是 tests/manual/probe-kb-e2e.mjs：它把假事件 POST 到真实运行的服务上， 而且为了绕开「每人每分钟 1 次 / 每群每分钟 10 条」的限流，刻意每条用不同用户 + 不同群 —— 于是凭空多出 5 个群。它们的 group_id 是连号 700000 + i，user_id 是 2000 + i， 时间集中在 2026-09-22，正好是最早的 id 1~10。

实测影响（清理前 → 清理后）：

指标 清理前 清理后
提问用户 / 群 27 / 8 22 / 3
群消息总数 3949 3939

清理脚本早就存在（tests/cleanup-sql/cleanup-probe-test-data.sql），只是没执行过。 我已在副本上完整跑通并核对（残留 0 行、无孤儿 raw/keyword）。数字也更新成了当前实测值。

这一步需要你来做：工作区是 9p 挂载，容器里写这个库会直接报 disk I/O error （WAL 需要共享内存段；我实测过，不是权限问题）。在宿主机上跑即可，不用停服务：

cp server/data/qa/qqbot.sqlite server/data/qa/qqbot-before-cleanup.sqlite
sqlite3 server/data/qa/qqbot.sqlite < tests/cleanup-sql/cleanup-probe-test-data.sql

另外我把探针脚本结尾的提醒改成无条件打印（原来只在"用了默认目标"时才提醒， 但显式设 APP_URL 同样可能正指着生产），并写明了"别在容器里跑"。

三、F2：每日图表差了一整天

QaAnalytics 里两处按天分桶写的是 substr(ts,1,10) —— 那是 UTC 日期。 容器里没设 TZ，所以北京时间早上 8 点之前的提问会被算到前一天。

真实数据上对比（提问量）：

本地日期 旧（UTC 分桶） 新（东八区） 差
2026-09-25 32 21 −11
2026-09-26 34 45 +11
2026-09-27 5 5 0

也就是说「09-26 突然涨了」里有 11 条其实是 09-25 的。

修法：新增 config/AppTime 作为唯一时间口径，SQL 改用 strftime('%Y-%m-%d', ts, '+08:00')。这一条同时被 F7（预算的「今日」）复用 —— 两处各写一遍时区，迟早会出现"图上算今天、预算算昨天"的自相矛盾。

实测确认 SQLite 能直接解析 Instant.toString() 产出的纳秒精度串 （2026-09-27T15:02:22.836835400Z），不需要先截断。

四、F3 / F4：哪些行不该算进「群消息」

PlazaStore.saveGeneratedAnswer（广场生成新答案）写的是 group_id = 0, user_id = 0， 注释里写得很清楚："这条不是群聊产生的，不该伪造归属"。但统计侧没有把 0 排除：

  • COUNT(DISTINCT group_id) → 会把 0 数成第 N 个群；
  • COUNT(*) 当「群消息总数」→ 会把广场答案算成群消息，导致总数 > 各 action 之和。

修法：overview 的整段聚合统一加 group_id > 0（KPI、action 分布、每日提问量都走同一个 where），并在类注释里写清为什么。目前库里还没有广场行，所以这次不会改变现有数字 —— 它挡的是下一次。

五、F5：广场「生成新答案」其实一直失败

PlazaStore 的 INSERT 里有 has_quote 和 text_len 两列，而 qa_stat 里根本没有它们 （CREATE TABLE 和 addColumnIfMissing 都没加过）。同一个问题还有 source 列 —— 代码在读写它，建表语句里却没有。

实测（在副本上跑修好前后的两条语句）：

旧语句 → ❌ table qa_stat has no column named has_quote
新语句 → ✅ 插入成功，读回 (group_id=0, user_id=0, answer_len=52, source='plaza')

而 PlazaStore.saveGeneratedAnswer 是被 try/catch 包着的，失败只会记一条日志 —— 所以表现是广场安安静静地没有新答案，不报错。

修法：

  1. 从 INSERT 里去掉 has_quote / text_len（没有任何地方读它们，补两列没人用的东西没意义）；
  2. QaStore.migrate() 补上 source TEXT DEFAULT 'chat' —— 全新库从此也能正常工作 （启动日志实测：[QA] 数据库迁移：qa_stat 表补上 source 列）。

六、F6：同一张卡片，两个地方数字不同

  • 数据大屏（/admin/screen）固定 days=7；
  • 数据看板（/admin/dashboard）窗口可在 7/30/90/全部之间切。

两处的卡片都叫「提问用户 / 群」，且都没写窗口。切来切去就会觉得数字在乱跳。 已给两张卡片都加上 近 7 天 · 提过问的（去重） / 近 N 天 · 提过问的（去重） 的提示。

七、F7：预算的「今日」在北京时间早 8 点重置

BudgetGuard 用 LocalDate.now()，容器默认 UTC → 日额度在北京时间 08:00 清零。 个人项目里这不算致命，但它和「每日提问量」的日期口径必须一致，所以一起改成 AppTime.ZONE。

九、需要你做的（只有一件）

在宿主机上执行一次测试数据清理（见第二节的命令）。执行完，数据大屏的 「提问用户 / 群」就会显示成 3（其中 100000002 是你自己那个群，只有 1 条记录）。
