飘雪喵 QQ 机器人 · 系统说明书

系统名称：飘雪喵（QQ 群问答机器人 + 双端 Web 站点） 运营：示例组织 ｜ 技术支持：示例作者 文档版本：v1.0 ｜ 日期：2026-10-02 ｜ 依据：仓库当前代码（master 工作区） 读者：接手维护、评审、二次开发这套系统的人 说明：本文以 当前代码与配置 为准。docs/md/ 下的设计文档记录的是设计过程，其中较早的几篇（wiki 抓取时代、五面板时代）与现状已有偏差，本文在"十一、已知偏差"里逐条列出。

一、系统是什么

1.1 一句话定位

一个跑在 QQ 群里的《雾锁王国》（Enshrouded）游戏问答助手：群友 @ 机器人提问，机器人先查我们自己的中文知识库，再把资料交给大模型组织成人话回答；外部还有两个 Web 界面 —— 给群友看的公开站、给自己用的管理后台。

系统不训练模型，也不自己抓取网页。它做的是：检索 + 提示词编排 + 安全与成本控制。知识库的原料由系统外部（人或另一个 AI）按固定格式产出，再从管理后台导入。

2.2 一条消息的完整生命周期

NapCat 上报 POST /onebot/event
  │
  ├─ OneBotEventController：立即返回 200，把事件丢进 @Async("botExecutor")
  │    线程池 core=max=8，队列 100；排队超过 20 秒直接丢弃并礼貌回一句
  ▼
MessageRouter.handle(event)
  │
  ├─ ① 忽略机器人自己发的消息
  ├─ ② 黑名单准入（唯一在指令之前跑的一层）
  ├─ ③ 指令匹配
  │      · 话术类（/help /ping …）→ 渲染变量 → 秒回，不走限流、不调模型
  │      · 智能问答类（agent）→ 只登记，继续往下走 Guard 与预算
  ├─ ④ 广场求助确认（群里发「求助：xxx」→ 只发到当前群）
  │
  ├─ ⑤ GuardPipeline 五层（全部零成本，顺序固定）
  │      access → mention → rate-limit → content-gate → inbound-words
  │      Drop = 静默丢弃；Reply = 回固定话术；Pass = 继续
  ├─ ⑥ BudgetGuard 成本预算（每人/每群/全局每日 + 全局 token）
  ├─ ⑦ 解析引用消息（调 get_msg 取被引用的文字与图片）
  │
  ├─ ⑧ ChatService
  │      1. 模型不可用 → 固定话术
  │      2. 无文字/无引用/无图 → 兜底话术
  │      3. 检索知识库（A/B/C 三路）→ 取 top-5，拼成 <<<KNOWLEDGE>>>
  │      4. 组装 user message（场景 / 发言者 / 引用 / 资料 / 用户输入）
  │      5. 有图 → 视觉模型；纯文本 → 文本模型（走降级链）
  │
  ├─ ⑨ OutboundFilter 出站敏感词过滤
  └─ ⑩ OutboundSender（间隔 + 抖动 + 分片 + 合并转发）→ OneBotApiClient
                                                              → NapCat → QQ

  同时：QaCollector 把「问题/引用/回答/检索指标/耗时」异步投进有界队列落库，
        绝不阻塞回答线程；库写坏了也只记日志。

2.3 四条结构铁律

这四条是从代码组织上保证"改一处不会牵全身"的约束，写在 server/README.md 里，代码也确实这样分的。

  1. onebot/ 包是唯一允许出现 OneBot 协议细节的地方；
  2. OneBotApiClient 是全工程唯一能发消息的出口；
  3. llm/ 包是唯一知道"用哪个模型"的地方；
  4. guard/ 包是唯一有权说"不"的地方。

补充一条数据侧的不成文约定：所有需要长期保留的人工成果都落在同一个 SQLite 文件，知识库块存储复用 QaStore 的连接（两个连接开同一个 SQLite 文件会让 WAL 共享内存冲突，实测报 SQLITE_IOERR_SHMOPEN）。

三、技术路线与关键取舍

这一节回答"为什么是这套东西"，每条都对应一个具体约束。

3.1 协议层用 NapCat + OneBot 11，业务层完全不碰 QQ 协议

  • QQ 官方 Bot 能力有限（群聊场景受限），社区方案里 NapCat 是维护最活跃的 OneBot 11 实现；
  • 业务层与协议端之间只有 HTTP 上报 + HTTP 动作 两种交互，全部收敛在 onebot/ 包；
  • 后果：换协议端不影响业务代码，业务逻辑可以用假 NapCat（tests/manual/fake-onebot-server.mjs）端到端测试，一次不碰真实 QQ。

3.2 业务层是单体 Spring Boot，不是微服务

  • 部署目标是一台 2 GB 内存的小机器，多一个常驻服务都不划算；
  • 单体让"一条消息的生命周期"可以在一台 JVM 里看全 —— 事件 → Guard → 检索 → 模型 → 出站，全部本地方法调用，没有网络跳数；
  • 需要隔离的是慢操作（模型调用），用有界线程池 + 队列等待超时解决，而不是拆服务。

3.3 存储用 SQLite 单文件

  • 统计要用 SQL 聚合，JSONL 每次都要全表扫；
  • 数据量小（几万行）、写入是单线程批量、读多写少 → SQLite 完全够用；
  • 一个文件装下全部人工成果（统计、词条、分类、文案、轮播清单、块与向量）→ 备份就是 sqlite3 .backup 一条命令；
  • 连接复用（QaStore.connection()）+ 幂等迁移（PRAGMA table_info 补列）→ 老库升级不用删库重建。

3.4 模型接入用 LangChain4j 的 OpenAI 兼容模块

  • 只依赖 langchain4j-open-ai 一个模块，但它对所有 OpenAI 协议兼容的厂商都能用；
  • 所以加一个新厂商只要改 yml，不用动一行 Java：base-url + api-key + model-name + capabilities；
  • capabilities: [chat, vision] 决定"这个模型会不会被用来处理图片"；
  • 降级链：主模型超时/报错/返回空 → 自动切下一个厂商；空回复也当作失败（推理模型给少了 max-tokens 会"想完没预算写答案"）。
  • 选择约束（实测）：只有走 /chat/completions 的模型能用；走 /messages、/responses 的厂商接不进来。

3.5 检索走"本地向量 + 术语关键词 + 标题闸门"的混合路线

这是整套系统里决策成本最高的一块，结论来自实测而不是直觉：

决策 为什么
为什么要有知识库（RAG）而不是靠模型自身知识 游戏版本更新频繁，模型训练数据会过期；资料必须能自己维护、能看到出处
为什么用外部 embedding + 本地余弦，不接向量数据库 2,649 块 × 1024 维 = 一次全量扫描 2.64 ms；引入向量库要额外常驻进程，收益为零
为什么 A 路（正文向量）之外必须有 B 路（术语关键词） 实测纯向量把「废料杯」的正确答案排到第 69 名；术语表一击就能顶到第一。两路各有盲区
为什么两路用 RRF 按排名融合而不是分数相加 余弦（0~1）与词频累加量纲不同，直接相加没有意义
为什么关键词路权重 2.0、标题命中权重 3.0 术语命中 = "确实有这个游戏名词"，精度远高于语义相似
为什么标题精确命中要额外 +0.5 搜「废料杯」时正文提到它的 Tableware 页会压过本体；正文里几乎不重复名字
为什么加 C 路标题向量闸门而不是把它当第三路进 RRF 实测：进 RRF 反而把 R@1 从 99.5% 拉到 49.5%（A 路在"按名字提问"上是系统性错的，让它平等投票等于用一半票数抬错误答案）。闸门 + 置顶才是 99.5%，且只有 2.5% 的口语提问被误触发
为什么闸门阈值是 0.70 实测拐点：0.70 时 200 条名字查询 100% 触发、120 条口语提问仅 2.5% 误触发；0.65 → 10%，0.80 → 名字覆盖率掉到 95.5%
为什么"建索引"和"查询"必须用同一个 embedding 模型 向量模型定义了坐标系，换模型（哪怕 Pro/ 前缀）向量就不可比，必须整库重建
为什么公开站的阈值（0.32）比群内（0.45）低 群内是"给模型当依据"宁缺毋滥；公开站是"按相关度排给人看"，阈值太高会一片空白

3.6 安全设计：零成本拦截优先，纵深防御

  • 顺序即成本：五层 Guard 全部是内存计算，跑完才轮到花钱的模型 —— 攻击者无法用敏感内容或注入话术烧 token；
  • 失败即拒绝（fail-closed）：私聊策略写成不认识的值，一律按"关闭私聊"处理，而不是放行；
  • 安全默认：ADMIN_PASSWORD 留空 = 整个 /admin 返回 503，绝不退化成"无密码可访问"；
  • 纵深防御：Nginx 层限流 + IP 白名单 + 公开站域名下 /admin/ 直接 404，应用层再有一道会话校验；
  • 隐私最小化：公开接口用独立的 PublicDtos 显式拷贝，绝不复用管理接口返回值；投票只收前端随机 clientId，服务端哈希后存库，不关联到人；后台访问统计里 IP 只存哈希。

3.7 前端：双入口 + 自研组件 + 设计令牌

  • 不用 UI 框架（不用 Element/Ant）：整套只有 16 个自研组件（shared/ui/），体积小、风格统一、没有"一眼看上去是模板"的问题；
  • 两个入口（public.html / admin.html）而不是两套工程：共用主题与组件，但 publicApi 与 adminApi 在客户端层面严格分开（路径前缀不同），公开站永远不该碰到管理接口；
  • 设计令牌集中在 theme/tokens.css：配色从 wiki 官方美术素材提取（灵火橙 #e8a04c、雾蓝 #141922、苔藓绿 #6b8f5e…），只做深色；
  • 产物由后端托管：web/dist 拷到 server/web-dist/，Spring 的 static-locations 列了多个候选路径，解决"从仓库根起"与"从 server/ 起"两种工作目录的差异。

3.8 工程方法：把"宿主"和"容器"当两套环境

这套系统同时被两个环境使用：Windows 宿主机（人工开发、IDEA、pnpm dev）与 Linux 容器（自动化构建与验证）。共用依赖目录必然互相破坏，因此：

  • 后端构建走 ./scripts/build-server.sh：把 pom.xml + src 复制到 .toolchain/server-ci/ 再编，绝不写 server/target。原因是一次真实事故：宿主机 IDEA 的运行 classpath 就是 server/target/classes，容器一 clean 就把运行中 JVM 的 classpath 从脚底下抽走，抛 NoClassDefFoundError: BudgetGuard$Verdict；
  • 前端构建走 ./scripts/build-web.sh：依赖装在 .toolchain/web-ci/，用 flock 串行化，避免 pnpm store 路径冲突、平台二进制冲突、符号链接在 Windows 上 EACCES；
  • 验证脚本与探针放在 tests/，tests/manual/ 下是 20 多个"直接打真实服务"的探针（竞态、检索排名、日志、广场、登录…），tests/*.js 是 Playwright 浏览器验收；
  • 文档约定"Markdown 源 + HTML 阅读产物"分目录存放（docs/md/ → docs/html/），用仓库外的 md2html 转换，产物完全离线。

公开站检索的三层"刹车"（PublicSearchService）：

  1. LRU 结果缓存（512 条）—— 同一句话重复搜不再调 embedding API；
  2. 每日配额（默认 800 次）—— 超了静默降级为纯关键词检索，搜索照常可用、不报错；
  3. 同页去重（一个页面切成多块，不去重会出现好几条一样的条目）。

参数与群内问答刻意不同：阈值 0.32（群内 0.45）、最多返回 20 条（群内 5 条）。

问答广场的完整闭环：

关键词聚合（只展示"被点赞过"的问答 → 隐私保护的核心）
   → 每条关键词展示 top-3 回答（相似度 > 0.9 的回答合并去重）
   → 访客投票：👍 赞 / 👎 踩 / 🕐 已过时
        （只收前端随机 clientId，服务端 SHA256(clientId + 盐) 后存库；
          UNIQUE(stat_id, voter_hash) 保证每人每答案一票）
   → 二级降级「问问新答案」：3 条全被踩（踩 > 赞 且 ≥ 2）→ 调模型重新生成
        （限额：每关键词每天 3 次、全局每天 100 次）
   → 三级降级「求助大佬」：再全被踩 → 生成一句「求助：xxx」
        （限额：同问每天 1 次、每用户每天 3 次、每群每小时 1 条）

三级降级刻意不直接发消息：网页访客无法证明自己属于某个群，若能指定群号就成了"向任意群广播"的漏洞。所以网页只生成一句待办文案，由用户复制到群里 @ 机器人，群号取自群聊上下文。

  • RRF 公式：score(块) = 1.0/(10 + 向量排名) + 2.0/(10 + 关键词排名)；
  • 标题加成：标题正好等于查询里的名词 → +0.5；标题包含该名词 → +0.15（并会剥掉结尾的「（English）」再比，否则「酸性菌丝（Acidic Mycelium）」的本体永远吃不到精确加成）；
  • B 路两种匹配：① 整条名字出现在问句里（靠人工写别名）；② 把问句切成 2~3 字中文片段去匹配名字（不需要人工写别名），命中名字太多的片段整段丢弃（"便宜的停用词表，会跟着语料自己变"）。实测稳态开销 0~2 ms；
  • 硬性约定：检索链路绝不抛异常。任何一路挂了、embedding 超时、索引没建，机器人都照常回答，只是手里没有资料。

name: Flame Altar
source: wiki
url: https://enshrouded.wiki.gg/wiki/Flame_Altar
tags: 必需品, 制作台

规则 说明
文档头 首行恰好是 <!-- doc，必须有闭合 -->；name 必填，url 强烈建议（会作为出处发给群友），未知键原样保留
分块 n*= 标题 n*= <!-- id: 可选 id -->；左右等号个数必须一样，否则不是分隔符（当普通正文）
id 只允许英文字母、数字、-；约定「英文页面名-序号」；只能追加，不要跟着标题改（它是数据库主键）
key 唯一性 有 id 用 id，没 id 用标题；同一份文档内 key 必须唯一，否则整份拒绝导入
长度 单块建议 40 ~ 1600 字
语言 正文与标题用中文，id 用英文，tags 用中文
增量语义 文件里的块：id 存在 → 覆盖，不存在 → 新增；文件里没出现的块 → 一个都不动
幂等 同一份文件导两次，第二次报告"新增 0、修改 0、无变化 N"
校验 ./scripts/validate-kb-doc.sh 文档.md，退出码 0 才能导入（不启动服务、不碰数据库、不联网）

导入流程：粘贴或拖入（支持整个文件夹，批量逐份预览）→ 先预览（只算不改，告诉你"新增 N / 覆盖 M / 无变化 K / 库里未被触及 X 块"）→ 确认后导入 → 只为新增/覆盖的块重算向量并热重载。

⚠️ 改正文必须走「文档」面板 —— 只有那里会重算向量。只改文本不重算向量，检索会按旧正文匹配，等于没改。

5.4.4 词条（原"术语表"）

  • 字段：en（块 id 对齐的英文标识）、zh（中文名，别名不是单独的列，就是 zh 里用「、」分隔的若干写法）、status（draft / verified / rejected）；
  • 状态只排除 rejected：draft 与 verified 都参与检索 —— 状态是给人看的进度，不是准入门槛；
  • 零成本、立即生效：补一个词就能让 B 路命中一个新说法，性价比最高；
  • 批量导入：Excel 另存 CSV（认中英文表头 英文名/中文名/别名/状态），旧的按列位置的 TSV 也仍可导。

5.5 问答记录与统计

两层数据策略：

表 存什么 生命周期
qa_raw 问题原文 / 引用原文 / 回答原文 定期删（默认 180 天，0 = 永不删）
qa_stat 时间 / 群 / 用户 / 检索指标 / 耗时 / 标注 永久
qa_keyword 从问题抽出的游戏名词 永久

三条硬性约束（都有单测守着）：

  1. 投递立即返回，绝不在回答线程里碰数据库；
  2. 队列有界（2000），满了丢弃并计数 —— 宁可少记一条，不可积压内存；
  3. 存储故障时只记日志，机器人照常回答。

追问检测：同一个人 60 秒内又问一次，自动把上一条标为 follow_up —— 不花钱的准确率信号（答好了通常不会马上再问）；只覆盖未标注的记录，不动人工结论。

统计口径（后台看板）：问答总量 / 命中率 / 独立用户与群 / 实际作答数；关键词排行（含未命中次数）；两类未命中（"连词都没认出来"与"认出来了但库里没答对"）；最高余弦分布（调 min-score 阈值的依据）；检索来源占比（vector / keyword / both / title）；人工标注分布。

记录里同时保存 best_cosine（卡阈值之后的最高余弦）与 best_cosine_raw（卡阈值之前的）—— 只有后者能区分"库里根本没有相关块（如 0.2）"和"差一点点被阈值挡住（0.43）"。

5.6 日志与可观测

日志落三处（logback-spring.xml）：

  1. 控制台 → systemd 收进 journal；
  2. 滚动文件 data/logs/qqbot.log（20 MB 一个、保留 7 个、总量上限 200 MB）—— 进程崩了之后唯一留存的地方；
  3. 内存环形缓冲（2000 条，DEBUG 不进缓冲）→ 后台"实时日志"页的 SSE 数据源。

两个数据源刻意分开，用于定位故障层级：

群里 @ 机器人
   ├─ NapCat 日志里没有这条消息  → 协议层问题（掉线/风控）
   ├─ NapCat 有、业务层没有      → 上报失败（ECONNREFUSED）
   ├─ 两层都有但没回复           → Guard 拦了 / 预算熔断 / 模型挂了
   └─ 都正常但答得不对           → 检索或提示词问题

脱敏默认开启：token / 密钥 / QQ 号 / 带签名的 URL 在进入网页缓冲前就被替换（日志页可能被截图外发）。

八、配置体系

8.1 三层优先级（高 → 低）

① server/config/overrides.yml      ← 配置中心 / 模型页写入的覆盖层（最高）
② 环境变量 与 仓库根 .env          ← 密钥与部署期差异
③ server/src/main/resources/application.yml   ← 代码默认值
  • .env 是 properties 格式（一行一个 KEY=value，值不要加引号）；DotenvEnvironmentPostProcessor 会从工作目录向上找工程根（AGENTS.md / server/pom.xml），与工作目录无关；
  • overrides.yml 不能有重复的顶层键 —— 曾经两个写入方各写各的，生成了两个 app: 块导致 YAML 解析失败、服务起不来。现在统一走 OverridesFile：读全量 → 合并 → 按路径树整份重写。

8.2 配置中心（后台"设置"页）

  • 可写白名单是安全的核心：只有 SettingsWhitelist 里列出的项才允许从界面修改，其余一律拒绝（即使有人伪造请求改 app.persistence.db 也会被挡掉）；
  • 分类原则：🟢 可写 = 纯业务行为（话术、开关、限流数值）；🔴 禁写 = 基础设施（端口、数据库路径、线程池）与密钥；
  • 覆盖 61 项，分 13 组：回复行为 / 频率限制 / 话术 / 成本预算 / 出站节奏 / 首页轮播 / 回复风格 / 功能开关 / 指令系统 / 媒体 / 知识库 / 站点信息 / 统计；
  • 保存即热生效（写进 overrides.yml，下一轮判定就读到）。

9.3 构建与发布

脚本 做什么
./scripts/build-server.sh 隔离构建：复制到 .toolchain/server-ci/ 再编，产物同名 target/，绝不写 server/target（保护宿主机正在运行的 IDEA 进程）；默认离线（MAVEN_OFFLINE=1）

9.5 NapCat 稳定性（踩过的坑）

  • 掉登录的根因：腾讯的设备指纹 GUID = MD5(/etc/machine-id + MAC)。容器重建会分配新随机 MAC → GUID 变 → 票据作废；
  • 对策：固定 mac_address（必须填当前正在用的值）、挂载固定的 /etc/machine-id、用 NAPCAT_QUICK_ACCOUNT（注意不是 NAPCAT_QQ，那个变量在源码里不存在）或 WebUI 的"快速登录"，实测重启后 41 秒自动登录成功；
  • 风控侧：最新 NapCat + 最新 QQ 会被频繁踢下线（社区 Issue #1728），建议固定到实测稳定的版本；曾有"公网无 token 的 OneBot 被扫导致大规模封号"的事件 —— 所以端口只绑回环。

  1. SQLite 主库 —— 一个文件装下全部人工成果：sqlite3 data/qa/qqbot.sqlite ".backup /backup/qa-$(date +%F).sqlite"；
  2. data/site-images/ —— 首页轮播图（管理端上传，丢了只能重新找图）。

# 问题 影响
1 标题**精确加成（+0.5）**也会发给"中文片段猜出来的词" 猜出的近义词会吃到满加成，可能把正主压在后面

5 后台是单管理员内存会话，重启即失效 无多管理员、无审计账号

附录 B：术语表

词 含义
块（block） 知识库的最小检索单位，有稳定 id；一个 Wiki 页面/一个主题通常切成多块
词条（term） 块对应的名字对象（中文名 + 别名 + 状态），B 路关键词检索的命脉
A / B / C 路 正文向量 / 术语关键词 / 标题向量闸门，三条召回通道
RRF Reciprocal Rank Fusion，按排名而非分数融合多路结果
闸门（gate） 标题向量的高阈值判定：命中就置顶那一条块，不参与投票
Guard 安全中间层的五层零成本拦截流水线
Stage Guard 的一层；任意一层返回非 Pass 即中断
降级链 主模型失败后自动切下一个厂商
临时件 / 知识库件 图片的两种生命周期，物理隔离
一键下架（retire） 检索不再使用，但数据保留、可恢复（区别于 delete）
