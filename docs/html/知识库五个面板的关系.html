知识库的五个面板：它们到底是什么关系

面向第一次接触「知识库」页的人。回答一个具体困惑：关键词、术语核对、分类、提案、资料——看着都差不多，到底谁是谁？

〇、先给一句话结论

它们不是五个相似的东西，而是「三个视角 + 两条入口」。

  • 三个视角看的是同一份知识：分类（货架）、关键词（货品）、术语核对（货品的名字翻译）。
  • 两条入口管的是知识怎么进来：资料（从外面收）、提案（从问答里挖）。

真正长得像的只有「关键词」和「术语核对」——因为它们本来就是同一批对象的两个侧面。分类是这批对象的属性；提案和资料则完全是流程，不是知识本身。

一、底层其实只有一条链

知识库落到磁盘上，就是下面这几样东西（都在 server/data/kb/）：

分类（货架）        关键词 / 词条（货品）        文本块              向量
cats[] 字段   →   chunks.jsonl 的 title   →   chunks.jsonl 正文  →  index.bin
 603 个原始分类        3,630 个 Wiki 页面          4,131 段文字          4131×1024 维
 归并成 9 个大类
层 是什么 存在哪 参与检索吗
分类 Wiki 的 603 个编辑用分类 → 归并成 9 个玩家能懂的大类 chunks 的 cats[] 字段 ❌ 完全不参与
关键词 一个 Wiki 页面 = 一个词条（实测 3,630 个） chunks 的 title 字段 ✅ 命中的就是它的文本
文本块 一个页面被切成的若干段（≤1600 字） chunks.jsonl ✅ 检索的直接目标
向量 每一段算出来的 1024 维数字 index.bin（与块同序） ✅ 检索核心
术语表 中英对照：英文名 / 中文名 / 页面 / 类别 / 状态 SQLite kb_term 表（2026-09-27 从 glossary/zh-en.tsv 迁入） ✅ B 路关键词检索的命脉

关键点：这套「分类 → 关键词 → 文本块」的分层不是新造的数据，它在语料里本来就有， 只是以前没有一个界面这样呈现它。后台只是把这几个字段拉出来给你看和改。

二、五个面板逐个说

1. 分类 —— 货架怎么摆

  • 管什么：把 Wiki 的 603 个原始分类，映射成 9 个玩家能懂的大类（战斗装备 / 建造装饰 / 材料消耗 / 敌人生物 / 地点探索 / 任务剧情 / 系统机制 + 大佬攻略 + 其他）。
  • 为什么需要：原始分类是给编辑用的，比如「Early Access Launch」这种版本更新分类占了 669 条，玩家根本不知道那是什么；还有 349 个分类只出现过一次。
  • 参与检索吗：不参与。改分类只影响公开站「按类别找资料」的浏览体验，不影响问答质量，可以放心大改。
  • 成本：秒级，不花钱。
  • 穿透：点某个分类的「N 条目」、或大类卡片上的「查看条目」，直接列出这个分类下具体有哪些条目（块 id、所属文档、标题、正文摘要），可以再搜一次收窄。列表和卡片上的数字走同一份语料、同一套过滤口径，所以条数一定对得上——对不上就说明有一边读错了存储。

2. 关键词 —— 库里有什么

  • 管什么：一条关键词 = 一个 Wiki 页面 = 一个词条。展开能看到它被切成的每一块文本，可以直接改（覆盖）。
  • 能做什么：改中文名 / 别名、挪板块、标术语状态、整个词条或单个文本块下架（下架 = 检索不再用它，不是删除）、新建词条。
  • 改动成本：改一块文本只需重算那一块的向量（1 次 embedding 请求），行号不变——所以不会让你以前的历史引用失效，也不是全量重建。

3. 术语核对 —— 名字翻译对不对

  • 管什么：术语表（kb_term 表，2026-09-27 从 zh-en.tsv 迁入）的人工核对工作台。每条有状态：draft（机器初稿）/ verified（已核对）/ rejected（不要用）。

  • 现状：3,358 条里 3,357 条还是 draft，只有 1 条 verified。这就是「术语核对」面板存在的理由——它是个内容活，不是代码活。

  • 为什么重要：群内检索的 B 路逻辑是「把中文词换成英文词，再去英文语料里找」。术语表里没有的词，B 路就找不到。所以补术语表 ≈ 直接提升检索命中率，而且零成本、立即生效。

  • 和「关键词」什么关系：术语表的英文列有 99.4% 与关键词标题一致。也就是说——术语表就是关键词的中英别名层。关键词面板和术语核对面板，看的是同一批对象：

    • 关键词面板问的是「这条词条内容长什么样、属于哪个板块」
    • 术语核对面板问的是「这条词条的中英文名字翻得对不对」

    一个证据：在关键词面板里改中文名，走的其实是 /glossary 接口。它们本来就是一份数据。

4. 提案 —— 从问答里挖改进建议

  • 从哪来：管理员在「问答记录」里给回答点「有帮助」→ 累计到阈值（默认 10 条）→ 点「让 agent 分析」→ agent 拿这些被人工认可的回答，和知识库现有文本比对，产出提案。
  • 两种提案：
    • overwrite：库里有这个词条，但内容过时/不全 → 建议覆盖
    • new：库里根本没有 → 建议新增
  • 重点：提案只是候选，不自动落库。模型幻觉会静默污染知识库，所以必须人工确认。
  • 采纳后去哪（这就是它和其他面板的接口）：
    • overwrite → 直接覆盖该关键词的第一块文本（单块重嵌）
    • new → 投递进「资料」队列，走「审核 → 增量建索引」

5. 资料 —— 往库里加新东西

  • 管什么：这条链的四件事——发邀请码 → 收投稿 → 审核 → 增量建索引。

  • 谁在投：公开站的用户，凭邀请码投稿（所以面板里有邀请码管理）。

  • 状态流转：

    pending ──审核通过──> approved ──建立索引──> indexed
   │                      │
   └──审核拒绝──> rejected  └──（可撤回）

    只有 indexed 的才出现在公开站，未索引的一律不可见。

  • 成本：建索引要给新增段落算向量，按量计费（而且必须用同一个 embedding 模型 BAAI/bge-m3，换模型就得全量重建）。

三、把它们串起来

   问答记录里点「有帮助」                        公开站用户凭邀请码投稿

            ↓                                              ↓ 审核

一句话读法：提案和资料是两条河，最终都汇进「关键词 → 文本块」这条主链；分类是河床的形状，术语核对是主链上每个词条的名牌。

四、对照速查表

面板 它管的数据 一句话 参与检索 改动成本

资料 contributions（问答库） 从外面收进来的新资料 ❌ 索引后才进 建索引按量计费

完善知识库的性价比排序

优先级 做什么 成本 效果
1 补术语表（术语核对） 零成本、零等待 ★★★ 直接提升 B 路命中率
2 改分类标签 零成本 只影响浏览体验
3 新增资料段落 要算向量（花钱） 补充 Wiki 没覆盖的
4 全量重建 21 秒 + 全部 embedding 费用 只在换模型 / 改切块 / 改清洗时做

结论：「完善知识库」的重心应该放在 1 和 2。

五、给新用户的阅读顺序

  1. 先当读者：进「关键词」，随便点开一条，看它怎么被切成好几块文本——理解「词条 = Wiki 页面 = 若干文本块」。
  2. 再看骨架：进「分类」，理解货架是怎么从 603 个原始分类归并来的。
  3. 再看名牌：进「术语核对」，理解它和「关键词」是同一批对象的两个面。
  4. 最后看入口：先看「资料」（外部怎么进），再看「提案」（内部怎么挖）。

前三步建立「知识长什么样」，后两步建立「知识怎么变多」。

六、为什么「术语核对」不能直接合进「关键词」删掉

一个很自然的想法：既然 99.4% 重合，那就在关键词上做中英互译，把术语核对这个 tab 删了。

结论：可以做界面融合（而且已经合了一半），但「删掉」会丢掉三样东西。 下面是实测数据。

6.1 先纠正前提：不是「99.4% 相同」，是「交集 3,340，两边各有对方没有的」

数量 key 空间是什么
关键词 3,630 chunks.jsonl 的 distinct title —— 有正文的页面
术语表 3,359 pages.jsonl 里的 Wiki 页面 —— 全部页面
交集 3,340 术语表的 99.4% 是关键词；关键词的 92.0% 有术语条目
只有术语表有 19 见下
只有关键词有 290 Bamboo Bench、Bamboo Cage I、Copper Bars… 全是还没中文名的具体物件

关键在两边各有的那部分：

  • 只属于术语表的 19 条：Equipment、Lore、Weapon Subtype、Weapons/Perks、Sets/Clothes、Sets/Unique Equipment…… 它们是 Wiki 页面存在、但没产出任何文本块的页面（全库 3,908 个页面里有 278 个产出 0 块：重定向页、汇总页、消歧页、版本页）。 而这 19 条恰恰是最口语的伞形词：「装备」「传说」「套装」。

  • 为什么这类词仍然有用：B 路是「把中文换成英文，再去正文里找」——不要求这个英文词是某个文本块的标题。实测：

    术语 命中含它的文本块
    Equipment 44 块
    Lore 404 块

    也就是说：「装备」这个词条在「关键词」面板里根本不存在这一行（没有正文 → 进不了 3,630 的集合），但它对检索很有用。只改关键词 = 这 19 条无处可改，也永远补不了新的同类词。

6.2 「在关键词上做中英互译」这件事，其实已经在做了

  • 关键词面板的筛选器里本来就有「术语状态」：draft / verified / rejected / **none**，其中 none 就是那 290 条没有术语条目的关键词（后端 KbKeywordService.stats() 的 noGlossary）。
  • 在关键词面板里改中文名，走的接口就是 /glossary（整条 upsert，还得把原来的 page / category 原样带回去）。

所以现状不是「两套数据」，而是一份数据、两块工作台。你的直觉方向是对的，系统已经在往那个方向走了。

6.3 那为什么还要单独留一个 tab

理由 具体是什么
工作单元不同 关键词的单位是页面/实体；术语表的单位是词。B 路匹配的是词，不是页。
工作方式不同（主要理由） 术语核对是一条 3,359 行的流水线校对队列：批量勾选、快捷键、核对进度条、draft/verified/rejected 三态、切换 tab 保留草稿。关键词是实体浏览器：展开看块、改文本、挪板块、下架。把 3,359 行的流水线塞进树形浏览器，两个体验都会变差。
失效面不同（安全理由） chunks.jsonl 行数必须恒等于 index.bin 的 N，写坏不报错，而是机器人从此静默不带资料回答。所以关键词的写路径全是「备份 → 临时文件 → 原子替换 → 校验行数 → 失败回滚」。术语表是运行时加载的独立 TSV，改坏了只影响 B 路命中，不碰向量、不花钱。合并 = 每一次改中文名都要走那条最危险的写入路径。
它是可交换的工作格式 5 列 TSV，可以直接丢进 Excel 批量校对，也可以发给别人翻译；不依赖后台。

补充一句诚实的：「一词多译」不是理由——实测 3,359 条里只有 2 条的中文名写了多别名（灵火祭坛、火焰祭坛）。所以别拿这个当借口。

6.4 真要动，方向是「打通」而不是「删除」

  1. 术语核对 → 关键词：每条术语加一个「跳到词条」链接（对有正文的那 3,340 条）。
  2. 关键词 → 术语核对：那 290 条 none 直接给个「补中文名」入口（现在只筛得出来，不能一键补）。
  3. 单独列出「有术语、没正文」的 19 条——这是目前唯一一块只有术语核对看得见的区域，也正是不该删掉它的直接证据。
  4. 可以顺手清理的：有 17 条术语（全是 Sets/*、Weapons/*）在语料正文里一次都没出现过，当前对 B 路零价值。
