wiki 图片资产：可行性、容量与难点

审计日期 2026-10-24 · 对象：kb.wiki 导入链路与 media 出站链路 · 数据来源：wiki API 实测 + 本机生产库 server/data/qa/qqbot.sqlite

结论：能做，而且基座已经具备大半。发图链路是通的：提示词教模型用 [[img:...]]、资料注入会把标记提到块尾、ImageLibrary 按来源分派、KbImageSource 从目录读字节、出站限 2 张 / 2048KB。缺的只有一段：从 wiki 页面里选出主图、下载落盘、在第 1 块末尾写一个 marker。

存储不是瓶颈。按"每页 1 张主图"算，当前 3,986 页大约 100~250MB；即使把全站约 4,500 张图的原图全部镜像下来也只有 约 2.5GB。50G 够用。

真正的瓶颈有两个：上游 Cloudflare 的突发限流，和"选错图"。前者决定你要花几小时还是几晚上，后者决定这个功能是加分还是扣分 —— 给技能页配一张属性点图标，比不配图更糟。

已落地 · 2026-10-25。P0 已按本文第三节实现，并已提交 e1d4b18：

  • kb/wiki/WikiImagePicker 从渲染 HTML 的 .druid-main-image 选主图，文件名过白名单；
  • kb/wiki/WikiImageStore 下载、原子落盘、共享图标过滤、目录配额；
  • media/WikiImageSource 解析 [[img:wiki:页面/文件]]，与 kb / map 两个来源并列；
  • UpstreamGate 从 kb.map 提到 media 并做成唯一 Bean，地图与配图排同一条队；
  • WikiArticleImporter 只在第 1 块末尾写 marker，任何失败都不影响正文。

首次生效要在管理端「知识库 → 抓取」点一次「强制重洗全部」：老块的 revid 没变，不会自己补图。按 6 秒一张估算，4,000 页约 4~5 小时，建议夜里跑，并且不要同时开地图预热。

一、现在为什么拿不到图

不是发不出去，是语料里从来没有图。三层各丢一次：

位置行为后果
WikitextCleaner.NOISE_KEYSimage / images / icon 被当作噪声参数丢掉infobox 的文件名进不了正文
WikitextCleaner.stripGalleries只取 [[X|标签]] 的标签，文件名与 link= 全丢gallery 被压成一串文字清单
WikiHtmlCleaner.walk只走文本节点，<img> 从未被读取渲染兜底拿回了正文，但图仍然没有

关键发现：图片 URL 其实已经"顺带"拿到了。渲染兜底对每一页都会调一次 action=parse，这一步返回的 HTML 里就带着 infobox 主图的 <img src> 与 srcset。也就是说，选图不需要新增任何 API 请求，新增的只有下载的那几十 KB。

出站这一侧已经是完整的

已有能力位置
标记协议 [[img:来源:名字]]，模型只许照抄，不许自己拼system.md:16、media/ImageMarkers.java
资料注入时把单张标记提到块尾，防止模型改写正文时把它一起改掉kb/TwoSectionInjector.java、kb/KbLookupTool.java
按来源前缀分派到不同的 ImageSourcemedia/ImageLibrary.java
本地字节直接读盘，不依赖公网地址media/KbImageSource.java
一条回复最多 2 张、单张 2048KB 的闸门media/OutboundImages.java
地图截图已经在用同一套标记kb/map/MapShotSource.java、[[img:map:...]]

所以这次不是从零做发图，而是给已有的发图链路补一个内容来源。

二、实测数据

2.1 全站图片有多大

list=allimages 抽 500 个文件，其中图片 401 个，合计 215.9MB：平均 551KB，中位 361KB，P90 1.1MB，最大 14.1MB。全站 5,602 个文件里图片约占八成，推算 约 4,500 张图、原图合计约 2.5GB。

2.2 正文实际引用了多少

取 4 个分类共 69 页，用 prop=images 展开：579 个不同文件，合计 45.1MB，平均 80KB。每页约 8.4 个引用，其中大量是跨页共享的图标：Skill Point.png、Blunt Damage.png、Quest marker.png。

这组数字说明一件事：页面引用的图里，大多数不是"这一页的图"，而是全站复用的 UI 图标。直接按引用全抓，既浪费空间，也会让回答里出现一张与问题无关的图标。

2.3 主图覆盖率：物品页很好，剧情页没有

抽样 24 页，检查渲染后 HTML 里的 .druid-main-image img：

分类有专用主图观察

Cosmetic Armor6 / 6同上，装备图标

主图是 250px 缩略图，实测 29~90KB。物品、装备、怪物、Boss 这类页面天然有主图；任务与剧情页几乎没有。这正好对应"看图才有意义"的问题类型：这件装备长什么样、这个怪长什么样。

三、推荐方案

3.1 管线

导入一页
  └─ 已有：action=parse 取渲染 HTML，每页一次，零新增请求
       └─ 选图：.druid-main-image img 的 src / srcset
            └─ 过滤：共享图标黑名单 + 体积/类型校验
                 └─ 下载：Special:FilePath?width=480，或 HTML 里的 thumb URL
                      └─ 落盘：data/wiki-images/<sha1前2>/<sha1>.<ext>
                           └─ 打标：第 1 块末尾写 [[img:wiki:<sha1>]]
                                └─ 回答时：ImageLibrary 解析 → 读字节 → QQ 出图

3.2 几个必须定下来的选择

决策选择理由
图片从哪来渲染 HTML 的 infobox 主图它是最终展示图；wikitext 的 image= 常常是文件名列表或未解析模板
键怎么定内容 sha1天然去重；文件换了版本自动换键，旧文件变孤儿可回收
存哪里data/wiki-images，与 kb-images、tmp-images 三向隔离清理脚本绝不能误删永久资产；启动守卫照 MediaStorageGuard 的做法加一条
什么时候抓独立、可续跑的后台任务4,000 页乘 6 秒是几个小时，不能塞进正文导入
缩放交给谁MediaWiki 的 ?width=2 核机器上不要在 JVM 里解码再缩，CPU 与堆都不值
失败怎么办单页失败只记状态，不影响正文与现有渲染兜底同一条纪律

四、难点，按严重程度排

4.1 上游限流 —— 唯一能卡住整个功能的

项目里已经有一段实测记录：2026-10-15 直接探对方，连两个从未取过的瓦片、间隔 6 秒，仍然都是 429，而且没有 Retry-After。所以地图取图的默认间隔被定成 6 秒，连续三次就整条暂停五分钟。

2026-10-24 我又抽测了一次：约 12 次图片请求，间隔 0.8~1.5 秒，全部 200，没有触发 429。这说明它更像突发限流而不是永久封禁，但也不能据此把闸门拆掉。

  • 必须共用闸门。地图预热与 wiki 抓图如果各开一个客户端，两边都会觉得自己很克制，合起来就把额度打穿。现在的 UpstreamGate 是包内可见，需要先挪到共享位置。
  • 必须可续跑。4,000 页按 6 秒是 6 小时以上，中途被暂停、重启、断网都得能接着跑；否则每次都是从头再撞一次。
  • 记住"没有这张图"。wiki 上确实有声明了但没上传的文件；不记就会每次重问。地图那边已经有 12 小时的 missing TTL，照抄即可。

4.2 选错图 —— 比没有图更伤

技能页 Arachnoid 的主图是 Attribute_Node_Green_Medium.png，这是全站复用的属性点图标。如果直接取"infobox 第一张图"，技能类问题会稳定配上一张属性点图标。

  • 用引用频率当黑名单。统计每个文件被多少页引用，超过阈值就判为共享图标，不配图。这个规则自带维护性，新增图标不用改代码。
  • 报告 0 图页。抓完列出"有页面但没选中图"的清单，人一眼能看出是页面本来没有，还是选择器失效了。
  • 宁可没图。标记不存在时出站链路本来就什么都不做；把这条当默认，不要为了覆盖率硬凑。

4.3 marker 进正文，就要重算向量

现在的增量判据是 revid，清洗器改了不会自动重洗。把 marker 写进块正文，等于整库 wiki 块都要重洗一次：7,357 块、335 万字，每块一次正文向量加一次标题向量，约 1.5 万次 embedding 调用。按量计费不贵，但时间是几个小时。

写法成本说明
marker 进正文一次性重洗 + 重新 embedding最简单，一个真相源；与现有文档配图的做法一致
旁路表 block_id → image_key零重洗检索时拼上去；要多一张表与两个注入点，块重切时按页面 id 迁移

建议先走"进正文"，因为它复用现有全部机制；如果重洗时间不可接受，再上旁路表。

4.4 版本漂移与孤儿文件

wiki 的 revid 只覆盖页面正文，不覆盖文件本身。图片被重新上传、改名、删除时，页面 revid 可能一个字都没变。

  • 用 sha1 做键，文件内容一变就是新键，旧键自然失效。
  • 定期回扫：只对"有图片的页"重新查一次 imageinfo 的 sha1，成本很低。
  • 孤儿回收：扫全部块正文里出现的 [[img:wiki:...]]，磁盘上没被引用的文件进回收站，给 7 天宽限。不要立刻删 —— 一次导入失败就可能让一批图暂时没有引用。

4.5 2G 内存与 2 核

不要把图片读进 JVM 再缩放。地图那边已经把缩放交给 MediaWiki 的 ?width=，这条路直接复用。出站时的峰值是单张 2.33 倍：byte[] 一份加 Base64 1.33 份；一张 100KB 的主图可以忽略，但别把上限放到 2MB 以上还允许一条回复两张。

4.6 版权与署名

wiki 的授权是 CC BY-SA 4.0。转发图片需要署名，而当前 reply-style.include-sources 是 false。这是个产品决定，不是技术障碍：要么在带图的回答末尾加一行来源，要么只对内部群使用。建议加一行，成本很低。

4.7 其他

项注意点
路径安全文件名来自上游，含空格、引号、括号；拼路径前必须校验，防目录穿越
失败隔离单页图片失败不能拖垮正文导入

六、验收清单

  1. 抓图报告：页数、成功、0 图、失败、字节数、限流次数，缺一项都不算完成。
  2. 黄金集门禁：重洗后跑 RetrievalGoldenTest，四项指标不得退化。
  3. 单测：物品页有图、剧情页无图、技能页图标被过滤、路径穿越被拒、配额淘汰正确。
  4. 压测：3 条并发回答各带 2 张图，堆峰值小于 400MB，发送队列不积压。
  5. 运维：磁盘水位、抓图失败率、孤儿文件数三个指标能在管理端看到。

七、不建议做的事

做法为什么不建议
全站原图镜像2.5GB、7.5 小时、收益接近 0
运行时按需回源群里要等 6 秒以上，而且必撞限流
在 JVM 里缩放或转码2 核 CPU 花在这上面不值
每页抓多张一条回复最多 2 张，抓多了也只是躺在磁盘上

一句话落地建议：P0 只做"物品/怪物页 1 张主图"，用现有渲染 HTML 选图、独立任务下载、第 1 块尾写 marker。这一版就能覆盖大多数"这东西长什么样"的问题，磁盘只多 100MB 左右，风险也最小。
