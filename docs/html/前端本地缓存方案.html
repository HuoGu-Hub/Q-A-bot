前端本地缓存方案

结论

没做。两端都没有应用级缓存：每次进入一个页面，组件从零挂载，数据全部重新请求一次。现在补上了，写在 API 客户端那一层，视图一行没改。

层排查时的状态证据
应用级数据缓存没有 没有 store、没有 TTL、没有请求去重web/src/shared/api/client.ts:24 的 request() 直通 fetch；各视图 onMounted 里直接调
路由级保活没有 只有合并页内部的 tab 用了 KeepAliveweb/src/public/App.vue:109、web/src/admin/App.vue:134 都是裸 <component :is>
浏览器 HTTP 缓存公开站有，后台没有公开 JSON 30–300 秒，见 PublicCacheAdvice.java:27-79；后台被 Nginx 显式 no-store，见 deploy/nginx/qqbot-domain.conf:220
Service Worker / IndexedDB没有全仓无 serviceWorker、indexedDB；localStorage 只存主题与语音群号
模块级单例只有三处useSiteText.ts:29 的 site、botName.ts:15、useAuth.ts:33

公开接口那层 60 秒 HTTP 缓存是唯一在起作用的缓存，但它救不了切页：组件照样重建、照样从骨架开始、过期后照样全量重取。后台接口则是连这层都没有。

证据

每个页面都是同一个模子：onMounted 里发请求、写 loading、组件卸载时状态一起丢掉。

公开站的配额是每分钟 60 次。按首页 2 次算，来回切 30 次就见底；地图页 3 次起，切 20 次见底。后台不受 Nginx 限流，但统计页那 8 个并发查询打在 SQLite 上，每次切页都要重新等一遍。

为什么体感是“一直加载中”

  1. 进入页面：组件全新挂载，loading = true，先渲染骨架。
  2. 发请求：没有任何缓存可查，全部走网络。公网或内网穿透下单次 200–500 ms。
  3. 撞限流：Nginx public_api 60r/m 加 burst 20，超了直接 429；应用内 PublicRateLimiter 还有一层 60/min。
  4. 429 之后：不会自动重试。HomeView 显示一行错误，LibraryView.loadGroups 直接 catch 吞掉，MapView 停在半屏空态。
  5. 再切一次：又从第 1 步开始，而且配额更少了。

真正的问题不是某一页慢，而是每次都要重新证明一次“我拿得到数据”。用户越急着来回看，越容易把配额打穿，于是越切越慢、最后整屏报错。

地图页为什么单独还在请求

第一轮改完之后，后台其余页面切来切去已经不发请求了，只有地图页还在发。原因有两个，一个是设计如此，一个是 bug。

点位被拉了两遍

地图页有两条装载路径：boot() 和 watch(mapName)。boot 把 mapName 设好之后自己 await loadMarkers() 一次，赋值又触发了 watcher，watcher 再拉一次。公开站与后台的地图页都是这个写法。

没有缓存时这两次调用被同一个在途请求挡住了，看不出问题。加了缓存之后，第一次调用把缓存「用掉」并把本次访问标记为已读，第二次就被当成「用户手动刷新」，于是真的打到网络 —— 每次进地图页固定多一次 /map/markers。

改法：换图只留一个入口。boot 与跳转都改走 selectMap()，它只改 mapName，点位交给 watcher 去拉，然后等 watcher 的任务结束。后台的「重新载入」按钮传 force，值没变也能重拉。

状态栏没进缓存

/map/status 是瓦片缓存与后台任务的读数，/map/anchor 是待复核点位。上一轮把它们当成「实时状态」排除在缓存之外，于是每次进页面固定两个请求。

它们其实是「补信息」：不挡首屏，晚十秒也不影响判断。现在按 10 秒与 30 秒缓存；点任何操作按钮时先发的写请求会整端失效，所以轮询与操作后的刷新仍然拿新数据。

状态栏按 tab 懒加载

再往前一步：这三份数据只在「点位列表」与「同步与状态」两个 tab 里出现，标注页一样都不显示。而它们原本是在 boot() 末尾无条件拉一遍的。

现在改成切到这两个 tab 时才拉一次。打开地图只看一眼点位再走，这三条请求一条都不会发；「重新载入」仍按当前 tab 刷新。

三处改完，停留在标注页时，地图与别的页面之间来回切不会产生任何 JSON 请求。

方案

三件事，前两件解决“重复请求”，第三件解决“撞了限流就卡死”。已经按这个方案改完。

A. 缓存建在 API 客户端这一层

视图是“进页面 → onMounted → load()”的模子，把缓存写进三十个视图既改不完也说不清策略；写在 client.ts 里，所有页面同时受益，TTL 表也只有一个文件可审。

只缓存白名单。默认不缓存，新增接口忘了登记，行为就是“跟以前一样每次都请求”，不会出现改了不生效。

B. 同一次停留只吃一次缓存

这条是这一版最关键的一处：光有 TTL 会让“手动刷新”在有效期内拿到旧值，用户点了刷新却什么都没变，比慢更难解释。

所以缓存条目记一个“最近一次被读取时所在的页面访问序号”。切页会让序号加一，于是：

  • 切走再切回来 → 序号变了 → 命中缓存，不请求。
  • 停在同一页点刷新 → 序号没变 → 条目本次已经用过 → 照常请求。

页面访问的边界由两个路由的 afterEach 各调一次 beginVisit() 标记。不需要给十二个面板各加一个 fresh 参数。

C. 429 按 Retry-After 退避一次

request() 里：响应 429 且 Retry-After 不超过 3 秒时等这么久重试一次；仍失败就抛 ApiError，消息统一成“请求过于频繁，N 秒后再试”。错误一律不进缓存。

这一条比调大限流更该做：它保证一次抖动不会变成一整页红字。

失效规则

写请求成功后清空该端的全部读取缓存，后台写清后台，公开投票清公开。粒度做得再细也不划算：一次保存后多取一次数据的代价，远小于“改了没生效”带来的困惑。登录与退出也会清一遍，换账号看不到上一个人的数据。

实现

新增两个文件，客户端接一层分支，两个路由各加一句。视图零改动。

// web/src/shared/api/cache.ts
export function cachedGet<T>(key: string, rule: CacheRule, fetcher: () => Promise<T>): Promise<T> {
  const hit = store.get(key)
  // 新鲜 + 本次停留还没读过 → 直接给
  if (hit && hit.servedAt !== visit && Date.now() - hit.at < rule.ttl * 1000) {
    hit.servedAt = visit
    return Promise.resolve(hit.data as T)
  }
  // 同一路径正在飞：复用，不重复发
  const running = inflight.get(key)
  if (running) return running as Promise<T>

  const task = fetcher()
    .then((data) => { store.set(key, { data, at: Date.now(), servedAt: visit }); return data })
    .finally(() => { inflight.delete(key) })
  inflight.set(key, task)
  return task
}

再加一条上限：条目超过 120 条就丢掉最旧的一条。地图点位单个就有几百 KB，长时间浏览不该把它们全堆在内存里；这一层要的是“切回来还在”，不是“永久保留”。

// web/src/shared/api/client.ts
function read<T>(scope: Scope, path: string): Promise<T> {
  const rule = ruleFor(scope, path)
  const url = urlOf(scope, path)
  if (!rule) return request<T>(url)
  return cachedGet<T>(`${scope}:${path}`, rule, () => request<T>(url))
}

async function write<T>(scope: Scope, path: string, init: RequestInit): Promise<T> {
  const result = await request<T>(urlOf(scope, path), init)
  invalidate(scope)
  return result
}

验证

  • pnpm typecheck 通过。
  • pnpm build:only 通过，产物正常。第二轮改动后重跑，同样通过。
  • 14 条行为断言全部通过，覆盖：TTL 命中、切回不请求、同页刷新重取、并发只发一次、写后失效、两端同名路径不串。

没有在真实后端上跑端到端：本地没有可用的服务端会话。第一次部署后用浏览器 Network 面板走一遍“首页到资料库到地图来回切十次”，JSON 请求应当只剩首轮。

不做的做法

  • 不用 localStorage 持久化接口数据。 后台数据涉及权限，登出后残留在磁盘上是事故；公开站用 HTTP 缓存已经够了。
  • 不引 pinia 或 TanStack Query。 现有视图是一段 load() 加几个 ref，加一整套 store 只会让改动面翻几倍。
  • 不拿 KeepAlive 当缓存。 组件活着不等于数据新鲜，而且地图页与日志页的定时器会被一直留着。
  • 不把 TTL 调成无限，也不设成 0。 前者会让后台改了不生效，后者等于没做。
  • 不靠调大限流解决。 配额是防刷的保护，问题在于前端在浪费配额。

后续可调

  1. 首屏预填。 命中缓存时仍要过一个微任务才回填，理论上骨架可能闪一帧。实测这一帧通常落在同一帧内，真觉得闪就加 peek() 预填初值，改动只在四个公开页。
  2. 后台 TTL 是否再短一些。 现在是 30–60 秒，两个人同时改配置时，另一个人最多看到一分钟前的值；保存会清空缓存，所以不会读到改前的。
  3. 路由级 KeepAlive。 能做，但它和缓存叠在一起会让“数据新鲜”更难推理，暂时不加。
  4. 公开站的点位与瓦片。 它们走的是 Nginx 600r/m 的另一条配额，这次没有动。
