重构总纲：目标架构、模块边界与迁移路线

本文是渐进式重构的总规划，不是立刻动工的施工单。每个阶段单独评审、单独可回滚。

配套文档：知识库口语问答重构方案.md（含语料扩维与地图数据接入）。

摸排依据：全量静态分析（126 个 Java 类逐类解析 import）+ server/data/qa/qqbot.sqlite 真实数据统计（21 张表、6,558 条问答记录、2,649 个知识块）。未运行测试（当时工具层不可用），故凡涉及"运行时是否通过"的结论都标了【待验证】。

〇、本文受哪些约束（已拍板）

二、目标架构

2.1 一句话

把"按技术分包的贫血单体"改成 "按业务能力分模块 + 模块内端口-适配器"：模块之间只认接口，技术细节（SQLite、HTTP、模型 SDK）全部退到适配器层。

2.2 模块划分

现状 21 个包收敛为 9 个业务模块 + 3 个基础模块。括号内是现状对应包。

模块 职责 拥有的数据 对外暴露的端口
protocol OneBot 协议细节（现状 onebot/） — OutboundPort（唯一发消息出口）、EventSource
guard 唯一有权说"不"（现状 guard/） rate limit 内存态 GuardPort（GuardResult decide(GuardRequest)）
command 指令匹配与渲染（现状 command/） bot_command CommandPort
conversation 回答编排（现状 agent/ + router/ 的问答部分） — ReplyUseCase
knowledge 知识库：检索 + 语料 + 术语 + 地图（现状 kb/ + 新 map） kb_block*, kb_term, kb_map_* RetrieverPort、CorpusPort、MapPort
qa 问答记录与统计（现状 qa/） qa_stat, qa_raw, qa_keyword QaRecordPort、QaAnalyticsPort
plaza 问答广场（现状 plaza/） answer_vote, help_request PlazaPort
site 公开站文案与轮播（现状 site/） site_text, site_carousel SitePort
llm 唯一知道"用哪个模型"（现状 llm/） — ChatModelPort、EmbeddingPort、RerankPort
platform (基础) 配置、日志、线程池、脱敏（现状 config/ + logs/） — 由装配层使用
persistence (基础) 唯一持有 SQLite 连接、事务、迁移 全部表 各模块自己的 Repository 接口
adminapi (基础) 后台鉴权与 HTTP 装配（现状 admin/ + settings/） admin_visit —

⚠️ publicapi 不是模块：现状 publicapi/（6 类 / 1,023 行）与 admin/（4 类 / 944 行）都只是传输适配器，它们应当分别调用 knowledge/qa/plaza/site 的端口，而不该自己承载业务逻辑。现状 PublicController 449 行直接 import Glossary/category/KbRetriever/QaAnalytics，就是"适配器里长出了业务"。

2.3 把"四条铁律"升级为可自动校验的规则

现状的四条铁律写在 server/README.md 里，方向完全正确——但它们只是文档，没有任何机制强制。重构的第一件事是让违反铁律的代码编译不过或测试挂掉。

用 ArchUnit（com.tngtech.archunit:archunit-junit5，开源、纯 Java、无运行时开销）写成普通单测：

# 规则 现状是否满足 ArchUnit 断言（示意）
R1 只有 protocol 能 import OneBot 协议类型 ✅ 满足 noClasses().that().resideOutsideOfPackage("..protocol..").should().dependOnClassesThat().resideInAPackage("..protocol.model..")
R2 只有 protocol 能发消息（唯一出站） ✅ 满足 禁止 protocol.client 被 protocol 之外引用
R3 只有 llm 知道模型厂商 ✅ 满足 禁止 dev.langchain4j 被 llm 之外引用
R4 只有 guard 能否决 ✅ 满足 禁止 GuardResult 被 guard 之外构造
R5 任何模块不得直接持有 SQLite 连接 ❌ 违反 12 处 禁止 java.sql / javax.sql 出现在 persistence 之外
R6 模块之间只认端口，不 import 实现类 ❌ 待建 slices().matching("com.example.qqbot.(*)..").should().beFreeOfCycles()
R7 config 的 Properties 不得被业务模块注入 ❌ 违反多处 业务包不得依赖 ..config..（仅 platform 装配层可依赖）

R1–R4 现在本来就满足，加上测试是"防退化"；R5–R7 是现状就在违反的，先写成 @Disabled 的"目标测试"，随各阶段逐个打开——这比"写进文档"有约束力得多。

三、五台手术

每台手术都给出：问题 → 方案 → 影响面 → 回滚 → 验收。

S1 持久化去单点 ★收益最高

问题：QaStore 同时是"问答记录仓储"和"全项目 SQLite 连接提供者"，被 12 个类直接依赖。这个耦合是技术约束逼出来的（代码注释写明：两个连接开同一个 SQLite 文件会因 WAL 共享内存冲突报 SQLITE_IOERR_SHMOPEN），所以不能简单"每个 Store 开自己的连接"——那正是当年的坑。

方案：

  1. 新建 persistence/SqliteDatabase：全项目唯一持有 Connection 的地方，暴露 inTransaction(...) 与 query/update。
  2. 各模块定义自己的 Repository 接口（如 knowledge 的 BlockRepository），实现放在各模块的 internal/ 下，构造时注入 SqliteDatabase。
  3. QaStore 退回"只做问答记录"，删掉它作为连接提供者的身份。
  4. 迁移脚本集中到 persistence/SchemaMigrator（保留现有幂等 PRAGMA table_info 补列的做法——这个做法是对的）。

影响面：12 个类的构造签名；无表结构变化、无数据迁移。

回滚：保留旧的 QaStore.connection() 委托到 SqliteDatabase，一个提交即可回退。

验收：ArchUnit R5 打开并通过；12 处 import QaStore 降为 0（或仅 qa 模块内）。

✅ S1 第一步已落地（2026-10-02）：连接提供者接口

先只换依赖类型，不动 SQL —— 这一步行为零变化，却能把一条架构规则从目标变成已生效。

  • 新增 persistence/SqliteConnectionProvider： connection() + isAvailable()。技术细节留在技术包里。
  • QaStore implements SqliteConnectionProvider, AutoCloseable。
  • 10 个类的依赖从 qa.QaStore 换成 SqliteConnectionProvider，字段名 qaStore → db （名字也是耦合：叫 qaStore 会让人以为它们在读写问答记录）。

实测效果：

指标 改造前 改造后
QaStore 的依赖方 12 2（AdminAuthFilter.recordVisit、AdminController.annotate）
kb → qa 编译依赖 4 个 Store 0
ArchUnit「kb 不得依赖 qa」 @Disabled（目标） 已生效
测试改动 — 0 个测试文件需要改（测试传 QaStore，它实现了接口）

诚实说明：依赖数量几乎没有下降（新的 SqliteConnectionProvider 有 11 个依赖方）， 变的是依赖什么 —— 从"依赖 qa 这个业务模块的具体类"变成"依赖一个技术接口"。 真正的收益是：kb 不再知道"问答记录"存在，且 kb↔qa 的编译期环被单向打破。 依赖总数要降下来得靠后面的 Repository 化，那是 S1 的第二步。

剩余（S1 第二步）：

  1. 把 10 个 Store 的手写 SQL 收进各自模块的 Repository，业务模块连 Connection 都不再直接拿； 然后 ArchUnit R5（java.sql 只许出现在 persistence）才能真正打开。
  2. 反向依赖 qa → kb 仍在（3 处：QaCollector 用 kb.Glossary / KbRetriever / KbTrace）。 要解它得把 KbTrace 挪成中性 DTO（它是"这次检索命中了什么"的记录，本就不该属于 kb 的实现细节）。
  3. @DependsOn("qaStore") 这个字符串耦合还在 8 处 —— 它是运行期初始化顺序，不是编译依赖； 等 SqliteDatabase 独立成 bean 后一并去掉。

S2 配置去中心化

问题：GuardProperties 661 行被 17 个类注入；SettingsService 注入 7 个 Properties；CommandController 注入 7 个。

方案：

  1. 按使用方而不是按技术名词拆：把 GuardProperties 拆成 RateLimitConfig、AccessConfig、ContentGateConfig、BudgetConfig、OutboundConfig、FileAccessConfig，各自只被真正需要它的类注入。
  2. 业务类不再注入 Properties，改为在装配层（@Configuration）把需要的值作为小而明确的参数对象传入构造器。可选进一步：用 records 做只读配置快照。
  3. 保留 config/overrides.yml 覆盖层与 SettingsWhitelist 白名单机制——这套设计是对的（安全默认 + 白名单，值得原样保留）。

影响面：config 包与所有注入方；application.yml 键名不变（避免运维破坏）。

回滚：新旧 Properties 并存一个迭代，逐个切换。

验收：ArchUnit R7 打开并通过；单个配置类不超过 ~150 行。

✅ S2 第一步已落地（2026-10-02）：把嵌套配置对象暴露成 bean

逐类核对 GuardProperties 的 17 个注入方后发现：12 个只用到一个嵌套对象 （RateLimitStage 只要 RateLimit、PathGuard 只要 FileAccess、ChatService 只要 ContentGate…）， 它们却都得把整个 661 行的对象拖进构造函数。

  • 新增 config/GuardConfig： 把已经存在的 7 个嵌套对象再暴露一次成 bean。 GuardProperties 仍是唯一的 @ConfigurationProperties("app.guard") 绑定者， yml 的键一个都没变。
  • 12 个类改成只注入自己需要的那一个（字段名也跟着改，如 properties → rateLimit）。
  • MessageRouter 只注入 RateLimit + Access。
  • 删掉 CommandController 里一处从未使用的 GuardProperties import。

实测效果：

指标 改造前 改造后
依赖 GuardProperties 根对象的类 17 3
每个嵌套配置的消费者 — 1~3 个（Budget/FileAccess 各 1 个）

剩下的 3 个都是合理依赖，已写进 ArchUnit 规则的白名单： GuardPipeline（guard 子系统自己的编排者，要根上的 enabled/kill-switch）、 QqbotServerApplication（组合根，@EnableConfigurationProperties）、 SettingsService（配置中心按反射读写全部配置）。

新增的已生效规则：noGodConfigObjectInBusinessCode —— 业务包不得再依赖 GuardProperties 根对象。 防的就是"图省事又把整个 661 行拖回来"。

剩余（S2 后续）：KbProperties（13 个依赖方）、QaProperties（10）、 MediaProperties/CommandProperties/LogProperties（各 7）同样可以按此办理； 更彻底的做法是业务类完全不注入 Properties，由装配层传入小参数对象。

S3 编排解体

问题：MessageRouter 452 行、24 个跨包依赖，是所有功能的必经之路。

方案：改成显式注册的用例链——

  1. 定义 InboundHandler 接口（boolean supports(InboundContext) / Outcome handle(InboundContext)）。
  2. 实现拆成：CommandHandler、PlazaHelpHandler、ChatHandler。
  3. 顺序由 List<InboundHandler> 的 @Order 决定，在装配层显式列出，而不是埋在 452 行的 if-else 里。
  4. GuardPipeline 本身已经是好设计（GuardStage + 有序 5 层），照搬这个模式即可。

影响面：router 包整体重写，但行为必须逐条对齐——这会引入最高的行为回归风险。

回滚：保留 MessageRouter 作为 InboundHandler 链的第一版实现，逐段搬。

验收：MessageRouterCommandTest（现有）全绿 + 新增"顺序与短路行为"测试；每个 handler 跨包依赖 ≤ 4。

S4 知识库内核化

问题：KbRetriever 597 行，三路算法、RRF、加成、闸门全部硬编码在一个 @Component 里；加一条召回路径就要动这个类。

方案：抽成可组合流水线（详见知识库方案）：

QueryUnderstanding → [RecallStage...] → FusionStage → RerankStage → AssembleStage
  • 现有的 A/B/C 三路变成三个 RecallStage 实现，参数外置到配置。
  • RerankStage 是新插入的一层（现状没有）。
  • 必须保留：RRF 按排名融合、关键词权 2.0 / 标题权 3.0 / 标题精确 +0.5、C 路"闸门+置顶"而非进 RRF——这些是实测调出来的，换实现但不许改数值。

影响面：kb 包内部；对 conversation 只暴露 RetrieverPort。

回滚：新旧 Retriever 并存，由配置开关切换。

验收：第 5 节的检索 golden set 指标不低于改造前基线。

S5 前端收敛

问题：TermPanel.vue 1,720 行；types.ts 679 行手抄 DTO。

方案：

  1. TermPanel 拆成"列表 + 筛选 + 批量操作 + 抽屉"四个子组件（现状文档 知识库维护成本收敛方案.md 早有此意图）。
  2. DTO 由后端生成：加一个 Maven 目标，把 @RestController 的返回类型导出为 TS 类型，替换手抄的 types.ts。
  3. 保留：publicApi/adminApi 客户端分离、18 个自研组件、设计令牌——这三样都是对的。

影响面：web/；无后端行为变化。

验收：vue-tsc 零错误；TermPanel.vue < 400 行。

四、迁移路线

原则：先建安全网，再动刀；每个阶段结束时代码都是可发布状态。

项 内容 产出

0.2 跑通并记录现有 34 个测试 基线：通过/失败清单

验收：口语子集 R@1 提升（目标值在知识库方案里给）。

Phase 3 — 语料扩维

五、回归基线怎么建（Phase 0 的核心交付）

现状没有任何"回答质量"的自动化度量——KbRetrieverTest 测的是"三路各自是否工作"，不是"口语提问答得对不对"。没有度量，Phase 2 的收益只能靠感觉。

做法：

  1. 黄金集：人工整理 150–200 条真实口语提问，分四类：
    • entity：报名字（"酸蚀之咬怎么获得"）— 现状尚可，防退化
    • descriptive：描述需求（"有没有加移速的鞋"）— 现状差
    • location：问位置（"永霜堡在哪"）— 现状完全失败（语料没有）
    • chitchat：闲聊（"你是什么模型"）— 现状误触发，正确行为是不检索
  2. 每条标注期望命中的块 id 集合（允许 1–3 个正确答案）。
  3. 指标：R@1 / R@5 / MRR，并按四类分别统计——混在一起算平均值会掩盖问题（现状 entity 类 99.5%、location 类 0%，平均看着还行）。
  4. 数据来源：qa_raw 有 6,543 条真实提问可直接挖（注意先做去重，实测存在同题重复入库）。

关于"正确答案从哪来"：先人工标 150 条（约半天），不要一开始就上 LLM 自动标注——location 类现在根本没有可命中的块，自动标注会把这批样本标成"无解"，从而掩盖真实缺口。

六、明确不做（防范围蔓延）

  • ❌ 不拆微服务、不换语言、不引入独立向量数据库（2,649 块全扫 2.64 ms，引入进程收益为零——这条现状判断是对的，保留）。注：语料扩维后需重新验证这个数字。
  • ❌ 不重写前端框架、不引入 Element/Ant（自研 18 组件 + 设计令牌的方向是对的）。
  • ❌ 不删除 config/overrides.yml + SettingsWhitelist 白名单机制（安全默认设计正确）。
  • ❌ 不动 AGENTS.md 的规则语义（它是运行中的系统提示词，改动有行为风险）。
  • ❌ 不清理 server/data/.legacy-archive/（13 MB 旧语料，是唯一的历史备份）。
