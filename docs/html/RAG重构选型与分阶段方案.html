RAG 重构：以 LangChain4j 官方骨架二开

官方就是 LangChain4j 本身。它的官方 RAG 管线已经随现有依赖进入我们的产物，官方样例里有 12 个 RAG 例子，其中 7 个我们已手写等价实现。所以这件事的性质是：把骨架换成官方实现，把领域参数留下来。

目标管线与扩展点映射见 rag-pipeline-mapping.html。

一、生态与版本

LangChain4j 最新发布 1.21.0，时间 2026-10-02；我们现在是 1.20.0。独立平台的 star 远高于库，但那是产品不是可嵌入的组件，数字不能直接兑换成我们的收益。

二、官方管线与我们的对应

官方 rag.md 定义的检索链是五个槽位，由 DefaultRetrievalAugmentor 串起来：

QueryTransformer → QueryRouter → ContentRetriever → ContentAggregator → ContentInjector
槽位官方实现我们的等价物处理
QueryTransformerDefaultQueryTransformer无可留空，后续补查询改写
QueryRouterDefaultQueryRouter三路并行分发换官方
ContentRetrieverEmbeddingStoreContentRetrieverA 路正文向量换官方
ContentRetriever无对应物B 路术语关键词自研
ContentAggregatorReciprocalRankFuser、ReRankingContentAggregatorRRF 加标题加成、闸门置顶、重排、意图提权组合式自研聚合器
ContentInjectorDefaultContentInjector两段出处注入自研

关键约束：官方管线只有一个聚合器槽位。我们的四段处理必须收进同一个 ContentAggregator。收益是阶段名固定、每个启发式有了归属；风险是这个组合器会变成新的巨石类。所以要求它内部只做纯函数组合，每段单独可测。

三、官方样例逐条对照

rag-examples 模块的结构与我们现有的实现几乎一一对应。

官方样例我们的等价物
_1_easy/Easy_RAG_Example无，依赖 SPI 自动装配，不需要
_2_naive/Naive_RAG_Example有，最小接入形态
_3_advanced/_01 Query Compression没有，可补
_3_advanced/_02 Query Routing部分，C 路闸门与意图分流
_3_advanced/_03 ReRanking有，RerankClient
_3_advanced/_04 Metadata部分，curated 出处
_3_advanced/_05 Metadata Filtering部分，按 docId 过滤
_3_advanced/_06 Skip Retrieval有，ReplyMode.NONE
_3_advanced/_07 Multiple Retrievers有，A / B / C 三路
_3_advanced/_08 Web Search没有，暂不需要
_3_advanced/_09 Return Sources有，注入时的编号与 url
_3_advanced/_10 SQL Database Retriever有，SQLite 语料

结论不是"我们毫无章法"，而是把官方样例的每一项都手写了一遍，还额外调出了一批领域参数。重构要做的是把前者换成官方骨架，把后者留下来。

四、两条接入路线

两者的差别取决于用到哪个 jar：langchain4j-core 已经在我们的 classpath 上，AiServices 在主包里，主包本地目前只有 1.19.0。

路线做法新增依赖改动面风险
A 只用 RetrievalAugmentor调用 augmentor.augment(...)，ChatService 继续自己拼 prompt无kb 包与 ChatService 的检索段工具要自己写
B 交给 AiServices 接管AiServices.builder(...).retrievalAugmentor(...)langchain4j 主包还包括 chat 调用、厂商降级链、预算守卫推荐

工具调用是确定要做的能力，而工具执行的整套机制不在 core 里：轮次上限、参数错误处理、执行失败处理、编造工具名的兜底、调用前钩子、并发执行、工具检索、工具来源 SPI。手写这九项等于再造一个 KbRetriever，所以终点选 B。

但 A 与 B 的差别只在最后一公里：RetrievalAugmentor 与 AiServices 是两层，检索骨架的改造在两条路线上完全一样。第 1 步与第 2 步照原计划做，不必等这个决定落地。

五、分阶段路线

第 0 步 评测门禁 · 已完成

./scripts/golden-gate.sh 一条命令，退出码就是结论。它把"测不了"从跳过改成失败，并接进 preflight.sh 第 5 步。手册见 检索回归门禁.html。

第 1 步 接缝化 · 已完成

KbRetriever 从 781 行降到 381 行，只剩编排。算法各归其位，每个接缝一个接口加一个默认实现，默认实现就是重构前那段代码本身。

接缝接口默认实现
召回器 A 路KbRecallPathVectorRecallPath
召回器 B 路KbRecallPathKeywordRecallPath
闸门 C 路KbTitleGateSourceTitleVectorGate
融合器KbFuserRrfFuser
重排器KbRerankerCrossEncoderReranker
注入器KbKnowledgeInjectorTwoSectionInjector

C 路单独一个接缝而不是并进召回器：闸门命中的块不参与 RRF 投票，伪装成一条召回路径就得让融合器靠 source 字符串去猜哪一条是闸门，那种隐式约定迟早会错。

验收：430 条单测通过，全量 Spring 上下文可启动；门禁实测在重构前后完全一致 —— entity 20 条 70.0% / 90.0%，colloquial 5 条 80.0% / 80.0%，chitchat 干净率 93.3%，gap 干净率 29.4%，注入块均值 4.5 / 5.0 / 3.5 / 0.3 全部相同。

第 2 步 换官方骨架 · 已完成

A 路已完成：向量检索改走官方 EmbeddingStore 接口，实现在 CorpusEmbeddingStore —— 余弦、阈值、候选数仍是我们那套，但对外的形状是官方的，下一轮 EmbeddingStoreContentRetriever 要消费的正是它。

官方 retriever 本身没有接受"已算好的问题向量"的入口，它必然自己调 EmbeddingModel.embed()。直接换会破坏"一次检索只调一次 embedding、A 与 C 共用同一个问题向量"这条钉死的验收，所以这一轮只换存储接口，retriever 与 EmbeddingModel 适配器留到与编排一起换。

顺带收窄了一条护栏：ArchitectureTest 原先禁止 llm 之外出现任何 dev.langchain4j 类型，与本方案直接冲突。现在改为：框架类型只许出现在 llm 与 kb；模型 SDK 仍然只有 llm 能用；data.message 仍然不许进 kb，那正是当初转正这条规则的原因。

编排与 B、C 路也已落地：DefaultRetrievalAugmentor 加 DefaultQueryRouter 负责"变换 → 路由 → 检索 → 聚合"；A 路与 B 路各自实现官方 ContentRetriever；融合、闸门置顶、重排、意图提权收在一个官方 ContentAggregator 里，内部仍复用既有的 KbFuser、KbTitleGateSource、KbReranker。

官方管线那一格我们的实现
QueryRouterDefaultQueryRouter，广播给两条召回
ContentRetriever A 路VectorContentRetriever，向量检索走官方 EmbeddingStore
ContentRetriever B 路KeywordContentRetriever
ContentAggregatorKbContentAggregator：融合 → 置顶 → 重排 → 提权 → 截断
ContentInjector直通。资料仍由 agent 层拼，KNOWLEDGE 标记与两段出处的契约挂在系统提示词第九章上

两个新概念是这次换骨架的副产物，都不是可选项：

  • KbRetrievalContext —— 一次检索的共享输入（语料快照、术语展开、已算好的问题向量），走官方 InvocationParameters 通道传给各检索器。没有它，检索器拿不到"一次检索内只该算一遍"的东西。
  • KbRetrievalDiagnostics —— 一次检索的过程记录。官方只回传 List<Content>，而各路候选数与卡阈值之前的最高余弦从结果里反推不出来，只能由检索器与聚合器写进这个记录本。

验收：430 条单测通过，全量 Spring 上下文可启动；门禁指标与换骨架之前完全一致。

第 2 步里明确不做的两项

计划表里还写着 ReciprocalRankFuser 与 ReRankingContentAggregator，逐条查过之后不做，理由不是"麻烦"：

官方实现实测到的性质换掉会失去什么
ReciprocalRankFuser字节码里 K 硬编码为 60；两路等权；没有任何加成钩子我们的 K=10、关键词权重 2.0、标题精确加成 0.5 —— 三项全是实测调出来的，换掉等于把调好的排序器换成通用排序器
ReRankingContentAggregator功能与我们的 CrossEncoderReranker 等价，但要一个 ScoringModelScoringModel 在 model 包里，只能放 llm，于是要新增一条 llm → kb 依赖来搬运一段已经在工作的代码，功能上零收益

结论：这两项不是"第二步没做完"，而是做完了会变差。所以它们的状态是"明确不做"，而不是"待办"。将来若真要换，ReciprocalRankFuser 必须先接受一次排序质量重调，那是一次实验而不是一次重构。

第 3 步 按需补能力 · 进行中

群聊检索缓存已完成：KbRetrievalCache，有界 LRU，键里带语料版本与检索参数。公开站一直有缓存与配额，群聊路径此前是裸的 —— 每条消息都触发一次 embedding 加一次 rerank，群里同一个问题被问很多遍时全是白付的钱和延迟。键里带语料版本意味着写完语料旧条目自动失效，不需要"记得清缓存"的约定。

按天配额：明确不做。你决定群聊暂不限制，所以不加这个开关 —— 一个永远不生效的配置项只会增加理解成本。真要限的时候照公开站的做法加即可。

一次实测：重排阈值不是可调项

黄金集里有两条 entity 样本返回空，余弦 0.5539 / 0.5522 —— 都在向量阈值 0.45 之上，所以不是被向量挡的，是被重排判定成"库里没有资料"。把重排下限从 0.02 调到 0.010 实测：

指标0.0200.010
entity R@170.0%75.0%
entity R@590.0%95.0%
entity MRR0.7790.829
colloquial R@1 / R@580.0% / 80.0%80.0% / 80.0%
gap 干净率29.4%29.4%
chitchat 干净率93.3%80.0%

结论：1 条 entity 换 2 条 chitchat，而且 chitchat 掉到正好压在 80% 的地板上 —— 再退一条门禁就红。所以回滚到 0.02，并把这段记录写进了 Rerank 的注释。

更重要的结论是：被拒的 21 次分数从 0.0003 连续分布到 0.0197，两类在 0.012~0.020 区间重叠 —— 和当初双塔余弦的困境一模一样。调这个阈值是权衡，不是修复；Rerank 注释里"真实问题 ≥ 0.04"那句话已被这次实测推翻。

补中文名：先做数据，再改一处代码才真正生效

查清词条表后发现它的形状与文档描述不同：2649 条物品类词条的 zh 存「中文名、English Name」两截；790 条 wiki 导入类词条的 en 是 slug（wiki-intelligence），zh 直接存了英文名（Intelligence）。

第一次尝试只改了数据（写入 17 条属性与机制词的中文名：力量、智力、体质、敏捷、耐力、制作、舒适度、战斗机制、瘴气、瘴气滤器、瘴气抗性、永恒之火），指标零变化 —— 因为黄金集没有覆盖这批词。按纪律补了 3 条样本去验证，门禁直接红了（entity R@1 60.9%、R@5 82.6%）。

那个红色给出了真正的根因：Glossary.load() 把每个中文别名映射到 e.en()，而 en 是 slug —— slug 只出现在块的 id 里，永远不会出现在标题或正文，所以关键词路拿它去找必然一条都匹配不到，而且不报错，只是静默少一路召回。

修法是在 load() 里把"英文那一侧"取成 zh 里那截英文名（物品类取「、」后面那半截，wiki 类本身就是英文名），拿不到才退回 slug。

entity 类别修复前 20 条修复后 23 条
R@1 答对数1415
R@5 答对数1821
R@1 / R@5 百分比70.0% / 90.0%65.2% / 91.3%
chitchat 干净率93.3%93.3%
gap 干净率29.4%29.4%

3 条新样本全部进 R@5，其中 1 条排第 1。百分比反而下降只是因为分母从 20 涨到 23 —— 答对的绝对条数是涨的。这也说明门槛用的是百分比，会随样本增长而漂移，值得单独处理。

第 3 步 按需补能力

  • 补 QueryTransformer，做查询改写，这是目前唯一空着的槽位。
  • 群聊路径补缓存与配额，与公开站拉齐。
  • KbBlockIndex 实现 EmbeddingStore，接入增量更新，去掉整份重载。
  • 用官方 observability 监听接口替换自制的 KbTrace。

第 4 步 工具接入 · 前置已完成

  • 已完成：LlmRouter 把"空文本 + 工具请求"与"空回复"分开判定。模型请求调用工具时 content 本来就是空的，两者混在一起的话，工具一接上，第一次工具调用就会被判成空回复 → 切换厂商 → 这次调用直接丢掉。
  • 已完成：补上 CAP_TOOLS 能力标签（Provider.capabilities 里本来就预留了 tools），降级链可以按"这家会不会调工具"过滤。
  • 已完成：加入 dev.langchain4j:langchain4j 主包并对齐版本（主包 1.20.0 与 core 1.20.0 一致）。AiServices 只在主包里。两件事必须一起做：core 与主包版本错配会在运行期炸且报错难懂；而 build-server.sh 默认离线，新依赖必须先联网拉进本机仓库。
  • 已完成：LlmRouter.chatMessages(...) —— 消息级入口，不注入系统提示词（AiServices 自己管系统消息）；LlmRouterChatModel implements ChatModel 把降级链包成官方模型，工具循环因此走的是我们的降级、能力过滤与预算累加。
  • 已完成：第一个只读工具 KbLookupTool，以及 KbToolAssistant（AiServices + 轮次上限 3 + 授权钩子）。授权是默认拒绝的白名单：新增工具必须同时改白名单，否则模型调它会被当场拒绝并记日志 —— "能被触发"与"该被触发"是两件事。
  • 已完成：工具循环与授权拒绝的端到端验证，用假模型跑，不碰网络。两条测试分别钉住：模型要工具时工具真的被执行（verify(retriever).retrieve(...)），以及白名单外的工具被拦下且根本没有被执行（verify(retriever, never())）。后者是安全边界，必须由测试钉住而不是靠注释。
  • 未做：工具还没有生产入口 —— KbToolAssistant 目前只在测试里被调用。接入口是下一步。
  • 补工具能力标签，让降级链能过滤不支持工具调用的厂商。
  • 接入 AiServices 与 tools，每一轮工具调用都计入预算。
  • 第一批只开放只读工具；敏感性操作不给群聊入口，授权依据是 BeforeToolExecution 里的调用方上下文。

六、评测与完成判据

官方 testing-and-evaluation 文档给出的推荐读物就是黄金集那一套，与我们已有的 检索基线.md 做法一致。所以纪律不必另起：

  • 黄金集 61 条作为任何改动的准入门槛。
  • 一次改动对应一条失败样本，说不出来源的改动不进主干。
  • 启发式数量设上限，超出即重构而不是继续追加。
  • 连续两批语料扩充门槛无退化，即冻结本轮扩张。

目标值待定：entity R@1 与 R@5 达标，gap 干净率显著高于当前的 31.6%。

七、风险

  • 组合式聚合器可能变成新的巨石类，这是本次重构最大的内部风险。
  • 迁移期两套编排并存，必须靠开关切换，不能让两条链路同时是事实来源。
  • ContentInjector 的默认拼装格式与我们两段出处的写法不同，必须自研，否则系统提示词第九章的规则失去落点。
  • 闸门置顶发生在融合之后、重排之前，接官方管线时要显式定义这个顺序。
  • 从 1.20.0 升到 1.21.0 需要一次完整回归，主包与 core 的版本要一起对齐。

八、待拍板

  1. B 已定，需要确认的是落地顺序。
  2. 第 1 步立刻做，还是先只补群聊缓存与配额。
  3. 是否把 Spring AI 与独立平台明确排除。
  4. 黄金集目标值定多少。
  5. 迁移期是否保留 KbRetriever 作为回退实现。
