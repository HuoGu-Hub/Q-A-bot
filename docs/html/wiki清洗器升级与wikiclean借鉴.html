wiki 清洗器能力盘点与 wikiclean 借鉴

对象：WikitextCleaner 与它前后的抓取链路。参考项目：lintool/wikiclean，已 clone 到 .toolchain/wikiclean 逐文件读过。审计日期 2026-10-11，全部数字实测自生产库 server/data/qa/qqbot.sqlite。

一句话结论：我们的清洗器在"保语义"这一侧已经比 wikiclean 走得更远，表格取单元格、模板取白名单参数是它没有的能力；真正的缺口只有两处 —— <gallery> 整块没处理、HTML 实体没反转义，两者合计影响 128 块。

但最大的杠杆不在 wikiclean 里：实测这个 wiki 的 action=parse 能返回数据层已填好的渲染文本。同一页 Goo 现在是 704 字原文清成 99 字，走渲染能拿到 2387 字可用文本。

更正 · 2026-10-11。本文原先用 Fool's Demise 与 Goo 举例说明白名单缺口。复查发现这两页在 kb_wiki_page 里没有记录，库里那两块是更早的导入留下的旧块，不属于当前导入链路。结论方向不变，但证据要换成导入集内的页面，而且实测范围更大：

  • Bat（Wildlife）：原文 366 字 → 清洗后 11 字，只剩 "A Bat" 与章节名 "Drops"。掉落物、Behavior、Faction、Region 全丢。
  • Counter Battery（Ranger Skills）：原文 327 字 → 清洗后 68 字，且首句是 " is a skill in Enshrouded."，主语 {{PAGENAME}} 被丢。
  • 范围：635 页里 196 页（31%）清洗后不足 300 字，其中技能 142 页、野生动物 27 页。

也就是说，文档质量的主要问题不是"标记没清干净"，而是内容根本没能留下来。

已落地 · 2026-10-13。清洗器的原则已经反转：从"白名单"改成"默认保留，只丢明确噪声"。整库重洗后，语料从 568,914 字涨到 651,793 字（+14.6%），变多 580 篇不变变多、46 篇变少、9 篇；清洗后不足 100 字的页从 66 篇降到 6 篇，不足 300 字的从 196 篇降到 137 篇。检索黄金集门禁 PASS，四项指标与改动前逐项一致。

  • 递归：外层模板不认识也先递归进去，内层表格式模板照样取值 —— 掉落表就是这么救回来的。
  • 参数值默认全留：短值输出成 Class: Ranger，长值原样保留；只丢文件名、尺寸、样式、图标这类参数。
  • 表格式模板一行一条：Fell Cyclops Head × 1 (Materials, Drop)。
  • 页面上下文：签名扩成 clean(wikitext, title)，{{PAGENAME}} 就地展开 —— " is a skill in Enshrouded" 这种缺主语的句子没有了。
  • 逐行去重：infobox 的描述与正文重复时只留一份（阈值 25 字），避免同一段话变成两个块互相稀释。
  • 键值字段一律带键名：长值（如列出五片区域的 Region）也不例外 —— 否则它既不匹配字段行、又丢了键名，孤零零留在开头。
  • 字段行排在正文之后：见下方"字段顺序"那条，这是保住检索排名的关键。
  • gallery 取标签、HTML 实体解码、表格一行一条记录、BOM 处理一并完成。
  • 强制重洗入口：--app.kb.wiki-import.force=true，补上"清洗器改了、老页不会自己重洗"这个洞。

验收：501 项测试全绿；黄金集门禁 PASS。

字段顺序：一个反直觉的坑

把模板参数留下来之后，文档开头变成了 Title: … / Class: Ranger / Unlock Cost: 3 这样的元数据，正文被挤到后面。结果黄金集里两条口语问题的期望块掉出了 top-5。

用重排模型直接打分才看清：问题「黑魔法是什么」对同一块的三种形态打分是 —— 字段排末尾 0.9691、旧文本 0.8314、字段排前面 0.4807。「还是不能召唤空荡独眼巨人」同样以排末尾最高。

所以现在的规则是："键: 值"这类字段统一移到文档末尾，长文本留在原处。内容一个字没少，排名回到基线，门禁 PASS。这条也有单测钉住。

实现中踩到的坑

这三个都是"看起来对、实测丢内容"的类型，写在这里免得下次再犯。

坑症状修法
把"参数值"当成"模板体"处理纯文本值被当成一个同名模板，全部返回空 —— 所有带参数的模板一起清成空白，测试直接暴露拆成两个函数：模板体走 resolveTemplate，参数值走 resolveValue，后者只递归处理里面的嵌套模板
把 Class 当成 CSS 的 class=Class=Ranger 被当样式丢掉，"这个技能属于哪个职业"没了噪声键里去掉 class 与 caption
字段行挡在正文前面检索排名下滑：重排模型看重开头，「黑魔法是什么」那块的重排分 0.83 → 0.48，掉出 top-5字段行统一挪到文档末尾，长文本留在原处
把纯数字当成尺寸Unlock Cost=3 与掉落数量 1 被丢尺寸判断必须带单位（px/em/%）才算噪声

二、wikiclean 是怎么做的

它解决的是"维基百科 XML dump → 纯文本"，主类 WikiClean 507 行，管线固定 16 步：

getWikiMarkup  ← 从 <text xml:space="preserve"> 里切出标记
removeFooter        （可选，按语言正则砍掉尾部章节直到文末）
removeRefs          （先删 <br>，再删两种 ref 形态 —— 顺序有注释说明）
removeInterWikiLinks（[[wikt:x|y]] 与 [[en:…]] 的区分靠有没有竖线）
removeParentheticals（IPA 模板带走它外面的括号，避免留下空 ()）
fixUnitConversion   （{{convert|100|km}} → 100 km）
ImageCaptionsRemover（手写状态机，处理 caption 里嵌套的 [[ ]]，整条图注删掉）
DoubleBracesRemover （手写状态机，所有模板整块删）
removeHtmlComments / removeEmphasis / removeHeadings / removeCategoryLinks
removeLinks（可选保留）
removeMath / removeGallery / removeNoToc / removeIndentation
TableRemover        （手写状态机，整张表删）
unescapeHtml4 ×2    （注释：有些实体被双重编码）
removeHtmlTags / compressMultipleNewlines

2.1 两个决定性的取舍

  • 模板一律删、表格整张删。它的目标是"纯正文散文"，为维基百科条目服务；信息框与表格在那边确实是噪声。我们的语料正好相反 —— 任务页的答案就在表格和模板参数里，所以这一条不能学。
  • 语言做成一等公民。Language 抽象只要求两样东西：尾部章节正则、分类链接正则。Chinese 只有 3 条尾部正则（参见 / 参考书目 / 参考网址），其余靠基类。

2.2 细节里值得抄的几处

  • 顺序是有原因的，而且写在注释里。removeRefs 先删 <br> 的理由是"否则 ref 正则配不上"，同样的话我们在 stripTables 与 stripTags 的顺序上也写过一次。
  • 双重反转义。它连续调两次 unescapeHtml4，注释只说"有些实体是双重编码的"。我们连一次都没做。
  • 空壳处理。IPA 模板删掉后会留下 ()，它用一条正则把"括号 + 模板"一起吃掉，而不是事后清理空括号。
  • 测试按语言分文件，每个语种一个测试类，另有 WikiCleanBasicTest 管通用行为。
  • 未闭合括号时截断剩余全文，三种手写状态机都是这个行为。我们也是 break，同样会丢后半页，见 §4.4。

四、值得借鉴的四条

4.1 <gallery> 整块处理 —— 124 块

证据。Decorations 原文 3636 字里，全部内容就是一段 <gallery>：

<gallery widths=100px>
File:Iron Door.png|link=Decorations/Doors|[[Decorations/Doors|Doors]]
File:Secret Stone Door.png|link=Decorations/Secret Doors|[[Decorations/Secret Doors|Secret Doors]]

我们的 stripTags 只吃掉 <gallery …> 这个标签本身（<[^>]+>），里面每行没有 [[ ]] 包着 File:，所以 stripLinks 也放它过去，最后留下 36 行 File:X.png|link=…。这类页面在库里是 wiki-decorations 与 wiki-decorations-2 两块，全是噪声。

但不要照抄"整块删"。照抄的话 Decorations 会清成空页 —— 而它每一行都带一个可读标签：Doors、Secret Doors、Windows。这个页面本身就是一张目录。

建议：先按行取标签（[[X|Y]] 取 Y，没有就取 link= 后面那段），去重后压成一行物品清单；取不到标签的行才丢。这样"整页图片目录"变成"这一页包含哪些东西"，与我们"宁可少留，不要留错"的原则一致。

4.2 HTML 实体反转义 —— 4 块 / 单页 118 处

证据。Survivors 清洗后仍有 118 处 &nbsp;&nbsp; 开头的行：&nbsp;&nbsp;Charcoal Kiln。库里 wiki-survivors-2 那块 1303 字，几乎每一行都带实体。

建议：在空白折叠之前加一步实体反转义，至少覆盖 &nbsp;、&amp;、&lt;、&gt;、&quot;、&#NNN;。wikiclean 的"调两次"提示同一份文本里可能双重编码，可以照做 —— 代价是一次全串扫描，可忽略。

4.3 高频模板要"专门处理"，而不是靠白名单碰运气 —— 这条是我们自己的缺口

这条不是从 wikiclean 抄的规则，而是它的 fixUnitConversion 提醒的做法：{{convert}} 在维基百科里太常见，与其等白名单，不如给它一条专门规则。我们的高频模板是谁？实测答案是 {{Item Infobox}}。

证据。Fool's Demise 原文 832 字，当前清洗后只剩 51 字，保留率 6%。因为该页正文全部在 {{Item Infobox|description=…}} 里，而白名单只收了 npc infobox、没收 item infobox，于是整块丢。库里现存的那一行是 365 字 —— 它来自更早的清洗器版本。

这同时说明一件事：白名单收窄是一种会静默丢内容的改动。缺陷清单里 §2 修的是 npc infobox，但同类问题在 item infobox 上仍在，而当时的对账用的是"页数"与"失败数"，看不出正文变短。

建议：把 item infobox 也收进 KEYED_TEMPLATES，键同样只取 description；并在缺陷清单的对账口径里加一条页级保留率，掉到某条线以下就报警，而不是只看"有没有变成 0"。

4.4 未闭合括号的行为要一致

两边都会在括号配不上时丢弃剩余内容：它 return s.substring(0, i)，我们 break 之后 out 里是前半段。这个行为在整页层面是对的 —— 半截 {{ 进了语料比缺内容更糟。但两处可以做得更好：丢掉这一段，继续从下一个 {{ 扫，而不是放弃整页。实测语料里 Goo 这类数据驱动页面就有大量未闭合形态的模板，值得先统计再决定。

五、明确不借鉴的

  • 整表删除、整模板删除。方向相反，会毁掉我们最好的那批页面。
  • 手写状态机。我们用一个 matchClose 配对扫描就解决了同样的嵌套问题，它那三段状态机每段 50 行且更难读。
  • 17 种语言 + 尾部章节层。实测我们语料里尾部章节 0 命中，暂时不需要。但"按来源配策略"这个形状值得留着 —— 将来再加第三个 wiki 时用得上。
  • 引入依赖。它依赖 ant、commons-io、commons-lang3；我们保持零依赖，规则抄思路就够。
  • XML dump 解析、withTitle。我们是 API 取单页，标题另有归属。

六、比 wikiclean 更值得做的一件事：渲染文本

这是本轮实测最有价值的发现，wikiclean 给不了，因为它读的是离线 dump。

口径Goo 这一页
原始 wikitext704 字
当前清洗器输出99 字，开头还是 is a crafting material…，主语 {{PAGENAME}} 被丢了
action=parse 渲染 HTML68,633 字
渲染 HTML 粗暴去标签2387 字

关键差别：渲染文本里数据层已经填好。同一页原文写的是 {{Get|description}}，渲染后是：

Goo A sticky paste used to bind chemical substances. Info Type Materials Rarity Common
Stack Size 250 Level 13 Biomes Revelwood Goo is a crafting material in Enshrouded.

{{Get}} 是这个 wiki 的数据查询层，离线永远解不出来 —— 我们现在的做法是整块丢掉，于是这页什么都没剩下。

路子结果
prop=extracts&explaintext=1 TextExtracts 扩展不可用，三页 extract 全为空，说明该扩展没装
action=parse&prop=text可用，但 mw-parser-output 容器不存在，wiki.gg 的皮肤结构不同，需要另找内容边界

建议做成混合策略，而不是全面替换：

  1. 默认仍走原文明文清洗 —— 便宜、纯函数、可离线单测，多数散文型页面它已经够好。
  2. 对"清洗后字数 / 原文字数低于某条线"或"原文含 {{Get|"的页，回退到渲染文本提取。
  3. 渲染路线的成本要如实计入：单页 68KB、需要 HTML 解析与内容区选择、UI 噪声要清（[ visual editing | edit source ] 这类）。

七、顺带发现的两个问题

7.1 陈旧块会让"改清洗器"这件事看起来没生效

库里 fools-demise 是 365 字，而现在重洗同一页只有 51 字（§4.3）。也就是说：清洗器改了、老页没重洗这件事已经在语料里留下了可观测的分层 —— 同一个 wiki，一部分块是旧规则产物、一部分是新规则产物。缺陷清单把它列为流程风险，现在有了具体样本。

建议在重洗脚本的验收里加一条对账：逐页比较"库里正文"与"当前清洗器重跑结果"，列出差异页数。这正是本轮用的方法，可以固化成脚本。

7.2 清洗器是纯函数，拿不到页面上下文

clean(String) 只收原文，于是 {{PAGENAME}}、{{SUBPAGENAME}} 这类"需要知道自己是谁"的模板只能被丢掉，Goo 的正文首句就是这样变成 is a crafting material… 的。基线里另有 1 块残留 {{Get，同属这一类。

建议把签名扩成带上下文的形式，例如 clean(String wikitext, PageContext ctx)，ctx 里先只放页面标题与来源；这样 {{PAGENAME}} 能就地展开，也不破坏纯函数性质 —— 上下文是入参，不是全局状态。

基线里另有一块残留 {{Get，id 为 goo，内容是中文与全角竖线（制作：耗时：{{Get｜产出：{{Get）。当前清洗器对 Goo 原文的输出里没有这个形态，所以它更像是旧版本或另一来源留下的陈旧块，不宜直接归到本条名下 —— 需要单独查一次它的来路。

做法不是"全面改用渲染"，而是取两份文本里更长的那份：实测 27 篇样本里渲染更多 11 篇、相当 14 篇、更少 2 篇 —— 只有数据表页真的受益，其余页面一个字不动，检索基线因此没有被扰动。

噪声怎么处理的

  • 丢：span.mw-editsection（"visual editing" 那一串编辑入口）、.ranger-navbox 与 .navigation-not-searchable（Bestiary / Skills 导航 —— 实测 Counter Battery 上 2191 字，比这页正文还长）、目录、参考文献。
  • 留：正文段落、table.wikitable、.cargoDynamicTable 数据表、ul.gallery 图注。
  • 字段行排到末尾：信息框字段单独收集后附到文档末尾，与 wikitext 那条路一致。
  • 与正文重复的字段不重复放：Counter Battery 的 +15% damage… 曾因此出现两次。

代价与注意

  • 依赖 jsoup（无传递依赖）。17~68KB 的机器生成 HTML 用手写正则处理太脆，结构与实体解码交给它。
  • 每页多一次请求，配置里有 render.delay-millis: 200 的间隔。
  • 新依赖要联网拉一次：MAVEN_OFFLINE=0 ./scripts/golden-gate.sh，之后离线构建才认它。

九、审计怎么做的

  1. 读源码。git clone --depth 1 https://github.com/lintool/wikiclean.git 到 .toolchain/wikiclean，逐文件读了 WikiClean / Language / Chinese / 测试。
  2. 量产物。把生产库复制到 .toolchain/wiki-audit.sqlite，用 Python 对 3367 条 source='wiki' 的块做正则扫描，逐项计数并抽样本。
  3. 重跑。从 wiki API 抓 5 页原文到 .toolchain/raw/，用一个临时的同包测试调**真清洗器**重跑，和库里已存的块逐一对照。
  4. 探路。对同一批页面依次试 prop=extracts、action=parse，确认哪条路可用。

注意：wiki API 对没有自定义 User-Agent 的请求返回 403，抓取要带上 app.kb.map-sync.user-agent 里那个值。

总结：清洗器本身的底子是好的 —— 保语义这条路线比 wikiclean 更适合我们的语料，缺的只是两处边角规则。真正值得投入的是另外两件：把"高频模板"当成一等公民而不是白名单碰运气，以及给数据驱动的页面一条渲染兜底。wikiclean 在这两件上都帮不上，但它提醒了两个我们没做的动作：实体反转义与空壳清理。
