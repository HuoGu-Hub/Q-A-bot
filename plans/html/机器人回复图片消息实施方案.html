机器人回复图片消息

实施方案 · 出站图片通道 + 知识库配图来源 + 地图截图来源

项目：飘雪喵问答机器人（E:\Project\agentWs\qqbot）　｜　阶段一已落地并通过全量测试　｜　阶段二见第七节

一、现状：确实回不了图

入站方向早就支持图片：群友发的图、被引用消息里的图都会下载下来交给视觉模型。但出站方向只有文本：

环节现状证据
入站图片已支持，带缓存与 SSRF 防护，走视觉模型media/ImageFetcher.java、agent/ChatService.java:116
出站消息段只能构造 text 与 at 两种段onebot/codec/MessageCodec.java 的构造区只有 textMessage / atPlusText / forwardNodes
出站发送入参是裸字符串，没有承载图片的位置onebot/outbound/OutboundSender.java 的 send(event, text)
提示词要求模型"需要图就给网址，不要下载"system.md 第八节

所以群友看到的永远是一串网址，而不是一张图。网址在 QQ 里不会自动展开成图片。

二、方案总览

模型不能直接指定 URL，只能引用我们自己登记的图片名字；标记由出站层摘掉并换成图片段，和正文同一条消息发出。

模型回复 它长这样 [[img:kb:copper-vein]]
→ 出站层 先摘标记，得到正文与 key
→ ImageLibrary 按来源解析 key，过三道闸门
→ MessageCodec 拼出 [text, image] 段
→ OneBotApiClient.sendGroupMsg 发出，正文与图在同一条消息里

为什么不是"模型直接给 URL"：模型编得出任意 URL，却编不出我们图库里的名字。名字必须来自资料块或工具结果，天然把"我们自己维护的资产"和"模型瞎编的外链"分开；未知 key 一律丢弃并记日志，绝不发给协议端。

三、标记协议

参考图：[[img:kb:copper-vein]]       ← kb-images 目录里的 copper-vein.png
位置如下：[[img:map:embervale/xxx]]   ← 阶段二：服务端合成的地图截图
规则说明
形状[[img:来源:名字]]，来源段只许字母数字下划线，名字段允许中文与 /
拦截名字里不许出现空段、.、..、路径分隔符、控制字符 —— key 最终会拼成磁盘路径
摘除解析后标记一定从正文里消失，哪怕它不合法；群里永远不会出现 [[img:...]]
顺序先摘标记再走出站过滤。反过来的话敏感词替换可能改写标记内部，图会静默消失

四、三道闸门

闸门配置默认失守时的行为
总开关app.media.outbound-images.enabledtrue标记当普通文本丢掉，一条消息都不多发
张数app.media.outbound-images.max-per-reply2超出的丢弃并记日志，不回话
单张大小app.media.outbound-images.max-size-kb2048超大的那张丢弃，其余照发

闸门放在解析中心而不是发送器：它判断的是"这张图能不能发"，与"发到哪个群、要不要 @"无关。将来多一个发送入口也不会绕过限制。

五、两张图片形态

形态什么时候用怎么给协议端
公网直链图本来就在公网上，我们零下载零内存data.file 直接填 URL
本地字节图在我们磁盘上，例如知识库配图与合成的地图截图data.file 填 base64://...

本地图必须走 base64：协议端跑在容器里，宿主机的路径对它不存在，给 file:// 只会得到一张"文件已过期"的破图。

七、怎么用

  1. 把图放进 server/data/kb-images/，文件名去掉扩展名就是 key。例如 copper-vein.png 对应 kb:copper-vein。
  2. 让模型知道这个 key。最顺的一条是写进知识库：新增一个块，标题即词条名，正文最后一行写 [[img:kb:copper-vein]]。命中这块时，资料段与 lookup 工具结果都会带上标记。建议图片文件名就用块的 id：块 id 只许英文字母数字与 -，正好是图片名允许的字符集。
  3. 模型照抄标记，出站层换成真图。抄错、图被删、超过上限都只表现为「少一张图」，正文照常发出。

两个渲染点会把唯一的那个标记提到块尾单独一行（ImageMarkers.hoistSingleMarker）：资料注入与工具结果各调用一次。理由是模型要改写正文，标记夹在句子中间最容易被顺手重写掉；出现两个及以上标记时一个都不动，因为那时图的顺序有含义。

目前还没有后台传图界面，配图靠往目录里放文件。目录本身就是唯一索引，因此不存在"索引与目录不一致"的悬案。

八、阶段二：地图截图

目标是让地点问答直接回一张带点位标记的地图图，key 形如 map:画布/点位。这一阶段还没动手，原因是要先确认三件事：点位坐标到画布像素的换算在后端有没有现成实现、瓦片拼图的尺寸从哪来、以及单次合成的耗时会不会拖慢出站。

要新增职责
kb/map/MapShotSource实现 ImageSource，scheme 为 map
瓦片合成器按画布清单把瓦片画成一张底图，再画点位标记
结果缓存同一张图重复请求直接命中，避免每次问答都重画

风险集中在两处：坐标换算必须与前端完全一致，差一点标记就画错位置；拼图是 CPU 与内存密集动作，必须有大小上限与缓存，否则一次群里的连续提问就能把 2G 机器顶到危险区。

九、已知限制

  • 带图不合并转发：图片塞进「聊天记录」卡片得点开才看得见，所以带图的回复一律逐条发。
  • 图片挂在第一段：长回复被切成多段时，图跟着第一段走，不跟着标记在原文里的位置。
  • 没有公网直链来源：ImageSource 已经为它留好位置，但没有 url: 实现，避免模型直接把任意外链塞进消息。
  • 图片不过敏感词过滤：过滤只看正文文本；图片来自我们自己登记的资产，不是模型生成的内容。
