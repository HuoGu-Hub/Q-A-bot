一、先回答一个容易误会的问题：图是谁的

地图图片最终是服务器上的本地文件，不是每次去 wiki 现取。链路是两段：

环节谁提供频率
地图元数据：画布四至、瓦片清单、点位坐标wiki 的 Map: 页面 JSON，由地图同步写进 SQLite手动触发一次同步
瓦片图片文件第一次从 wiki 下载，之后由 MapImageCache 永久落在 server/data/map-tiles/同一张只下一次

所以「wiki 抖动」只影响从来没取过的那一张瓦片。已经取过的，读磁盘就是零网络。

四、四个关键决策

决策 1：视口把「目标点 + 最近地标」一起框进去

不把目标点放在正中，而是让它和最近的地标同时出现在图里 —— 群友靠地标认路，比看孤零零一个点有用得多。规则：

  1. 取目标点，以及它的最近地标 —— 这个地标不需要新算，locate 工具已经在算「距最近地标 X 方向 N 单位」；
  2. 视口 = 两点的外接矩形 + 四周留白，再按 1280×800 的长宽比调整；
  3. 跨度夹取：最小 1200、最大 6000 crs 单位。太小会放大成一片马赛克，太大就只画目标点不放地标；
  4. 输出固定 1280×800，覆盖的世界范围随跨度变。输出画布 ARGB 约 4 MB，是整图的百分之一。

瓦片档位由跨度反推，公式很直白：

需要的档位宽度 ≈ 1280 × 1280 ÷ 跨度

跨度 2560  → 640 档瓦片     相交 4~9 张
跨度 5120  → 320 档瓦片     相交 16~25 张
跨度 10240 → 160 档瓦片     相交 36~49 张

取不超过这个值的最大可用档位，就不会白下载高清。相交的瓦片数每轴是 跨度/1280 + 1。

决策 2：出站路径有硬 deadline，超时就只回文字

取每张瓦片之前检查剩余时间，超过总预算就放弃本次渲染、返回"这次不发图"，同时丢一个后台预热任务。三种结果都可预期：

情况结果耗时
相交瓦片都在磁盘缓存里出图毫秒级，零网络
有缺，但 wiki 回得快出图总预算内，默认 2 秒
wiki 慢或被限流本次不出图，只回文字，同时触发预热到预算就放弃

截图用的是我们自己的缓存文件，但没缓存的那一张仍然要问 wiki。这条规则要挡的正是那一次询问 —— 让它最多影响 2 秒，而不是决定群友等多久。

决策 3：key 用「画布 + 点位 id」的规范化形式，模型只负责抄

模型看到的输入只有「铜矿脉在哪」这句话，它不可能知道库里哪个点是铜矿脉。所以流程必须是：工具先查到那个点，把取图凭据附在工具结果里，模型原样抄进回答。

【Ancient Spire - Springlands】位于春之原野，距……
配图：[[img:map:Embervale/Main#AncientSpire-Springlands]]

为什么凭据不能用地名，也不能只用 marker_id：

做法问题
地名当 key地名普遍带空格，标记协议禁空白；且一个名字可能对应多个点位
只用 marker_id实测 38 组重复 —— 同一批收集品同时存在于 Collectibles 与 Collectibles2 两张画布；另有 3 条 id 本身带空格
画布 + 点位 id唯一，且改中文名、改翻译都不受影响

落地时把两者规范化成合法字符，再建一张"规范化 key → 点位"的内存索引用于反查 —— 不靠字符串反向解析，靠表本身，所以不会出现有损还原。

决策 4：坐标换算写成纯函数，并用真实点位把像素值钉死

前端有一份公式把"游戏坐标"换成"图片上的像素"，后端要画图就得有第二份。两份只要有一处不同，标记就画偏，而且不会报错 —— 你只会看到图里没圈住那个点。所以：

  • MapProjection 是零依赖纯函数：输入画布与坐标，输出像素，可以直接单测；
  • 测试用真实点位的真实数字固定期望值。最容易错的两处是 y 轴向上导致的翻转，和瓦片取上边还是下边。

一个真实算例

点位 Ancient Spire - Springlands，坐标 (3508, 1982)；画布 Embervale/Background，四至 (0,10240) → (10240,0)，瓦片 1280×1280，瓦片格原点 (0,0)：

画布像素 = (3508 - 0, 10240 - 1982) = (3508, 8258)     ← y 被翻转，这是最容易写错的一步

瓦片列 = floor((3508 - 0) ÷ 1280) = 2
瓦片行 = floor((1982 - 0) ÷ 1280) = 1        ← 用 crs 坐标算行，不是用画布像素
该瓦片在画布上的位置 = (0 + 2×1280 - 0, 10240 - (0 + 2×1280)) = (2560, 7680)

校验：8258 落在 [7680, 8960) ✓    3508 落在 [2560, 3840) ✓

测试就断言这几个数字。前端公式或被后端改错，测试立刻红。

五、数据流

群友问「远古尖塔在春之原野的哪」
→ locate 工具查到点位与最近地标，拿到身份、画布、坐标
→ 工具结果里附一行 [[img:map:Embervale/Main#AncientSpire-Springlands]]
→ 模型照抄进回答
→ OutboundSender 摘标记，交给 MapShotSource
→ 反查点位，用 MapProjection 算视口与相交瓦片
→ 逐张取瓦片：磁盘缓存优先，总预算 2 秒
→ 画底图，画目标点标记与地标
→ 编码 PNG，转 base64，与正文同一条消息发出

七、风险与对策

风险对策
内存峰值只画视口，输出固定 1280×800；先缩后拼，绝不加载整图
坐标算错却不出声纯函数 + 真实算例测试；渲染测试断言标记所在像素的颜色
画布选错用现成的 canvasIndex 归属，不自己猜；归属拿不到就不出图
瓦片长期取不到deadline 到点降级为纯文字；日志写清是"未缓存"而不是"失败"
点位 id 撞车key 里带画布；反查索引按规范化 key 精确命中，不做模糊
图太大发不出去输出过大小闸门，超 2 MB 先降 JPEG 再缩一档
