提案与广场：考古、去向判断与清理计划

2026-10-24 ｜ 结论先放这里：两项功能都不建议按现形态保留。广场整体下线；提案删掉分析管线，保留人工标注用于统计。

一、先分清三个名字

代码里其实有三样东西，名字很像，命运不同。你记忆里的“提案”大概率是第一个。若你记得的是“让群友交资料”，那是第三个，代码早就不在了。

名字代码与表现在还在吗它到底是什么
提案 kb/proposal/、kb_proposal 在，但从未产生过数据 管理员把某些回答标成“有帮助”，攒够 10 条后让模型跟知识库比对，产出“新增词条”或“覆盖词条”的建议，人工确认后才落库。
广场 plaza/、answer_vote、help_request 在，但公开页是空的 公开站按关键词展示群里的历史问答，访客点赞/踩/标过时；都不满意时可以“问问新答案”或“求助大佬”。
投稿 / 邀请码 kb_contribution、kb_token 代码已删，表还在 早期让群友凭邀请码向知识库投递资料。已经下线，知识库导入与使用手册 写明“整块功能下线”。

第三个功能只剩两张 0 行的空表。如果这就是你印象里的“提案”，清理成本只有几分钟；本文重点分析前两个仍在运行的功能。

还有一条旁证：plans/html/雾锁王国地图查看器与地点问答实施计划.html:260 的“已知未决”里写过，“是否要「点位纠错」的群友提案通道：现有 kb_proposal 是问答提案，地图点位是否复用需单独定”。这说明当时确实想过把提案扩成通用投稿口，但没有落地。地图现在有自己的管理端标注和待复核点位，不需要靠这条老链路。

三、考古：它们本来是一条链

README 的功能表里有一句话，把两个功能绑在一起：

问答广场 ｜ 群内发起求助，投票认可的回答沉淀为改进提案

这句话不是现状，是当时的设想。把它拆成六步，再对照代码，断点非常清楚。

#设想中的环节代码里的实现状态
1群友提问，问答入库qa_stat / qa_raw / qa_keyword成立
2公开站按关键词聚合AnswerAggregator.hotKeywords / page成立
3访客投票表达认可PlazaController.vote 写 answer_vote成立，但 0 票
4被认可的答案公开only-voted=true 只放行 up > 0 的答案成立，但没有票就没有内容
5不满意就生成新答案或求助ask-new 调模型；help-request 生成短码半成品
6认可的回答沉淀为提案，人工确认后进知识库KbProposalService 读 qa_stat.verdict='good'未接线

断点 1：投票从来没有变成“认可”

提案的入口是 verdict='good'，这个字段只能由后台“问答记录”里的人工标注写入。广场投票写的是另一张表 answer_vote。两者之间没有任何代码相连：没有触发器、没有定时任务、没有“赞数达到 N 就置为 good”的分支。

// KbProposalRepository.java:87
SELECT COUNT(*) FROM qa_stat s WHERE s.verdict = 'good' ...
// 全库 verdict 分布：unknown 44,105

// PlazaStore.java:118
public boolean vote(long statId, long voterQq, String vote)
// 只写 answer_vote，不碰 qa_stat.verdict

所以“投票认可的回答沉淀为提案”只完成了前半句。票数只影响广场里的排序和是否展示，进不了提案队列。

断点 2：求助链路只写不收

网页点“求助大佬”会生成一个短码，并把“短码|问题”写进 help_request，状态 pending。但前端拿到响应后只用 text 字段，code 字段没有展示、没有复制入口。群里真正触发发送的是另一条路径：用户手动输入“求助：xxx”，由 MessageRouter.tryHelpRequest 匹配前缀后直接发群。

结果是：findPendingHelp、confirmHelp、FallbackService.askHelp 都没有调用方。那条 10-10 的 pending 记录永远不会被消费。求助发出后，群友的回答也没有回写链路，不会自动变成广场里的新答案。

断点 3：提案的目标在文档里也说岔了

KbProposalService 的类注释写的是“让标记变便宜，标记之后真的有用”，处理对象是“被人工认可的回答”。但 知识库运营手册 让运营者每月去“知识库 → 提案”看“哪些问题没答上”。这两件事不是一回事：前者是“答对了，值得沉淀”，后者是“没答上，需要补内容”。

这个偏差说明：连功能自己的使用说明都没有形成稳定心智。它不是被用坏的，是从来没有被真正理解过。

五、为什么这两块会空转

5.1 广场：认可门槛和流量互相卡死

  • 冷启动死锁：only-voted=true 要求至少 1 个赞才展示答案；公开站没有形成能带来投票的访问量；没有赞就没有内容；没有内容就更没有人来投票。29 天 0 票，这个循环一次都没有转起来。
  • 公开页是“半开的门”：热词来自群聊关键词，所以列表看起来有内容；点进去每条答案都被 up <= 0 过滤掉，访客看到的是空列表和“还没有被认可的答案”。
  • “被点赞 = 同意公开”不成立：投票只凭前端随机 clientId，清缓存就能重投；任何人只要知道 statId 就能给任意一条回答投票。匿名赞不能代替提问者或群主的同意，隐私论证站不住。
  • 两级降级是成本与打扰的来源：问新答案会调模型，求助会往群里发消息；这两条路都没有闭环，却各自带一套限额和状态机。

5.2 提案：把“改一条”变成了“标十条、跑模型、逐条审”

  • 入口动作没人做：29 天 44,105 条问答，annotate 0 次。不是按钮藏得深，是这个动作没有进入日常习惯。
  • 阈值放大了摩擦：默认 10 条才能点一次分析。0 条标注意味着 canAnalyze 永远是 false，面板长期停在“再有 10 条就能分析”。
  • 路径比直接改块更长：标记 → 攒 10 条 → 手动分析 → 读模型 diff → 采纳或拒绝。同样是把一条好答案写进知识库，直接在“文档”里改块只要一次编辑。
  • 产出质量仍要人兜底：模型会给 new / overwrite / none，还会幻觉。项目定位是“资料不足就说没查到”，批量生成提案与这个定位天然紧张。
  • 真正的运营路径是导入文档：知识库运营手册 的主线是“准备符合格式的文档 → 导入 → 校验”，不是“从群聊回答里挖提案”。提案是一条支线，支线没有入口流量。

六、判定：还需不需要

能力有人用吗服务主线吗维护成本更简单的替代判定
广场浏览与投票0 票弱，和“策展资料库”的定位冲突中，1,973 行后端 + 1,286 行前端 + 隐私口径公开资料库已能浏览下线
问问新答案1 次探针否中，模型成本、限额、曾整段失败群里直接问机器人删除
求助大佬1 条探针否中，短码链路半成品、打扰群友群里直接问删除
提案分析0弱，运营不走这条路高，模型调用 + 人工审阅 + 无测试直接编辑知识库块删除
人工标注 verdict0 次，但成本极低统计口径需要低，一行 UPDATE无保留

判断

广场：不建议保留。 它不是“差一点就能用”，而是产品面本身与项目定位冲突：一边是严格策展、资料不足就承认不知道；另一边是把群聊里未经编辑的问答公开，还让匿名访客决定什么该公开。即使修好技术问题，它仍然需要持续运营和流量，而目前没有证据表明这两样存在。

提案：不建议保留当前形态。 目标本身合理，把好回答沉淀进知识库是值得做的事；但“批量模型分析 + 阈值 + 逐条审阅”这条路太重，重到 29 天没人走。保留人工标注，需要沉淀时直接改块，成本更低、质量更可控。

只有同时满足下面两条，才值得考虑保留或重构：

  1. 公开问答是你想主推的产品面，而不是顺手做的一个页面；
  2. 你或有人愿意每周至少花 10 分钟标注、审核、处理求助。

如果这两条有一条不成立，直接走清理。若两条都成立，看第八节的方案 B，但不要原样复活现在的代码。

先备份，再把两行探针数据导出留档，最后删表。当前库里没有真实投票、提案或求助，删除不会损失用户数据。

--    cp server/data/qa/qqbot.sqlite server/data/qa/qqbot-before-plaza-cleanup.sqlite

-- 1) 导出探针残留，留档
--    1 行 qa_stat.source='plaza'，1 行 help_request

BEGIN;

-- 2) 删广场生成的那条问答及其附属行
DELETE FROM qa_keyword WHERE stat_id IN (SELECT id FROM qa_stat WHERE source = 'plaza');
DELETE FROM qa_raw     WHERE id       IN (SELECT id FROM qa_stat WHERE source = 'plaza');
DELETE FROM qa_stat    WHERE source = 'plaza';

-- 3) 删功能表。answer_vote / help_request 当前为空，kb_proposal 为空
DROP TABLE IF EXISTS answer_vote;
DROP TABLE IF EXISTS help_request;
DROP TABLE IF EXISTS kb_proposal;

-- 4) 顺带删两张遗留空表
DROP TABLE IF EXISTS kb_contribution;
DROP TABLE IF EXISTS kb_token;

COMMIT;

-- 5) 核对
SELECT COUNT(*) FROM qa_stat;          -- 应减少 1
SELECT COUNT(*) FROM qa_raw;           -- 应减少 1
SELECT COUNT(*) FROM qa_keyword;       -- 应减少 1

如果暂时不想删表，只执行第 2 步也可以。代码删掉后表不会再被写入，但会长期占着 schema，建议一并清掉。

八、方案 B：重构

只有当你确认“公开问答要作为产品面”时才走这条。原则是砍掉不闭环的两级降级，把认可权收回人工，把提案缩成单条动作。

步骤做什么为什么工时
1只保留浏览 + 投票，删掉 ask-new、help-request、FallbackService、help_request 表这两级成本最高、链路最碎、打扰群友1 天
2把“公开”改成管理员显式标记，不再用匿名赞代替同意；投票只做排序和提示修复隐私论证，避免任何人给任意回答“上架”1 天
3在问答记录或广场管理页加“沉淀为词条”按钮，复用 KbBlockAdminService.add/updateText；不做阈值、不做批量、不调模型保留“好答案进知识库”的真实价值，路径最短1 天
4删掉 kb_proposal、KbProposalService、ProposalPanel；提案不再是独立队列避免两套“写知识库”的入口0.5 天
5补测试：排序/去重/过滤、投票幂等、单条沉淀的写入顺序现在这块是 0 测试1 天

总计 3 到 5 天，之后仍然需要持续审核。它会把“空房间”变成一个“有人打扫的房间”，但前提是有人来。
