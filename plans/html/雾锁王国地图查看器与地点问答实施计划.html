一、目标与验收标准

#目标验收标准
1公开站地图查看器访问 /map 能看到与 wiki 同源的底图与点位；拖拽/缩放稳定在 60fps 量级（1440×900、点位全开）；可按键组筛选、搜索、点开点位详情
2管理端地图标注管理员在 /admin/map 点地图任意位置即可新增地点，填名称/分类/备注/是否地标/是否公开；可编辑、删除、搜索、导出
3相对位置描述问「哪里有铁矿」时，系统能落出附近点位并给出「在『远古尖塔·春之原野』东北方向（地图右上）约 N 坐标单位」这类描述，并交给大模型组织成回答

关键实测：同名的「一张地图」内部存在多套坐标系。 Map:Embervale/Collectibles 的 crs 是 topLeft=[-3695,-9045]，与 Map:Embervale/Main 的 [0,10240] 不同，且它的 marker 出现负坐标。 所以「一个 map 一个画布」是错的假设 —— 画布必须按页面记录，渲染时按页面归属分组。

当前缺口

  • 地图数据表在本地库是空的（kb_map_marker 0 行），本地从未跑过同步；需要真实同步一次。
  • 没有画布元信息的落库：crs 与瓦片清单解析后丢掉了，看图的人无从知道怎么铺底图。
  • 没有任何地图控制器：既没有公开读取接口，也没有管理端写入接口。
  • 没有管理员自定义点位的存储层 —— 而「wiki 上点位不多、没有常见地名」正是本次要补的。
  • 没有相对位置算法，地点语料只写了「地图坐标示例：(x, y)」，玩家读了不知道在哪。

三、总体架构

摄入（kb/map）　wiki DataMaps JSON　→　解析　→　定点表
　　　　　　　　　　wiki 瓦片图 / 图标　→　本地缓存　→　按需缩略
领域（kb 核心）　点位目录契约 PlaceDirectory　+　相对位置算法 RelativeLocation
出口　公开站 /api/public/map/**　｜　管理端 /admin/api/map/**　｜　大模型只读工具 locate

为什么要摆一个接口在核心

ArchitectureTest 有一条已经转正的规则：kb 核心不得依赖任何摄入来源（wiki / map）。 而任务 3 的调用方 —— 大模型工具 KbLookupTool —— 住在 kb 核心。若核心直接 import kb.map，构建会红。

因此按仓库既有做法（TermSource / KbCorpus 同一套路）： 契约由消费方定义，实现由生产者提供。核心只认自己包里的 PlaceDirectory， Spring 把 kb.map.WikiPlaceDirectory 注进去。方向保持单向：生产者 → 核心。

kb/PlaceDirectory.java      （契约，核心）   —— 点位只读视图
kb/PlacePoint.java          （值对象，核心） —— 名字/别名/坐标/分类/备注/是否地标/优先级
kb/RelativeLocation.java    （纯算法，核心） —— 方向、距离、最近地标、成句
kb/PlaceAnswer.java         （组装，核心）   —— 提问 → 候选点位 → 相对位置描述
kb/map/WikiPlaceDirectory.java （实现，生产者）—— 合并 wiki marker + 管理员点位 + 备注

四、数据模型

现有三张 wiki 表保持不变。新增三张，都在 kb_map_ 前缀下：

4.1 kb_map_canvas　画布元信息

回答「这张图怎么铺」。按 (map, page) 记录，因为同一地图的多个页面坐标系可能不同。

列说明
map, page联合主键
top_left_x/y, bottom_right_x/ycrs 四至，决定坐标 → 像素的线性映射
tiles_json瓦片清单 [{image,position}] 原样存；at / tile_size 单列存
background_image旧 schema 的单张整图
backdrop, zoom_min, zoom_max观感与缩放范围

4.2 kb_map_place　管理员自定义点位

列说明
id自增主键
map, page, x, y归属画布与坐标
name, aliases中文主名 + 别名（逗号分隔，检索用）
category分类键：resource / poi / npc / boss / landmark / custom
note备注正文，进检索与相对描述
icon, color显示用
landmark, priority能否当地标锚点；优先级越高越容易被选作锚点
visible是否出现在公开站
created_at, updated_at审计

为什么不复用 kb_map_marker：那张表是「某一页的镜像」，同步时按页先删后插。 管理员数据混进去会被下一次同步静默清掉。写入方不同的数据必须分表。

4.3 kb_map_marker_note　给 wiki 点位加备注

主键 (map, page, marker_id) —— 与 kb_map_marker 主键同形，所以同步幂等替换不会丢备注。

列说明
alias中文别名，比如给 Ancient Spire 补「远古尖塔」
note备注正文
landmark, priority提升为地标锚点
hidden该点不进公开站

六、前端查看器：卡顿从哪来，怎么治

wiki 那份卡，主要是三件事叠在一起。逐条对症：

症状根因治法
1700+ 个 marker 是 DOM 节点，每帧拖拽都触发 1700 次样式重算与绘制改 canvas 打点。DOM 只留一个 <canvas>，帧内一次画完
指针事件里直接改 transform，一帧改几十次rAF 合帧：指针只写目标值，requestAnimationFrame 里统一提交一次
一次性把 64 张 1280px 瓦片和全量图标塞进视野只画视口内的点（裁剪）+ 缩小时画圆点不画图标（LOD）+ 瓦片按需加载
缩到最小时仍要铺满 10240×10240 的瓦片服务端合成一张总览图，低倍走总览、高倍才走瓦片
图标每次都从网络取图标走本地缓存 + 浏览器 immutable 长缓存；解码后的 Image 常驻内存

坐标映射

// crs: topLeft(x0, y0)、bottomRight(x1, y1)，其中 y0 > y1（y 轴向上）
px = (x - x0) / (x1 - x0) * canvasW
py = (y0 - y) / (y0 - y1) * canvasH

组件切分

web/src/shared/map/MapCanvas.vue     画布：底图 + canvas 打点 + 指针交互
web/src/shared/map/useMapTransform.ts 纯数学：屏幕 ↔ 地图坐标、缩放锚点、夹取
web/src/shared/map/types.ts           两端共用的类型
web/src/public/views/MapView.vue      公开查看器（浏览模式）
web/src/admin/views/MapAdminView.vue  管理端（编辑模式）

两端复用同一个画布组件，差别只在 mode：浏览模式点击弹详情，编辑模式点击落点。

七、相对位置算法

7.1 方向

地图正北朝上，所以屏幕坐标与罗盘方位一致：

bearing = atan2(dx, dy)        // dx = 目标x - 地标x，dy = 目标y - 地标y（y 向上）
扇区   = round(bearing / 45°) mod 8
八个方向：正北 / 东北 / 正东 / 东南 / 正南 / 西南 / 正西 / 西北

同时给出玩家直觉说法：东北 = 右上、西南 = 左下……因为群友问的时候想的是「在地图上往哪边看」。

7.2 距离

米数不做默认假设。wiki 的 x/y 是游戏坐标系，本次调研无法从公开资料确证 1 单位等于多少米。 凭空写「约 800 米」会被大模型当成事实转述给群友 —— 这比不给距离更糟。 所以默认输出坐标单位与相对量级（很近 / 不远 / 较远 / 很远，按地图对角线归一）， 米制转写留一个配置开关 app.kb.map.units-per-meter，默认 0 = 不输出米。确证比例后改一个数字即可。

7.3 选哪个地标

按「够近 + 够有名」联合排序，取第一名：

score = 距离分 + 名望分
  距离分：归一化到地图对角线，越近越高
  名望分：管理员手工优先级 > landmark 分类 > 远古尖塔/火焰神龛一类高频 POI > 普通具名地点
只考虑同画布、半径阈值内的点；半径内没有地标则退化为「区域 + 坐标」描述

7.4 成句样例

铁矿（3 处）
· 在「远古尖塔·春之原野」东北方向（地图右上），约 320 坐标单位，很近。
  坐标 (3720, 2210)
· 在「火焰神龛·启示林」正南方向（地图正下），约 1150 坐标单位，较远。
  坐标 (5610, 3300)

八、与知识库 / 大模型的衔接

  1. 只读工具：KbLookupTool 增加 locate，入参是地点/物产名，出参就是上面的成句文本。 模型问「哪里有铁矿」时自己调，拿到的是算好的事实而不是它的猜测。
  2. 派生语料：LocationCorpusBuilder 每个地点块追加一行相对位置摘要（挑最知名的 1~2 个锚点）， 纯 RAG 路径也能答出方位，不依赖模型是否想到调工具。
  3. 公开站：/map/locate 给查看器做「搜一下就定位」的体验，同时是这条链路的可观测入口。

九、风险与取舍

风险取舍
首次拉全量瓦片约 26 MB，会给 wiki 添流量懒加载：只取当前视野需要的瓦片，落盘缓存；带来源 UA，遵守对方礼仪
wiki 改版 / 瓦片改名画布元信息来自同步，改版后重跑一次同步即可；渲染层不写死文件名
多套坐标系按页面记录画布，界面按画布分组切换，不硬做跨画布叠加
管理员误标全部可编辑可删；公开站只显示 visible；改动写审计时间
坐标单位无法确证不输出米，只给坐标单位与相对量级，比例做成配置
